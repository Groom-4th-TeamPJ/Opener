1. 실시간 AI 튜터링 채팅 파이프라인 설계

기능
학생이 보낸 질문에 AI 튜터가 답하는 실시간 채팅. 브라우저와 SSE 연결을 유지한 채 OpenAI 응답을 전달하는 경로
개선
연결 상한과 첫 글자 대기를 함께 걷어내고, 화면·저장본·상류 구독이 어긋나던 경로까지 차단

전체적인 아키텍처

채팅 서비스 동작 구조 — SSE 연결과 메시지·저장 경로

문제 원인 및 한계점

  • LLM 응답 생성에 십수 초 — 응답 완료까지 평균 15초라 끝날 때까지 연결을 유지하는 long-lived 구조가 필요
  • 초기 구현은 @Async + SseEmitter + blockLast() 동기 대기 — 연결 1개가 바운디드 풀(core 10 / max 50 / queue 100)의 스레드를 스트림 종료까지 점유해, 풀을 넘으면 큐잉 후 거부
  • 스레드 고갈과 전달 지연이 서로 다른 원인 — 풀 고갈은 바운디드 풀이라는 상한에서 오고, 첫 글자까지의 대기는 blockLast()가 스트림을 끝까지 모은 뒤 한 번에 넘기는 전달 방식에서 옴. 한쪽만 고치면 다른 쪽이 그대로 남는 구조
  • 토큰마다 붙는 콜백이 응답을 읽는 스레드를 그대로 점유 — 한 사용자의 저장·전이 작업이 같은 루프를 쓰는 다른 사용자의 스트림까지 멈추는 구조
  • 생산 속도를 늦출 수 없는 스트림 — LLM 토큰은 되감을 수 없어 소비가 느리면 넘치고, 넘친 뒤의 처리와 중간 실패 처리에 따라 화면과 저장본이 서로 반대 방향으로 어긋날 수 있는 구조
  • 클라이언트가 끊어도 상류 LLM 스트림은 계속 진행 — 구독을 취소할 수단을 쥐고 있지 않으면 아무도 보지 않는 응답에 토큰이 끝까지 소비·과금
  • 응답 경로와 저장 경로가 한 흐름에 묶임 — DB 쓰기가 토큰 전달과 같은 경로에 있으면 저장 지연이 곧 응답 지연

해결 과정

  1. 스레드 고갈부터 Virtual Thread 전환으로 해소 — spring.threads.virtual.enabled 한 줄로 요청마다 가상 스레드가 생기게 해 바운디드 풀이라는 상한 자체를 소멸. 대리 부하(sleep 엔드포인트)로 처리량이 스레드 풀 상한에 종속되지 않는 것까지 확인. 다만 Virtual Thread는 스레드를 "반납"시키는 것이 아니라 블로킹 동안 carrier 스레드에서 unmount 시킬 뿐이라, 첫 글자까지의 대기는 이 조치로 줄지 않음
  2. 남은 "완료 후 일괄 전달"은 blockLast() 제거로 전환 — 서블릿 스택은 둔 채 컨트롤러가 Flux<ServerSentEvent>를 반환해 MVC async 경로를 타게 함. 요청 스레드를 점유하지 않고 토큰이 도착하는 즉시 전달
  3. WebFlux(Netty) 전면 이전 대신 Reactor 타입만 넣은 하이브리드를 선택 — JPA·Security 재작성 비용을 피한 것이고, Virtual Thread가 있는데 Reactor를 더한 것은 취향이 아니라 API 제약. Spring AI의 ChatClient.stream().content()가 Flux<String>만 반환하므로, LLM 대기는 리액티브 호출에 맡기고 남은 동기 조회는 요청 스레드(= virtual thread)에서 처리
  4. 토큰 콜백의 블로킹을 publishOn(Schedulers.boundedElastic()) 뒤로 오프로딩 — 그냥 두면 콜백(Redis 저장·상태 전이, 오프너 분석은 JDBC 트랜잭션까지)이 OpenAI 응답을 읽는 이벤트 루프 스레드 위에서 돌아 같은 루프가 담당하는 다른 사용자의 스트림까지 함께 멈춤. 일반 채팅과 오프너 분석 두 경로 모두 구독 직후·콜백 앞에 두어야 성립 — 한쪽만 옮기면 다른 경로가 같은 루프를 막음. 실제로 걸렸는지는 첫 청크에서만 콜백 스레드명을 로그로 확인(매 청크에 찍으면 로그가 토큰 수만큼 늘어남)
  5. SSE 연결을 ConcurrentHashMap<sessionId, Sink>로 관리하고 속도 차를 버퍼로 흡수 — 생산을 늦추는 진짜 백프레셔가 아니라 되감을 수 없는 LLM 스트림을 버퍼링으로 회피한 것. 크기는 SSE_BUFFER_SIZE = 256으로 명시. 이 맵은 프로세스 로컬이라 단일 인스턴스 운영을 전제하고, 증설하려면 발행을 Pub/Sub으로 팬아웃해야 함
  6. "화면에 보인 것 = 저장된 것"이 양방향으로 깨져 함께 차단 — ① 오버플로 시 tryEmitNext가 FAIL_OVERFLOW를 주면 로그만 남기고 청크를 조용히 버려 화면에 없는 내용이 저장본에 잔존 → tryEmitError로 끊는 쪽으로 전환(끊김은 재연결로 복구되나 빠진 청크는 복구 불가) ② 스트림 중간 실패 시 보낸 토큰이 저장되지 않아 화면에만 잔존 → doOnError에서 받은 만큼 저장하고 chat.stream.partial.saved로 계측
  7. 구독 핸들을 세션별로 보관해 취소 경로를 확보 — subscribe()의 Disposable을 쥐고 있지 않아 취소할 수단 자체가 부재했던 것. 보관 후 doOnCancel · disconnectSession · 하트비트 사망 세션 3지점에서 정리. 스레드 점유를 보러 들어가서 더 크게 새던 자원인 상류 구독과 LLM 비용을 발견 — 스트리밍 전환과 구독 누수 차단이 같은 조사에서 나온 결과
  8. 저장 경로를 응답 경로에서 분리 — 전용 큐로 발행하고 Consumer가 Redis 조회·검증·PostgreSQL 적재를 맡게 해, DB 쓰기가 토큰 전달 흐름에 얹히지 않도록 경계를 가름. 발행 트리거는 사용자의 저장 요청(POST /chat/save-message)
Java · ChatServiceImpl 
// 버퍼 크기를 기본값(256)에 맡기지 않고 상수로 고정
private static final int SSE_BUFFER_SIZE = 256;
Sinks.Many<ServerSentEvent<String>> sink =
        Sinks.many().multicast().onBackpressureBuffer(SSE_BUFFER_SIZE);

Sinks.EmitResult result = sink.tryEmitNext(sse);
if (result == Sinks.EmitResult.FAIL_OVERFLOW) {
    // 청크를 조용히 버리면 사용자가 본 화면과 Redis 에 저장된 전문이 어긋난다
    // 유실보다 끊는 쪽이 낫다 -> 브라우저가 재연결하면 히스토리부터 다시 받는다
    log.warn("[SSE] 버퍼 초과로 연결 종료 - sessionId: {}, event: {}", sessionId, eventName);
    meterRegistry.counter("chat.sse.overflow").increment();
    sink.tryEmitError(new BusinessException(ErrorCode.SSE_BUFFER_OVERFLOW));
    disposeSubscription(sessionId);   // 상류 LLM 구독까지 함께 끊는다 (토큰 과금 중단)
    sinks.remove(sessionId, sink);    // 값 비교 제거 — 그 사이 등록된 다른 Sink 를 지우지 않게
} else if (result.isFailure()) {
    log.warn("[SSE] emit 실패 - sessionId: {}, result: {}", sessionId, result);
}

결과

  • 전달 구조가 완료 대기에서 도착 즉시로 바뀜 — blockLast() 제거로 첫 토큰 생성 즉시 SSE로 흐름. 첫 글자까지 중앙값 1.09s · p95 1.73s(20회 · 일반 채팅 POST /chat/message · RAG on)
  • 이 수치는 RAG를 켠 불리한 조건에서 나온 값 — 20회 전부 pgvector 검색이 돌아 문서 5건을 프롬프트에 결합(app.rag.enabled=true). 임베딩 왕복과 벡터 검색을 빼지 않은 값이고, 여기서 바꾼 것은 "완료 후 일괄"을 "도착 즉시"로 만든 전달 구조 — 외부 API 지연의 절대값과 무관하게 그 구조적 차이는 유지됨
  • 화면과 저장본이 어긋나는 두 경로를 각각의 카운터로 분리해 추적이 성립 — 버퍼 오버플로(chat.sse.overflow) · 스트림 중단 시 부분 응답(chat.stream.partial.saved)
  • 한 사용자의 콜백이 다른 사용자의 스트림을 멈추지 않는 구조 — 저장·상태 전이·트랜잭션을 별도 스케줄러로 내보내, 같은 이벤트 루프를 쓰는 다른 연결이 콜백 시간만큼 정지하던 경로를 차단
  • 클라이언트가 떠나면 상류 LLM 구독까지 함께 정리 — 취소 지점을 세 곳(구독 취소 · 명시적 연결 해제 · 하트비트 사망 판정)에 두어 보지 않는 응답에 토큰이 계속 소비되는 경로를 종료

2. 채팅 세션 저장소 설계

기능
멀티턴 대화의 문맥을 담는 저장소 — AI가 이전 턴을 이어받으려면 매 턴 지난 대화를 다시 읽어 프롬프트에 실어야 하므로, 세션 TTL 1시간 동안 대화 버퍼를 보관
개선
진행 중인 멀티턴 문맥이 통째로 날아가던 단일 장애점을 복제본 자동 승격으로 제거하고, 문맥 조회가 저장을 막던 구조를 갈라 포화 지점을 뒤로 이동

전체적인 아키텍처

실제 동작 구조 — 인증 요청과 채팅 요청이 흐르는 Redis 경로

문제 원인 및 한계점

  • Redis Standalone 단일 노드 구조에서 노드가 죽으면 진행 중인 모든 세션의 멀티턴 문맥이 한 번에 유실되는 SPOF(단일 장애점)
  • 인증용 Redis와 채팅용 Redis가 같은 인스턴스를 공유하는 구조라, 한쪽 도메인의 장애가 다른 도메인까지 전파될 위험이 존재
  • 장애 발생 시 수동으로 인스턴스를 재기동해야 했고, 이 복구에 5~10분이 걸려 그 사이 채팅 기능 전체가 중단됨
  • 읽기와 쓰기가 한 노드의 단일 이벤트 루프를 공유 — 멀티턴 문맥을 만들려면 매 턴 세션 전체를 다시 읽어야 해서 조회가 LRANGE 0 -1이라 한 번에 수십 KB를 직렬화하는데, Redis는 노드당 단일 스레드라 그 사이 같은 노드로 온 RPUSH가 대기. 같은 노드에 요청이 동시에 몰릴수록 조회 뒤에 줄 선 저장이 그만큼 밀리는 구조라, 동시 요청 수에 비례해 악화

해결 과정

  1. Redis Cluster를 Master 3 + Replica 3, 총 6노드로 구성하고 Auth Redis와 Chat Redis를 별도 Spring 빈으로 분리해 장애 도메인을 격리 — 유실 시 대화가 통째로 사라지는 채팅 세션만 Cluster로 이중화하고, 재로그인으로 즉시 복구 가능한 인증 토큰 저장소는 Standalone을 유지해 인프라 비용과 보호 수준의 균형을 조정
  2. 같은 세션의 키들을 Hash Tag 패턴(chat:{sessionId}:session)으로 묶어 동일 슬롯에 배치함 — 다만 이건 겪은 장애를 고친 게 아니라 선제 조치. 현재 chat 클러스터에 대한 호출은 전부 단일 키라 CROSSSLOT이 날 여지가 없고, Lua·트랜잭션·파이프라인도 부재. 나중에 멀티키 연산이 필요해질 때 키 명명을 전수 이관하는 비용을 미리 없앤 것이 정확한 근거
  3. 저장소 층에서 읽기와 쓰기의 책임을 가름 — CQRS의 라우팅 적용. 쓰기(Command)는 master 한 곳으로 모으고 조회(Query)는 복제본으로 내보내 두 워크로드가 서로 다른 노드의 자원을 쓰게 한 것. 줄서기 자체를 빠르게 만드는 것이 아니라 줄이 생기는 자리를 나눈 처방
  4. 읽기 분산과 프롬프트 정합성이 충돌 — 전 경로가 REPLICA_PREFERRED였는데 saveMessage 직후 같은 요청에서 히스토리를 읽어, 복제가 수 ms만 늦어도 멀티턴 문맥에서 방금 한 질문만 빠지는 정합성 버그
  5. 전부 master로 돌리면 분산이 사라지므로 지점별로 세 갈래 판정 — 프롬프트 조립용은 master 고정(창이 항상 열림), 영속화용 전체 조회는 replica 유지(별도 요청이라 창이 닫힘), 소유자 검증은 replica 우선 + 비었을 때만 master 재확인(무조건 master면 분산이 사라지고, 재확인이 없으면 방금 만든 세션이 거부됨). ReadFrom이 팩토리 단위 설정이라 master 전용 팩토리를 작은 풀(5/3/1)로 분리하되 조립은 헬퍼 하나로 공유
  6. 여기에 더해 라우팅과 무관하게 질문 자체를 잃지 않도록 프롬프트 조립을 순수 함수로 분리해 현재 질문 원문을 명시적으로 보장함(마지막 메시지가 같으면 중복 미추가). 선형화는 "히스토리를 최신으로 만든다", 이쪽은 "히스토리가 낡아도 질문만은 잃지 않는다"로 층이 다른 두 방어. 지점별 라우팅이 의도대로 갈리는지는 chat.redis.read Timer에 route=master|replica 태그를 붙여 비율로 관측
  7. failover 대응의 실체는 커넥션 검증이 아니라 토폴로지 갱신 — ClusterTopologyRefreshOptions(주기 갱신 + enableAllAdaptiveRefreshTriggers)로 승격을 감지하고, DisconnectedBehavior.REJECT_COMMANDS로 끊긴 커넥션에 명령을 쌓아 두지 않고 즉시 실패시켜 장애가 큐잉으로 번지는 경로를 차단. 풀의 testOnBorrow=true는 그 아래 단계의 죽은 커넥션 방지용으로 역할을 구분해 둠
  8. Cluster가 주는 것은 가용성(HA)이지 내구성(Durability)이 아님 — 복제가 비동기라 Master가 죽는 순간 복제되지 않은 쓰기는 사라짐. 큐 이벤트가 본문을 싣지 않고 sessionId만 실어 Consumer가 본문을 Redis에서 다시 읽는 구조라 영속 경로도 Redis의 하류이므로, 목표를 내구성 확보가 아니라 유실 감지로 설정

결과

  • Master 강제 종료 통제 실험에서 복제본 자동 승격으로 약 7초 자동 복구 — 이 7초는 설정값의 결과이고 cluster-node-timeout 5000(장애 판정 5초) + 선출·승격 시간
  • 인증·채팅 저장소 분리로 한쪽 장애가 다른 도메인으로 전파되는 경로 차단
  • Redis 커넥션 풀(Lettuce · commons-pool2)은 maxTotal=20 / maxIdle=10 / minIdle=5로 상한이 명확하고, 20개 풀로 100 VU를 종단 p95 133ms에 수용 — 이 133ms는 요청이 들어와 응답이 나가기까지의 애플리케이션 종단 값이라, 아래 표의 Redis 명령 단위 p95(1~2ms대)와는 재는 구간이 다름
  • 읽기/쓰기 분리의 이득은 마스터가 포화된 뒤에 나타남 — 같은 클러스터에 실제 명령 모양(쓰기 RPUSH, 읽기 LRANGE 0 -1·40건 세션)을 걸어 개선 전(읽기·쓰기 모두 master)과 개선 후(쓰기 master · 읽기 replica)를 대조. 아래는 부하가 가장 큰 동시 클라이언트 64대 구간
    동시 클라이언트 64대 개선 전 개선 후 변화
    합계 처리량 57,610 ops/s 107,238 ops/s +86%
    읽기 처리량 35,109 ops/s 51,983 ops/s +48%
    읽기 p95 (명령 단위) 2.195ms 2.206ms +0.5%
    쓰기 처리량 22,501 ops/s 55,256 ops/s +146%
    쓰기 p95 (명령 단위) 2.121ms 1.338ms −37%
    같은 대조를 클라이언트 3대에서 걸면 합계는 +12%에 그침. 개선 전은 약 6만 ops/s에서 천장을 치고 클라이언트를 더 늘리면 오히려 감소하는 반면, 개선 후는 천장이 약 11만 ops/s로 이동 — 분리가 명령을 빠르게 만든 것이 아니라 포화 지점을 뒤로 민 것
  • 가장 크게 개선된 쪽은 읽기가 아니라 쓰기 — 처리량은 쓰기가 +146%로 읽기(+48%)의 세 배이고, p95도 쓰기만 −37% 줄고 읽기는 제자리. 무거운 조회가 master의 단일 이벤트 루프를 비우자 같은 노드에서 대기하던 쓰기가 먼저 이득을 봄. 이 −37%는 RPUSH 한 건의 처리가 빨라진 것이 아니라 같은 이벤트 루프에서 조회 뒤에 줄 서던 대기가 사라진 결과. 읽기 p95가 제자리인 것은 이 표가 가장 부하가 큰 64대 구간이기 때문 — 부하가 절반인 24대에서는 읽기 p95도 −13%로 함께 개선. 지연 이득은 쓰기 쪽이 더 크고 더 높은 부하까지 유지
  • 부하에서만 터지던 프롬프트 누락을 라우팅으로 차단 — 쓰기 직후 같은 값을 복제본에서 읽었을 때 미반영률이 유휴 시 0/3,000(0%)인데 쓰기 클라이언트 16대가 붙은 상태에서는 2,079/3,000(69.3%). 수렴까지 평균 0.35ms · p95 0.73ms · 최대 8.7ms. 이 대비가 뜻하는 것은 개발 중에는 한 번도 재현되지 않는 종류라는 것이고, 쓰기 직후 같은 요청에서 다시 읽는 프롬프트 조립만 master로 고정한 판단의 근거
  • 내구성 대신 감지를 확보 — 복제되지 않은 쓰기가 master 소실과 함께 사라지는 경로 자체는 잔존하나, 그 사라짐이 조용히 성공으로 기록되지는 않음. 영속화 컨슈머가 TTL을 넘긴 정상 만료와 TTL 이내의 비정상 소실을 갈라 계수하고, 후자는 예외로 끊어 DLQ에 적재. 유실을 막지는 못하되 유실이 일어났다는 사실은 남는 상태
읽기/쓰기 분리 실측 — 동시 클라이언트 수별 합계 처리량 (Redis Cluster · 12초)

3. 채팅 영속화 파이프라인 설계

기능
멀티턴 대화를 세션이 끝난 뒤에도 남기는 경로 — 사용자의 저장 요청으로 Redis 버퍼의 대화를 RabbitMQ 큐를 거쳐 PostgreSQL에 적재. 대화 요약도 함께 생성
개선
멀티턴 기록이 사라졌을 때 "버퍼가 비었다"를 만료·유실·인가 실패 세 사유로 갈라 관측 가능하게 전환

전체적인 아키텍처

영속화 컨슈머의 판정 경로 — 부재의 두 가지 뜻과 ACK/DLQ 결정

문제 원인 및 한계점

  • 채팅 버퍼는 Redis에 세션 TTL 1시간으로 두고 영속화는 큐로 넘기는 구조라, 이벤트가 도착한 시점에 버퍼가 이미 비어 있을 가능성이 상존
  • "비었다"에 두 뜻이 겹쳐 존재 — 하나는 TTL을 넘겨 사라진 정상 만료, 다른 하나는 복제 유실·allkeys-lru 축출로 인한 비정상 소실. 둘은 대응이 정반대인데 코드에서는 같은 분기
  • 조용히 ACK하면 유실이 성공으로 기록 — 큐는 비고 지표는 깨끗한데 대화만 사라지므로, 사고가 났다는 사실 자체가 어디에도 미기록. 반대로 전부 DLQ로 보내면 정상 만료가 장애로 쌓여 DLQ가 신호를 상실
  • LLM 호출이 십수 초인데 트랜잭션 안에서 기다리면 HikariCP(max 20)가 고갈 — 외부 호출 지연이 번지는 것을 막아야 할 자리에서 영속화 경로가 스스로 연쇄 지연을 만드는 구조

해결 과정

  1. 판정 근거를 이벤트에 적재 — 발행 시각 publishedAt을 페이로드에 넣고, now − publishedAt ≥ 세션 TTL이면 정상 만료로 판정. 버퍼의 부재만으로는 원인을 알 수 없고 시각이 있어야 갈림. 다만 이 판정은 유실을 탐지하는 장치이지 내구성 장치가 아님 — 큐 이벤트가 sessionId만 실어 본문을 Redis에서 다시 읽으므로 영속 경로가 Redis의 하류이기 때문. 기준값을 세션 TTL과 같은 상수로 둔 이유는 두 값이 어긋나는 순간 판정이 틀리기 때문
  2. 세션 TTL 1시간은 임의 상수가 아니라 한 문항 세션의 예상 수명 — 오답 한 문항을 붙들고 푸는 시간이 10~30분 남짓이라, 그 문항을 두고 오가는 질문이 이 창 안에서 끝난다고 보고 산정. 풀이 시간의 약 2배를 여유로 둔 값이라 정상 사용자가 TTL 만료에 걸릴 일이 드물고, 그래서 만료로 버려진 건수(reason=expired)가 올라가면 상수를 다시 볼 신호로 읽힘
  3. 정상 만료는 ACK하되 사실을 남김 — 재처리해도 되살아나지 않으므로 큐에서 내리는 것이 맞으나, chat.persist.dropped{reason=expired}로 계상해 얼마나 자주 만료로 버려지는지가 보이게 함
  4. TTL 이내의 빈 버퍼는 예외로 끊어 DLQ로 보냄 — reason=lost를 올리고 CHAT_BUFFER_LOST를 던져 메시지를 남김. 고칠 수 있는 유실과 어쩔 수 없는 만료를 다른 통로로 보낸 것이 판정의 목적
  5. publishedAt이 없는 구 메시지는 안전한 쪽인 정상 만료로 판정 — 판정 근거가 없는 것을 유실로 몰면 배포 직후 구 메시지가 전부 DLQ로 쏟아짐. 모르는 것을 사고로 세지 않는다가 기준
  6. 소유자 검증 실패(SESSION_NOT_FOUND · SESSION_ACCESS_DENIED)도 ACK 대상으로 두고 reason=unauthorized로 계상 — 재처리해도 결과 동일. 이 경로만 소유자 검증 어드바이스에서 빼 둔 이유는 진입 규약이 다르기 때문 — 이벤트는 userId를 인자가 아니라 페이로드로 갖고, 실패 처리도 HTTP 거부가 아니라 ACK/DLQ 결정
  7. @Transactional을 걷고 TransactionTemplate으로 DB 쓰기 구간만 트랜잭션으로 한정 — LLM 호출은 트랜잭션을 열기 전에 끝내고, 커넥션 점유를 저장 구간으로 한정. 트랜잭션 경계를 메서드가 아니라 자원 점유 시간으로 정한 것이 판단

결과

  • "메시지가 없다"가 세 사유로 갈린 지표가 됨 — expired · lost · unauthorized가 한 카운터의 태그로 분리돼, 전체 건수가 아니라 사유별 추이로 읽힘
  • 유실이 DLQ에 남아 추적 가능 — DLQ 적재 자체가 "고칠 수 있는 사고"의 신호로 동작
  • 커넥션 점유가 DB 쓰기 구간으로 한정돼, 요약이 느려져도 풀 잠식 미발생
  • 요약 서킷이 열려도 대화는 저장 — 요약을 부가 정보로 다뤄 본문 영속화가 외부 호출에 종속되지 않게 분리

4. RAG 검색 파이프라인 설계

기능
질문과 유사한 한국어 수학 모의고사 문제·풀이를 pgvector에서 찾아 프롬프트에 붙이는 검색 증강 생성(RAG). 근거 없는 답을 줄이는 것이 목적
개선
검색 0건의 원인을 임계값 스윕으로 규명하고, 플래그를 내리면 기동이 깨지던 경로를 양방향으로 성립

전체적인 아키텍처

실제 동작 구조 — 색인 경로와 요청 시 RAG 분기

문제 원인 및 한계점

  • LLM 단독으로는 수능·모의고사 지문에 정확한 근거를 대지 못하고 사실과 다른 답을 내는 Hallucination 위험이 존재
  • pgvector + HNSW 벡터 스토어를 구성하며 코사인 유사도 임계값을 0.7로 잡았는데 관련 문서가 미검색 — 0.7은 프레임워크 기본값이 아니라 근거 없이 고른 값(Spring AI 실제 기본값은 SIMILARITY_THRESHOLD_ACCEPT_ALL = 0.0, 전부 통과)
  • RAG를 끄면 애플리케이션이 기동 실패 — 조건부 빈이 켜짐 쪽에만 존재해 VectorStore를 요구하는 주입 지점이 그대로 남는 구조라, 플래그를 내리는 것이 곧 장애
  • 플래그가 켜지면 일반 채팅도 같은 벡터 검색 경로를 경유 — 분기 기준이 질문의 용도(오프너 분석 vs 일반 대화)가 아니라 플래그 하나라, 검색이 필요 없는 대화에도 매 턴 검색 비용이 부과
  • 대화 히스토리를 전량 프롬프트에 주입하는 구조라 턴이 쌓일수록 토큰 비용과 첫 토큰 지연이 함께 증가

해결 과정

  1. 임계값을 0.7에서 0.2로 낮춰 검색이 0건으로 떨어지던 상태를 먼저 해소
  2. 검색이 비면 컨텍스트를 억지로 채우지 않고 RAG 없는 프롬프트로 폴백
  3. RAG를 코드 분기가 아니라 Feature Flag(app.rag.enabled)로 가른 이유는 셋 — ① 차단 스위치: 검색 경로는 OpenAI 임베딩 API와 pgvector라는 외부 의존을 매 턴 타므로, 그쪽이 흔들릴 때 재배포 없이 설정 한 줄로 RAG만 끄고 채팅 자체는 살릴 수 있어야 함 ② 대조 실험의 전제: 같은 코드·같은 질문셋을 플래그만 뒤집어 통과시켜야 RAG의 효과와 비용을 같은 조건에서 비교 가능. RAG 비용을 잰 수치는 전부 이 토글 위에서 얻은 값 ③ 의존 격리: 플래그가 꺼진 환경은 pgvector·임베딩 빈을 아예 만들지 않아, 벡터 스토어 없이도 기동
  4. LlmService는 사용·미사용 구현체를 짝으로 두어 플래그가 어느 값이든 빈이 하나는 생기게 함
  5. 반면 RagService는 조건부 구현체 하나뿐이라 플래그를 끄면 기동 실패 — 조건부 빈은 그 타입을 주입받는 쪽까지 봐야 방어가 성립 — 짝을 만들 수 있는 곳은 짝으로, 조건이 없는 소비자 하나는 ObjectProvider로. 주입 클래스 다섯 개를 전수 확인하고 플래그를 양방향으로 실제 기동해 검증
  6. 프롬프트에 실리는 대화 히스토리 비용도 통제 — 전량 주입을 최근 N턴 윈도우(app.chat.history-window, 기본 20)로 제한함. 다만 직후 DB에 영구 저장되는 요약이 20턴 기준으로 잘리는 회귀를 발견해 조회 계약을 LLM 컨텍스트용(윈도우)과 영속화용(전량)으로 분리함 — 비용 최적화가 저장 데이터를 훼손하지 않게 경로를 가른 결정
  7. 첫 가설은 한국어 질문과 영어 중심 임베딩 모델의 언어 정렬로 두고 대안 셋을 비교 — ① 다국어 모델 ② BM25 하이브리드 ③ Reranker. ①은 차원 하드코딩·1536 단일 스키마·문서가 1건이라도 있으면 색인을 통째로 건너뛰는 조건 세 곳을 동시에 고쳐야 하는 범위라 후순위로 배치

결과

  • 근거 없는 응답이 감소 — RAG On/Off 양방향으로 동일 질문셋을 통과시켜 대조
  • 플래그가 운영 스위치로 성립 — 켠 상태와 끈 상태 양쪽 모두 기동하므로, 긴급 차단과 대조 실험이 같은 스위치 하나 위에서 가능
  • 검색 0건에서 재현율 85%로 전환 — 임계값을 0.7에서 0.2로 내려 20문항 중 17문항이 정답 분류 문서를 회수. 스윕으로 잡은 유효 상한은 0.3이고 그 이하는 topK=5가 먼저 차므로, 0.2는 코퍼스가 늘어 분포가 올라가도 여유가 남는 위치
  • 검색 0건일 때 컨텍스트를 비우고 일반 프롬프트로 폴백해, 문서를 못 찾은 상황이 응답 실패로 번지지 않게 처리
유사도 임계값 스윕 실측 — 질문 20문항 · topK=5
  • 다음 품질 개선의 대상을 자료 형식으로 확정 — 첫 가설이던 "영어 자료 + 한국어 질문의 정렬"은 색인 대상 5,799청크가 사실상 전부 한국어 수학 모의고사 문제·풀이(MATH-ko-test.jsonl · ko_math-500.jsonl)이고 영어는 공식 요약 PDF 4쪽뿐이라 성립 불가. 실제로 걸린 것은 그림이 이미지가 아니라 Asymptote 소스 코드 텍스트로 적재된 것 — 787청크(13.6%)가 [asy] 블록을 포함하고 그 블록이 청크 길이의 평균 47%를 차지. 질문은 자연어 한 문장인데 문서 절반이 좌표·draw 명령인 구조
  • RAG 비용이 경로별로 드러나는 상태로 전환 — rag.vector.search에 path=chat|opener 태그를 붙이고 일반 채팅 경로에도 같은 Timer를 걸어, 첫 토큰까지 off 547ms → on 1,093ms(플래그 양방향 각 20회 · 중앙값)로 RAG가 얹는 546ms를 벡터 검색 401ms와 프롬프트 증가분 약 145ms로 분해. 두 경로의 검색 비용은 401ms(chat · n=22) · 361ms(opener · n=10 · 중앙값 350ms · p95 502ms)로 사실상 동일해, 검색이 필요 없는 일반 대화도 같은 비용을 무는 것이 수치로 확정
  • 턴이 쌓여도 프롬프트 비용이 함께 늘지 않는 구조로 전환 — 컨텍스트는 최근 20턴만, 저장본은 전량. 두 경로가 갈려 비용 절감이 기록을 침범하지 않음

5. LLM 호출·세션 안정화 계층 설계

기능
OpenAI 호출과 채팅 세션의 연결·전송·스트리밍·종료 상태를 다루는 계층
개선
장애 전파를 서킷·타임아웃으로 끊고, 비정상 전이는 차단하되 고착 상태는 회수까지

전체적인 아키텍처

실제 동작 구조 — 채팅 요청 중 Circuit Breaker 개입 지점과 State Machine 연동

문제 원인 및 한계점

  • LLM은 OpenAI 외부 의존성이라 장애·지연이 발생하면 느린 실패가 누적됨 — 게다가 처음에는 타임아웃이 하나도 부재. WebClient.builder()를 그대로 빈으로 내보내고 있어 커넥터에 연결·응답 상한이 걸리지 않았고, 상류가 응답을 멈추면 호출이 무기한 매달림
  • 실패 중인 외부 API를 계속 호출하면 연쇄 지연(Cascading Failure)으로 번질 위험이 존재
  • 세션 상태가 여러 boolean 플래그에 분산돼 있어 "스트리밍 중 재전송", "연결 전 메시지 전송" 같은 비정상 전이를 코드 수준에서 차단 불가

해결 과정

  1. Resilience4j @CircuitBreaker를 채팅 스트리밍·오프너 분석·대화 요약·캐시 저장소 호출 4개 지점에 서로 다른 정책으로 분리 적용 — 외부 LLM 세 지점은 느리고 호출 단가가 높아 보수적으로, 윈도우 10 · 최소 호출 5건 · 실패율 50% 초과 시 OPEN → 30초 후 HALF-OPEN(허용 3건)으로 설정
  2. 캐시 저장소는 호출이 빠르고 훨씬 빈번해 표본 하나의 무게가 가볍다는 특성을 확인하고, 이 지점만 윈도우 20 · 최소 호출 10건 · 실패율 60% · OPEN 10초로 차등화 — 표본을 더 모아 통계적으로 판단하고, 임계는 너그럽게, 회복 대기는 짧게 둔 것. 네 지점을 한 값으로 맞추지 않은 이유는 호출 특성이 다르면 서킷 정책도 달라야 한다고 봤기 때문
  3. 최소 호출 수를 둔 이유는 표본이 적을 때의 오판을 막기 위해서 — 호출 2건 중 1건 실패를 실패율 50%로 읽고 서킷을 열면 우연한 실패 하나로 기능 전체가 차단됨. 호출 빈도가 높은 캐시 지점에 더 큰 최소값(10건)을 요구한 것도 같은 이유
  4. Spring State Machine으로 IDLE → CONNECTED → PROCESSING → STREAMING → COMPLETED와 에러 3상태(총 8개)를 정의하고, 전이 테이블에 선언된 쌍만 허용해 비정상 전이를 코드 수준에서 차단
  5. 다만 잘못된 전이를 차단하는 것과 어긋난 상태를 회수하는 것은 다르다는 것을 확인 — LLM이 빈 응답을 주면 STREAM_START가 발화되지 않아 상태가 PROCESSING에 남고, 뒤이은 STREAM_COMPLETE가 거부되며 세션이 고착돼 이후 요청이 전부 SESSION_EXPIRED로 막히는 경로를 발견. 첫 청크 발생 여부를 확인해 청크가 0개면 STREAM_ERROR로 상태를 회수하도록 보완하고, 전이 거부를 조용히 삼키던 sendEvent 반환값을 전 지점에서 검사하도록 정리
  6. 에러 상태에서 나가는 길이 CLOSE → IDLE 하나뿐이고 IDLE은 SEND_MESSAGE를 받지 않아, LLM이 한 번 실패하면 SSE 연결은 살아있는데 재전송만 영구히 막히는 구조. STREAM_ERROR·PROCESSING_ERROR에서 SEND_MESSAGE로 PROCESSING으로 돌아가는 전이 2개를 추가 — LLM의 일시 실패는 세션을 끝낼 사유가 아니라고 판단
  7. 서킷이 감싸는 구간이 실제로는 반쪽이었던 것을 실패 주입으로 발견하고 차단. chatStream이 메서드 본문에서 히스토리 조회와 벡터 검색을 동기로 하고 있어, 상류가 죽으면 Flux를 만들기도 전에 예외가 나감 — 리액티브 서킷은 구독 시점 오류만 집계하므로 그 실패는 한 건도 미집계. 조회·조립을 Flux.defer로 구독 시점에 옮겨 검색 실패까지 서킷 안으로 편입. 같은 결함이 세션도 망가뜨리고 존재 — 조립 시점 예외는 doOnError를 타지 않아 상태가 PROCESSING에 남고, 그 세션의 이후 메시지가 전부 거부됨(실측: 1번째 500 뒤 2~6번째 연속 401)
  8. 외부 호출 상한을 responseTimeout으로 적용 — 총 시간이 아니라 read 사이 간격 상한. 연결 5s · 응답 20s로 잡았고, @TimeLimiter를 쓰지 않은 이유가 여기 존재 — 총 시간 상한이면 정상 장문 응답까지 잘라냄. 튜터링 답변은 길고, 토큰이 계속 도착하는 한 끊지 않아야 함. 반대로 상류가 멈추면 그 시점부터 20초 뒤에 끊김. 설정 파일에 값을 적은 것과 그 값이 실제로 동작하는 것은 별개라, 응답을 주지 않는 소켓을 세워 실제로 끊기는지 단위 테스트로 고정함

결과

  • 외부 LLM 장애가 다섯 번의 실패 뒤 여섯 번째 호출부터 차단 — OpenAI 채팅 엔드포인트만 죽은 포트로 돌리고(임베딩은 로컬 스텁으로 살려 둠) 채팅 6회를 보낸 결과, llm-chat 서킷에 failed 5 · successful 0 · ignored 0이 집계되고 state=open · 실패율 100%로 전이했으며, 6번째 호출은 not_permitted 1건으로 아예 미실행. 설정(최소 호출 5 · 실패율 50%)과 정확히 일치하고, "차단했다"의 실체가 그 미실행 1건. ignored 0은 도메인 예외 무시 설정이 인프라 실패까지 삼키지는 않는다는 확인이기도 함
  • 캐시 저장소 장애는 대체 응답이 아니라 "저장만 포기"로 흡수함 — 저장 실패를 chat.redis.save.dropped{reason}으로 계상하고 스트리밍은 그대로 이어 감. 가짜 답변을 만들어 내려보내지 않는 이유는 대상이 수능·모의고사를 준비하는 학생이기 때문 — 그럴듯한 오답은 침묵보다 해로움. 반대로 소유자 검증은 같은 서킷을 쓰면서도 fail-close임 — 인가 게이트를 못 읽는 상태에서 통과시키면 그 자체가 인가 우회. 두 호출이 같은 Redis 장애를 보는 것이라 회로는 공유하되, 차단이냐 흡수냐는 호출의 의미에 따라 갈랐음
  • 비정상 상태 전이(스트리밍 중 재전송 등)를 전이 테이블에 선언된 쌍만 허용하는 방식으로 구조적 차단
  • 빈 응답·LLM 일시 실패로 PROCESSING에 남은 상태를 회수하고 같은 세션에서 재전송할 수 있도록 전이를 보강해 복구 경로 확보

6. 인증·세션 방어선 설계

기능
폼·카카오 로그인과 회원가입 4경로로 JWT를 발급하고 로그아웃 시 폐기하는 인증, 그리고 채팅 SSE 연결이 본인 세션인지 확인하는 소유권 검증
개선
단일 통과점 구조로 통제를 모으고 런타임 검증 절차를 확립

전체적인 아키텍처

방어선이 실제로 걸리는 지점 — 로그아웃 무효화 경로와 SSE 세션 소유권 검증

문제 원인 및 한계점

  • 출발점은 이전 프로젝트의 제약 — 휠 파인더 프로젝트에서 Refresh Token을 토큰 전문으로 키잡아 사용자 단위 폐기를 못 했고 Redis 장애 정책도 부재. 같은 실수를 반복하지 않는 것이 첫 요구사항이라 키 기준·장애 정책·검증 절차를 먼저 정하고 구현에 착수
  • "방어 장치가 동작한다"를 무엇으로 증명할지를 먼저 정의해야 함 — 기능 테스트는 정상 흐름만 증명하지 방어선이 거부하는지는 증명하지 못함. 토큰 무효화는 쓰기·읽기·거부 세 지점이 짝을 이뤄야 성립하고(blacklist:access:{jti} 를 어디에 쓰고 어느 필터가 읽고 어떤 규칙으로 거부할지), 그 범위도 결정이 필요함 — access만 폐기할지 서버 보관본 refreshToken:{userId} 까지 포함할지에 따라 재발급 경로가 남는지가 갈림
  • SSE 연결 생성은 신규·재사용 두 분기로 갈라짐 — 검증을 호출부마다 두면 분기가 늘 때마다 새므로 검증을 어느 계층에 둘 것인가가 문제의 본질
  • 보안 설정은 yml에 값을 적는 것과 그 값이 실제 빈에 바인딩되는 것이 별개 — 키 위치가 한 단계만 어긋나도 기동 오류 없이 기본값으로 조용히 대체되는 구조라, 잠금 정책을 강화해도 그대로 적용된다는 보장이 미성립

해결 과정

  1. Redis 키를 전수 검색해 쓰기·읽기·삭제를 대조 — 방어 장치는 "쓰는 코드가 있다"가 아니라 "읽고 거부하는 코드가 있다"로만 검증된다고 판단. blacklist:access:{jti}는 통과했으나 refreshToken:{userId}는 발급 4경로 중 저장이 1곳뿐 — 폼 로그인만 저장하고 카카오·폼 회원가입·OAuth 회원가입은 쿠키만 양보. 재발급이 서버 보관본과 대조하는 방식이라 그 세 경로 사용자는 access 1시간이 끝나면 반드시 재로그인해야 함
  2. 원인은 발급 코드가 4곳에 복제된 것 — 한 곳에만 저장을 추가하면 나머지는 컴파일도 테스트도 통과하면서 조용히 다름. 발급·쿠키·저장을 TokenIssuer 한 메서드로 묶어 누락이 구조적으로 불가능하게 함
  3. 같은 대조에서 수명이 세 값으로 갈라진 것도 도출 — JWT exp 14일 vs Redis TTL·쿠키 7일이라 7일 뒤에는 폼 로그인 사용자도 재발급 실패였고 주석은 "TTL 7일 = 수명"으로 착오를 고정. 셋 다 jwt.access/refresh-token-expiration 에서 계산하게 통일해 양쪽 모두 리터럴 부재. access 쿠키는 발급 지점이 최초 발급·재발급 2곳이라 한쪽만 고치면 수명이 다시 갈라지므로 함께 교체 — 리터럴 60분과 설정 3,600,000ms 가 우연히 같아 증상 없이 잠복하던 종류
  4. 인증 필터가 블랙리스트를 조회해 거부하고 jti 없는 토큰도 폐기 취급. 조회 실패 시 통과냐 차단이냐를 명시적으로 결정 — fail-open은 장애 시간만큼 폐기 토큰을 되살리므로 fail-close, 근거는 코드에 남김. 로그아웃은 refreshToken:{userId}까지 지우고 손상·만료 토큰에도 쿠키 정리 후 정상 반환하는 멱등 처리
  5. "단일 통과점"에는 두 뜻이 있는데 약한 쪽만 구현돼 존재 — 판정은 헬퍼 하나로 모았지만 호출은 각 진입점이 손으로 해야 해서, 새 엔드포인트에서 빠뜨리면 그대로 구멍. 같은 클래스에만 검증 호출이 5곳. 판정과 진입 통제를 분리해 통제를 @RequireSessionOwner + 어드바이스로 이관하고, 인자 추출은 인터페이스 계약으로 정해 추출 실패 시 거부 — 통과시키면 애너테이션이 방어가 아니라 장식이 됨. 검증 지점 6곳 → 어드바이스 1 + 근거 있는 예외 2곳(연결 생성은 세션을 지금 만드는 요청이라 전제가 다르고, 메시지 소비자는 실패 처리가 HTTP 거부가 아니라 ACK/DLQ 결정)
  6. 거부를 사유별로 갈라 관측 가능하게 전환 — 소유자 불일치가 400 C_001로 나갔는데 이 코드는 요청 본문 검증 실패에도 붙어 오타와 세션 탈취 시도가 같은 버킷에 혼입. 403(인가 실패)과 404(대상 부재)로 분리. 통과점을 우회하는 목록도 함께 정리 — permitAll에 부하 테스트용 /test/**가 남아 dev가 곧 배포 프로파일인 이 저장소에서 스레드 점유 엔드포인트가 미인증 공개
  7. 설정도 같은 방식 — application*.yml 3개 파일 6곳이 한 단계 깊게 들여써져 엉뚱한 부모 키 아래였고, 경고 없이 SSE 30분 타임아웃·dev 1분 계정 잠금·prod 로그 레벨이 전부 미적용. 그래서 런타임 바인딩까지 확인하는 단계를 도입 — /actuator/configprops·/actuator/loggers로 실효값을 보고 계정 잠금은 423과 해제 시각까지 재현(임시 노출 + 인증 쿠키가 필요해 로컬 확인으로 한정)
  8. 인프라를 띄워 API로 재현 — 로그아웃한 access token 재요청 401 거부, 블랙리스트 TTL이 고정값이 아니라 토큰 잔여 수명 연동(3,579초), 멱등성은 토큰 부재·변조·형식 불명·만료·이미 로그아웃 5개 변형 전부 정상 종료. 소유권은 두 시나리오로 확인 — ① 원 사용자 연결 생존 ② 연결이 끊기고 Redis 세션만 TTL이 남은 상태(원래 빠져 있던 시나리오)

결과

  • 로그아웃한 토큰이 즉시 무효가 되는 상태로 전환 — 로그아웃 후 재요청 401이고, 블랙리스트 TTL이 잔여 수명에 맞춰 걸림(만료 1시간 토큰 → 3,579초). access만 끊으면 남은 refresh로 되살아나므로 서버 보관본까지 함께 지워 재발급 경로도 차단
  • 카카오·회원가입 사용자의 재발급이 영구 실패하던 결함을 해소 — 발급을 단일 진입점으로 묶어 새 경로가 늘어도 저장이 빠질 수 없는 구조로 전환. 수명이 세 값으로 갈려 7일 경계에서 폼 로그인 사용자까지 재발급이 깨지던 것도 함께 제거
  • 타인 세션 접근이 실제로 차단되고 거부 사유가 갈려 나옴 — 타인 세션 403 C_013, 없는 세션 404 C_014, 대조군인 정당한 소유자는 200 + text/event-stream 통과. 판정(헬퍼)과 진입 통제(어드바이스)를 갈라 새 엔드포인트가 늘어도 애너테이션 하나로 걸림
  • 적어 둔 보안 설정이 조용히 무시되는 상태를 제거 — 적힌 값과 실제 바인딩을 갈라 확인하는 단계를 검증 표준에 포함

7. 조회 경로 데이터 모델 설계

기능
문제 목록·스크랩북 조회와 RAG 벡터 검색을 담당하는 조회 경로
개선
쿼리 튜닝이 아니라 모델·인덱스 선택 단계에서 비용을 확정

전체적인 아키텍처

조회 세 갈래 — 기본값대로 둔 경우와 모델 단계에서 처리한 경우

문제 원인 및 한계점

  • 문제 상세는 지문·보기가 본문과 항상 함께 읽히는 단위인데 이를 자식 테이블 관계로 두면 목록 조회에서 문제 N건마다 지문·보기 조회가 따라붙음 — 화면 하나가 쿼리 1 + N회로 번지는 구조
  • RAG 검색은 1536차원 벡터의 코사인 거리 상위 K를 뽑는 질의라, 등호·범위 비교를 전제한 B-tree 인덱스가 개입할 자리가 부재 — 인덱스를 걸어도 전체 순차 스캔
  • 스크랩북 필터 조회는 화면에 쓰는 컬럼이 엔티티의 일부인데 엔티티로 받으면 쓰지 않는 컬럼과 연관까지 따라옴. 여기에 컬렉션을 fetch join으로 당기면 페이징이 DB가 아니라 메모리에서 일어나는 함정까지 겹침

해결 과정

  1. N+1 처방 후보 넷을 성질로 갈라 비교 — fetch join · @BatchSize · @EntityGraph · 데이터 모델 변경. 앞의 셋은 N번 나가던 쿼리를 1~2번으로 줄이는 처방이고 관계 자체는 유지되므로, 조회 지점이 늘어날 때마다 같은 판단을 다시 해야 함. 지문·보기는 문제와 독립으로 조회·수정되는 일이 부재한 값이라 관계로 둘 이유가 없다고 보고 @JdbcTypeCode(SqlTypes.JSON)으로 passages · options를 JSONB 컬럼에 합침 — 조인 횟수를 줄이는 것이 아니라 조인 대상을 소멸
  2. 합치는 쪽의 대가를 먼저 확정하고 선택 — 지문 단위의 SQL 검색과 보기 하나만의 부분 갱신을 포기하게 됨. 이 도메인은 문제 단위로만 읽고 쓰므로 감당 가능하다고 판단. 반대로 대가가 큰 곳에는 같은 처방을 쓰지 않음 — 사용자·시험 결과처럼 독립 조회·집계 대상인 관계는 그대로 둠
  3. 관계로 남긴 집계 조회에는 다른 처방 — 스크랩북 필터 조회를 SELECT new ...ScrapbookFilterResponse(...) JPQL 생성자 표현식으로 받아 필요한 컬럼만 가져옴. 엔티티를 로딩하지 않으므로 컬렉션 fetch join의 페이징 함정 자체가 미발생 — 두 처방이 같은 함정을 서로 다른 방향으로 회피한 것
  4. 벡터 인덱스는 후보 성질부터 나뉨 — B-tree·GIN은 정렬 기준이 값이 아니라 계산 결과라 애초에 탈락. pgvector가 주는 두 후보 중 IVFFlat은 적재된 데이터 분포로 클러스터를 잡아야 인덱스 품질이 서므로 문서가 계속 추가되는 구조에서는 재색인 주기가 필요. HNSW는 삽입마다 그래프를 갱신해 그 주기가 불필요하고, 대가인 색인 크기·삽입 비용은 적재가 배치로 한 번 일어나는 이 시스템에서 부담이 작음 — 그래서 USING hnsw (embedding vector_cosine_ops)로 확정
  5. 세 처방의 공통 판단 — 셋 다 조회 시점에 손대는 튜닝이 아니라 모델·인덱스를 정하는 단계에서 비용을 없앰. N+1은 ORM의 결함이 아니라 "언제 가져올지를 안 정한 상태"의 증상이라, 정할 자리를 조회 코드가 아니라 스키마로 옮긴 것

결과

  • 지문·보기로 인한 추가 쿼리가 구조적으로 미발생 — 조회 코드를 어떻게 쓰든 조인할 대상이 부재하므로, 새 조회 지점이 생겨도 같은 판단을 반복할 필요가 없음
  • 스크랩북 필터 조회가 화면에 필요한 컬럼만 가져오는 경로로 성립 — 엔티티 로딩이 없어 쓰지 않는 연관이 따라붙지 않고, 컬렉션 fetch join이 만드는 메모리 페이징도 회피
  • 벡터 검색이 순차 스캔이 아닌 그래프 탐색 경로로 성립 — 현재 코퍼스 5,799청크에서 검색이 평균 361~401ms(임베딩 왕복 포함, 경로별 실측)로 응답

1. 선착순 쿠폰 발급 파이프라인 설계

기능
한정 수량 쿠폰을 선착순으로 발급하는 기능. 오버셀링 방지가 핵심 요구
개선
"선착순"이 무엇의 순서인지를 단일 판정으로 확정하고, 발급 경로에서 락과 DB를 제거

전체적인 아키텍처

선착순 발급 경로 — Redis는 부하 필터, 순서의 진실은 Kafka 오프셋, 확정은 파티션당 단일 컨슈머

문제 원인 및 한계점

  • 선착순의 기준점 정의 부재. 서버가 여러 대면 "먼저 온 요청"을 판정할 주체가 사라짐 — 인스턴스 수신 시각은 NTP 오차만큼 흔들리고 클라이언트 시각은 조작 가능함. 기준의 정의가 없어 증설하는 순간 순서가 흔들림
  • DB 비관적 락(SELECT ... FOR UPDATE)은 정확성은 지키나 DB 커넥션 풀(HikariCP)이 곧 동시 처리 상한이 됨. 풀은 maximumPoolSize=20이고 늘려도 컨텍스트 스위칭·DB 측 잠금 경합이 먼저 늚. 그 풀을 주문·결제가 함께 써서 쿠폰 이벤트 한 번이 서비스 전체 지연으로 번지는 경로가 열려 있었고, 임계 구역에 DB I/O가 있는 한 증설로는 초과 불가
  • 대안으로 검토한 Redisson 분산 락은 직렬화 지점만 옮김. 핫 쿠폰에선 전 요청이 한 락을 통과해야 해 대기가 쌓이고, tryLock(waitTime=3s)을 넘긴 요청은 재고가 남아도 품절 응답을 수신 — 정확성용 도구가 만든 것은 거짓 품절이라는 가용성 결함
  • 부하로 확인한 것은 그 락이 대가만큼의 보장도 못 준다는 사실 — 같은 구성 2회 측정에서 발급 지연 중앙값이 341ms에서 10,650ms로 튀며 고정 leaseTime(5초)을 넘었고, 그 구간에서 중복 발급 1건을 실제로 관측함. 머신 부하만 달라졌는데 상호배제가 깨진 것이고, 고정 leaseTime은 "임계 구역은 항상 5초 안에 끝난다"는 검증되지 않은 전제
  • 확장 구성에선 Redis를 정확성의 단독 근거로 사용 불가(standalone이라 관측이 아니라 확장 시 성립할 제약) — 복제가 비동기라 승격이 일어나면 마지막 수 ms의 쓰기가 되감기고, 재고 카운터·순번이 되감기면 그대로 초과발급

해결 과정

  1. 선착순의 기준점을 Kafka 브로커 도달 순서(오프셋)로 정의 — 클라이언트 시각은 조작 가능, API 수신 시각은 N대 시계 오차, Redis 도달 순서는 failover에서 되감김. Kafka만 파티션 안에서 결정적 전순서가 서고 그 순서를 재생 가능 — 이 선택으로 확보한 것은 정상 운영에서의 순서 결정성과 재생 가능성 둘
  2. 두 계층을 가른 근거는 도달 가능한 보장의 차이 — Kafka는 RF≥3 · acks=all · min.insync.replicas=2 설정만으로 장애 시에도 순서 보존을 얻지만, Redis는 재생 가능한 로그가 없어 같은 속성에 도달 불가. 기준점을 Kafka에 둔 것은 이 성질 때문
  3. 파티션 키를 couponId로 잡아 한 쿠폰의 이벤트를 한 파티션에 집약. 그 파티션의 컨슈머는 1명이라 API가 N대여도 쿠폰당 판정자는 항상 1명 — 상호배제를 락으로 사는 대신 파티션 소유권으로 얻어 분산 락이 필요 없어짐
  4. Redis를 정확성의 근거에서 내리고 부하 필터로 재배치 — Lua가 "마감·중복"을 왕복 한 번에 판정해 5,000건 중 100건만 브로커에 실림. 근사여도 안전한 것은 최종 판정을 컨슈머가 하기 때문이고, Lua인 이유는 서버 대수와 무관하게 "확인 → 차단"이 쪼개지지 않기 때문. 다만 보장 범위는 한 왕복의 불가분성이지 사용자별 1회성이 아니라, 게이트를 거치지 않는 경로와 확정 실패 시 되돌림이 있어 같은 사용자가 다시 통과할 가능성. 키의 해시태그는 Cluster 전환 시 CROSSSLOT을 피하려는 선제 조치
  5. 대기 순번은 아예 응답하지 않기로 함. "당신은 N번째"가 확정 결과와 같아야 하는데 접수 시점엔 확인 불가 — 게이트 통과 순서와 오프셋 순서가 컨텍스트 스위칭으로 어긋나고, 게이트는 근사라 통과분이 재고보다 많을 가능성. 주는 순간 지킬 수 없는 순서를 약속하므로, 접수는 requestId만 돌려주고 확정은 상태 조회로 이월. ZSet 원장에 ZRANK로 순번을 두는 안은 미도입 — 오프셋 순서를 한 번 더 복제하는 것이라, 두 순서가 어긋나면 진실을 정할 방법이 부재
  6. 응답 경로에서 DB를 제거. API는 Lua 게이트 통과와 Kafka 발행까지만 하고 즉시 응답하며, DB 쓰기는 컨슈머가 담당함. 쿠폰 스파이크가 커넥션을 점유하지 않아 주문·결제 경로에 무간섭 — 쿠폰 장애가 매출 경로로 번지지 않는 구조. 대가는 사용자가 발급 결과 대신 접수 확인만 받는 것
  7. 최후 방어선은 DB에 두 겹 — 유니크 제약과 조건부 UPDATE. 중복은 UNIQUE(coupon_id, user_id)로, 초과발급은 UPDATE ... WHERE quantity > 0의 영향 행 수 0 판정으로 차단 — 검사와 차감이 한 문장에서 끝나기 때문
  8. 실제로 걸어 보니 dev DB에 이미 위반 데이터가 존재 — 같은 사용자·같은 쿠폰 2건이 56ms 간격. Redis는 스크립트를 직렬 실행하므로 뒤엣것은 중복 검사에 걸렸어야 함 — 최소 한 건은 게이트를 거치지 않았다는 뜻이고, 실제로 재고 키가 없으면 NOT_INITIALIZED로 통과시켜 DB 폴백에 맡기는 경로가 코드에 존재(어느 경로였는지는 로그가 없어 미단정). 이 제약은 보험이 아니라 이미 난 사고를 막는 장치
  9. 분산 락은 발급 경로에서 걷어내 배치·관리 경로로 이관. N대면 @Scheduled가 N번 실행되므로, 재고 대조·보정 배치에는 하나만 실행하도록 락을 적용. 락을 쓸 조건은 저빈도 · 긴 임계 구역 · 큰 중복 실행 피해인데, 배치는 셋 다 맞고 발급 경로는 셋 다 반대. 쿠폰 자동 비활성화의 Kafka Streams는 같은 중복 실행 문제를 파티션 소유권으로 풀었으나, 보정 배치는 Kafka 토폴로지 밖이라 그 방법은 적용 불가
Lua 
-- KEYS[1] coupon:{id}:stock   KEYS[2] coupon:{id}:issued_users   ARGV[1] userId
-- 반환 1=성공 0=품절 -1=중복 -2=미초기화
-- 정확성의 근거가 아니라 부하 필터다 — 통과량이 실제 재고보다 많아도 컨슈머가 최종 판정한다

-- 중복 검사를 재고 검사보다 앞에 둔다. 뒤에 두면 재고가 0 이 된 뒤로는
-- 이미 받은 사용자의 재요청까지 "품절"로 응답돼 실패 집계에서 중복과 품절이 섞인다
-- 재고 소진은 이벤트 초반에 오므로 그 뒤의 요청이 다수다 - 오분류가 예외가 아니라 기본값이 된다
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1
end

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -2                                -- 미초기화: 판정을 컨슈머의 DB 폴백에 위임한다
end
if stock <= 0 then
    return 0                                 -- 마감: 브로커 앞에서 자른다
end

-- 통과 예상 인원만 줄인다. DB 확정이 실패하면 호출부가 INCR + SREM 으로 되돌린다
-- 확정에 닿기 전에 유실되면 되돌릴 주체가 없다 - 그 몫은 대조 배치가 회수한다
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1

결과

  • 인스턴스를 늘려도 선착순 순서가 흔들리지 않음 — 기준이 Kafka 도달 순서이고 파티션 로그에 남아 재생 가능함. N대로 늘려도 판정자는 파티션당 1명이라 순서가 인스턴스 수와 무관
  • 발급 경로에서 락과 DB를 동시에 제거 — 응답까지 드는 일은 Lua 왕복 1회와 Kafka 발행뿐이고 대기 구간이 없어 락 대기 초과로 생기던 거짓 품절이 원인 단계에서 소멸(재측정에서 경합 실패 0건). DB 커넥션을 점유하지 않아 주문·결제와 자원 경합 부재
  • 브로커에 닿는 요청이 5,000건에서 100건으로 감소 — 수량 100개 쿠폰에 VU 200 · 5,000 요청에서 Lua 게이트가 4,900건을 접수 단계에서 차단(품절 2,559 · 중복 2,341)해 브로커에는 정확히 100건만 도달. 확정도 100건 전부 성공했고 issued_users · coupon_issue 행수 · 차감된 수량 세 값이 100으로 일치해 초과발급·중복 각 0건. 미초기화 폴백이 0건이라 이 수치는 DB 폴백이 아닌 게이트를 잰 값
  • 네 도구의 보호 범위 중복 부재 — Lua는 부하 필터, Kafka 오프셋은 순서의 진실, 컨슈머는 정합성의 근거, 분산 락은 배치의 배타 실행. 락과 Lua가 같은 임계 구역을 이중으로 지키던 것이 정리됨
  • 락이 못 지킨 것은 총량 상한이 아니라 상호배제 — 같은 락 구성 부하에서 수량 100개 쿠폰에 VU 200 · 5,000 요청으로 100건 발급으로 상한 자체는 지켜졌고, 깨진 것은 부하가 튈 때의 상호배제(중복 발급 1건). 이 둘을 갈라야 락을 걷어낸 이유가 성립

2. PG 결제 보상 파이프라인 설계

기능
Toss Payments 승인 후 주문 상태 변경·재고 차감까지 마치는 결제
개선
부분 실패에도 장부가 남게 만들고, 한쪽 장애가 반대쪽 보상을 막지 않도록 회로를 분리

전체적인 아키텍처

결제 실패 시 보상 흐름 — 즉시 취소 → 실패 시 배치 재시도 → 최종 포기 격리

문제 원인 및 한계점

  • Toss Payments 승인 성공 후 내부 DB 후처리(주문 상태 변경, 재고 차감)가 실패하면 "결제만 되고 주문이 없는" 부분 실패가 발생
  • 외부 PG 승인은 DB 롤백으로 되돌릴 수 없는 비가역 작업인데, 내부 가역 작업과 트랜잭션 경계 분리 부재
  • 멱등성이 없어 재시도 시 이중 결제가 발생할 위험이 존재
  • 보상 경로 자체가 실패할 수 있다는 것이 다음 문제 — 보상 기록과 실행이 한 트랜잭션에 묶이면 이 경로에 진입하는 원인이 DB 장애일 때 기록부터 함께 무너져 채무는 남고 장부는 사라지는 상태. 재시도 배치가 주울 대상 자체가 부재
  • 보상 레코드에 상태 개념이 없으면 재시도가 성공 건을 덮어씀 — 이미 취소가 끝난 건에 취소가 다시 나가는 경로가 열린 상태
  • 멱등키는 PG의 멱등성 윈도우 안에서만 유효 — 재시도 한도와 백오프를 그 윈도우와 무관하게 정하면 키가 목적을 상실
  • 외부 PG의 느린 실패가 다른 요청까지 끌고 감 — 게다가 승인과 취소는 같은 외부 시스템이라도 실패의 뜻이 서로 상이해 한 묶음으로 다루면 한쪽 장애가 반대쪽을 함께 차단

해결 과정

  1. 결제 승인 호출은 NOT_SUPPORTED 비트랜잭션으로, DB 후처리는 REQUIRES_NEW 독립 트랜잭션으로 분리해 "되돌릴 수 없는 것"과 "되돌릴 수 있는 것"이 하나의 트랜잭션에 묶이지 않도록 함
  2. DB 후처리가 실패하면 Saga 보상 트랜잭션으로 외부 PG 취소 API를 즉시 호출하고, 그마저 실패하면 보상 테이블에 적재해 @Scheduled 배치가 재시도하도록 구현 — 즉시 시도 1회 + 실패마다 지수 백오프(2·4·8·16분) 재시도 4회로 총 5회 시도, 초과 시 GIVEN_UP 전환과 운영자 알림
  3. 2단 방어의 순서가 반대 — 보상 레코드 INSERT와 PG 취소 호출과 결과 기록이 전부 한 트랜잭션(같은 클래스 자기호출이라 트랜잭션이 하나로 합쳐짐). 그런데 이 경로에 진입하는 조건이 DB 후처리 실패라, 원인이 DB 장애면 INSERT부터 실패해 1단이 무너지면 2단이 읽을 레코드도 함께 사라짐 — 채무는 있는데 장부가 없는 상태. Saga 보상의 기본은 "의도 기록을 커밋한 뒤 실행"이므로, 레코드 기록을 REQUIRES_NEW로 떼어 먼저 커밋시키고 실행을 그 뒤로 둠
  4. 재시도 배치도 트랜잭션 없이 돌고 존재 — 배치가 실행 메서드를 자기호출해 @Transactional이 애초에 미적용. 프록시 경유로 바꾸고, 테스트가 "프록시를 통해 호출했는지"를 직접 고정하도록 함 — 결과만 보는 테스트로는 이 회귀를 잡을 수 없기 때문
  5. 보상 대상은 두 갈래 — Redis 재고 선점분 복원(즉시·멱등)과 PG 취소(재시도 대상). 선점 복원을 먼저 두는 이유는 실패해도 재고 과소 계상이라는 안전한 방향에 그치는 반면, PG 취소 지연은 사용자 금전에 직결되기 때문. 두 보상은 독립 멱등이라 부분 성공이 나도 각각 재시도로 수렴함
  6. 보상 레코드는 4개 상태의 전이표로 관리 — PENDING·FAILED에서만 다음으로 갈 수 있고 SUCCEEDED·GIVEN_UP은 종단. 원래는 현재 상태를 보지 않고 덮어써 "취소 성공 후 다시 재시도"가 열려 있었고, 조회 쿼리 조건에만 의존하면 새 호출부가 생기는 순간 뚫림. 전이표를 엔티티 안에 두어 거부되게 하고, 거부 시 재시도 횟수도 오르지 않도록 판정을 카운트보다 앞에 둠
  7. 승인 경로 멱등성은 내부 결제 키 선조회와 외부 PG Idempotency-Key 헤더의 2단계 — 다만 두 단계는 미대등. 선조회는 트랜잭션 없는 읽기라 동시 요청 둘이 함께 통과할 수 있어 정합성 보증이 아니라 조기 반환 최적화이고, 실제로 이중 결제를 막는 것은 PG의 멱등키와 결제 상태 머신(두 번째 요청은 상태 전이에서 막혀 롤백됨). PG가 발급한 결제 키는 재시도 사이에 변하지 않는 불변 값
  8. 보상(취소) 경로에도 승인 경로와 같은 기준을 수립 — 멱등키가 만족해야 하는 성질을 ① 동일 의도는 동일 키 ② 다른 의도는 다른 키 ③ 프로세스 재시작에도 살아남을 것 세 가지로 정리하고, 보상 레코드의 식별자처럼 재시도 간 불변인 값을 키로 삼는 것을 기준으로 설정. 재시도 횟수처럼 시도마다 변하는 값이 키에 섞이면 첫 번째 성질이 깨져 "상대는 취소를 처리했는데 응답만 타임아웃된" 경우를 새 요청으로 오인하게 되고, 그러면 멱등키가 목적을 상실
  9. 재시도 한도와 백오프 간격은 PG 멱등성 윈도우를 상한으로 두고 정해야 하는 값 — 백오프는 실패 시점 기준이고 배치가 30초 주기로 줍기 때문에 실제 경과는 항상 크며, 총합 30분은 상한이 아니라 하한. 같은 키를 다시 보내도 새 요청으로 취급되는 시점을 넘기면 키 자체가 무의미해지기 때문
  10. Resilience4j 서킷브레이커로 실패율 50% 초과 시 30초 OPEN, HALF-OPEN 단계적 복구를 적용해 PG 장애가 다른 요청까지 지연시키는 Cascading Failure를 방지 — 단, 서킷이 승인 경로에만 붙어 있었고 취소 호출은 무보호. PG 전면 장애 구간에서 보상 취소가 매번 타임아웃까지 스레드를 붙잡아 보상 배치 자체가 느려지는 구조
  11. 취소에도 서킷을 붙이되 승인과 같은 회로에 물리지 않고 전용 회로로 분리함 — 같은 회로면 양방향 모두 나쁨: 보상 취소 실패가 회로를 열면 정상 결제까지 막히고, 반대로 승인 장애로 열린 회로가 취소를 fast-fail시키면 채무가 쌓이는 동안 아무 시도도 못 함. 하나의 외부 시스템이라도 실패의 의미가 다른 호출은 회로를 나눠야 함

결과

  • 보상 경로가 실패해도 장부는 남는 구조가 됨 — 의도 기록을 먼저 커밋하므로 실행이 무너져도 배치가 주울 대상이 남고, 상태 전이표가 종단 상태를 지켜 재시도가 성공 건 덮어쓰기 불가.
  • 외부 PG 장애(5s 지연 + 500 주입) 시 서킷브레이커 fast-fail 응답 평균 632.9ms, 장애 구간 호출의 97.8%(667/682)를 PG 미도달로 차단
  • 서킷브레이커와 보상 재시도의 값이 서로를 고려해 확정 — 취소 전용 회로가 OPEN인 구간에는 취소도 fast-fail되지만, 첫 백오프 2분이 OPEN 30초를 충분히 넘기므로 2회차부터 정상 복구 경로에 진입함. 즉 즉시 시도 1회는 서킷이 닫혀 있는 일반 실패용이고, PG 전면 장애에서는 2회차가 실질 첫 시도. 이 계산은 취소에 회로를 붙인 뒤에야 성립함 — 이전에는 존재하지 않는 메커니즘에 대한 계산
  • 승인과 취소가 같은 멱등 기준 위에 놓임 — 재시도 간 불변인 값을 키로 삼아, 상대는 처리했는데 응답만 유실된 경우가 새 요청으로 오인되지 않는 구조. 재시도 한도·백오프도 PG 멱등성 윈도우를 넘기지 않는 것을 기준으로 설계
  • 실패 응답 경로의 비용 구성이 드러나 후속 개선으로 이어짐 — fast-fail 응답의 0.6초를 재고 선점 해제·실패 기록 비용으로 분해하고, 결제 이벤트 Outbox와 재시도 포기(GIVEN_UP) 건 전용 DLQ 이관을 도입

3. 쿠폰 자동 비활성화 파이프라인 설계

기능
쿠폰마다 정해진 만료 시각이 되면 자동으로 비활성화하는 기능
개선
폴링 대안 대신 StateStore + Punctuator를 택해 최악 지연 1.1s 확보

전체적인 아키텍처

폴링 스캔 vs StateStore + Punctuator 지연 비교

문제 원인 및 한계점

  • 이 문제는 자원 경합이 아니라 지연 스케줄링 — 동시에 하나의 자원을 다투는 구조가 아니라, 예약된 시각에 정확히 한 번 실행하는 것이 요구사항이라 재고 차감·결제 사례와는 다른 종류의 해법이 필요함
  • 비교 대상인 폴링 방식은 저장소에 커밋된 구현이 아니라 설계 단계에서 놓고 계산한 대안 — @Scheduled(fixedDelay=10s)로 전체 스캔 후 인메모리 TaskScheduler에 지연 실행을 등록하는 형태이고, 폴링 주기 10초 + 스캔 2초로 최대 지연 약 12초가 나옴. 이전 구현을 개선한 것이 아니라 두 설계를 비교해 하나를 고른 것
  • 그 방식의 문제는 둘 — ① 매번 전체를 훑는 스캔이라 대상이 늘수록 비용이 선형 증가하고, ② 서버 재시작 시 인메모리 스케줄러 등록분이 통째로 사라져 도래할 쿠폰이 미비활성화(다음 스캔이 다시 주워야 복구되므로 유실이 지연으로 나타남). 그래서 도구 선택의 근거를 규모가 아니라 부하의 이동 방향(DB 밖으로)에 배치

해결 과정

  1. 단순 주기 단축(1초 폴링 + scheduled_at 인덱스)을 먼저 검토함. 이 방식으로도 조회 복잡도는 O(log N + M)으로 같아지고 지연도 같게 만들 가능성. 도입하지 않은 이유는 둘 — ① 주기를 10초에서 1초로 줄이면 스캔 빈도가 10배가 되어 DB가 스케줄링 부하를 그대로 수신 ② 처리 인스턴스를 늘리면 같은 쿠폰을 중복 실행하지 않도록 별도 조율(락 또는 샤딩)을 설계해야 함. StateStore는 조회를 DB 밖으로 빼고 파티션 소유권이 정상 상태에서 중복 실행을 배타적으로 막아 이 둘을 동시에 해결함 — 다만 리밸런싱 구간에서는 소유권이 이동해 중복 실행 가능성이 잔존
  2. Kafka Streams Processor API + StateStore를 도입해 지연 처리 토폴로지를 구성하고, 실행 예정 시각(초 단위)을 키로·같은 초에 도래하는 이벤트 목록을 값으로 하는 영구 StateStore에 적재하도록 전환 — 동일 시각 이벤트가 여러 건이어도 목록에 누적돼 미유실
  3. 이벤트 적재(발급 시점의 예약 등록)와 실제 비활성화 트리거(예약 시각 도래 시 Punctuator 실행)의 시점을 분리했고, 새 이벤트 유입과 무관하게 항상 스캔되도록 punctuate 스케줄을 WALL_CLOCK_TIME 기준으로 등록
  4. Punctuator가 1초 주기로 Range Query(O(log N + M))만 수행해 "전체 스캔"을 "도래한 것만 조회"로 전환
  5. exactly_once_v2를 적용하되 그것이 덮는 범위를 정확히 한정함 — EOS의 트랜잭션 경계는 입력 오프셋 커밋 · StateStore changelog · 출력 토픽까지이고, 쿠폰 비활성화는 DB 쓰기라 이 경계 밖. 따라서 "출력 후 커밋 전 장애 → 재처리"에서 비활성화가 두 번 실행될 가능성. 비활성화는 is_active = false를 쓰는 연산이라 몇 번을 실행해도 결과가 같아 실효 멱등이므로 재처리가 일어나도 결과는 동일 — EOS가 덮는 범위와 멱등이 덮는 범위를 갈라 둠
  6. 실패 이벤트는 전용 DLQ 토픽과 별도 Consumer로 분리하고, Prometheus + Micrometer로 consumer lag·throughput·StateStore 크기를 노출해 정상 파이프라인에 영향 없이 관측하도록 함
  7. 구 Transformer에서 신 Processor API로 이관 — 구 API는 Kafka Streams 4.0에서 제거라 다음 메이저에서 깨짐. 바꾼 것은 클래스명 하나뿐이고 스토어명은 유지 — 바꾸면 changelog 토픽명과 RocksDB 디렉터리가 달라져 대기 중이던 지연 이벤트가 통째로 유실. 동작 동일성은 TopologyTestDriver로 이관 전 베이스라인을 잡고 고정
Java · CouponDelayProcessor 
@Override
public void init(ProcessorContext<String, CouponDelayEvent> context) {
    this.context = context;
    this.stateStore = context.getStateStore(stateStoreName);   // 스토어명을 바꾸면 대기 이벤트가 유실된다
    // WALL_CLOCK 을 쓰는 이유는 STREAM_TIME 이 신규 레코드 없이는 전진하지 않아,
    // 유입이 멈춘 구간에서 대기 중인 쿠폰이 영원히 비활성화되지 않기 때문이다
    context.schedule(Duration.ofSeconds(1), PunctuationType.WALL_CLOCK_TIME, this::checkStoreAndForward);
}

@Override
public void process(Record<String, CouponDelayEvent> record) {
    CouponDelayEvent event = record.value();
    // 실행 예정 시각을 '초' 로 그룹화한다. 밀리초로 두면 키가 과도하게 늘어난다
    long executionSecond = (context.currentSystemTimeMs() + event.getDelayMillis()) / 1000;

    CouponDelayEventListWrapper wrapper = stateStore.get(executionSecond);
    if (wrapper == null) wrapper = new CouponDelayEventListWrapper(new ArrayList<>());
    wrapper.getEvents().add(event);   // 같은 초의 이벤트는 누적한다 — 덮어쓰면 유실된다
    stateStore.put(executionSecond, wrapper);
}

// 도래한 초만 range 로 훑어 forward 하고 즉시 지운다. 지우지 않으면 다음 초에 중복 처리된다
private void checkStoreAndForward(long wallClockTime) {
    try (KeyValueIterator<Long, CouponDelayEventListWrapper> iter =
                 stateStore.range(0L, wallClockTime / 1000)) {
        while (iter.hasNext()) {
            KeyValue<Long, CouponDelayEventListWrapper> entry = iter.next();
            for (CouponDelayEvent event : entry.value.getEvents()) {
                // 출력 키는 '초' 가 아니라 couponId 다 — 그래야 하류에서도
                // 쿠폰당 파티션이 유지돼 "쿠폰당 판정자 1명" 이 깨지지 않는다
                context.forward(new Record<>(String.valueOf(event.getCouponId()), event, wallClockTime));
            }
            stateStore.delete(entry.key);
        }
    }
}

결과

  • 지연 단축의 직접 원인은 주기 단축(10s → 1s)이며, Kafka Streams를 택한 이유는 그 주기를 DB 부하 증가 없이 감당하기 위해서 — 폴링을 1초로 줄이면 스캔 빈도가 10배가 되지만 StateStore 조회는 DB 밖에서 끝남. 즉 이 전환의 성과는 "더 빠른 도구"가 아니라 "같은 속도를 DB 부하 없이, 그리고 인스턴스를 늘려도 중복 실행 없이"임
  • 처리 지연 최악값 1.1s(이벤트 발행~비활성 전환 시각 차 직접 측정)이고, punctuate 주기 1s + 처리시간이라는 이론 최악값에 수렴
  • 이벤트 상태를 changelog 기반 영구 StateStore에 저장해 서버 재시작 후에도 대기 작업이 잔존 — 기존 인메모리 스케줄러에서 재시작마다 사라지던 등록분이 유지됨
  • 실패 이벤트를 DLQ로 격리해 정상 파이프라인 영향 없이 처리

4. 추첨 예약 실행 파이프라인 설계

기능
응모 마감 시각이 지나면 당첨자를 뽑는 추첨 실행
개선
예약을 프로세스 밖에 두어 재기동에 견디게 하고, 발행·처리 실패가 모두 재시도로 수렴

전체적인 아키텍처

추첨 예약 실행 경로 — 시각 판정은 Redis ZSet, 실행은 Kafka 컨슈머

문제 원인 및 한계점

  • 추첨은 선착순 쿠폰 발급과 성질이 반대 — 접수 순서가 아니라 마감 이후의 한 시점에 단 한 번 실행되는 작업이라, 요청이 실행을 끌어내지 않고 시각이 실행을 끌어냄
  • 인메모리 타이머에 두면 재기동마다 예약이 소멸. 실행 시각이 며칠 뒤일 수 있고 그 사이 배포가 들어가므로, 예약은 프로세스 밖에 있어야 함
  • 어디에 두든 마감 시각을 감시하는 주기 조회는 불가피하므로, 갈리는 기준은 폴링 여부가 아니라 조회 한 번이 곧 "지금 실행할 것 전부"가 되는가 — 실행 시각을 애플리케이션이 매번 계산해야 하면 그 계산이 조회마다 따라붙음. 마감 취소로 예약을 지우는 경로도 따로 필요
  • 추첨은 중복 실행 피해가 큰 작업 — 발행과 처리 어느 쪽이 실패해도 유실 아니면 중복 중 하나를 고르게 되므로, 되돌릴 수 있는 쪽을 정해 둬야 함

해결 과정

  1. 예약을 어디에 둘지부터 후보 셋을 성질로 갈라 비교 — ① DB 스케줄 테이블 폴링 ② Quartz(JDBC JobStore) ③ Redis Sorted Set. ①은 전용 테이블과 마이그레이션이 새로 생기고 취소도 삭제 쿼리로 다뤄야 함. ②는 클러스터 모드로 중복 실행까지 막아 주지만 전용 스키마와 스케줄러 운영이 함께 따라옴 — 예약 대상이 추첨 한 종류뿐이라 범용 스케줄러가 주는 값에 비해 부담이 큼. ③은 필요한 연산 두 개가 자료구조 자체의 연산으로 성립하고(시각순 범위 조회 · 멤버 제거) 이미 세션·재고에 쓰고 있어 새 인프라가 불필요 — ③ 선택
  2. score를 실행 시각(epoch ms)으로 설정 — rangeByScore(0, now) 한 번이 곧 "지금 실행할 것 전부"라, 시각 비교를 애플리케이션이 아니라 자료구조가 수행. 취소는 멤버 제거 한 번이고, 프로세스 밖에 있어 재기동에도 잔존
  3. 시각 판정과 실행을 분리 — 폴링이 하는 일은 대상 조회와 Kafka 발행까지이고 추첨 로직은 컨슈머가 담당. 폴링 루프가 무거운 작업을 들고 있으면 다음 주기가 밀려 지연이 누적되므로, 루프는 짧게 유지하고 실행은 큐 뒤로 밀어냄
  4. 발행이 성공한 뒤에만 ZSet에서 제거 — 발행 콜백에서 제거하고 실패하면 그대로 둬 다음 주기가 다시 수거. 먼저 지우고 발행하면 유실, 발행하고 못 지우면 중복인데, 둘 중 되돌릴 수 있는 쪽인 중복을 선택한 것
  5. 컨슈머는 수동 ACK로 두고 추첨 실행이 끝난 뒤에만 커밋 — 실패하면 커밋하지 않아 재처리 대상으로 잔존. 3과 4가 겹쳐 발행 실패·처리 실패 양쪽이 재시도로 수렴
  6. 당첨자 알림은 별도 try/catch로 격리 — 알림 실패가 이미 확정된 추첨을 되돌리지 않게 함. 부가 작업의 실패가 본 작업의 성공을 취소하지 않는다는 경계
  7. 설정 실수 한 건을 먼저 분리해 수정 — fixedDelay가 6,000,000ms(100분) 리터럴인데 주석은 "1분"이라 값과 서술이 100배 어긋난 상태. 리터럴이라 아무도 안 읽는 자리였고, 저장소의 다른 배치 3개는 이미 전부 fixedDelayString + 설정 키 형태. 같은 관례로 통일해 raffle.drawing.poll-delay-ms(기본 60,000ms)로 이관하고 근거를 yml 주석에 남김
  8. 지연 상한이 곧 폴링 주기라는 것은 값이 아니라 구조의 성질 — 주기를 줄이면 상한이 줄 뿐 구조는 불변. 쿠폰 자동 비활성화에서 같은 폴링 지연을 Kafka Streams Punctuator로 없앤 것과 정반대 선택이고, 두 도메인의 요구가 달라 갈린 것

결과

  • 예약이 프로세스 밖에 남아 재기동에 견딤 — 배포가 예약을 지우지 않고, 취소는 ZSet 멤버 제거 한 번으로 끝남
  • 시각 판정 비용이 자료구조로 이동 — 애플리케이션은 조회 결과를 그대로 발행만 하므로 폴링 루프가 짧게 유지됨
  • 발행·처리 실패가 모두 재시도로 수렴하는 at-least-once — 실패가 유실이 아니라 재시도로 흡수됨

5. 재고 차감 전략 설계

기능
결제 승인과 함께 상품 재고를 차감하는 기능. 오버셀링 방지가 핵심 요구
개선
Lost Update를 막고, 세 가지 차감 전략 실측으로 기본 전략을 선정

전체적인 아키텍처

재고 차감 2단 방어 — Redis 선점 게이트 → DB 비관적 락

문제 원인 및 한계점

  • 동시 결제 시 재고 차감에 Lost Update 위험이 존재
  • 비관적 락은 정확성을 지키지만 고경합에서 DB 행 잠금을 장기 점유해 처리량이 떨어짐
  • 주문 생성 시점의 재고 검증은 읽고 나서 판단하는 비원자 검사라, 검증을 통과한 뒤 결제 확정에 닿기 전에 재고가 바닥나면 그대로 PG까지 도달함
  • 어느 차감 전략이 이 워크로드에 맞는지는 고르기 전에 알 수 없음 — 낙관적 락 · 조건부 UPDATE · 비관적 락은 전제하는 경합 수준이 서로 달라, 근거 없이 하나를 고르면 재시도 한도 같은 파생 값도 함께 근거를 상실
  • Redis 게이트를 앞에 두면 두 저장소가 같은 수량을 각자 셈 — 정합의 최종 책임은 DB인데 선점 수와 DB 재고가 어긋날 수 있고, 정상 인플라이트와 진짜 어긋남이 겉으로는 같은 모양

해결 과정

  1. 상품 엔티티에 @Version 낙관적 락을 걸고 충돌 시 자동 재시도 — @Retryable(maxAttempts=3, @Backoff(delay=100, multiplier=2, random=true, maxDelay=1000)). 지터는 thundering herd를 분산하려는 것이고, 한도 3은 이후 3종 실측으로 재검토(그 실측으로 기본 전략은 비관적 락으로 전환하고, 낙관적 락 경로는 설정 선택지로 잔존)
  2. 재고 차감을 REQUIRES_NEW 독립 트랜잭션으로 처리해 매 시도가 새 트랜잭션에서 커밋·충돌 감지되게 하고, 결제 진입 직전 Redis DECR 원자 연산으로 재고를 선점해 부족분을 PG 호출 전에 차단함
  3. Redis 미초기화 상품은 DB 락으로 폴백하는 2단 방어 — 이때 Redis에 되쓰지 않고 게이트만 통과시키는 것이 중요. Redis는 부하 필터일 뿐 최종 정합은 DB의 차감 전략이 책임짐. 재고에 쿠폰 쪽 방식(Redis를 정확성의 근거로 승격)을 쓰지 않은 이유는 재고 차감이 주문 상태 전이·이력 기록과 같은 트랜잭션 경계 안에서 일어나기 때문 — 재고만 DB 밖에서 세면 그 정합을 별도로 방어해야 함
  4. 재시도 한도가 타당한지 보려면 실제 충돌 횟수를 알아야 해 Micrometer로 계측 — 일반 트래픽은 평균 0.35회/건으로 대부분 무충돌 통과이나, 1만 건이 단일 행에 몰리는 극단 경합에서는 재시도 소진이 실패의 전량. 조건이 다른 두 수치를 나란히 놓고 한도를 정할 수 없어 미상향 — 한도는 차감 전략 3종 실측으로 이월
  5. 선점 키에 만료를 두지 않은 것은 의도된 선택 — 재고 카운터 자체를 DECR로 선점하는 구조라 TTL로 사라지면 미초기화 폴백으로 떨어져 게이트가 무력해짐. 대신 실패 경로 전부(선점 도중 부족 · PG 승인 실패 · 승인 후 DB 실패 · 결제 취소)에서 선점분을 되돌리는 구조로 덮었고, 부하 로그의 복원 포기 마커가 0건이라 예외가 잡히는 실패에 한해 이 경로가 새지 않음을 확인
  6. 죽은 카운터를 발견해 예외 재포장까지 해소 — 락 충돌 카운터가 한 번도 미증가. 결제 오케스트레이션의 catch (Exception)이 BusinessException을 익명 RuntimeException으로 감싸 에러 코드가 소실, 409여야 할 응답이 500으로 나감. 구조적으로 증가할 수 없는 죽은 카운터였고, 재포장을 걷어 503·502까지 500으로 뭉개던 것도 함께 해소
  7. 대안 ① 원자적 조건부 UPDATE(stock >= :qty 조건을 UPDATE에 실어 충돌 개념 자체를 소멸) — 재고 단일 필드만 다룰 때는 명백히 우월하나, 이 시스템은 재고가 상품 엔티티의 한 필드라 가격·판매 상태 같은 다른 필드와 @Version 하나를 공유함. 그래서 기각이 아니라 실측으로 이월
  8. 세 전략을 같은 조건에 세우기 위해 차감 전략을 인터페이스로 분리 — 3종을 모두 구현하고 설정값 하나로 교체되게 한 뒤 같은 머신에서 연속 측정. 전환이 실제로 일어났는지는 환경변수가 아니라 메트릭으로 확인 — 낙관적 락에서만 stock_optimistic_retries가 노출되고 나머지 둘에서는 사라짐. 오타는 조용히 기본값으로 떨어지므로 이 확인이 없으면 세 번 같은 것을 재게 됨
  9. ② 차감 시점을 PG 승인 이전으로 이동 — 승인 후 취소 왕복은 사라지지만 PG 실패 시 재고를 되돌리는 반대 방향 보상이 새로 생김. 어느 쪽 보상을 감당할지의 선택 문제이고, 이미 Redis 게이트가 PG 앞에서 부족분을 걸러 이득이 크지 않다고 판단. ③ 예외 재포장 중단은 기각이 아니라 채택했고 죽은 카운터의 직접 처방

  • 실패 경로가 낙관적 락 재시도 소진 하나로 좁혀짐 — 재고 부족 카운터가 0건(초기 재고와 요청 수가 같아 부족 상황 자체가 미발생)이고, 로그의 [STOCK_CONFLICT_GIVEUP] · [PAYMENT_CONFIRM_DB_FAILED] · [PAYMENT_COMPENSATION_SUCCESS] 세 마커가 파일 단위로 같은 건수로 짝지어지고(80/80/80 · 98/98/98 · 111/111/111) 동일 워커 스레드에서 17ms 간격으로 기록. 재현 측정에서 실패 에러 코드가 100% PRODUCT_STOCK_CONFLICT 단일
  • PG 승인까지 갔다가 환불 보상을 부를 11건을 결제 앞에서 차단 — 재고 3,000개에 결제 10,000건 조건에서 주문 생성 단계의 재고 검증이 6,989건을 먼저 반려하고, 그 검증을 통과한 뒤 결제 확정에 닿기까지 재고가 바닥난 11건만 Redis DECR 게이트가 차단([STOCK_RESERVE_OUT] 마커로 대조). 게이트의 값어치는 대량 차단이 아니라 앞단 검사가 원리적으로 못 덮는 경쟁 구간 전담 — 주문 생성의 검사는 읽고 나서 판단하는 비원자 구조라 판단과 차감 사이에 틈이 남고, 게이트가 그 틈만 전담. 부하 도구가 주문 직후 곧바로 결제를 호출해 틈이 최소인 조건이라 11건은 하한
  • 커넥션 풀 병목을 걷어내 같은 부하가 10분 27초 → 10.7초 — 프리플라이트에서 Could not open JPA EntityManager 403건이 나며 1,000회 중 423회만 완주. 원인은 yml에 Hikari 설정이 없어 풀이 기본값 10이었던 것(결제 1건이 중첩 REQUIRES_NEW로 커넥션 2개를 쓰므로 VU 5부터 이미 부족). 커넥션 확보에서 막히면 락 경합 신호가 통째로 묻힘 — 풀을 50으로 고정하자 p95도 30.55s → 35.7ms
  • 지터로 성공률 91.44% → 94.08%, 대신 p95는 381 → 543ms — 첫 측정에서는 성공률 57%→72%, 지연 59ms→47ms로 둘 다 좋아진 것처럼 보였으나 두 런의 VU가 달라(20 vs 10) 지터 효과와 동시성 효과가 섞여 있던 값. VU를 20으로 고정해 다시 잰 것이 위 수치. 지터는 실패를 대기로 바꿈 — 재시도 시점을 서로 다르게 흩으니 한도 안에 성공하는 요청이 늘지만 각 요청은 더 기다림. 효과는 경합이 셀수록 커져 VU 10에서는 +0.34%p에 그침

    이유는 워크로드가 낙관적 락의 전제와 반대이기 때문 — 단일 상품 행에 전량이 몰려 충돌이 상시라 재시도가 곧 낭비가 되고, 한도를 넘긴 5.44%가 실패로 끝남. 나머지 둘이 100%인 것은 충돌 개념 자체가 없어서 — 조건부 UPDATE는 DB가 원자적으로 판정하고 비관적 락은 행을 잠가 직렬화하므로 재시도 미발생. 정확성이 동급인 둘 중 세 지연 지표 모두에서 앞선 비관적 락을 기본 전략으로 선정(평균 64.8 vs 84.6ms · p95 100.9 vs 162.7ms · p99 135.8 vs 302.0ms)
  • 한도를 올리는 대신 전략을 바꿔 실패와 지연이 함께 사라짐 — 실측은 재시도 _max가 한도 3에 도달하고 충돌이 5.44%라 "한도를 올려라"를 가리켰지만, 한도를 키우면 실패가 지연으로 바뀔 뿐이기 때문. 다만 비관적 락이 가장 빠른 것은 이 조건 한정 — 처음 우려한 행 잠금 장기 점유는 임계 구역이 재고 UPDATE 한 줄이라 나타나지 않았고, 경합이 극단적이라 직렬화 비용보다 재시도 낭비가 컸던 것이고, 임계 구역이 길거나 경합이 드물면 뒤집힘
  • 두 저장소가 어긋나면 지표로 드러나는 상태로 전환 — Redis 선점 수와 DB 재고를 배치로 대조하고 Micrometer 게이지로 노출. 어려운 부분은 정상 인플라이트와 진짜 드리프트를 구분하는 것이었고, 방향과 지속성 두 갈래로 분리. redis > db는 선점이 만들 수 없는 방향이라 1회로 확정하고, redis < db는 선점의 수명 상한(외부 결제 타임아웃 × 재시도 + 보상)이 수십 초라 스캔 2회 연속일 때만 승격. 자동 보정은 두지 않음 — 보정 자체가 새 드리프트 원인이 될 수 있어 목표를 탐지까지로 한정

전동보장구(전동 휠체어·스쿠터) 사용자를 위한 카카오 지도 기반 충전소 정보·경로 안내 플랫폼으로, 보호자에게 실시간 위치를 공유하는 기능을 제공. 기획안·ERD·API 명세서를 작성해 팀원 간 개발 범위와 인터페이스를 사전에 정의. 세 프로젝트 중 가장 이른 것으로, 여기서 부딪힌 키 설계·인스턴스 확장 제약이 뒤의 두 프로젝트에서 설계 기준이 됨

서비스 전체 아키텍처 — 인증·실시간 위치·외부 API 연동

1. 보호자 실시간 위치·경로 공유 설계

기능
전동보장구 사용자의 실시간 위치와 내비게이션 경로를 보호자 화면으로 전달하는 기능
개선
어느 인스턴스에 연결돼도 위치가 닿게 하고, 늦게 접속해도 최신 경로를 받게 전환

전체적인 아키텍처

위치 발행-구독 흐름 — 인스턴스 경계를 넘는 SSE 전달
경로 정보 저장·조회·정리 흐름

문제 원인 및 한계점

  • 보호자가 사용자 위치를 실시간으로 확인해야 하는데, 클라이언트가 주기적으로 요청하는 폴링 방식은 불필요한 요청과 지연을 유발
  • 인스턴스가 갈릴 때의 문제 — 서버가 여러 인스턴스로 확장되면 위치를 발행한 인스턴스와 보호자가 SSE로 연결된 인스턴스가 다를 수 있어, 단순 인메모리 브로드캐스트로는 위치가 미전달
  • 접속 시점이 어긋날 때의 문제 — 초기에는 내비게이션 경로도 위치와 동일하게 Pub/Sub으로만 전달했는데, Pub/Sub은 발행 시점의 구독자에게만 닿고 재생이 불가능해, 사용자가 안내를 시작한 시점에 보호자가 미접속이면 경로를 알 방법이 부재
  • SSE는 응답이 끝나지 않는 장기 연결이라, 연결을 관리하는 구조 없이는 이탈·네트워크 단절 시 커넥션이 메모리에 계속 남는 문제가 존재

해결 과정

  1. 보호자-사용자 관계(relationId)마다 SseEmitter를 발급하고 ConcurrentHashMap<relationId, SseEmitter>로 연결을 관리. 10분 타임아웃과 onCompletion/onTimeout/onError 콜백에서 맵의 연결을 제거해 끊어진 연결이 누적되지 않도록 함
  2. 인스턴스가 갈리는 문제의 처방 — 위치가 갱신되면 Redis Pub/Sub 채널(location:{relationId})로 발행하고, 각 인스턴스가 이 채널을 구독해 자신에게 연결된 보호자에게만 전달하도록 구독 로직을 분리. 프로세스 로컬 맵만으로는 인스턴스 경계를 넘지 못하므로, 전달 자체를 브로커 경유로 바꾼 것
  3. 두 데이터에 다른 전달 방식을 적용한 기준 — 위치는 초 단위로 새 값이 도착하는 연속 스트림이라 놓친 값의 재생 가치가 없지만, 경로는 안내 시작 시 한 번 발생하는 이산 이벤트라 그 시점에 미접속이면 복구 경로가 부재. 이 성질 차이를 근거로 위치는 Pub/Sub에 그대로 두고 경로만 영속 저장으로 이관
  4. 접속 시점이 어긋나는 문제의 처방 — 내비게이션 시작 시 출발지·도착지 좌표와 명칭을 location-stream:{relationId} Redis Stream에 XADD로 적재하고, 보호자가 접속·새로고침하면 XREVRANGE ... COUNT 1로 최신 경로를 즉시 조회. 목적지 도착 시 DEL로 정리
  5. String 대신 Stream을 택한 이유 — 요구만 보면 SET/GET으로도 충분함. Stream을 고른 것은 안내 1회 안에서 경로가 여러 번 갱신되기 때문 — SET은 갱신마다 이전 값을 덮어써 "직전 경로로 되돌아갔는지"를 알 수 없지만, XADD는 안내가 끝날 때까지 갱신 이력이 순서대로 잔존. 다만 도착 시 DEL로 지우므로 이 이력은 안내 세션 안에서만 유효하고 완료된 경로의 장기 보관은 목적이 아님 — 그래서 Consumer Group도 미도입

결과

  • 보호자가 어느 인스턴스에 연결돼도 위치가 도달 — 발행을 Redis Pub/Sub으로 넘겨 프로세스 경계가 전달을 가르지 않게 함
  • 발행 시점에 보호자가 미접속이었어도 접속 시점에 최신 경로를 조회할 수 있어, Pub/Sub의 시점 의존성을 데이터 성질에 따라 선택적으로 보완
  • 연결 생명주기 콜백으로 끊어진 SSE 커넥션이 맵에 남지 않도록 하고, 재연결 시 기존 연결을 교체해 같은 관계에 중복 커넥션이 쌓이지 않게 함

2. 배포·라우팅 구성 설계

기능
프론트엔드(Next.js)와 백엔드(Spring Boot)를 한 대의 EC2에서 서비스하고 배포하는 구성
개선
도메인 하나로 두 서버를 공존시키고, 로컬·운영의 실행 방식 차이와 수동 배포 절차를 제거

전체적인 아키텍처

배포 파이프라인 — Push부터 컨테이너 재기동까지

문제 원인 및 한계점

  • 프론트엔드(Next.js)와 백엔드(Spring Boot)를 하나의 도메인에서 서비스해야 함 — 별도 도메인으로 나누면 CORS와 쿠키 도메인 불일치를 매번 다뤄야 해서, 요청 경로로 두 서버를 가르는 구성이 필요함
  • 개발 초기에는 백엔드를 로컬에서 직접 실행하는 방식이라 배포 환경과 실행 방식이 달라, 배포 때마다 수동 작업이 필요함
  • DB·Redis·백엔드·프론트엔드·Nginx로 구성 요소가 다섯이라 팀원 각자의 로컬에서 동일하게 재현하기 어려웠고, "제 환경에서는 됩니다"가 반복됨

해결 과정

  1. 두 서버를 가르는 방법 셋 중 경로 라우팅을 선택 — ① 별도 도메인 ② 서브도메인 ③ 한 도메인 + 경로 분기. ①·②는 CORS preflight와 쿠키 도메인 설정을 프론트·백엔드 양쪽에서 계속 맞춰야 하고, 인증 쿠키를 교차 출처로 보내려면 SameSite까지 완화해야 함. ③은 브라우저에게 동일 출처라 그 설정이 아예 등장하지 않음 — 문제를 푸는 대신 발생하지 않게 한 선택. 그래서 Nginx에서 /api/v1/은 백엔드(포트 8080, context-path /api)로, 그 외 경로는 프론트엔드(포트 3000)로 분기
  2. PostgreSQL·Redis·Backend·Frontend·Nginx를 하나의 docker-compose로 묶음 — 각자 로컬에 다섯 종을 직접 설치하는 방식과 갈리는 지점은 버전·포트·초기 스키마가 파일 하나에 고정된다는 것. "제 환경에서는 됩니다"는 설치 절차를 문서로 공유해서가 아니라 절차 자체를 실행 가능한 파일로 바꿔야 사라진다고 판단
  3. Nginx에서 TLS 종료(Let's Encrypt)와 HTTP→HTTPS 리다이렉트, 보안 헤더를 함께 처리해 각 애플리케이션 서버가 인증서를 직접 다루지 않도록 책임을 분리 — 인증서 갱신이 애플리케이션 배포와 무관해짐
  4. CI 도구는 별도 서버를 늘리지 않는 쪽으로 — Jenkins도 후보였으나 CI 서버 한 대를 더 운영해야 하고, 팀에 상시 관리자가 부재. GitHub Actions는 저장소에 붙어 있어 러너 관리가 불필요하므로, prod 브랜치 푸시 시 EC2에 SSH로 접속해 최신 코드를 반영하고 컨테이너를 재기동하는 파이프라인을 구성. 무중단 배포는 미도입 — 재기동 순간의 짧은 중단을 감수한 선택이고, blue-green은 인스턴스가 한 대라 지금 구성으로는 성립 불가

결과

  • CORS·쿠키 도메인 문제가 구성 단계에서 사라짐 — 도메인 하나로 프론트·백엔드를 함께 서비스하면서도 각 서버의 역할은 Nginx 설정으로 분리
  • docker-compose 기반 구성으로 로컬·운영 환경 차이를 줄이고, 배포 자동화로 수동 배포 절차 제거

3. JWT 즉시 무효화 설계

기능
로그아웃·비밀번호 변경 시 이미 발급된 JWT를 즉시 못 쓰게 만드는 기능
개선
개별 토큰과 사용자 전체 두 단위를 한 검증 경로로 통합

전체적인 아키텍처

인증 필터의 두 갈래 조회 — 토큰 하나를 죽이는 키와 사용자 전체를 죽이는 키

문제 원인 및 한계점

  • JWT는 서명만 맞으면 통과하는 무상태 구조라 서버가 발급 후에 취소할 방법이 부재 — 로그아웃을 눌러도 만료 시각까지는 유효한 토큰이 남음
  • 무효화 단위가 둘 — 로그아웃은 그 토큰 하나, 비밀번호 변경·전체 로그아웃은 그 사용자의 발급분 전부. 두 요구를 한 저장 구조로 덮을 수 없음
  • 발급한 토큰의 목록을 서버가 보관하지 않으므로, 사용자 전체 무효화를 "열거해서 지우기"로는 구현 불가
  • 즉시 무효화를 붙이는 순간 무상태의 이점을 얼마나 내줄지가 결정 사항이 됨 — 검증마다 저장소 조회가 붙고 인증 경로가 그 저장소에 종속

해결 과정

  1. 개별 토큰은 블랙리스트, TTL은 고정값이 아니라 잔여 수명 — 로그아웃 시 blacklist:access:{token}을 등록하되 만료 시각까지 남은 시간만큼만 살려 둠. 고정 TTL을 쓰면 양쪽으로 틀림 — 짧게 잡으면 아직 유효한 폐기 토큰이 되살아나고, 길게 잡으면 이미 만료돼 검증에서 걸리는 토큰을 계속 저장. 잔여 수명으로 잡으면 만료와 동시에 키가 자동 정리돼 별도 청소 작업이 불필요
  2. 사용자 전체는 열거 대신 버전 카운터 — 발급분을 보관하지 않는 이상 지울 목록을 만들 수 없으므로, blacklist:user:{id}:version을 올리고 발급 시 토큰 claim에 그 시점의 version을 실어 둠. 필터가 claim의 version과 저장된 version을 비교해 낮으면 폐기 취급 — 토큰을 하나도 열거하지 않고 그 시점 이전 발급분 전체를 무효화
  3. 두 판정을 한 검증 경로로 합침 — 무효화 종류마다 필터를 따로 두면 새 진입점에서 한쪽을 빠뜨릴 수 있으므로, 인증 필터가 매 요청에 두 키를 함께 조회하고 한 곳이라도 히트하면 인증을 주입하지 않는 단일 규칙으로 둠
  4. version 키의 TTL을 Access Token 수명과 맞춤 — 키가 토큰보다 먼저 만료되면 비교 대상이 사라져 무효화했던 옛 토큰이 되살아나는 창이 열림. 15분으로 맞춰 그 창을 차단. 무효화 장치의 수명은 무효화 대상의 수명보다 짧으면 안 된다는 것이 이 값의 근거
  5. 대안이었던 "짧은 만료 + Refresh 회전"은 요구를 미충족 — 만료를 기다리는 방식이라 즉시가 요구사항이면 성립하지 않음. 대신 지불한 것은 매 요청 Redis 조회 2회와 인증 경로의 Redis 종속이고, 이 교환을 감수한다고 결정. 다만 Redis 장애 시 통과할지 차단할지의 정책은 이 프로젝트에서 미결정

결과

  • 개별 토큰과 사용자 전체라는 두 무효화 단위가 하나의 검증 경로로 통합 — 진입점이 늘어도 무효화 판정은 필터 한 곳에서만 일어남
  • 여기서 드러난 키 설계의 한계가 다음 프로젝트의 설계를 전환 — Refresh Token을 refresh_token:{token}으로 저장한 탓에 사용자 단위 열거·폐기가 불가능했고, AI 튜터링에서는 refreshToken:{userId} 기준으로 잡고 블랙리스트 키도 토큰 전문이 아닌 jti로 옮겨 키 설계 쪽 제약은 제거
  • 무상태의 이점을 내주고 즉시 무효화를 산 교환 — 미결정으로 남긴 Redis 장애 정책은 AI 튜터링에서 fail-close(장애 시 인증 거부)로 확정하고 근거를 코드에 남김. fail-open은 장애 지속 시간만큼 폐기된 토큰을 되살리기 때문
