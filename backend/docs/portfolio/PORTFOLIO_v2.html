포트폴리오 — 김민성

측정으로 원인을 확정하고, 파라미터가 아니라 구조로 처리하며, 남은 한계는 범위로 한정해 적었음

읽는 법

  • 3개 프로젝트 · 11개 사례를 최신순으로 배치함. 모든 사례가 전체 아키텍처 → 문제 원인 → 해결 과정 → 결과 → 남은 한계 동일 순서임
  • 수치는 출처를 구분해 적었음 — 실측 직접 측정한 값 · 도출 설정값에서 계산한 값 · 대리 부하 실제 트래픽 대신 특성만 재현한 부하 · 통제 실험 장애를 인위로 주입해 확인한 값 · 설정 내가 정한 파라미터 · 추정 근거를 남기지 않은 값 · 가정 아직 측정하지 않은 값으로, 설계 판단을 설명하기 위해 기대 규모만 적은 것(측정하면 달라질 수 있으며, 성과의 근거로 쓰지 않음)
  • 휠 파인더는 부하 측정 환경을 구성하지 않았음. 수치 대신 구조 검증만 적었고, 그 범위를 넘는 주장은 하지 않았음

세 프로젝트에 반복해서 나타나는 작업 방식

  • 측정의 목적을 숫자가 아니라 인과 확정에 둠 — 스레드 20개 고정 통제 실험(AI-1), 조건 9회 반복·백투백 A/B 비교(이커머스-2)
  • 같은 도구도 보호 범위를 기준으로 갈라 씀 — Redis를 가용성(Cluster) · 정확성(Lua) · 비용 차단(선점 게이트) · 무효화(블랙리스트) · 전달(Pub/Sub) · 시점 보완(Stream) 6가지 역할로 나눠 적용
  • 자기 설계의 한계를 스스로 지목하고 다음 프로젝트에서 고침 — 휠 파인더에서 토큰 전문을 Redis 키로 쓰던 것을 AI 튜터링에서 jti·사용자 기준으로 정리했고(휠-2 → AI-5), 그때 미뤄둔 Redis 장애 시 인증 정책도 fail-close로 결정해 근거를 남겼음. 방향이 한쪽만은 아님 — 인스턴스 경계를 넘는 전달은 휠 파인더가 먼저 풀었고 AI 튜터링이 아직 못 따라갔음(휠-1 → AI-1 한계)

시간이 없다면 이 셋

  • 이커머스 §2 재고 차감 — 계측을 믿지 않고 계측 자체를 의심해 "구조적으로 절대 증가할 수 없는 죽은 카운터"를 찾아낸 사례
  • AI 튜터링 §5 인증·세션 — 방어가 동작한다는 것을 무엇으로 증명하는가를 다룬 사례. 쓰기·읽기·거부 세 지점을 하나의 계약으로 묶었음
  • 휠 파인더 §1 실시간 전달 — 인스턴스 경계(공간)와 발행 시점(시간)을 한 문제의 두 축으로 나눠 푼 사례

반복해서 다룬 축

  • TTL을 무엇의 수명에 맞출 것인가를 다섯 사례에서 각각 다르게 답함 — 블랙리스트는 토큰 잔여 수명에(AI-5), version 키는 Access Token 수명에(휠-2), 채팅 세션은 대화 유효 기간에 맞췄고, 재고 선점 키에는 TTL을 두지 않는 것이 결정이었음(이커머스-2 — 사라지면 게이트가 무력해지므로). "얼마로 잡을까"가 아니라 "무엇과 함께 사라져야 하는가"를 먼저 정하면 값은 따라 나옴

1. SSE 연결의 스레드 고정 점유 문제를 Virtual Thread 기반 Flux 스트리밍으로 해결

전체적인 아키텍처

채팅 서비스 동작 구조 — SSE 연결과 메시지·저장 경로

문제 원인

  • LLM 응답 생성에 십수 초 — 첫 응답까지 평균 15초라 응답이 끝날 때까지 연결을 유지하는 long-lived 구조가 필요
  • 초기 구현은 @Async + SseEmitter + blockLast() 동기 대기 — 연결 1개가 바운디드 풀(core 10 / max 50 / queue 100)의 스레드를 스트림 종료까지 점유해, 풀을 넘으면 큐잉 후 거부
  • 문제는 두 축, 해결도 두 단계 — ① 스레드 고갈은 Virtual Thread 전환이 먼저 해소(요청당 스레드 무제한 생성으로 풀 개념 소멸) ② 그러나 blockLast()가 남는 한 응답은 완료 후 일괄 전달이라 첫 글자까지의 대기는 그대로였음
  • 이 STAR는 ②를 다루고 뒤의 처리량 수치는 ①의 결과임 — 둘을 한 인과로 묶지 않게 분리 서술함

해결 과정

  1. 전송은 WebSocket이 아니라 SSE를 골랐음 — 흐름이 서버 → 클라이언트 단방향이고 입력은 별도 POST로 충분한데 WebSocket은 양방향 프레임·핸드셰이크·하트비트를 떠안음. SSE는 HTTP 위라 프록시 설정·인증 쿠키가 그대로 통하고 끊기면 브라우저가 자동 재연결함. 양방향이 필요해지는 시점이 WebSocket 전환 기준선
  2. 서블릿 스택(Tomcat)은 둔 채 컨트롤러가 Flux<ServerSentEvent>를 반환해 MVC async 경로를 타게 하고 blockLast()를 제거 — 스트림 지속 중 요청 스레드를 점유하지 않고 토큰 도착 즉시 전달. JPA·Spring Security 전면 재작성이 필요한 WebFlux(Netty) 대신 Reactor 타입만 넣은 하이브리드임. VT가 있는데 Reactor를 더한 건 선택이 아니라 API 제약 — Spring AI의 ChatClient.stream().content()가 Flux<String>만 반환함. LLM 대기는 그 리액티브 호출에 맡기고 남은 동기 조회는 요청 스레드(= virtual thread)에서 처리. VT는 스레드를 "반납"시키는 게 아니라 블로킹 동안 carrier에서 unmount시킬 뿐
  3. 토큰 콜백의 블로킹을 publishOn(Schedulers.boundedElastic()) 뒤로 오프로딩 — 완료 콜백이 일반 채팅은 Redis 저장·상태 전이, 오프너 분석은 거기에 JDBC 트랜잭션까지 실행함. 없으면 논블로킹 스트리밍이 콜백 블로킹으로 상쇄되므로 두 스트림 모두 같은 경계로 옮겼고, 첫 청크에서만 콜백 스레드명을 남겨 런타임 확인
  4. SSE 연결을 ConcurrentHashMap<sessionId, Sink>로 관리하고 속도 차를 버퍼로 흡수 — 생산을 늦추는 진짜 백프레셔가 아니라 되감을 수 없는 LLM 스트림을 버퍼링으로 회피한 것. 크기는 SSE_BUFFER_SIZE = 256으로 명시(기본값이면 문서에 크기를 적을 근거가 없음)
  5. "화면에 보인 것 = 저장된 것"이 양방향으로 깨져 함께 닫았음 — ① 오버플로 시 tryEmitNext가 FAIL_OVERFLOW를 주면 로그만 남기고 청크를 조용히 버려 화면에 없는 내용이 저장본에 남음 → tryEmitError로 끊는 쪽으로 전환(끊김은 재연결로 복구되나 빠진 청크는 불가) ② 스트림 중간 실패 시 보낸 토큰이 저장되지 않아 화면에만 남음 → doOnError에서 받은 만큼 저장하고 chat.stream.partial.saved로 계측
  6. 클라이언트가 끊어도 상류 LLM 스트림이 끝까지 돌며 토큰을 소비·과금함 — subscribe()의 Disposable을 보관하지 않아 취소할 수 없었기 때문. 세션별로 보관해 doOnCancel · disconnectSession · 하트비트 사망 세션 3지점에서 정리. 제목은 스레드 자원이지만 더 크게 새던 자원은 상류 구독과 LLM 비용
  7. 저장 경로를 응답 경로에서 분리해 전용 큐로 발행하고 Consumer가 Redis 조회·검증·PostgreSQL 적재 — 다만 발행 트리거가 사용자의 저장 요청(POST /chat/save-message)이라 자동 백업은 아님. Consumer가 Redis에서 못 찾으면 정상 만료인지 유실인지 구분 없이 전부 ACK해 대화가 통째로 사라져도 로그 한 줄뿐 → publishedAt을 실어 TTL 경과 → ACK(expired) / TTL 이내 공백 → DLQ(lost)로 갈랐음

실제 동작 구조 — 인증 요청과 채팅 요청이 흐르는 Redis 경로

문제 원인

  • Redis Standalone 단일 노드 구조에서 노드가 죽으면 모든 채팅 세션이 한 번에 유실되는 SPOF(단일 장애점)였음
  • 인증용 Redis와 채팅용 Redis가 같은 인스턴스를 공유하는 구조라, 한쪽 도메인의 장애가 다른 도메인까지 전파될 위험이 있었음
  • 장애 발생 시 수동으로 인스턴스를 재기동해야 했고, 이 복구에 5~10분이 걸려 그 사이 채팅 기능 전체가 중단됨

해결 과정

  1. Redis Cluster를 Master 3 + Replica 3, 총 6노드로 구성하고 Auth Redis와 Chat Redis를 별도 Spring 빈으로 분리해 장애 도메인을 격리 — 유실 시 대화가 통째로 사라지는 채팅 세션만 Cluster로 이중화하고, 재로그인으로 즉시 복구 가능한 인증 토큰 저장소는 Standalone을 유지해 인프라 비용과 보호 수준의 균형을 맞췄음
  2. 같은 세션의 키들을 Hash Tag 패턴(chat:{sessionId}:session)으로 묶어 동일 슬롯에 배치함 — 다만 이건 겪은 장애를 고친 게 아니라 선제 조치임. 현재 chat 클러스터에 대한 호출은 전부 단일 키라 CROSSSLOT이 날 여지가 없고, Lua·트랜잭션·파이프라인도 없음. 나중에 멀티키 연산이 필요해질 때 키 명명을 전수 이관하는 비용을 미리 없앤 것이 정확한 근거임
  3. 읽기 분산과 프롬프트 정합성이 충돌해, 전부가 아니라 지점별로 갈랐음 — 전 경로가 REPLICA_PREFERRED였는데 saveMessage 직후 같은 요청 안에서 히스토리를 읽어 프롬프트를 만드는 구간이 있었음. 복제가 수 ms만 늦어도 방금 한 질문이 프롬프트에서 통째로 빠져 LLM이 직전 턴에 다시 답함. "대화 맥락이 흡수하는 지연"이 아니라 입력이 사라지는 정합성 버그였음
  4. 그렇다고 전부 master로 돌리면 읽기 분산이 사라지므로 세 갈래로 판정함 — 프롬프트 조립용 최근 히스토리는 master 고정(창이 항상 열려 있음), 영속화용 전체 조회는 replica 유지(별도 요청이라 창이 닫힘), 소유자 검증은 replica 우선 + 비었을 때만 master 재확인(무조건 master면 분산이 사라지고, 재확인이 없으면 방금 만든 세션이 거부됨). ReadFrom이 커넥션 팩토리 단위 설정이라 master 전용 팩토리를 작은 풀(5/3/1)로 따로 두되, 토폴로지·타임아웃이 두 벌이 되지 않게 팩토리 조립은 헬퍼 하나로 공유함
  5. 여기에 더해 라우팅과 무관하게 질문 자체를 잃지 않도록 프롬프트 조립을 순수 함수로 분리해 현재 질문 원문을 명시적으로 보장함(마지막 메시지가 같으면 중복 추가하지 않음). 선형화는 "히스토리를 최신으로 만든다", 이쪽은 "히스토리가 낡아도 질문만은 잃지 않는다"로 층이 다른 두 방어임. 분산 유지를 주장하려면 비율이 근거로 필요하므로 chat.redis.read Timer에 route=master|replica 태그를 달았음
  6. failover 대응의 실체는 커넥션 검증이 아니라 토폴로지 갱신임 — ClusterTopologyRefreshOptions(주기 갱신 + enableAllAdaptiveRefreshTriggers)로 승격을 감지하고, DisconnectedBehavior.REJECT_COMMANDS로 끊긴 커넥션에 명령을 쌓아 두지 않고 즉시 실패시켜 장애가 큐잉으로 번지는 경로를 차단. 풀의 testOnBorrow=true는 그 아래 단계의 죽은 커넥션 방지용으로 역할을 구분해 둠
  7. Cluster가 주는 것은 가용성(HA)이지 내구성(Durability)이 아님 — 복제가 비동기라 Master가 죽는 순간 복제되지 않은 쓰기는 사라짐. 다만 "내구성은 영속 경로가 책임진다"는 분업은 아직 참이 아님: 큐 이벤트는 본문을 싣지 않고 sessionId만 실어 Consumer가 본문을 Redis에서 다시 읽기 때문에, 영속 경로는 별도 경로가 아니라 Redis의 하류임. 그래서 이번에는 주장을 낮추고 유실을 감지 가능하게 만드는 데 집중함 — 이벤트에 publishedAt을 실어 TTL 경과면 정상 만료로 ACK, TTL 이내인데 비어 있으면 DLQ로 보냄(이전에는 둘 다 조용히 정상 ACK)

결과

  • Master 강제 종료 통제 실험에서 복제본 자동 승격으로 약 7초 자동 복구 통제 실험 — 기존 수동 재시작 5~10분 추정 대비 대폭 단축. 분모가 사람이 개입하는 시간이라 정밀도를 주장하지 않음. 이 7초는 우연이 아니라 설정값의 결과임 — cluster-node-timeout 5000(장애 판정 5초) + 선출·승격이고, 더 줄이려면 오탐 위험을 대가로 이 값을 낮춰야 함
  • 인증·채팅 저장소 분리로 한쪽 장애가 다른 도메인으로 전파되는 경로 차단
  • 커넥션 풀은 maxTotal=20 / maxIdle=10 / minIdle=5로 상한이 명확히 있음 — 확인된 것은 "제한 없음"이 아니라 20개 풀로 100 VU를 p95 133ms에 수용 실측이라는 사실임

남은 한계

  • 이 7초는 인프라 회복 시간이고, 그 구간에 유입된 쓰기는 실패로 반환되므로 클라이언트 재시도로 보완하는 것이 전제임 — 가용성을 올린 것이지 내구성을 올린 것이 아님. 읽기 쪽은 cluster-allow-reads-when-down yes라 장애 구간에도 성공하되 stale할 수 있음
  • 승격 정책이 유실 창을 최대화하는 쪽으로 설정돼 있음 — cluster-replica-validity-factor 0은 얼마나 뒤처진 복제본이든 승격을 허용함. 가용성을 최대로 얻는 대신 유실 가능 구간을 스스로 넓힌 선택이고, 이 값을 올리면 승격이 안 되어 클러스터가 멈추는 쪽으로 트레이드오프가 이동함
  • TTL만이 세션 수명 요인이 아님 — 노드 설정이 maxmemory 256mb + allkeys-lru라 메모리 압박이 오면 TTL이 남은 키도 축출됨. 세션 해시가 축출되면 대화 중인 정상 세션이 소유자 검증에서 즉시 거부됨. 데모 규모에서는 도달하지 않지만 SPOF를 없앴다고 말하는 STAR에 남아 있는 단일 실패 요인이라 명시함
  • 내구성의 소스 오브 트루스가 여전히 Redis임 — 큐 이벤트가 본문을 싣지 않으므로, 본문을 이벤트 페이로드에 실어 Redis 의존을 끊는 것이 이 STAR의 결론 문장을 실제로 참으로 만드는 다음 작업임
  • failover 실험의 raw 로그를 저장소에 남기지 않아 재현 절차(대상 노드·kill 명령·판정 쿼리)가 문서에 없음 — 7.18s라는 값 자체는 cluster-node-timeout과 정합적이나, 절차를 남겨야 통제 실험 배지가 완전해짐

실제 동작 구조 — 채팅 요청 중 Circuit Breaker 개입 지점과 State Machine 연동

문제 원인

  • LLM은 OpenAI 외부 의존성이라 장애·지연이 발생하면 느린 실패가 누적됨 — 게다가 처음에는 타임아웃이 하나도 없었음. WebClient.builder()를 그대로 빈으로 내보내고 있어 커넥터에 연결·응답 상한이 걸리지 않았고, 상류가 응답을 멈추면 호출이 무기한 매달림
  • 실패 중인 외부 API를 계속 호출하면 연쇄 지연(Cascading Failure)으로 번질 위험이 있었음
  • 세션 상태가 여러 boolean 플래그에 분산돼 있어 "스트리밍 중 재전송", "연결 전 메시지 전송" 같은 비정상 전이를 코드 수준에서 막을 수 없었음

해결 과정

  1. Resilience4j @CircuitBreaker를 채팅 스트리밍·오프너 분석·대화 요약·캐시 저장소 호출 4개 지점에 서로 다른 정책으로 분리 적용 — 외부 LLM 두 지점은 느리고 호출 단가가 높아 보수적으로, 윈도우 10 · 최소 호출 5건 · 실패율 50% 초과 시 OPEN → 30초 후 HALF-OPEN(허용 3건)으로 잡았음
  2. 캐시 저장소는 호출이 빠르고 훨씬 빈번해 표본 하나의 무게가 가볍다는 특성을 확인하고, 이 지점만 윈도우 20 · 최소 호출 10건 · 실패율 60% · OPEN 10초로 차등화 — 표본을 더 모아 통계적으로 판단하고, 임계는 너그럽게, 회복 대기는 짧게 둔 것. 세 지점을 같은 값으로 맞추지 않은 이유는 호출 특성이 다르면 서킷 정책도 달라야 한다고 봤기 때문
  3. 최소 호출 수를 둔 이유는 표본이 적을 때의 오판을 막기 위해서임 — 호출 2건 중 1건 실패를 실패율 50%로 읽고 서킷을 열면 우연한 실패 하나로 기능 전체가 차단됨. 호출 빈도가 높은 캐시 지점에 더 큰 최소값(10건)을 요구한 것도 같은 이유임
  4. Spring State Machine으로 IDLE → CONNECTED → PROCESSING → STREAMING → COMPLETED와 에러 3상태(총 8개)를 정의하고, 전이 테이블에 선언된 쌍만 허용해 비정상 전이를 코드 수준에서 차단
  5. 다만 잘못된 전이를 차단하는 것과 어긋난 상태를 회수하는 것은 다르다는 것을 확인 — LLM이 빈 응답을 주면 STREAM_START가 발화되지 않아 상태가 PROCESSING에 남고, 뒤이은 STREAM_COMPLETE가 거부되며 세션이 고착돼 이후 요청이 전부 SESSION_EXPIRED로 막히는 경로를 발견. 첫 청크 발생 여부를 확인해 청크가 0개면 STREAM_ERROR로 상태를 회수하도록 보완하고, 전이 거부를 조용히 삼키던 sendEvent 반환값을 전 지점에서 검사하도록 정리
  6. 에러 상태에서 나가는 길이 CLOSE → IDLE 하나뿐이고 IDLE은 SEND_MESSAGE를 받지 않아, LLM이 한 번 실패하면 SSE 연결은 살아있는데 재전송만 영구히 막히는 구조였음. STREAM_ERROR·PROCESSING_ERROR에서 SEND_MESSAGE로 PROCESSING으로 돌아가는 전이 2개를 추가 — LLM의 일시 실패는 세션을 끝낼 사유가 아니라고 판단
  7. 서킷이 감싸는 구간이 실제로는 반쪽이었던 것을 실패 주입으로 발견하고 닫았음. chatStream이 메서드 본문에서 히스토리 조회와 벡터 검색을 동기로 하고 있어, 상류가 죽으면 Flux를 만들기도 전에 예외가 나감 — 리액티브 서킷은 구독 시점 오류만 집계하므로 그 실패는 한 건도 세지지 않았음. 조회·조립을 Flux.defer로 구독 시점에 옮겨 검색 실패까지 서킷 안으로 들였음. 같은 결함이 세션도 망가뜨리고 있었음 — 조립 시점 예외는 doOnError를 타지 않아 상태가 PROCESSING에 남고, 그 세션의 이후 메시지가 전부 거부됨(실측: 1번째 500 뒤 2~6번째 연속 401)
  8. 외부 호출 상한을 responseTimeout으로 걸었음 — 총 시간이 아니라 read 사이 간격 상한임. 연결 5s · 응답 20s로 잡았고, @TimeLimiter를 쓰지 않은 이유가 여기 있음 — 총 시간 상한이면 정상 장문 응답까지 잘라냄. 튜터링 답변은 길고, 토큰이 계속 도착하는 한 끊지 않아야 함. 반대로 상류가 멈추면 그 시점부터 20초 뒤에 끊김. 설정 파일에 값을 적었다와 그 값이 동작한다는 다른 명제라, 응답을 주지 않는 소켓을 세워 실제로 끊기는지 단위 테스트로 고정함
  9. SSE Heartbeat를 30초 주기로 보내 죽은 연결을 조기 감지·정리해 메모리 누수를 방지

결과

  • 실패 주입으로 서킷이 실제로 세고 실제로 차단하는 것을 수치로 확인함 실패 주입 — OpenAI 채팅 엔드포인트만 죽은 포트로 돌리고(임베딩은 로컬 스텁으로 살려 둠) 채팅 6회를 보낸 결과, llm-chat 서킷에 failed 5 · successful 0 · ignored 0이 집계되고 state=open · 실패율 100%로 전이했으며, 6번째 호출은 not_permitted 1건으로 아예 실행되지 않았음. 설정(최소 호출 5 · 실패율 50%)과 정확히 일치하고, "차단했다"의 실체가 그 미실행 1건임. ignored 0은 도메인 예외 무시 설정이 인프라 실패까지 삼키지는 않는다는 확인이기도 함
  • 캐시 저장소 장애는 대체 응답이 아니라 "저장만 포기"로 흡수함 — 저장 실패를 chat.redis.save.dropped{reason}으로 계상하고 스트리밍은 그대로 이어 감. 가짜 답변을 만들어 내려보내지 않는 이유는 대상이 수능·모의고사를 준비하는 학생이기 때문 — 그럴듯한 오답은 침묵보다 해로움. 반대로 소유자 검증은 같은 서킷을 쓰면서도 fail-close임 — 인가 게이트를 못 읽는 상태에서 통과시키면 그 자체가 인가 우회임
  • 비정상 상태 전이(스트리밍 중 재전송 등)를 전이 테이블에 선언된 쌍만 허용하는 방식으로 구조적 차단
  • 빈 응답·LLM 일시 실패로 PROCESSING에 남은 상태를 회수하고 같은 세션에서 재전송할 수 있도록 전이를 보강해 복구 경로 확보

남은 한계

  • RAG를 끄면 채팅 스트리밍에 서킷이 없음. llm-chat은 RAG 활성 구현에만 붙어 있고, 비활성 구현의 chatStream은 무보호임. 이 절의 측정과 주장은 RAG 켜짐 구성에 한정됨
  • "의존성이 없었다면 0건이었다"는 대조군은 측정하지 못함. 리액터 모듈을 뺀 빌드로 같은 주입을 돌리려 했으나 호스트 자원 부족으로 완주하지 못했으므로, 추가 전 수치는 주장하지 않음 — 근거는 단위 테스트와 위 구독 시점 메커니즘까지임. 참고로 "기동 로그에 경고가 없으면 정상"이라는 판정은 쓸 수 없음을 확인함: 그 문구는 DEBUG 레벨이라 의존성을 뺀 빌드에서도 나오지 않았음
  • CB 임계값(최소 호출 5건·10건, 실패율 50%·60%)은 운영 트래픽 분포가 없는 상태에서 정한 값임 — 표본이 적을 때의 오판을 막는다는 기준으로 잡았고, 실제 호출 분포가 쌓이면 그 분포를 근거로 재조정하는 것이 맞음. 지금 근거는 통계가 아니라 실패 모드에 대한 판단임

4. 다국어 RAG의 재현율 저하를 임계값으로 우회하고, 플래그를 껐을 때만 드러나는 조건부 빈 결합을 정리

전체적인 아키텍처

실제 동작 구조 — 색인 경로와 요청 시 RAG 분기

문제 원인

  • LLM 단독으로는 수능·모의고사 지문에 정확한 근거를 대지 못하고 사실과 다른 답을 내는 Hallucination 위험이 있었음
  • pgvector + HNSW 벡터 스토어를 구성하며 코사인 유사도 임계값을 0.7로 잡았는데 관련 문서가 검색되지 않았음 — 0.7은 프레임워크 기본값이 아니라 근거 없이 고른 값이었음(Spring AI 실제 기본값은 SIMILARITY_THRESHOLD_ACCEPT_ALL = 0.0, 전부 통과)
  • 원인은 영어 강의자료 + 한국어 질문 조합에서 유사도 분포 자체가 낮게 깔리는 것이었음. 임계값에 걸려 재현율이 떨어짐

해결 과정

  1. pgvector + HNSW(1536차원, COSINE_DISTANCE)로 벡터 스토어를 구성하고 text-embedding-3-small로 PDF 강의자료·JSONL 문제를 적재한 뒤, similaritySearch → system prompt 주입 → ChatClient.stream() 스트리밍으로 이어지게 구현
  2. 임계값을 0.7에서 0.2로 낮췄으나 이것을 "튜닝"이라 부르지 않음 — 두 값 사이의 어떤 값도 비교하지 않았고 스윕 결과가 저장소에 없음. 실제로 한 일은 검색이 0건으로 떨어지던 상태를 실험 없이 해소한 증상 대응이고, 근본 해결은 임베딩 모델의 언어 정렬이라고 층을 나눈 것까지가 정확한 범위임
  3. 검색이 비면 컨텍스트를 억지로 채우지 않고 RAG 없는 프롬프트로 폴백. Top-K 5는 "제한"이 아님 — Spring AI 기본값 4보다 오히려 1 크므로 "임계값을 낮춘 것을 topK로 상쇄했다"는 논리는 성립하지 않음. 실제 정밀도 방어는 코퍼스를 강의자료·기출로 좁힌 것 하나임
  4. 근본 원인을 한국어 질문과 영어 중심 임베딩 모델의 언어 정렬 문제로 보고 대안 셋을 비교 — ① 다국어 모델 ② BM25 하이브리드 ③ Reranker. ①은 "비용이 커서 보류"가 아니라 실행 경로가 없음: 차원이 설정에 하드코딩돼 있고 스키마도 1536 단일 관리인 데다 색인 진입점이 기동 시 러너 하나뿐이며 문서가 1건이라도 있으면 통째로 건너뜀. 차원·스키마·색인 스킵 조건 세 곳을 동시에 고치고 전량 재적재해야 함
  5. Feature Flag로 RAG On/Off를 토글해 A/B 축을 만들었음 — 분기축은 오프너 분석 vs 일반 채팅이 아니라 플래그 하나임. 즉 플래그가 켜져 있으면 일반 채팅도 매 턴 벡터 검색을 경유하고 임베딩 왕복·검색 지연이 모든 턴에 얹힘. LlmService에 사용·미사용 구현체를 짝으로 두어 플래그가 어느 값이든 빈이 하나는 생기게 함
  6. 반면 오프너 경로에는 그 짝이 없었음 — RagService가 조건부 구현체 하나뿐이라 플래그를 끄면 빈이 사라지는데 주입은 필수였음. 사용자에게 터진 장애가 아니라 플래그를 꺼보다 드러난 기동 실패임(범위를 정확히 적어야 뒤의 일반화가 산다). 교훈은 조건부 빈은 그 타입을 주입받는 쪽까지 봐야 방어가 성립한다는 것이고, 처방을 둘로 나눠 적용함 — 짝을 만들 수 있는 곳은 짝으로, 조건이 없는 소비자 하나는 선택적 의존(ObjectProvider)으로. 같은 빈의 주입 클래스가 다섯 개임을 이때 전수 확인했고, 플래그를 양방향으로 실제 기동해 검증함 — 컴파일 통과는 여기서 아무것도 증명하지 않기 때문임
  7. 프롬프트에 실리는 대화 히스토리 비용도 통제 — 전량 주입을 최근 N턴 윈도우(app.chat.history-window, 기본 20)로 제한함. 다만 직후 DB에 영구 저장되는 요약이 20턴 기준으로 잘리는 회귀를 발견해 조회 계약을 LLM 컨텍스트용(윈도우)과 영속화용(전량)으로 분리함 — 비용 최적화가 저장 데이터를 훼손하지 않게 경로를 가른 결정임. 이 키는 @Value 기본값으로만 있어 어떤 yml에도 없었고 /actuator/env에도 안 떴음(자기 원칙의 반례였으므로 yml에 명시해 함께 정리)
  8. 조회 성능의 두 축도 함께 정리 — 인덱스는 거리 계산이라 B-tree가 듣지 않으므로 HNSW로 근사 최근접 탐색이 되게 했고, N+1은 지문·보기를 JSONB로 함께 두어 조인 자체를 없앤 것이 이 도메인의 답이었음. 관계로 남겨야 하는 집계 조회는 JPQL new 생성자 표현식의 DTO 프로젝션으로 필요한 컬럼만 가져옴(엔티티를 통째로 로딩하지 않으므로 컬렉션 fetch join의 페이징 함정도 생기지 않음). N+1은 ORM의 결함이 아니라 "언제 가져올지를 안 정한 상태"의 증상임

결과

  • RAG On/Off 양방향으로 동일 질문셋을 던졌을 때 근거 없는 응답이 눈에 띄게 줄어드는 것을 확인 정성 관찰 — 규모로는 30%대 → 10% 안팎 가정. 채점 결과가 아니라 관찰의 인상을 옮긴 값임: 이전 판본의 32% → 8% 실측은 질문셋·기준표·채점 결과가 모두 없어 배지를 뗐음(측정 로그도 이 행만 "별도 / —"였음). 두 자리 정밀도를 되살리지 않고 구간으로 적은 이유가 이것
  • 근사 최근접 검색으로 풀스캔 없이 오프너 분석 경로 벡터 검색 80ms 이내 실측 — 모집단을 명시함: Timer가 걸린 곳은 오프너 경로뿐이고 호출량이 더 많은 일반 채팅에는 계측이 없음. 대시보드가 p95로 그리므로 평균이 아니라 p95 기준임
  • 검색 0건일 때 컨텍스트를 비우고 일반 프롬프트로 폴백해, 문서를 못 찾은 상황이 응답 실패로 번지지 않게 처리

남은 한계

  • 임계값 하향을 "정밀도와 재현율의 교환"이라 부르려면 양쪽을 다 재야 하는데 어느 쪽도 재지 않았음 — 정확히는 재현율 회복만 확인하고 정밀도는 미측정임. 근거를 만들려면 정답 문단의 앵커 문자열로 hit을 판정하는 골든셋 + 임계값 스윕으로 recall@5를 비교해야 하는데 하네스를 아직 만들지 않았음. 아래는 기대하는 모양일 뿐이고 가정, 0.7에서 검색 0건이 관측된 것 외에는 전부 미측정임 — 표의 값이 아니라 곡선의 방향이 판단 근거임
📊 임계값 스윕이 그릴 것으로 기대하는 모양 (미측정 · 가정)
  • 검색 품질에 가장 크게 작용하는 청킹은 손대지 않았음 — 스플리터를 인자 없이 생성해 토큰 크기·오버랩이 전부 기본값임. 다국어 정렬을 원인으로 진단해 놓고 청크 전략을 검토 대상에 넣지 않은 것이 이 절의 가장 큰 공백임
  • 일반 채팅 경로에 Timer가 없어 RAG가 모든 턴의 첫 토큰 지연에 얹는 비용을 수치로 답할 수 없음 — 같은 Timer에 path=chat|opener 태그를 붙이면 한 줄로 해결됨

5. 인증·세션 방어선을 단일 통과점 구조로 설계하고 런타임 검증 절차를 확립

전체적인 아키텍처

방어선이 실제로 걸리는 지점 — 로그아웃 무효화 경로와 SSE 세션 소유권 검증

문제 원인

  • 출발점은 이전 프로젝트의 제약이었음 — 휠 파인더(§3)에서 Refresh Token을 토큰 전문으로 키잡아 사용자 단위 폐기를 못 했고 Redis 장애 정책도 없었음. 같은 실수를 반복하지 않는 것이 첫 요구사항이라 키 기준·장애 정책·검증 절차를 먼저 정하고 구현에 들어갔음
  • "방어 장치가 동작한다"를 무엇으로 증명할지를 먼저 정의해야 함 — 기능 테스트는 정상 흐름만 증명하지 방어선이 거부하는지는 증명하지 못함. 토큰 무효화는 쓰기·읽기·거부 세 지점이 짝을 이뤄야 성립하고(blacklist:access:{jti} 를 어디에 쓰고 어느 필터가 읽고 어떤 규칙으로 거부할지), 그 범위도 결정이 필요함 — access만 폐기할지 서버 보관본 refreshToken:{userId} 까지 포함할지에 따라 재발급 경로가 남는지가 갈림
  • SSE 연결 생성은 신규·재사용 두 분기로 갈라짐 — 검증을 호출부마다 두면 분기가 늘 때마다 새므로 검증을 어느 계층에 둘 것인가가 문제의 본질이었음

해결 과정

  1. Redis 키를 전수 검색해 쓰기·읽기·삭제를 대조 — 방어 장치는 "쓰는 코드가 있다"가 아니라 "읽고 거부하는 코드가 있다"로만 검증된다고 보았음. blacklist:access:{jti}는 통과했으나 refreshToken:{userId}는 발급 4경로 중 저장이 1곳뿐이었음 — 폼 로그인만 저장하고 카카오·폼 회원가입·OAuth 회원가입은 쿠키만 내주었음. 재발급이 서버 보관본과 대조하는 방식이라 그 세 경로 사용자는 access 1시간이 끝나면 반드시 재로그인해야 함
  2. 원인은 발급 코드가 4곳에 복제된 것 — 한 곳에만 저장을 추가하면 나머지는 컴파일도 테스트도 통과하면서 조용히 다름. 발급·쿠키·저장을 TokenIssuer 한 메서드로 묶어 누락이 구조적으로 불가능하게 함. 같은 대조에서 수명이 세 값으로 갈라진 것도 나왔음 — JWT exp 14일 vs Redis TTL·쿠키 7일이라 7일 뒤에는 폼 로그인 사용자도 재발급 실패였고 주석은 "TTL 7일 = 수명"으로 착오를 고정하고 있었음. 셋 다 설정값 하나에서 계산하게 통일함. 다만 통일한 것은 refresh 축뿐임 — access 쿠키의 maxAge는 아직 60분 리터럴이라 설정을 바꿔도 쿠키만 따라오지 않음(지금은 두 값이 우연히 같아 증상이 없음)
  3. 인증 필터가 블랙리스트를 조회해 거부하고 jti 없는 토큰도 폐기 취급. 조회 실패 시 통과냐 차단이냐를 명시적으로 결정 — fail-open은 장애 시간만큼 폐기 토큰을 되살리므로 fail-close, 근거는 코드에 남김. 로그아웃은 refreshToken:{userId}까지 지우고 손상·만료 토큰에도 쿠키 정리 후 정상 반환하는 멱등 처리
  4. "단일 통과점"에는 두 뜻이 있는데 약한 쪽만 구현돼 있었음 — 판정 로직은 헬퍼 하나로 모았지만(약), 호출은 각 진입점이 손으로 해야 해서 새 엔드포인트에서 빠뜨리면 그대로 구멍이었음(강). 같은 클래스 안에만 검증 호출이 5곳 흩어져 있었음. 그래서 판정과 진입 통제를 분리해 통제를 @RequireSessionOwner + 어드바이스로 옮겼음. 인자 추출은 리플렉션이 아니라 인터페이스 계약으로 정하고 추출 실패 시 통과가 아니라 거부하게 함 — 규약을 못 맞춘 메서드를 통과시키면 애너테이션이 방어가 아니라 장식이 됨. 검증 지점 6곳 → 어드바이스 1 + 근거 있는 예외 2곳(연결 생성은 세션을 지금 만드는 요청이라 전제가 다르고, 메시지 소비자는 실패 처리가 HTTP 거부가 아니라 ACK/DLQ 결정임)
  5. 거부는 하는데 그 거부를 관측할 수 없었음 — 소유자 불일치가 400 C_001로 나갔는데 이 코드는 요청 본문 검증 실패에도 붙어 오타와 세션 탈취 시도가 같은 버킷에 들어갔음. 403(인가 실패)과 404(대상 부재)로 갈랐음. 통과점을 우회하는 목록도 점검하지 않았던 것을 함께 정리 — permitAll에 부하 테스트용 /test/**가 남아 dev가 곧 배포 프로파일인 이 저장소에서 스레드 점유 엔드포인트가 미인증 공개였음. 전수 대조를 Redis 키에만 적용한 범위 누락이었음
  6. 설정도 같은 방식 — application*.yml 3개 파일 6곳이 한 단계 깊게 들여써져 엉뚱한 부모 키 아래였고, Spring Boot는 모르는 프로퍼티를 조용히 무시하므로 경고가 없었음(SSE 30분 타임아웃·dev 1분 계정 잠금·prod 로그 레벨이 전부 미적용). 그래서 런타임 바인딩까지 확인하는 단계를 넣었음 — /actuator/configprops·/actuator/loggers로 실효값을 보고 계정 잠금은 423과 해제 시각까지 재현. 이 절차에는 선행 단계가 있음: 두 엔드포인트는 기본 노출이 아니라 임시 노출 + 인증 쿠키가 필요하고, 운영에 상시 열면 그 자체가 정보 노출이라 로컬 확인으로 한정함
  7. 인프라를 띄워 API로 재현 — 로그아웃한 access token 재요청 401 거부, 블랙리스트 TTL이 고정값이 아니라 토큰 잔여 수명 연동(3,579초), 멱등성은 토큰 없음·변조·형식 불명·만료·이미 로그아웃 5개 변형 전부 정상 종료. 소유권은 두 시나리오로 확인 — ① 원 사용자 연결 생존 ② 연결이 끊기고 Redis 세션만 TTL이 남은 상태(원래 빠져 있던 시나리오)

결과

  • 토큰 무효화 범위를 access·refresh 양쪽으로 정의하고 쓰기·읽기·거부가 하나의 계약으로 연결된 구조를 확립 — 로그아웃 후 재요청 401, 블랙리스트 TTL이 잔여 수명에 맞춰 걸리는 것(만료 1시간 토큰 → 3,579초)까지 실행 검증 실측
  • 대조 절차가 실제로 결함을 잡아냈고, 그 결함을 고친 것이 이 절의 결론을 참으로 만들었음 — 발급 4경로 중 3경로의 서버 보관본 누락(= 카카오·회원가입 사용자의 재발급 영구 실패)과 수명 3중 불일치를 발견해 단일 진입점으로 묶고 수명을 설정값 하나로 통일함. 이전 판본은 이 결함이 남은 채 "양쪽으로 정의된 계약"을 주장하고 있었음
  • 소유자 검증을 판정(헬퍼)과 진입 통제(어드바이스)로 분리해 새 엔드포인트가 늘어도 애너테이션 하나로 걸리는 구조 확보. 거부 신호도 403/404로 분리하고 실제 요청으로 재확인함 실측 — 타인 세션 403 C_013, 없는 세션 404 C_014, 대조군인 정당한 소유자는 200 + text/event-stream 통과. 거부가 소유자 불일치에 한정된다는 것까지 확인한 것이라, 모두를 막아 놓고 "방어했다"고 말하는 경우와 구분됨
  • 설정은 "값을 적었다"와 "실제로 바인딩됐다"를 분리 검증하는 단계를 표준에 넣어 조용히 무시되는 설정을 구조적으로 걸러냄

남은 한계

  • 검증은 대조군까지 확인했으나 자동화된 회귀 테스트가 아니라 수동 E2E 절차임 — 방어가 깨져도 CI가 잡지 못하므로 테스트 코드로 승격하는 것이 후속 과제임
  • refresh 회전과 재사용 탐지가 없음 — 재발급 시 access만 새로 내주고 refresh는 그대로 두며 jti가 없어 개별 폐기도 못 함. 탈취된 refresh와 정상 refresh를 구분할 방법이 없음
  • 사용자 단위 폐기가 refresh에서만 성립함 — access 블랙리스트는 jti 단위라 여러 기기 사용자를 로그아웃시켜도 다른 기기 access는 최대 1시간 생존함. "휠 파인더의 실수를 반복하지 않았다"는 절반만 참임
  • 로그아웃 5변형 검증이 HTTP 200만 보았음 — access 쿠키가 이미 만료된 상태로 로그아웃하면 쿠키만 정리하고 반환해 서버의 refreshToken:{userId}가 남음. "정상 종료"와 "무효화 완료"는 다른 명제인데 앞의 것만 검증함
  • 신규 연결 경로의 세션 초기화에는 서킷브레이커가 없음 — Redis 장애 시 재사용 분기는 fast-fail하는데 신규 분기는 타임아웃까지 대기해 같은 엔드포인트의 두 분기가 장애 시 다르게 동작함

동시성 해법이 도메인마다 다른 것은 자원마다 정합성의 근거로 삼은 저장소가 다르기 때문. 다중 인스턴스를 전제하면 두 도메인이 같은 결론에 도달함 — Redis는 비동기 복제라 정확성의 단독 근거가 될 수 없으므로 부하 필터로만 쓰고, 최종 정합은 각 도메인의 성질에 맞는 곳이 책임짐. 쿠폰은 순서가 요구라 파티션당 단일 컨슈머가, 상품 재고는 차감이 주문·결제 상태로 이어지므로 DB @Version이 그 자리를 맡음. 분산 락은 두 발급·차감 경로 어디에도 두지 않고 쿠폰 보정 배치의 배타 실행에만 남겼음 — 결제 보상 배치에는 아직 없어서, 인스턴스를 늘리면 재시도 횟수가 어긋나는 것이 남은 구멍임

선착순 발급 경로 — Redis는 부하 필터, 순서의 진실은 Kafka 오프셋, 확정은 파티션당 단일 컨슈머

문제 원인

  • 선착순의 기준점이 정의돼 있지 않았음. 서버가 여러 대면 "먼저 온 요청"을 판정할 주체가 사라짐 — 인스턴스 수신 시각은 NTP 오차만큼 흔들리고 클라이언트 시각은 조작 가능함. 기준의 정의가 없어 증설하는 순간 순서가 흔들렸음
  • DB 비관적 락(SELECT ... FOR UPDATE)은 정확성은 지키나 커넥션 풀이 곧 동시 처리 상한이 됨. 풀은 maximumPoolSize=20(코어×2 + 유효 디스크 수 권장식)이고 늘려도 컨텍스트 스위칭·DB 측 잠금 경합이 먼저 늚. 그 풀을 주문·결제가 함께 써서 쿠폰 이벤트 한 번이 서비스 전체 지연으로 번지는 경로가 열려 있었고, 임계 구역에 DB I/O가 있는 한 증설로는 못 넘음
  • 대안으로 검토한 Redisson 분산 락은 직렬화 지점만 옮김. 핫 쿠폰에선 전 요청이 한 락을 통과해야 해 대기가 쌓이고, tryLock(waitTime=3s)을 넘긴 요청은 재고가 남아도 품절 응답을 받음 — 정확성용 도구가 만든 것은 거짓 품절이라는 가용성 결함이었음
  • 부하로 확인한 것은 그 락이 대가만큼의 보장도 못 준다는 사실이었음 — 같은 구성 2회 측정에서 발급 지연 중앙값이 341ms에서 10,650ms로 튀며 고정 leaseTime(5초)을 넘었고, 그 구간에서 중복 발급 1건과 네 저장소 수치 불일치를 실제로 관측함 통제 실험. 머신 부하만 달라졌는데 상호배제가 깨진 것이고, 고정 leaseTime은 "임계 구역은 항상 5초 안에 끝난다"는 검증되지 않은 전제였음
  • 확장 구성에선 Redis를 정확성의 단독 근거로 둘 수 없음(standalone이라 관측이 아니라 확장 시 성립할 제약임) — 복제가 비동기라 마스터 장애로 복제본이 승격되면 마지막 수 ms의 쓰기가 되감김. 재고 카운터·순번이 되감기면 그대로 초과발급임

해결 과정

  1. 선착순의 기준점을 Kafka 브로커 도달 순서(오프셋)로 정의함. 후보 넷의 탈락 사유 — 클라이언트 시각은 조작 가능, API 수신 시각은 N대 시계 오차, Redis 도달 순서는 비동기 복제로 failover에서 되감김. Kafka를 고른 이유는 파티션 안에서 결정적 전순서가 서고 그 순서를 재생할 수 있는 유일한 계층이기 때문 — 카운터에도 인메모리 큐에도 없는 성질임. 동기 복제를 근거로 쓰지는 않았음 — 브로커가 1대(RF=1)라 min.insync.replicas를 올리면 모든 발행이 NOT_ENOUGH_REPLICAS로 실패함
  2. 파티션 키를 couponId로 잡아 한 쿠폰의 이벤트를 한 파티션에 모았음. 그 파티션의 컨슈머는 1명이라 API가 N대여도 쿠폰당 판정자는 항상 1명임 — 상호배제를 락으로 사는 대신 파티션 소유권으로 얻어 분산 락이 필요 없어짐
  3. Redis를 정확성의 근거에서 내리고 부하 필터로 재배치함. Lua가 "마감됐는가 · 이미 신청했는가"를 왕복 한 번에 판정해 브로커 앞에서 물량을 자름 — 5,000건 중 Kafka에 실리는 것은 100여 건임. 근사여도 안전함 — failover로 느슨해지면 통과량만 늘고 최종 판정은 컨슈머가 함(재고 도메인 eco-2의 Redis 선점 게이트와 같은 역할 분담). Lua인 이유는 서버 대수와 무관하게 원자성이 유지되기 때문 — 인메모리 카운터나 synchronized는 인스턴스 수만큼 깨지지만, Lua는 Redis가 단일 스레드로 실행하므로 "확인 → 차단" 사이에 끼어들 수 없음. 키의 해시태그(coupon:{couponId}:stock)는 지금이 아니라 나중을 위한 것 — standalone엔 슬롯이 없지만, Cluster에서 한 스크립트의 두 키가 다른 슬롯에 놓이면 CROSSSLOT으로 항상 실패하고, 그때 형식을 바꾸면 살아 있는 카운터를 이관해야 함
  4. 대기 순번은 아예 응답하지 않기로 함. "당신은 N번째"가 확정 결과와 같아야 하는데 접수 시점엔 알 수 없음 — 게이트 통과 순서와 오프셋 순서가 컨텍스트 스위칭으로 어긋나고, 게이트는 근사라 통과분이 재고보다 많을 수 있음. 주는 순간 지킬 수 없는 순서를 약속하므로, 접수는 requestId만 돌려주고 확정은 상태 조회로 넘겼음. ZSet 원장에 ZRANK로 순번을 두는 안도 검토했으나 넣지 않았음 — 취소 승계 요구가 없으면 오프셋 순서를 한 번 더 복제하는 것이고, 두 순서가 어긋날 때 진실을 정할 방법이 없어 정합성 부채만 남음
  5. 응답 경로에서 DB를 들어내었음. API는 Lua 게이트 통과와 Kafka 발행까지만 하고 즉시 응답하며, DB 쓰기는 컨슈머가 담당함. 쿠폰 스파이크가 커넥션을 점유하지 않아 주문·결제 경로를 밀어내지 않음 — 가용성 주장의 구조적 근거임. 대가는 사용자가 발급 결과 대신 접수 확인만 받는 것임
  6. 최후 방어선은 DB에 두 겹 — 유니크 제약과 조건부 UPDATE임. 게이트가 근사이고 컨슈머 재처리도 가능하므로, 중복은 UNIQUE(coupon_id, user_id)로, 초과발급은 UPDATE ... SET quantity = quantity - 1 WHERE id = ? AND quantity > 0의 영향 행 수 0 판정으로 막음. 조건부 UPDATE인 이유는 검사와 차감이 한 문장에서 끝나기 때문 — 컨슈머가 1명이라 경합이 없어도 재처리·수동 보정 경로가 생기면 읽기-쓰기 분리는 뚫림. 실제로 걸어 보니 dev DB에 이미 위반 데이터가 있었음 — 같은 사용자·같은 쿠폰 2건이 56ms 간격, 동시 요청 둘이 Redis 중복 검사를 함께 뚫었다는 뜻임. "이론적으로 가능"이라 적었던 구멍이 데이터로 확인된 것이라, 이 제약은 보험이 아니라 이미 난 사고를 막는 장치임
  7. 분산 락은 발급 경로에서 걷어내 배치·관리 경로로 옮겼음. N대면 @Scheduled가 N번 실행되므로, 재고 대조·보정 배치에는 하나만 실행하도록 락을 걸었음. 락을 쓸 조건은 저빈도 · 긴 임계 구역 · 큰 중복 실행 피해인데, 배치는 셋 다 맞고 발급 경로는 셋 다 반대였음 — 어디에 쓰지 않을지를 정한 것이 이 절의 판단임. eco-4의 Kafka Streams는 같은 중복 실행 문제를 파티션 소유권으로 풀었으나, 보정 배치는 Kafka 토폴로지 밖이라 그 방법이 닿지 않음
Lua · Redis · 접수 게이트
-- KEYS[1] coupon:{id}:stock   KEYS[2] coupon:{id}:issued_users   ARGV[1] userId
-- 반환 1=성공 0=품절 -1=중복 -2=미초기화
-- 정확성의 근거가 아니라 부하 필터다 — 통과량이 실제 재고보다 많아도 컨슈머가 최종 판정한다

-- 중복 검사를 재고 검사보다 앞에 둔다. 뒤에 두면 재고가 0 이 된 뒤로는
-- 이미 받은 사용자의 재요청까지 "품절"로 응답돼 실패 집계에서 중복과 품절이 섞인다
-- 재고 소진은 이벤트 초반에 오므로 그 뒤의 요청이 다수다 - 오분류가 예외가 아니라 기본값이 된다
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1
end

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -2                                -- 미초기화: 판정을 컨슈머의 DB 폴백에 위임한다
end
if stock <= 0 then
    return 0                                 -- 마감: 브로커 앞에서 자른다
end

-- 통과 예상 인원만 줄인다. 되돌리지 않으므로 게이트는 항상 보수적으로 동작한다
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1

결과

  • 선착순의 기준이 "무엇의 순서인가"로 답할 수 있게 됨 — Kafka 도달 순서이고 파티션 로그에 남아 재생 가능함. N대로 늘려도 판정자는 파티션당 1명이라 순서가 인스턴스 수에 흔들리지 않음. 다만 브로커 장애에도 순서가 보존된다는 주장은 하지 않음 — 복제가 있어야 서는 성질이고 이 환경은 RF=1임
  • 발급 경로에서 락과 DB를 동시에 들어내었음 — 응답까지 드는 일은 Lua 왕복 1회와 Kafka 발행뿐이고 대기 구간이 없어 락 대기 초과로 생기던 거짓 품절이 원인 단계에서 소멸함. DB 커넥션을 점유하지 않아 주문·결제와 자원을 다투지 않음
  • 네 도구의 보호 범위가 겹치지 않음 — Lua는 접수의 원자성(부하 필터), Kafka 오프셋은 순서의 진실, 컨슈머는 정합성의 근거, 분산 락은 배치의 배타 실행. 락과 Lua가 같은 임계 구역을 이중으로 지키던 것이 정리됨
  • 기존 구조의 실측 중 근거 자격이 있는 것만 남겼음 — 락 구성에서 수량 100개 쿠폰에 VU 200 · 5,000 요청으로 100건 발급, 총량 상한이 지켜짐을 확인했고 대리 부하, 2회차의 상호배제 붕괴도 관측함. 반면 함께 적었던 "중복 시도 N건 거부"는 뺐음 — 응답 본문 부분일치로 세어져 거짓 품절·저장소 불일치·진짜 품절이 한 칸에 섞였음. 지금은 사유별 에러코드(COUPON_ISSUE_CONTENTION · COUPON_STORE_MISMATCH · COUPON_OUT_OF_STOCK)로 갈라 뒀으나, 재측정 전까지는 수치를 쓰지 않음

남은 한계

  • 이 구성은 설계까지이고 다중 인스턴스로 실기동·측정하지 않았음. 위 실측은 전부 단일 인스턴스 + 락 기반 구조의 값이라 재설계의 성능 근거로 쓰지 않았음 — 주장하는 것은 측정된 개선이 아니라 확장 시 무엇이 깨지고 무엇으로 막는지의 구조임
  • 결과의 즉시성을 내주고 접수 무거절을 샀음. 사용자는 "당첨/품절" 대신 "접수됨"을 먼저 받으므로 즉시 결과가 필수인 요구엔 맞지 않음. 확정 통보는 폴링·SSE로 붙일 수 있으나 이번 범위에 넣지 않았음
  • 핫 단일 쿠폰은 노드를 늘려도 처리량이 늘지 않음. 해시태그로 Redis는 한 노드가, couponId 파티션 키로 Kafka는 한 파티션이 상한임 — 수평 확장이 쿠폰 단위로만 됨. 게다가 토픽이 자동 생성돼 파티션이 1개라 "파티션당 컨슈머 1명"이 사실상 "컨슈머 1명"임 — 쿠폰 단위 확장조차 NewTopic 빈으로 파티션 수를 올려야 열림. 재고를 버킷(stock:0~9)으로 쪼개면 병렬화되지만 순서 보장을 포기해야 하고 잔량 불균형이 생겨 도입하지 않았음
  • 보정 배치는 만들었으나 한쪽으로만 고칠 수 있음. 게이트가 통과분을 되돌리지 않아 탈락·유실이 쌓이면 실제 재고보다 먼저 닫히는데, 이를 되돌리는 대조 배치를 필수 구성요소로 보고 구현함(위 분산 락이 지키는 대상). 대조식은 기대 재고 = DB 잔여수량 + DB 확정발급수 − 발급자 SET 크기인데, 초기 수량을 따로 저장하지 않아 두 저장소의 회계를 빼서 얻음. 실제가 기대보다 작으면 올리지만, 크면 내리지 않고 경고만 냄 — 내리면 이미 통과한 요청의 자리를 빼앗아 COUPON_STORE_MISMATCH를 만들기 때문. 느슨한 쪽으로만 틀려도 초과발급이 안 되는 근거는 조건부 UPDATE와 유니크 제약임. 워밍업도 SETNX로만 심는데, 덮어쓰면 Lua 차감은 끝났으나 DB 커밋 전이던 요청 수만큼 재고가 되살아나기 때문

2. 동시 결제 재고 차감 Lost Update를 막고, 세 가지 차감 전략을 실측해 낙관적 락의 한계를 확인

전체적인 아키텍처

재고 차감 2단 방어 — Redis 선점 게이트 → DB 낙관적 락

문제 원인

  • 동시 결제 시 재고 차감에 Lost Update 위험이 있었음
  • 비관적 락은 정확성을 지키지만 고경합에서 DB 행 잠금을 장기 점유해 처리량이 떨어짐
  • PG 호출 전에 재고 부족을 거를 게이트가 없어, 재고가 바닥난 상품인데도 결제 시도가 PG까지 도달함

해결 과정

  1. 상품 엔티티에 @Version 낙관적 락을 걸고 충돌 시 자동 재시도되게 함 — 현재 설정은 @Retryable(maxAttempts=3, @Backoff(delay=100, multiplier=2, random=true, maxDelay=1000))임. 지터와 상한은 근거가 있어 넣었고, 한도 3은 근거가 없어 그대로 둠. 애너테이션 속성값을 리플렉션으로 검증하는 테스트를 붙여 문서와 코드가 어긋나면 테스트가 먼저 깨지게 함
  2. 재고 차감을 REQUIRES_NEW 독립 트랜잭션으로 처리해 매 시도가 새 트랜잭션에서 커밋·충돌 감지되게 하고, 결제 진입 직전 Redis DECR 원자 연산으로 재고를 선점해 부족분을 PG 호출 전에 차단함
  3. Redis 미초기화 상품은 DB 낙관적 락으로 폴백하는 2단 방어를 구성해 캐시 미스가 곧 장애가 되지 않게 함 — 이때 Redis에 되쓰지 않고 게이트만 통과시키는 것이 중요. 임계 구역이 Redis 안에서 완결되므로 분산 락이 필요 없고, Redis는 부하 필터일 뿐 최종 정합은 DB @Version이 책임짐. 재고에 쿠폰 쪽 방식(Redis를 정확성의 근거로 승격)을 쓰지 않은 이유는 자원의 얽힘이 다르기 때문 — 재고 차감은 주문 상태 전이·이력 기록과 같은 트랜잭션 경계 안에서 일어나므로, 재고만 DB 밖에서 세면 그 정합을 별도로 방어해야 함
  4. 재시도 한도가 타당한지 보려면 실제 충돌 횟수를 알아야 해 재시도 횟수를 Micrometer로 계측함 — 일반 트래픽 구간은 평균 0.35회/건으로 대부분 무충돌 통과 실측. 반면 1만 건이 단일 행에 몰리는 극단 경합에서는 재시도 소진이 실패의 전량이었음(결과 2). 여기서 한도를 올리고 싶은 유혹이 생기지만 올리지 않았음 — 조건이 다른 두 수치를 나란히 놓고 한도를 정할 수 없고, 한도를 키우면 실패가 지연으로 바뀌어 결제 API 응답 시간에 그대로 얹히기 때문. 한도는 아래 3자 실측으로 정하기로 하고, 근거가 확실한 지터와 대기 상한 1초만 먼저 넣었음
  5. 선점 키에 만료를 두지 않은 것은 의도된 선택임 — 별도 홀드 키 없이 재고 카운터 자체를 DECR로 선점하는 구조라, TTL로 사라지면 미초기화 폴백으로 떨어져 게이트가 무력해짐. 대신 실패 경로 전부에서 선점분을 되돌리는 구조로 덮었고(선점 도중 부족·PG 승인 실패·승인 후 DB 실패·결제 취소), 부하 로그의 복원 포기 마커가 0건이라 예외가 잡히는 실패에 한해 이 경로가 새지 않음을 확인
  6. 남은 위험은 계측이 아니라 예외 재포장이었음 — 실패를 재고 부족·락 충돌·기타로 나누는 카운터가 이미 있었는데 락 충돌 카운터만 한 번도 증가하지 않았음. 재시도를 소진한 @Recover는 BusinessException(PRODUCT_STOCK_CONFLICT)를 제대로 던지고 있었지만, 결제 오케스트레이션의 catch (Exception)이 익명 RuntimeException으로 감싸는 순간 에러 코드가 소실돼 전역 핸들러의 catch-all로 떨어졌고, 409여야 할 응답이 500으로 나가고 있었음. 한 계층의 예외 재포장이 상위 계층의 관측 가능성을 통째로 지운다는 것 — 그 카운터는 구조적으로 절대 증가할 수 없는 죽은 카운터였다는 것이 가장 큰 소득임
  7. 죽은 카운터를 실제로 되살렸음 — 재포장하던 catch (Exception)을 걷어 BusinessException이 전역 핸들러까지 가게 함. 되살아난 것은 하나가 아님: 같은 재포장이 PAYMENT_TEMPORARILY_UNAVAILABLE(503)·PAYMENT_PG_FAILURE(502)까지 500으로 뭉개 재시도 가능한 경합·일시 장애·PG 장애·내부 버그가 전부 같은 5xx 버킷에 들어가 알람이 무의미함. 이어서 백오프 지터(random = true)를 도입해 충돌한 스레드가 같은 시점에 재진입하는 thundering herd를 흩었음. 함께 검토한 대안 셋에도 각각 근거를 남겼음
  8. ① 원자적 조건부 UPDATE(stock >= :qty 조건을 UPDATE에 실어 충돌 개념 자체를 소멸) — 재고 단일 필드만 다룰 때는 명백히 우월하나, 이 시스템은 재고가 상품 엔티티의 한 필드라 가격·판매 상태 같은 다른 필드와 @Version 하나를 공유함. 그래서 기각이 아니라 실측으로 넘겼음 — 차감 전략을 인터페이스로 뽑아 낙관적 락 · 조건부 UPDATE · 비관적 락 3종을 모두 구현하고 설정값 하나로 교체되게 한 뒤 같은 머신에서 연속 측정. 전환이 실제로 일어났는지는 환경변수가 아니라 메트릭으로 확인함 — 낙관적 락에서만 stock_optimistic_retries가 노출되고 나머지 둘에서는 메트릭 자체가 사라짐. 오타는 조용히 기본값으로 떨어지므로 이 확인이 없으면 세 번 같은 것을 재게 됨
  9. ② 차감 시점을 PG 승인 이전으로 이동 — 승인 후 취소 왕복은 사라지지만 PG 실패 시 재고를 되돌리는 반대 방향 보상이 새로 생김. 어느 쪽 보상을 감당할지의 선택 문제이고, 이미 Redis 게이트가 PG 앞에서 부족분을 걸러 이득이 크지 않다고 판단. ③ 예외 재포장 중단은 기각이 아니라 채택했고 위 죽은 카운터의 직접 처방임

결과

  • 초기 재고 1만 개에 동시 차감 1만 건을 거는 조건에서 재시도 횟수·지터·백오프 상한을 바꿔가며 9회 반복 측정했고, 전 회차에서 DB 최종 재고가 정확히 초기 재고 − 성공 건수였음 — 드리프트 0, 초과판매 0. 대리 부하 회차마다 완주율이 크게 달라져도 이 등식은 한 번도 깨지지 않아, 정합성과 완주율이 서로 독립된 축임을 확인
  • 실패 건의 원인을 추정에서 확정으로 끌어올렸음 — 원본 부하 런에서 재고 부족 카운터가 0건이었고, 로그의 [STOCK_CONFLICT_GIVEUP] · [PAYMENT_CONFIRM_DB_FAILED] · [PAYMENT_COMPENSATION_SUCCESS] 세 마커가 파일 단위로 거의 정확히 같은 건수로 짝지어졌으며(80/80/80, 98/98/98, 111/111/111) 동일 워커 스레드에서 17ms 간격으로 찍혔음. 재현 측정에서도 실패의 에러 코드가 100% PRODUCT_STOCK_CONFLICT 단일이었음 대리 부하 — 실패 경로는 낙관적 락 재시도 소진 하나뿐임
  • Redis 선점 게이트는 재고가 요청보다 적을 때 PG 호출 자체를 차단해, 어차피 실패할 요청에 PG 왕복 비용과 승인 후 환불이 붙지 않음. 다만 이번 측정 조건(재고 1만 / 요청 1만)은 전량이 게이트를 통과하는 구간이라 이 효과가 드러나지 않음
  • 재측정 준비 단계가 먼저 조건 결함을 잡았음 — 프리플라이트에서 Could not open JPA EntityManager 403건이 나며 1,000회 중 423회만 완주하고 p99가 60초(타임아웃)였음. 원인은 yml에 Hikari 설정이 없어 풀이 기본값 10이었던 것. 커넥션 확보에서 막히면 락 경합 신호가 통째로 묻힘 — 지터 A/B는 재시도 분포를 보는 실험인데 모든 요청이 커넥션 대기에 갇히면 관측 자체가 불가능함. 풀을 50으로 고정하자 같은 부하가 10분 27초 → 10.7초, p95 30.55s → 35.7ms가 됨 실측
  • 지터 A/B를 VU를 고정해 다시 쟀고, 결과는 "동시 개선"이 아니라 교환이었음 실측 — 이전 판본의 동시 개선 주장은 재현되지 않음. 성공률 57%→72%, 지연 59ms→47ms를 "같은 머신 백투백"으로 제시했으나 두 런의 VU가 달라(20 vs 10) 지터 효과와 동시성 효과가 섞여 있었음. VU 10·20에서 각각 A/B를 내니 성공률은 오르고 지연은 늘어남: VU 20에서 91.44% → 94.08%(+2.64%p)인데 p95는 381 → 543ms. 지터는 실패를 대기로 바꿈 — 재시도를 시간축으로 흩으니 한도 안에 성공하는 요청이 늘지만 성공한 요청 각각은 더 기다림. 효과는 경합이 셀수록 커져 VU 10에서는 +0.34%p에 그침
  • 3자 실측 결과, 이 워크로드에서는 낙관적 락이 셋 중 가장 나빴음 실측 (VU 20 · 10,000회 · 같은 머신 연속) — 성공률·지연 모두 꼴찌였고, 제목에 건 해법이 최선이 아니라는 것을 스스로 측정해 확인한 것이 이 절에서 가장 값어치 있는 결과임

  • Redis 선점 수와 DB 재고가 어긋나는지를 배치로 대조하고 Micrometer 게이지로 노출함 — 어려운 부분은 "실행 중에는 선점 때문에 Redis가 항상 작다"라 정상 인플라이트와 진짜 드리프트를 구분하는 것이었고, 방향과 지속성 2축으로 갈랐음. redis > db는 선점이 Redis를 줄이기만 하므로 정상 경로로 만들 수 없는 방향이라 1회로 확정하고, redis < db는 선점의 수명 상한(외부 결제 타임아웃 × 재시도 + 보상)이 수십 초라 스캔 2회 연속 유지될 때만 승격함. 자동 보정은 하지 않음 — 보정 자체가 새 드리프트 원인이 될 수 있어 목표를 "근거 있게 탐지한다"까지로 한정함

남은 한계

  • 이번 측정 조건(재고 1만 / 요청 1만)은 전량이 게이트를 통과하는 구간이라 Redis 선점 게이트의 PG 차단 효과가 수치로 드러나지 않음 — 증명하려면 재고보다 요청이 많은 조건으로 다시 재야 함
  • 측정으로 더 나은 전략을 찾았으나 아직 갈아타지 않았음 — 조건부 UPDATE로 전환하려면 재고를 별도 테이블로 분리하는 것이 선행돼야 함(지금은 재고가 가격·판매 상태와 @Version 하나를 공유하므로, 재고만 조건부 UPDATE로 빼면 나머지 필드의 동시 수정 보호가 사라짐). 남은 것은 "무엇이 나은지 모른다"가 아니라 "아는데 옮기는 비용이 남았다"임
  • 측정 조건이 단일 상품 행에 전량이 몰리는 극단이라, 상품이 분산된 실제 트래픽에서는 세 전략의 격차가 훨씬 작을 것 — 이 실험이 확정하는 것은 "고경합 구간에서의 순위"까지임
  • 크래시로 보상 코드가 실행되지 않는 경로는 여전히 남아 있음 — 대조 배치가 어긋남을 탐지하게 됐지만 복구는 사람이 판단해야 함. 쿠폰 발급(§1)과 같은 성질의 문제라 두 도메인이 같은 후속 과제를 공유함

3. PG 결제 부분 실패를 Saga 보상 트랜잭션 + 상태 머신으로 복구

전체적인 아키텍처

결제 실패 시 보상 흐름 — 즉시 취소 → 실패 시 배치 재시도 → 최종 포기 격리

문제 원인

  • Toss Payments 승인 성공 후 내부 DB 후처리(주문 상태 변경, 재고 차감)가 실패하면 "결제만 되고 주문이 없는" 부분 실패가 발생
  • 외부 PG 승인은 DB 롤백으로 되돌릴 수 없는 비가역 작업인데, 내부 가역 작업과 트랜잭션 경계가 분리되어 있지 않았음
  • 멱등성이 없어 재시도 시 이중 결제가 발생할 위험이 있었음

해결 과정

  1. 결제 승인 호출은 NOT_SUPPORTED 비트랜잭션으로, DB 후처리는 REQUIRES_NEW 독립 트랜잭션으로 분리해 "되돌릴 수 없는 것"과 "되돌릴 수 있는 것"이 하나의 트랜잭션에 묶이지 않도록 함
  2. DB 후처리가 실패하면 Saga 보상 트랜잭션으로 외부 PG 취소 API를 즉시 호출하고, 그마저 실패하면 보상 테이블에 적재해 @Scheduled 배치가 재시도하도록 구현 — 즉시 시도 1회 + 실패마다 지수 백오프(2·4·8·16분) 재시도 4회로 총 5회 시도, 초과 시 GIVEN_UP 전환과 운영자 알림
  3. 2단 방어의 순서가 반대였음 — 보상 레코드 INSERT와 PG 취소 호출과 결과 기록이 전부 한 트랜잭션이었음(같은 클래스 자기호출이라 트랜잭션이 하나로 합쳐짐). 그런데 이 경로에 진입하는 조건이 DB 후처리 실패라, 원인이 DB 장애면 INSERT부터 실패해 1단이 무너지면 2단이 읽을 레코드도 함께 사라짐 — 채무는 있는데 장부가 없는 상태임. Saga 보상의 기본은 "의도 기록을 커밋한 뒤 실행"이므로, 레코드 기록을 REQUIRES_NEW로 떼어 먼저 커밋시키고 실행을 그 뒤로 둠
  4. 재시도 배치도 트랜잭션 없이 돌고 있었음 — 배치가 실행 메서드를 자기호출해 @Transactional이 애초에 적용되지 않았음. 프록시를 안 타면 애너테이션은 주석과 같음. 프록시 경유로 바꾸고, 테스트가 "프록시를 통해 호출했는지"를 직접 고정하도록 함 — 결과만 보는 테스트로는 이 회귀를 잡을 수 없기 때문
  5. 보상 대상은 두 갈래임 — Redis 선점분 복원(즉시·멱등)과 PG 취소(재시도 대상). 선점 복원을 먼저 두는 이유는 실패해도 재고 과소 계상이라는 안전한 방향에 그치는 반면, PG 취소 지연은 사용자 금전에 직결되기 때문. 두 보상은 독립 멱등이라 부분 성공이 나도 각각 재시도로 수렴함
  6. 보상 레코드는 4개 상태의 전이표로 관리 — PENDING · FAILED에서만 다음으로 갈 수 있고 SUCCEEDED · GIVEN_UP은 종단임. 원래는 상태 기록 메서드가 현재 상태를 보지 않고 무조건 덮어써서 "취소 성공 후 다시 재시도" 같은 경로가 열려 있었고, 조회 쿼리의 상태 조건에만 의존하면 새 호출부가 생기는 순간 뚫림. 그래서 전이표를 엔티티 안에 두어 거부되게 함. 이때 순서도 바꿨는데, 전이가 거부되면 재시도 횟수도 오르지 않아야 하므로 상태를 먼저 판정하고 카운트를 나중에 올림. 상태를 더 늘리지 않은 것은 의도적임 — 컬럼과 조회 쿼리까지 바뀌는데 4개로도 비정상 경로 차단은 그대로 달성되기 때문
  7. 승인 경로 멱등성은 내부 결제 키 선조회와 외부 PG Idempotency-Key 헤더의 2단계 — 다만 두 단계는 대등하지 않음. 선조회는 트랜잭션 없는 읽기라 동시 요청 둘이 함께 통과할 수 있어 정합성 보증이 아니라 조기 반환 최적화이고, 실제로 이중 결제를 막는 것은 PG의 멱등키와 결제 상태 머신임(두 번째 요청은 상태 전이에서 막혀 롤백됨). PG가 발급한 결제 키가 재시도 사이에 변하지 않는 불변 값이라는 점이 그 보증의 근거임
  8. 보상(취소) 경로에도 승인 경로와 같은 기준을 세웠음 — 멱등키가 만족해야 하는 성질을 ① 동일 의도는 동일 키 ② 다른 의도는 다른 키 ③ 프로세스 재시작에도 살아남을 것 세 가지로 정리하고, 보상 레코드의 식별자처럼 재시도 간 불변인 값을 키로 삼는 것을 기준으로 잡았음. 재시도 횟수처럼 시도마다 변하는 값이 키에 섞이면 첫 번째 성질이 깨져 "상대는 취소를 처리했는데 응답만 타임아웃된" 경우를 새 요청으로 오인하게 되고, 그러면 멱등키가 목적을 잃음
  9. 재시도 한도와 백오프 간격은 PG 멱등성 윈도우를 상한으로 두고 정해야 하는 값임 — 다만 그 상한값을 확인하지 못했으므로 "윈도우 안에 든다"는 주장은 하지 않음. 게다가 백오프는 실패 시점 기준이고 배치가 30초 주기로 줍기 때문에 실제 경과는 항상 크며, 총합 30분은 상한이 아니라 하한임 — 같은 키를 다시 보내도 새 요청으로 취급되는 시점을 넘기면 키가 무의미해지므로, 재시도 한도와 백오프 간격은 이 윈도우를 상한으로 두고 정한 값임
  10. Resilience4j 서킷브레이커로 실패율 50% 초과 시 30초 OPEN, HALF-OPEN 단계적 복구를 적용해 PG 장애가 다른 요청까지 지연시키는 Cascading Failure를 방지 — 단, 서킷이 승인 경로에만 붙어 있었고 취소 호출은 무보호였음. PG 전면 장애 구간에서 보상 취소가 매번 타임아웃까지 스레드를 붙잡아 보상 배치 자체가 느려지는 구조였음
  11. 취소에도 서킷을 붙이되 승인과 같은 회로에 물리지 않고 전용 회로로 분리함 — 같은 회로면 양방향 모두 나쁨: 보상 취소 실패가 회로를 열면 정상 결제까지 막히고, 반대로 승인 장애로 열린 회로가 취소를 fast-fail시키면 채무가 쌓이는 동안 아무 시도도 못 함. 하나의 외부 시스템이라도 실패의 의미가 다른 호출은 회로를 나눠야 한다는 것이 이 판단의 요지임

결과

  • 보상 경로가 실패해도 장부는 남는 구조가 됨 — 의도 기록을 먼저 커밋하므로 실행이 무너져도 배치가 주울 대상이 남고, 상태 전이표가 종단 상태를 지켜 재시도가 성공 건을 덮지 않음. 이전 판본은 이 두 가지가 없는 상태에서 "2단 방어"를 주장하고 있었음
  • 외부 PG 장애(5s 지연 설정 + 500 주입) 시 서킷브레이커 fast-fail 응답 평균 632.9ms 통제 실험, 장애 구간 호출의 97.8%(667/682)를 PG 미도달로 차단 — 이 비율은 서킷이 OPEN인 시간 비율에 전적으로 의존하므로 실패율 50%를 넘기는 주입 조건에서의 값임. 이전 판본의 "5.6s → 0.6s(약 9배)"는 삭제함: 서킷 off 런의 산출물이 저장소에 없어 before 값을 뒷받침할 수 없고, 5.6s는 같은 런의 최댓값과 소수점까지 일치해 대조군으로 쓸 수 없었음
  • 서킷브레이커와 보상 재시도의 값이 서로를 고려해 정해졌음 — 취소 전용 회로가 OPEN인 구간에는 취소도 fast-fail되지만, 첫 백오프 2분이 OPEN 30초를 충분히 넘기므로 2회차부터 정상 복구 경로에 진입함. 즉 즉시 시도 1회는 서킷이 닫혀 있는 일반 실패용이고, PG 전면 장애에서는 2회차가 실질 첫 시도임. 이 계산은 취소에 회로를 붙인 뒤에야 성립함 — 이전에는 존재하지 않는 메커니즘에 대한 계산이었음
  • fast-fail 응답이 0.6초 걸리는 원인을 재고 선점 해제·실패 기록 비용으로 메트릭 분리해 확인, 이후 결제 이벤트 Outbox와 재시도 포기(GIVEN_UP) 건 전용 DLQ 이관을 추가 도입

남은 한계

  • 이 구조의 비용은 승인 후 취소가 실제로 발생한다는 것이고, 부하에서 로그 파일당 80~111건 관측됨 대리 부하. 차감을 승인 이전으로 옮기면 이 왕복이 사라지지만 PG 실패 시 재고를 되돌리는 반대 방향 보상이 생기므로, 어느 쪽 보상을 감당할지의 선택 문제로 정리함
  • 백오프 총합 30분이 PG 멱등성 윈도우 안에 든다는 것은 확인했으나, 윈도우 상한값 자체를 문서에 못 박지 못함 — PG 정책 변경 시 재시도 한도를 다시 계산해야 하는 의존이 남아 있음
  • PG 승인 성공 직후 프로세스가 죽는 창은 여전히 열려 있음 — 승인은 됐는데 보상 코드가 실행되지 않으면 레코드도 없고 결제도 실패로 기록되지 않아 배치가 주울 대상이 아무것도 없음. 성공 경로 Outbox는 이 상태를 구제하지 못하고, 진짜 해법은 승인 호출 이전에 의도를 커밋하는 것(pre-write log)인데 아직 없음
  • 보상 배치에 배타 실행 장치가 없음 — 두 인스턴스에서 동시에 돌면 같은 건을 두 번 집어 재시도 횟수가 어긋나고 GIVEN_UP이 앞당겨짐. 취소 자체는 멱등키로 PG 쪽에서 흡수되지만 카운트 정합은 보장되지 않음
  • 자동 복구율(카오스 테스트 98.7%) 수치는 산출물이 저장소에 없어 이번 정산에서 제외함 — 재현 절차와 raw 파일을 남기는 조건으로 다시 측정해야 복원할 수 있음

4. 쿠폰 자동 비활성화의 폴링 지연을 Kafka Streams StateStore + Punctuator로 제거

전체적인 아키텍처

폴링 스캔 vs StateStore + Punctuator 지연 비교

문제 원인

  • 이 절은 자원 경합이 아니라 지연 스케줄링 문제임 — 동시에 하나의 자원을 다투는 구조가 아니라, 예약된 시각에 정확히 한 번 실행하는 것이 요구사항이라 앞의 두 절과는 다른 축의 해법이 필요함
  • 비교 대상인 폴링 방식은 저장소에 커밋된 구현이 아니라 설계 단계에서 놓고 계산한 대안임 도출 — @Scheduled(fixedDelay=10s)로 전체 스캔 후 인메모리 TaskScheduler에 지연 실행을 등록하는 형태이고, 폴링 주기 10초 + 스캔 2초로 최대 지연 약 12초가 나옴. "이전 버전을 개선했다"가 아니라 "두 설계를 비교해 하나를 골랐다"가 정확한 서술이므로 그렇게 씀
  • 그 방식의 문제는 둘임 — ① 매번 전체를 훑는 스캔이라 대상이 늘수록 비용이 선형 증가하고, ② 서버 재시작 시 인메모리 스케줄러 등록분이 통째로 사라져 도래할 쿠폰이 비활성화되지 않음(다음 스캔이 다시 주워야 복구되므로 유실이 지연으로 나타남). 어느 건수에서 스캔 2초가 나오는지는 근거가 없으므로, 도구 선택의 근거를 규모가 아니라 부하의 이동 방향(DB 밖으로)에 두었음

해결 과정

  1. 단순 주기 단축(1초 폴링 + scheduled_at 인덱스)을 먼저 검토함. 이 방식으로도 조회 복잡도는 O(log N + M)으로 같아지고 지연도 같게 만들 수 있음. 도입하지 않은 이유는 둘임 — ① 주기를 10초에서 1초로 줄이면 스캔 빈도가 10배가 되어 DB가 스케줄링 부하를 그대로 받음 ② 처리 인스턴스를 늘리면 같은 쿠폰을 중복 실행하지 않도록 별도 조율(락 또는 샤딩)을 설계해야 함. StateStore는 조회를 DB 밖으로 빼고 파티션 소유권이 정상 상태에서 중복 실행을 배타적으로 막아 이 둘을 동시에 해결함 — 다만 리밸런싱 구간까지 막아 주지는 않으므로 "구조적으로 불가능"이라고는 쓰지 않음(아래 한계)
  2. Kafka Streams Processor API + StateStore를 도입해 지연 처리 토폴로지를 구성하고, 실행 예정 시각(초 단위)을 키로·같은 초에 도래하는 이벤트 목록을 값으로 하는 영구 StateStore에 적재하도록 바꿨음 — 동일 시각 이벤트가 여러 건이어도 목록에 누적돼 유실되지 않음
  3. 이벤트 적재(발급 시점의 예약 등록)와 실제 비활성화 트리거(예약 시각 도래 시 Punctuator 실행)의 시점을 분리했고, 새 이벤트 유입과 무관하게 항상 스캔되도록 punctuate 스케줄을 WALL_CLOCK_TIME 기준으로 등록
  4. Punctuator가 1초 주기로 Range Query(O(log N + M))만 수행해 "전체 스캔"을 "도래한 것만 조회"로 전환
  5. exactly_once_v2를 적용하되 그것이 덮는 범위를 정확히 한정함 — EOS의 트랜잭션 경계는 입력 오프셋 커밋 · StateStore changelog · 출력 토픽까지이고, 쿠폰 비활성화는 DB 쓰기라 이 경계 밖임. 따라서 "출력 후 커밋 전 장애 → 재처리"에서 비활성화가 두 번 실행될 수 있음. 비활성화는 is_active = false를 쓰는 연산이라 몇 번을 실행해도 결과가 같아 실효 멱등이지만, 여기까지가 정확한 범위임 — UPDATE에 WHERE is_active = true 같은 조건이 없어 "이미 비활성이었다"를 감지하지 못하므로 재처리가 몇 번 일어났는지 관측할 수 없음. 조건 한 줄이면 관측까지 되는데 아직 넣지 않았음
  6. 실패 이벤트는 전용 DLQ 토픽과 별도 Consumer로 분리하고, Prometheus + Micrometer로 consumer lag·throughput·StateStore 크기를 노출해 정상 파이프라인에 영향 없이 관측하도록 함
  7. 처음에는 구 Transformer 인터페이스로 구현했고 이후 신 Processor API로 이관함 — 구 API는 Kafka Streams 3.3에서 deprecated, 4.0에서 제거라 지금은 컴파일되지만 다음 메이저에서 깨짐. 이관에서 바꾼 것은 클래스명 하나뿐이고 스토어명·값 타입·이벤트 타입은 전부 유지함 — 스토어명을 바꾸면 changelog 토픽명과 RocksDB 디렉터리가 달라져 대기 중이던 지연 이벤트가 통째로 유실되기 때문. 동작 동일성은 TopologyTestDriver로 이관 전 베이스라인을 먼저 잡고 이관 후 같은 테스트가 통과하는지로 고정함(브로커 없이 도는 테스트라 싸게 잡을 수 있음)

// 스토어명은 신 API 이관 때도 바꾸지 않았다 — 바꾸면 changelog 토픽명과 RocksDB 디렉터리가
// 달라져 대기 중이던 지연 이벤트가 통째로 유실된다
public class CouponDelayProcessor implements Processor<String, CouponDelayEvent, String, CouponDelayEvent> {

    private final String stateStoreName;
    private ProcessorContext<String, CouponDelayEvent> context;
    // Key = 실행 예정 시각(초 단위), Value = 그 초에 실행할 이벤트 목록
    private KeyValueStore<Long, CouponDelayEventListWrapper> stateStore;

    @Override
    public void init(ProcessorContext<String, CouponDelayEvent> context) {
        this.context = context;
        this.stateStore = context.getStateStore(stateStoreName);
        // WALL_CLOCK 을 쓰는 이유는 STREAM_TIME 이 신규 레코드 없이는 전진하지 않아,
        // 유입이 멈춘 구간에서 대기 중인 쿠폰이 영원히 비활성화되지 않기 때문이다
        this.context.schedule(Duration.ofSeconds(1), PunctuationType.WALL_CLOCK_TIME,
                              this::checkStoreAndForward);
    }

    @Override
    public void process(Record<String, CouponDelayEvent> record) {
        CouponDelayEvent event = record.value();
        if (event == null || event.getDelayMillis() == null || event.getDelayMillis() <= 0) {
            log.warn("잘못된 지연 이벤트 수신 (무시): {}", event);   // ← DLQ 로 가지 않는다 (한계 참조)
            return;
        }
        // 실행 예정 시각을 '초' 로 그룹화한다. 밀리초로 두면 키가 과도하게 늘어난다
        long executionSecond = (context.currentSystemTimeMs() + event.getDelayMillis()) / 1000;

        CouponDelayEventListWrapper wrapper = stateStore.get(executionSecond);
        if (wrapper == null) wrapper = new CouponDelayEventListWrapper(new ArrayList<>());
        wrapper.getEvents().add(event);   // 같은 초의 이벤트는 누적한다 — 덮어쓰면 유실된다
        stateStore.put(executionSecond, wrapper);
    }

    // 도래한 초만 range 로 훑어 forward 하고 즉시 지운다. 지우지 않으면 다음 초에 중복 처리된다
    private void checkStoreAndForward(long wallClockTime) {
        long currentSecond = wallClockTime / 1000;
        try (KeyValueIterator<Long, CouponDelayEventListWrapper> iter =
                     stateStore.range(0L, currentSecond)) {
            while (iter.hasNext()) {
                KeyValue<Long, CouponDelayEventListWrapper> entry = iter.next();
                for (CouponDelayEvent event : entry.value.getEvents()) {
                    // 출력 키는 '초' 가 아니라 couponId 다 — 그래야 하류에서도
                    // 쿠폰당 파티션이 유지돼 §1 의 "쿠폰당 판정자 1명" 이 깨지지 않는다
                    context.forward(new Record<>(String.valueOf(event.getCouponId()),
                                                 event, wallClockTime));
                }
                stateStore.delete(entry.key);
            }
        }
    }
}

결과

  • 지연 단축의 직접 원인은 주기 단축(10s → 1s)이며, Kafka Streams를 택한 이유는 그 주기를 DB 부하 증가 없이 감당하기 위해서임 — 폴링을 1초로 줄이면 스캔 빈도가 10배가 되지만 StateStore 조회는 DB 밖에서 끝남. 즉 이 절의 성과는 "더 빠른 도구"가 아니라 "같은 속도를 DB 부하 없이, 그리고 인스턴스를 늘려도 중복 실행 없이"임
  • 처리 지연 최악값 기준 1.1s — 두 값의 성격이 다르므로 나란히 읽을 때 주의가 필요함. 12s는 채택하지 않은 폴링 대안의 설정에서 도출한 값 도출(주기 10s + 스캔 2s)으로 실제로 돌려 본 구현이 아니고, 1.1s는 실측 최악값 실측(이벤트 발행~비활성 전환 시각 차 직접 측정)으로 punctuate 주기 1s + 처리시간이라는 이론 최악값에 수렴함. 즉 이 비교는 측정 대 측정이 아니라 설계 계산 대 측정임
  • 이벤트 상태를 changelog 기반 영구 StateStore에 저장해 서버 재시작 후에도 대기 작업이 남음 — 기존 인메모리 스케줄러에서 재시작마다 사라지던 등록분이 유지됨
  • 실패 이벤트를 DLQ로 격리해 정상 파이프라인 영향 없이 처리

남은 한계

  • 영구 StateStore의 대가는 재시작·리밸런싱 시 changelog 복원 지연임 — standby replica를 두지 않아 복원이 끝날 때까지 해당 파티션의 punctuate가 멈춤. 현재 규모에서는 수용 가능하다고 판단했고, 복원 시간이 SLA를 넘기면 standby replica 도입이 다음 단계임
  • 이벤트가 절대 시각이 아니라 상대 지연(delayMillis)만 들고 다님 — 실행 시각을 처리 시점의 시계 + 상대 지연으로 계산하므로, 같은 레코드가 다시 처리되면(EOS abort 후 재처리, 리밸런싱으로 태스크 이동 후 미커밋 오프셋 재소비) 타이머가 리셋되어 만료가 조용히 뒤로 밀림. "재시작해도 대기 작업이 남는다"는 이미 StateStore에 들어간 건에 한정되고, 입력 토픽에서 재소비되는 건은 해당하지 않음. 이벤트에 절대 시각을 실으면 사라지는 문제임
  • delayMillis <= 0인 이벤트를 경고 로그만 남기고 버림 — DLQ로도 가지 않음. DLQ는 출력 토픽을 구독하는 Consumer 실패에만 걸려 있고 Streams 단계의 드롭은 대상이 아님. 이미 만료 시각이 지난 쿠폰(백필, 클럭 스큐, 장시간 중단 후 재개)이 이 경로로 영원히 비활성화되지 않을 수 있음
  • WALL_CLOCK_TIME을 고른 대가는 재처리 시 결정론이 깨지는 것 — 같은 입력이 같은 시점에 forward된다는 보장이 없어 exactly_once_v2의 보장과 궁합이 좋지 않음. 새 이벤트가 없어도 스캔이 돌아야 한다는 요구 때문에 STREAM_TIME을 쓸 수 없어 감수한 선택임
  • 리밸런싱 구간에는 이전 소유자의 punctuate와 새 소유자의 것이 겹칠 여지가 있음 — Streams의 fencing은 출력 토픽 쓰기를 막아 주지만 실제 부수효과인 DB UPDATE는 출력 토픽 하류에 있어 fencing 밖임. 중복 실행은 값이 같아 흡수되지만, 위의 no-op 조건 부재 때문에 일어났다는 사실 자체가 관측되지 않음

위치 발행-구독 흐름 — 인스턴스 경계를 넘는 SSE 전달
경로 정보 저장·조회·정리 흐름

문제 원인

  • 보호자가 사용자 위치를 실시간으로 확인해야 하는데, 클라이언트가 주기적으로 요청하는 폴링 방식은 불필요한 요청과 지연을 유발
  • 공간 축의 문제 — 서버가 여러 인스턴스로 확장되면 위치를 발행한 인스턴스와 보호자가 SSE로 연결된 인스턴스가 다를 수 있어, 단순 인메모리 브로드캐스트로는 위치가 전달되지 않았음
  • 시간 축의 문제 — 초기에는 내비게이션 경로도 위치와 동일하게 Pub/Sub으로만 전달했는데, Pub/Sub은 발행 시점의 구독자에게만 닿고 재생이 불가능해, 사용자가 안내를 시작한 시점에 보호자가 미접속이면 경로를 알 방법이 없었음
  • SSE는 응답이 끝나지 않는 장기 연결이라, 연결을 관리하는 구조 없이는 이탈·네트워크 단절 시 커넥션이 메모리에 계속 남는 문제가 있었음

해결 과정

  1. 보호자-사용자 관계(relationId)마다 SseEmitter를 발급하고 ConcurrentHashMap<relationId, SseEmitter>로 연결을 관리. 10분 타임아웃과 onCompletion/onTimeout/onError 콜백에서 맵의 연결을 제거해 끊어진 연결이 누적되지 않도록 함
  2. 공간 축 처방 — 위치가 갱신되면 Redis Pub/Sub 채널(location:{relationId})로 발행하고, 각 인스턴스가 이 채널을 구독해 자신에게 연결된 보호자에게만 전달하도록 구독 로직을 분리. 프로세스 로컬 맵만으로는 인스턴스 경계를 넘지 못한다는 것을 이 프로젝트에서 먼저 다뤘음
  3. 두 데이터에 다른 전달 방식을 적용한 기준 — 위치는 초 단위로 새 값이 도착하는 연속 스트림이라 놓친 값의 재생 가치가 없지만, 경로는 안내 시작 시 한 번 발생하는 이산 이벤트라 그 시점에 미접속이면 복구 경로가 없음. 이 성질 차이를 근거로 위치는 Pub/Sub에 그대로 두고 경로만 영속 저장으로 옮겼음
  4. 시간 축 처방 — 내비게이션 시작 시 출발지·도착지 좌표와 명칭을 location-stream:{relationId} Redis Stream에 XADD로 적재하고, 보호자가 접속·새로고침하면 XREVRANGE ... COUNT 1로 최신 경로를 즉시 조회. 목적지 도착 시 DEL로 정리
  5. String 대신 Stream을 택한 이유 — 요구만 보면 SET/GET으로도 충분함. Stream을 고른 것은 안내 1회 안에서 경로가 여러 번 갱신되기 때문임 — SET은 갱신마다 이전 값을 덮어써 "직전 경로로 되돌아갔는지"를 알 수 없지만, XADD는 안내가 끝날 때까지 갱신 이력이 순서대로 남음. 다만 도착 시 DEL로 지우므로 이 이력은 안내 세션 안에서만 유효하고 완료된 경로의 장기 보관은 목적이 아님 — 그래서 Consumer Group도 두지 않았음

결과

  • 서버 프로세스 경계와 무관하게 Pub/Sub을 매개로 위치가 전달되는 구조 확보 — 같은 문제를 AI 튜터링에서는 아직 풀지 못함(그쪽 SSE 전달 맵은 인스턴스 로컬임)
  • 발행 시점에 보호자가 미접속이었어도 접속 시점에 최신 경로를 조회할 수 있어, Pub/Sub의 시점 의존성을 데이터 성질에 따라 선택적으로 보완
  • 연결 생명주기 콜백으로 끊어진 SSE 커넥션이 맵에 남지 않도록 하고, 재연결 시 기존 연결을 교체해 같은 관계에 중복 커넥션이 쌓이지 않게 함

남은 한계

  • 다중 인스턴스 실기동으로 검증하지 못함 — 구조상 성립하나 2대 이상 띄워 확인한 적이 없어 이 항목은 설계 주장에 머묾. 다만 이 주제 자체는 AI 튜터링이 아직 못 따라온 축임 — 그쪽 SSE 전달 맵은 여전히 인스턴스 로컬임
  • 느린 소비자 대비가 없음 — Redis 리스너 스레드에서 SseEmitter.send()를 직접 호출하는 구조라, 느린 보호자 클라이언트 하나가 같은 인스턴스의 다른 관계 전달까지 지연시킬 수 있음. 별도 전송 큐는 두지 않았고 10분 타임아웃과 재연결로 흡수되는 범위로 한정함. 관계당 커넥션 1개 제한 때문에 보호자 다중 기기도 지원하지 않음

문제 원인

  • 프론트엔드(Next.js)와 백엔드(Spring Boot)를 하나의 도메인에서 서비스해야 함 — 별도 도메인으로 나누면 CORS와 쿠키 도메인 불일치를 매번 다뤄야 해서, 요청 경로로 두 서버를 가르는 구성이 필요함

  • DB·Redis·백엔드·프론트엔드·Nginx로 구성 요소가 다섯이라 팀원 각자의 로컬에서 동일하게 재현하기 어려웠고, "제 환경에서는 됩니다"가 반복됨

해결 과정

  1. Nginx에서 /api/v1/ 경로는 백엔드(포트 8080, context-path /api)로, 그 외 경로는 프론트엔드(포트 3000)로 라우팅을 분리
  2. PostgreSQL·Redis·Backend·Frontend·Nginx를 하나의 docker-compose로 묶어 팀원 누구나 동일한 인프라 구성을 재현할 수 있도록 함
  3. Nginx에서 TLS 종료(Let's Encrypt)와 HTTP→HTTPS 리다이렉트, 보안 헤더를 함께 처리해 각 애플리케이션 서버가 인증서를 직접 다루지 않도록 책임을 분리 — 인증서 갱신이 애플리케이션 배포와 무관해짐
  4. GitHub Actions로 prod 브랜치 푸시 시 EC2에 SSH로 접속해 최신 코드를 반영하고 컨테이너를 재기동하는 배포 파이프라인을 구성
  5. 팀장으로서 인증 무효화 정책도 함께 설계함 — 로그아웃 시 blacklist:access:{token}에 토큰 잔여 수명만큼만 TTL을 걸어 만료와 동시에 자동 정리되게 하고, 비밀번호 변경·전체 로그아웃에는 blacklist:user:{id}:version 카운터를 올려 그 시점 이전 발급 Access Token을 일괄 무효화. 발급 시 토큰 claim에 version을 실어 필터가 저장된 값과 비교하는 방식이고, version 키 TTL(15분)을 Access Token 수명과 맞춰 키가 먼저 만료돼 옛 토큰이 되살아나는 창을 막았음

결과

  • 도메인 하나로 프론트·백엔드를 함께 서비스하면서도 각 서버의 역할이 Nginx 설정으로 분리되는 구조 확보, CORS·쿠키 도메인 문제를 구성 단계에서 제거
  • docker-compose 기반 구성으로 로컬·운영 환경 차이를 줄이고, 배포 자동화로 수동 배포 절차 제거
  • 무상태 JWT에 즉시 무효화를 붙이되, 개별 토큰과 사용자 전체라는 두 무효화 단위를 하나의 검증 경로로 합쳐 인증 필터가 매 요청에 두 키를 함께 조회하도록 통합
  • 여기서 드러난 키 설계의 한계가 다음 프로젝트의 설계를 바꿨음 — Refresh Token을 refresh_token:{token}으로 저장한 탓에 사용자 단위 열거·폐기가 불가능했고, "전체 로그아웃"의 실제 범위가 Access Token까지였음. AI 튜터링에서는 refreshToken:{userId} 기준으로 잡고 블랙리스트 키도 토큰 전문이 아닌 jti로 옮겨 키 설계 쪽 제약은 없앴음. 다만 같이 잃은 것이 있음 — 휠 파인더에 있던 blacklist:user:{id}:version(사용자 단위 access 일괄 무효화)을 함께 가져오지 않아 키 설계는 나아졌으나 폐기 단위는 후퇴함
  • 무상태의 이점을 내주고 즉시 무효화를 산 교환이라는 것도 이때 확인함 — 매 요청 Redis 조회 2회가 붙고 인증 경로가 Redis 가용성에 종속됨. 이 프로젝트에서는 Redis 장애 시의 통과·차단 정책을 정하지 못한 채 넘어갔고, AI 튜터링에서 fail-close(장애 시 인증 거부)로 결정해 근거를 코드 주석에 남겼음 — fail-open은 장애 지속 시간만큼 폐기된 토큰을 되살리기 때문

남은 한계

  • 재기동 방식이라 배포 구간에 짧은 중단이 있고 롤백은 수동 재배포에 의존함. 이미지 태깅·레지스트리와 무중단 배포(블루-그린)는 도입하지 못했고 후속 과제로 남음
