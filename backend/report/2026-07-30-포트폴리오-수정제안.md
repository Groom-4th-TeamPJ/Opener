## 1. 반드시 고쳐야 할 것 — `tech` 배열

### 현재
```python
"tech": ["Spring", "Spring AI", "Spring WebFlux", "RAG",
         "Redis Cluster", "RabbitMQ", "Resilience4j"],
```

### 문제
`"Spring WebFlux"` 가 **사실과 다르다.**

| 근거 | 위치 |
|---|---|
| `spring-boot-starter-web` 을 함께 의존 → 서블릿 스택이 이긴다 | `build.gradle:33` |
| `server.servlet.context-path: /api` | `application.yml` |
| `server.tomcat.mbeanregistry.enabled` | `application.yml` |
| `spring.mvc.async.request-timeout` 으로 SSE 타임아웃 제어 | `application.yml` |

WebFlux 런타임(Netty 서버)이 아니라, **MVC 의 `ReactiveTypeHandler` 가 `Flux` 반환을 async 요청으로 처리**하는 구조다.

**"WebFlux 쓰셨네요, Netty 이벤트 루프 몇 개로 도나요?" 한 마디에 무너진다.**

### 제안
```python
"tech": ["Spring", "Spring AI", "Project Reactor", "SSE", "RAG",
         "Virtual Thread", "Redis Cluster", "RabbitMQ", "Resilience4j"],
```

`Spring WebFlux` → `Project Reactor` + `SSE` 로 교체하고 `Virtual Thread` 를 명시한다.
**이게 오히려 강하다** — "서블릿 스택 위에서 Reactor 타입으로 스트리밍하고, 블로킹 구간은 Virtual Thread 로 흡수한
하이브리드"는 버즈워드보다 설명하기 어려운 주제이고, 왜 전면 WebFlux 로 안 갔는지(JPA·Spring Security 전면 재작성)를
트레이드오프로 말할 수 있다.

## 2. STAR 1 — 문구 정정 + 이번 리팩토링 반영

### 2-1. `how` 첫 항목

**현재**
> 컨트롤러가 `Flux<ServerSentEvent>` 를 직접 반환하고 동기 대기 `blockLast()` 를 제거해 …

**제안** (앞부분에 스택 사실을 명시)
> 서블릿 스택을 유지한 채 컨트롤러가 `Flux<ServerSentEvent>` 를 반환하도록 바꿔
> MVC 의 async 요청 처리 경로를 타게 하고, 동기 대기 `blockLast()` 를 제거해 …

전면 WebFlux 전환을 **하지 않기로 한 판단**이 드러나야 한다.

### 2-2. `how` 에 신규 항목 추가 — 이번에 실제로 한 일

> LLM 응답을 읽는 이벤트 루프에서 Redis 저장·상태 전이·JDBC 트랜잭션이 실행되던 것을
> `publishOn(boundedElastic)` 으로 분리 — 논블로킹 스트리밍이 콜백의 블로킹으로 상쇄되던 구조를 제거

**이게 없으면 STAR 1 의 핵심 주장("스레드 점유와 연결 수명 분리")이 코드와 충돌한다.**
`ChatServiceImpl` 의 `doOnComplete` 안에서 JDBC 트랜잭션이 돌고 있었다.

### 2-3. `change` 에 추가

> 오프로딩 후 콜백 스레드명을 로깅해 실제로 이벤트 루프를 벗어났는지 확인하는 계측을 남김
> — "논블로킹으로 바꿨다"는 주장을 코드가 아니라 런타임으로 확인할 수 있게 함

> ⚠️ 단, 스레드명 실측은 **인프라 기동 후에만 확인 가능**하다. 아직 실행하지 않았으므로
> 위 문구는 "계측을 심었다"까지만 주장하고 "확인했다"로 쓰지 마라.

## 3. STAR 3 — "비정상 전이 차단" 주장 보강

### 현재 `result`
> 비정상 상태 전이(스트리밍 중 재전송, 연결 전 메시지 전송 등)를 구조적으로 차단

### 문제였던 점
LLM 이 **빈 응답**을 주면 `STREAM_START` 가 발화되지 않아 상태가 `PROCESSING` 에 머무는데,
`doOnComplete` 가 무조건 `STREAM_COMPLETE` 를 보내 거부당하고 **세션이 고착**됐다.
다음 요청은 전부 `SESSION_EXPIRED` 로 막힌다. 즉 "차단"은 됐지만 **회수**가 안 됐다.

### 제안 — `change` 에 추가
> 상태 머신이 잘못된 전이를 거부하는 것만으로는 부족했다 — 빈 응답 스트림에서
> `STREAM_START` 없이 `STREAM_COMPLETE` 가 거부되며 세션이 `PROCESSING` 에 고착되는 경로를 발견,
> 첫 청크 발생 여부를 확인해 `STREAM_ERROR` 로 상태를 회수하도록 보완.
> 전이 거부를 조용히 삼키던 `sendEvent` 반환값도 전 지점에서 검사하도록 정리

**"차단"과 "회수"는 다르다**는 걸 아는 게 상태 머신을 실제로 운영해본 근거가 된다.

## 6. 신규 STAR 제안 (선택) — 조용히 죽어 있던 설정 6곳

STAR 를 하나 더 늘릴지는 분량 문제라 **선택 사항**이다. 넣는다면 핵심은:

> `application*.yml` 3개 파일에서 6곳이 한 단계 깊게 들여써져 엉뚱한 부모 키 아래로 들어가 있었다.
> Spring Boot 는 모르는 프로퍼티를 조용히 무시하므로 **컴파일도 부팅 로그도 경고를 주지 않는다.**
> 그 결과 문서에 적힌 "SSE 30분 타임아웃", "dev 1분 계정 잠금", prod 로그 레벨·actuator 노출 축소가
> 전부 미적용 상태였다. 교정 후 `/actuator/env` 로 실제 바인딩을 확인하는 절차를 도입했다.

**분량이 부담되면 STAR 5(인프라·모니터링)의 `change` 에 흡수시켜라** — 관측 체계 이야기와 자연스럽게 이어진다.

## 7. 여전히 주장하면 안 되는 것

| 주장 | 이유 |
|---|---|
| "수평 확장 가능" | SSE Sink·상태 머신이 인메모리라 **인스턴스 1대가 한계**. `2026-07-30-확장-한계와-설계.md` 참조 |
| "prod 환경 운영" | prod 프로필은 `app.rag.enabled`·Redis 클러스터 노드·`jwt.*` 미정의로 **기동조차 안 된다**. 실배포는 dev 프로필 |
| 이번 리팩토링의 성능 수치 | LLM 키 만료·인프라 미기동으로 **측정하지 않았다** |
| "테스트 커버리지 N%" | 이번에 추가한 것은 핵심 경로 단위 테스트이지 커버리지 목표 달성이 아니다 |

면접에서 수평 확장을 물으면 **"지금은 단일 인스턴스 한계이고, Redis Pub/Sub 라우팅과 sticky session 중
트레이드오프를 정리해 뒀다"** 가 정직하면서 강한 답이다. 한계를 아는 것도 평가 대상이다.
