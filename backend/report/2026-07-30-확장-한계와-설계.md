# SSE 채팅 수평 확장 한계와 설계안

- **작성일**: 2026-07-30
- **근거**: `2026-07-30-백엔드-분석.md` §5, `2026-07-30-리팩토링-계획.md` §4-H
- **범위**: 현 구조의 한계 진단 + 설계안 제시. **코드 변경 없음**

> 이 문서는 "무엇을 했다"가 아니라 **"무엇을 안 했고 왜 안 했는지"** 를 기록한다.
> 아래 설계안은 어느 것도 구현되지 않았다.

---

## 1. 한 줄 요약

세션 **데이터**는 Redis 클러스터에 있지만, SSE **전달 경로**(Sink)와 **세션 상태**(StateMachine)는
JVM 인메모리 `ConcurrentHashMap` 이라 백엔드는 **인스턴스 1대까지만 정상 동작**한다.

---

## 2. 현재 구조 — 무엇이 어디에 있나

| 항목 | 저장 위치 | 근거 |
|---|---|---|
| 세션 소유자(`userId`), 메시지 목록 | **Redis 클러스터** (공유) | `ChatRedisServiceImpl.java` — `chat:{sessionId}:session`, `chat:{sessionId}:messages` |
| 영속 대화 기록 | **PostgreSQL** (공유) | `ChatMessageConsumer.java:48` |
| **SSE 전달 경로 (Sink)** | **JVM 힙** (인스턴스 로컬) | `ChatServiceImpl.java:82` — `ConcurrentHashMap<Long, Sinks.Many<ServerSentEvent<String>>> sinks` |
| **세션 상태 머신** | **JVM 힙** (인스턴스 로컬) | `ChatSessionStateMachineService.java:27` — `ConcurrentHashMap<Long, StateMachine<...>> machines` |

즉 **"누구 세션인가"는 공유되는데 "어디로 흘려보낼 것인가"는 공유되지 않는다.**
`Sinks.Many` 는 구독 중인 HTTP 응답 스트림에 직접 물려 있는 객체라 직렬화해서 옮길 수 있는 값이 아니다.
이게 문제의 본질이다 — 데이터는 외부화됐지만 **연결 그 자체**는 외부화될 수 없다.

### 요청 두 개가 서로 다른 리소스를 만진다

```
GET  /api/chat/connect?sessionId=123   → sinks.put(123, sink)      (ChatServiceImpl.java:169)
POST /api/chat/message                 → sinks.containsKey(123) 확인 (ChatServiceImpl.java:250)
                                       → emitEvent 가 sinks.get(123) 으로 청크 발행 (ChatServiceImpl.java:545)
```

두 요청이 **같은 JVM 에 도달해야만** 성립한다.

## 3. 증상 — 2대 이상 띄우면 어떻게 깨지나

인스턴스 A, B 가 있고 로드밸런서가 라운드로빈이라고 하자.

1. 클라이언트가 `GET /api/chat/connect?sessionId=123` → **A** 로 라우팅
   → A 의 `sinks` 에 `123` 등록 (`ChatServiceImpl.java:169`), A 의 `machines` 에 머신 생성 (`ChatSessionStateMachineService.java:32`)
   → SSE 스트림은 A 와 클라이언트 사이에 열린 채 유지
2. 클라이언트가 `POST /api/chat/message` → **B** 로 라우팅
3. B 의 `sinks` 에는 `123` 이 없다 → `ChatServiceImpl.java:250-253` 에서 **`SESSION_EXPIRED`**
4. 설령 3번을 통과시켜도 B 의 `machines` 에 머신이 없어
   `ChatSessionStateMachineService.java:46-50` 이 다시 `SESSION_EXPIRED` 를 던진다

**증상의 성격**: 조용한 열화가 아니라 **명시적 실패**다. 사용자에겐 "세션이 만료되었습니다"로 보이고,
같은 세션에서 새로고침 없이 계속 실패한다. 라운드로빈이면 요청의 절반이 아니라
**연결한 인스턴스가 아닌 곳으로 간 요청 전부**가 깨진다.

**지금은 드러나지 않는다.** `nginx/nginx.dev.conf:54-56` 의 upstream 이 `backend-dev:8080` 단일 서버라
모든 요청이 같은 JVM 으로 간다. 즉 이 결함은 **인스턴스를 늘리는 순간 처음 나타난다.**

## 4. 상태 머신도 같은 문제다

`ChatSessionStateMachineService` 는 Sink 와 **똑같은 형태의 인스턴스 로컬 상태**를 갖는다.
다만 성격이 조금 다르다.

| | Sink (`sinks`) | 상태 머신 (`machines`) |
|---|---|---|
| 왜 로컬인가 | **직렬화 불가능** — 열린 HTTP 응답에 물린 객체 | **직렬화 가능** — 현재 상태는 enum 하나 |
| 외부화 난이도 | 높음. Sink 자체를 옮길 수 없어 **메시지를 옮겨야** 함 | 상대적으로 낮음. 상태값을 Redis 에 두면 됨 |
| 정합성 위험 | 청크 순서·유실 | 동시 전이 시 경쟁 조건 (Redis Lua/WATCH 필요) |

`ChatSessionStateMachineService.java:31-39` 의 `computeIfAbsent` 는 **한 JVM 안에서만** 원자적이다.
2대로 늘리면 인스턴스마다 독립된 머신이 생겨 같은 세션에 대해 서로 다른 상태를 갖게 된다.

Sink 를 Pub/Sub 으로 해결하면(§5-A) 상태 머신은 **소유 인스턴스에서만 돌게 되므로 자동으로 함께 해결된다.**
sticky session 으로 우회하면(§5-B) 역시 같은 인스턴스로 고정되므로 함께 해결된다.
**둘 중 무엇을 택하든 상태 머신을 별도로 손댈 필요는 없다** — 단, 인스턴스가 죽으면 상태도 함께 사라진다는 점은 두 방식 모두 동일하다.

## 5. 확장 설계안

### A. Redis Pub/Sub 으로 청크를 소유 인스턴스에 라우팅

**아이디어**: Sink 는 계속 로컬에 두되, **청크를 소유 인스턴스로 배달**한다.

```
POST /chat/message → B 인스턴스
   B: LLM 스트리밍 수행
   B: 청크마다 PUBLISH chat:sse:{sessionId} <chunk>
        ↓ Redis
   A: SUBSCRIBE chat:sse:{sessionId} 로 수신
   A: 로컬 sinks.get(123).tryEmitNext(chunk)  ← 여기서만 실제 SSE 발행
```

구현 시 필요한 것:
- 각 인스턴스가 `connectSession` 시점에 해당 채널을 구독하고, `doOnCancel`(`ChatServiceImpl.java:181-186`)에서 구독 해제
- `POST /chat/message` 쪽의 존재 확인(`ChatServiceImpl.java:250`)을 로컬 Map 이 아니라
  **Redis 의 세션 활성 여부**로 바꿔야 함 (지금은 로컬 Map 이 사실상 "연결됐나"의 유일한 근거)
- 상태 머신 전이도 소유 인스턴스에서 수행하도록 이벤트를 같은 채널로 보내야 함

**트레이드오프 (정직하게)**

| 항목 | 내용 |
|---|---|
| 지연 | 청크마다 Redis 왕복이 추가된다. 토큰 단위 스트리밍이라 **청크 수만큼 배수로 붙는다**. 응답 하나에 수백 청크면 무시 못 할 크기 |
| 신뢰성 | Redis Pub/Sub 은 **fire-and-forget** 이다. 구독자가 순간적으로 없으면 그 청크는 그냥 사라진다. 재연결 구간에서 토큰이 조용히 유실될 수 있어, 보장이 필요하면 Streams(`XADD`/consumer group)로 올려야 하고 그러면 복잡도가 한 단계 더 올라간다 |
| 장애 모드 | Redis 가 새 SPOF 가 된다. 지금은 Redis 가 죽어도 "세션 초기화 실패"로 끝나지만, Pub/Sub 을 쓰면 **진행 중인 스트림 전부가 죽는다** |
| 순서 | 단일 채널이므로 순서는 보장되나, 인스턴스 간 재연결이 끼면 경계에서 순서 역전 여지가 생긴다 |
| 복잡도 | 구독 생명주기 관리(누수 시 채널이 계속 쌓임)가 새로 생긴다. 테스트도 Redis 를 띄워야 의미가 있다 |

---

### B. Sticky session 으로 우회

**아이디어**: 애초에 같은 클라이언트를 항상 같은 인스턴스로 보낸다. 코드 변경 0.

`nginx/nginx.dev.conf:54-56` 의 upstream 을 이렇게 바꾸는 수준이다.

```nginx
upstream backend {
    ip_hash;                    # 또는 hash $cookie_sessionid consistent;
    server backend-dev-1:8080;
    server backend-dev-2:8080;
}
```

**트레이드오프 (정직하게)**

| 항목 | 내용 |
|---|---|
| 재배포 | 롤링 배포로 인스턴스가 내려가면 **그 인스턴스에 붙어 있던 세션이 전부 유실**된다. `sinks` 도 `machines` 도 힙에 있으니 프로세스와 함께 사라진다. Redis 의 메시지 기록은 남지만 진행 중이던 스트림은 끊긴다 |
| 노드 이탈 | `ip_hash` 는 서버 목록이 바뀌면 해시가 재분배되어 **관계없는 세션까지 다른 인스턴스로 튄다**. `hash ... consistent` 를 쓰면 재분배 범위가 줄지만 0은 아니다 |
| 부하 분포 | IP 기준이라 NAT/모바일 캐리어 뒤의 다수 사용자가 한 인스턴스로 몰릴 수 있다 |
| 확장성 | 세션은 여전히 인스턴스에 묶여 있다. **한 인스턴스가 감당할 동시 연결 수가 곧 세션 상한**이며, 이 한계 자체는 사라지지 않는다 |
| 비용 | 거의 0. 인프라 설정 몇 줄 |

---

### 비교

| | A. Redis Pub/Sub | B. Sticky session |
|---|---|---|
| 코드 변경 | 큼 (`ChatServiceImpl` 전달 경로 재설계) | 없음 |
| 인프라 변경 | 없음 (Redis 이미 있음) | nginx upstream |
| 스트림 중 재배포 | 살아남게 만들 수 있음 (설계하기 나름) | 유실 |
| 새 장애 모드 | Redis Pub/Sub 유실·SPOF·구독 누수 | 부하 편중, 해시 재분배 |
| 지연 | 청크당 Redis 왕복 추가 | 변화 없음 |
| 진짜 해결인가 | 그렇다 | 아니다 — **유예**다 |

**권고**: 인스턴스를 늘려야 하는 시점이 오면 **B 를 먼저 적용**한다.
비용이 거의 0이고, "인스턴스가 2대가 됐다"는 사실만으로 서비스가 깨지는 상황은 막아준다.
A 는 **세션 유실이 실제로 문제가 됐을 때**(재배포 중 스트림 끊김 민원, 무중단 배포 요구) 착수한다.
처음부터 A 로 가면 지금 없는 장애 모드(Pub/Sub 유실, 구독 누수)를 미리 떠안는다.

## 6. 왜 지금 하지 않았나

1. **인스턴스가 1대다.** `nginx/nginx.dev.conf:54-56` 이 단일 upstream 이고,
   증설 계획이 정해진 바 없다. 없는 문제를 위해 코드를 복잡하게 만드는 셈이 된다
2. **장애 모드가 순증한다.** §5-A 표의 5개 항목은 지금 존재하지 않는 실패 유형이다.
   특히 Pub/Sub 유실은 **조용히 일어나고 재현이 어렵다** — 지금의 `SESSION_EXPIRED` 는
   최소한 시끄럽게 실패한다는 장점이 있다
3. **검증 수단이 없다.** chat 도메인 테스트가 0건이고(`2026-07-30-백엔드-분석.md` §6-5),
   OpenAI 키가 만료되어 실호출 검증도 불가능하다. 이 상태로 전달 경로를 재설계하면
   깨졌는지 알 방법이 없다. **테스트가 먼저다**
4. **한계가 문서화되어 있지 않았던 것이 진짜 위험이었다.** 코드만 보고는
   "Redis 에 세션이 있으니 스케일아웃되겠지"로 오해하기 쉽다. 그 오해를 없애는 것이
   이 문서의 1차 목적이다

## 7. 필요해지는 시점의 신호

아래 중 **하나라도** 관측되면 §5-B 를, 두 개 이상이면 §5-A 를 검토한다.

| 신호 | 관측 방법 | 임계 |
|---|---|---|
| 동시 SSE 연결 수 | `ChatServiceImpl` 이 이미 `sinks.size()` 를 로그에 남긴다 (`:176-177`, `:246-247`). 메트릭으로 승격 필요 | 인스턴스당 지속 500 이상 |
| 요청 스레드 풀 포화 | `application.yml:64-66` 의 `server.tomcat.mbeanregistry.enabled=true` 로 노출되는 `tomcat_threads_busy` | max 대비 70% 지속 |
| 힙 사용량 | Sink 버퍼(`onBackpressureBuffer`, `ChatServiceImpl.java:166`)는 상한이 없다. 느린 클라이언트가 많으면 힙을 먹는다 | 여유 30% 미만 |
| 인스턴스 증설 결정 | 조직 차원 결정. **코드보다 먼저 오는 신호다** | 증설이 논의되는 시점 |
| 무중단 배포 요구 | 배포 중 스트림 끊김이 민원으로 올라오는 시점 | — |

> 지금 당장 할 수 있는 저비용 준비는 **`sinks.size()` 를 `MeterRegistry` 게이지로 노출**하는 것이다.
> `ChatSessionStateMachineService.java:25` 가 이미 `MeterRegistry` 를 주입받고 있으니 자리는 있다.
> 이것도 이번 범위에서는 하지 않았다.

## 8. 이 문서가 주장하지 않는 것

- Pub/Sub 이나 sticky session 을 **도입했다고 주장하지 않는다.** 둘 다 미구현이다
- §5 의 설계안은 **설계 수준**이며 벤치마크나 PoC 로 검증된 바 없다
- §7 의 임계값은 **일반적 감각에 기반한 초안**이고, 이 서비스에서 실측한 값이 아니다
- 청크당 Redis 왕복 지연의 실제 크기는 측정하지 않았다
