# 채팅 세션 저장소의 읽기/쓰기 분리(CQRS) 실측

- 일자: 2026-08-13
- 대상: 포트폴리오 「4. 채팅 세션 저장소 설계」의 읽기 라우팅 분리 주장
- 목적: "읽기를 복제본으로 내보낸 것"이 실제로 어떤 이득을 주는지, 그 대가인 복제 지연은 얼마인지 수치화

## 1. 측정 환경

| 항목 | 값 |
|---|---|
| 저장소 | Redis 7-alpine Cluster · master 3(6380~6382) + replica 3(6383~6385) |
| 기동 | `docker compose -f docker-compose.local.yml up -d redis-cluster-init` |
| 대상 슬롯 | 해시태그 `{7}` → slot 1716 → master `redis-chat-1` / replica `redis-chat-5` |
| 부하 생성기 | 자체 RESP 클라이언트(파이썬 · 멀티프로세스), `python:3.12-alpine` 컨테이너를 `opener_local-network` 에 붙여 실행 |
| 구간 | 워밍업 2초 후 12초 측정 |

워크로드는 `ChatRedisServiceImpl` 의 실제 명령 모양을 따름.

- 쓰기 = `RPUSH chat:{7}:w <500B>` (`saveMessage`)
- 읽기 = `LRANGE chat:{7}:r 0 -1` (사전 적재 40건 × 500B ≈ 20KB · `getSessionMessages` / `getRecentSessionMessages`)
- 읽기 : 쓰기 = 3 : 2

시나리오

- **A. 미분리** — 읽기·쓰기 전부 master
- **B. 분리(CQRS)** — 쓰기 master · 읽기 replica(`READONLY` 선행)

## 2. 결과 — 동시 클라이언트 수별 합계 처리량

| 동시 클라이언트 (읽기 · 쓰기) | A 미분리 (ops/s) | B 분리 (ops/s) | 변화 |
|---|---|---|---|
| 3 (2:1) | 20,532 | 23,036 | +12.2% |
| 6 (4:2) | 37,661 | 45,169 | +19.9% |
| 12 (8:4) | 55,455 | 76,505 | +38.0% |
| 24 (16:8) | 60,485 | 109,798 | +81.5% |
| 40 (24:16) | 63,708 | 106,455 | +67.1% |
| 64 (40:24) | 57,610 | 107,238 | +86.1% |

- 미분리는 **약 60,000 ops/s 에서 천장**을 치고 클라이언트를 더 늘리면 오히려 감소
- 분리는 천장이 **약 110,000 ops/s** 로 이동
- 저부하(클라이언트 3대)에서는 이득이 +12% 뿐 — **분리가 명령을 빠르게 만드는 것이 아니라 포화 지점을 뒤로 미는 것**

## 3. 결과 — 읽기와 쓰기 중 어느 쪽이 이득을 보는가

동시 클라이언트 24대(읽기 16 · 쓰기 8) 기준

| 지표 | A 미분리 | B 분리 | 변화 |
|---|---|---|---|
| 읽기 처리량 | 39,270 ops/s | 55,373 ops/s | +41.0% |
| 읽기 p95 | 0.620ms | 0.537ms | −13.4% |
| 쓰기 처리량 | 21,216 ops/s | 54,425 ops/s | +156.5% |
| 쓰기 p95 | 0.559ms | 0.298ms | −46.7% |

**가장 크게 개선되는 쪽은 읽기가 아니라 쓰기.** Redis 는 노드당 단일 스레드라, 20KB 를 직렬화하는 `LRANGE` 가 같은 이벤트 루프를 점유하는 동안 `RPUSH` 가 대기. 조회를 복제본으로 내보내면 그 대기가 사라져 쓰기가 먼저 이득.

## 4. 분리의 대가 — 복제 지연 창

`SET` 직후 같은 키를 복제본에서 `GET` 해 미반영 여부와 수렴 시간을 측정 (n=3,000)

| 조건 | 미반영률 | 수렴 avg | p50 | p95 | max |
|---|---|---|---|---|---|
| 유휴 | 0 / 3,000 (0.00%) | — | — | — | — |
| 쓰기 클라이언트 16대 | 2,079 / 3,000 (**69.30%**) | 0.347ms | 0.261ms | 0.730ms | 8.739ms |

- 유휴 상태에서는 **한 번도 재현 불가**. 부하가 걸리는 순간 3건 중 2건이 미반영
- 프롬프트 조립 경로가 `saveMessage` 직후 같은 요청에서 히스토리를 읽는 구조인 이상, 이 창은 곧 "방금 한 질문이 프롬프트에서 빠짐"
- 지점별 라우팅(프롬프트 조립 = master 고정 / 영속화 조회 = replica / 소유자 검증 = replica 우선 + 공백 시 master 재확인)의 근거가 이 수치

## 5. 폐기한 측정 — 부하 생성기를 호스트에서 실행

처음에는 호스트(macOS)에서 `127.0.0.1:6380` · `6384` 로 걸었으나, 합계 처리량이 클라이언트를 늘려도 **양쪽 모두 약 12,500 ops/s 에서 평평**.

| 동시 클라이언트 | A 합계 | B 합계 | 변화 |
|---|---|---|---|
| 5 | 9,361 | 8,339 | −10.9% |
| 10 | 11,160 | 11,070 | −0.8% |
| 20 | 11,758 | 11,519 | −2.0% |
| 40 | 12,416 | 12,273 | −1.2% |
| 60 | 12,583 | 12,478 | −0.8% |

병목이 Redis 노드가 아니라 **호스트↔컨테이너 네트워크 경로**. 두 시나리오가 같은 천장에 갇히므로 분리 효과가 측정 불가. 부하 생성기를 같은 도커 네트워크 안으로 옮긴 뒤에야 차이가 드러남.

**교훈** — 분리의 효과는 분리 대상이 실제로 포화될 때만 관측 가능. 포화되지 않는 측정 조건에서 나온 "차이 없음"은 설계에 대한 반증이 아니라 측정 조건에 대한 반증.

## 6. 한계

- 단일 호스트에서 6개 노드가 CPU 를 공유하는 조건이라, 노드가 물리적으로 분리된 환경의 절대값과 다름
- 복제 지연은 같은 도커 브리지 네트워크 기준(RTT 가 매우 짧음). 노드 간 지연이 큰 환경에서는 미반영 창이 더 넓어짐
- 애플리케이션(Lettuce · `ReadFrom`)이 아니라 RESP 레벨에서 잰 값. 커넥션 풀·직렬화 비용은 미포함

## 7. 재현

```bash
docker run --rm --network opener_local-network -v "$PWD:/w" -w /w \

  -e MHOST=redis-chat-1 -e RHOST=redis-chat-5 python:3.12-alpine python stale_bench.py
```
