## STAR 4 — RAG 재현율·조건부 빈 (PORTFOLIO.html:417~498)

### 치명적 결함

#### 4-C1. "실측" 배지를 단 32% → 8% 의 원자료가 저장소에 없다

**주장** (`PORTFOLIO.html:490`)
> 동일 질문셋 100문항 A/B 비교 … 발생률 `32% → 8%` **실측**

**코드·문서 근거**
- `backend/docs/measurements/TUTORING_MEASUREMENT_LOG.html:127`
  ```html
  <tr><td>환각율 32%→8% · 검색 80ms</td><td>RAG A/B · 벡터검색</td>
      <td>수동 라벨링 · Timer</td><td><span class="pill p-na">별도</span></td><td>—</td></tr>
  ```
  상태 = **별도**, 실측 결과 = **—**. 같은 표의 다른 행(`03_thread_exhaustion.js` 등)은 `backend/k6/results/*.json` raw 를 가리키는데 이 행만 산출물이 없다.
- `backend/report/2026-07-30-API-실측결과.md` 에도 RAG A/B 절이 없다(인증·세션 검증만 있다).
- 저장소 전체에서 100문항 질문셋·채점표·라벨링 결과 파일이 발견되지 않았다.

**왜 틀렸나**
포트폴리오는 "블라인드가 아님", "1인 채점", "교차검증 없음"까지 스스로 한계를 밝혀 방어를 두껍게 쳤다. 그런데 그 방어는 **채점 방법의 한계**를 다룬 것이고, 지금 문제는 그보다 앞선 **채점 기록의 부재**다. 측정 로그가 자기 손으로 "별도 / —" 라고 적어둔 수치에 `실측` 배지를 다는 건, 이 문서에서 `실측`이라는 라벨이 뜻하는 바(= 재현 가능한 원자료가 있음)를 스스로 무너뜨린다. 같은 문서 STAR 5 의 수치들은 `2026-07-30-API-실측결과.md` 에 curl 응답까지 붙어 있어 대비가 더 선명하다.

**면접에서 어떻게 깨지나**
"32%는 어떤 문항 100개였고, 채점표는 어디 있나요? 파일로 볼 수 있나요?" → 없다고 답하는 순간, 옆에 붙은 한계 서술("1인 채점이라 절대값이 아니라 전후 차이로만 쓴다")이 정직함이 아니라 **없는 데이터를 있는 것처럼 포장한 수사**로 재해석된다. 한 문장이 무너지면서 같은 문단의 방어 서술 전체가 역효과를 낸다.

**제안**
둘 중 하나다. (a) 질문셋 100문항·기준표·라벨 결과를 `backend/docs/measurements/` 에 파일로 커밋하고 로그 행의 상태를 갱신한다. (b) 배지를 `실측` → `추정`/`정성 관찰`로 낮추고 "원자료 미보관"을 한계에 명시한다. 지금처럼 두 문서가 서로 다른 말을 하는 상태가 가장 나쁘다.

#### 4-C2. 아키텍처 다이어그램이 "일반 채팅 = RAG 미경유"로 그려져 있으나 코드는 정반대다

**주장** (`PORTFOLIO.html:448, 451, 457` — SVG 라벨)
> `오프너 분석 + RAG Flag?` → **NO (일반 채팅)** → `OpenAiLlmServiceWithoutRag` (검색 없이 바로 호출)

**코드 근거**
- `OpenAiLlmService.java:99~105` — 일반 채팅 스트리밍 경로가 벡터 검색을 **한다**
  ```java
  SearchRequest searchRequest = SearchRequest.builder().query(lastUserMessage)
          .topK(topK).similarityThreshold(similarityThreshold).build();
  List<Document> similarDocuments = vectorStore.similaritySearch(searchRequest);
  ```
  이어서 `:127` 에서 `buildChatRagSystemPromptWithRule(ragContext)` 로 system prompt 에 주입한다.
- `OpenAiLlmService.java:29~37` / `OpenAiLlmServiceWithoutRag.java:22~29` — 두 구현체를 가르는 조건은 **`app.rag.enabled` 플래그**이지 "오프너 분석 vs 일반 채팅"이 아니다.
- `application-dev.yml:159` — `app.rag.enabled: true`. CLAUDE.md 기준 dev 가 배포 환경에서도 실제로 뜨는 프로파일이므로, **운영 상태의 일반 채팅은 매 턴 RAG 를 경유한다**.

**왜 틀렸나**
다이어그램의 분기 라벨이 축을 바꿔치기했다. 실제 분기는 `플래그 ON → OpenAiLlmService(RAG 검색 포함)` / `플래그 OFF → OpenAiLlmServiceWithoutRag` 인데, 그림은 `오프너 분석 → RAG` / `일반 채팅 → RAG 없음` 으로 그렸다. 더 나쁜 건 이 오독이 바로 아래 `:479` 의 A/B 서술과 **자기모순**을 만든다는 점이다. 그림대로라면 일반 채팅에는 애초에 RAG 가 없으니 "동일 질문셋 A/B" 의 대조군·실험군이 성립하지 않는다. 코드대로라면 그림이 틀렸다. 둘 중 하나는 반드시 거짓이다.

**면접에서 어떻게 깨지나**
"일반 채팅에서 학생이 아무 질문이나 던지면 벡터 검색이 도나요, 안 도나요?" → 그림을 보고 "안 돕니다"라고 답하면 `OpenAiLlmService.java:105` 한 줄로 반박된다. 후속 질문이 더 아프다. "그럼 검색 지연과 임베딩 API 호출이 모든 채팅 턴의 TTFT 에 얹히는데, 그 비용은 측정했나요?" → 벡터 검색 Timer 가 이 경로에는 없다(4-L3 참조).

**제안**
SVG 라벨을 `NO (일반 채팅)` → `플래그 OFF` 로, `오프너 분석 + RAG Flag?` → `app.rag.enabled?` 로 고친다. 그리고 "RAG ON 상태에서는 일반 채팅도 검색을 경유한다"는 사실 한 줄을 본문에 추가한다. 이건 감추기보다 드러내는 쪽이 유리하다 — 채팅 전 구간에 검색이 얹힌다는 사실 자체가 비용·지연 트레이드오프 질문으로 이어지는 좋은 소재다.

#### 4-C3. "튜닝했다"고 말할 만한 실험이 존재하지 않는다

**주장** (`PORTFOLIO.html:468, 476, 477`)
> 코사인 유사도 임계값을 **기본값 0.7**로 설정했는데 … 임계값을 0.7에서 0.2로 낮춰 재현율을 회복 … **Top-K 5로 주입 컨텍스트 수를 제한**

**코드 근거**
- `RagServiceImpl.java:42~47` / `OpenAiLlmService.java:47~51` — 두 값 모두 `@Value` 로 외부화, 코드 기본값은 `top-k:5`, `similarity-threshold:0.7`
- `application-dev.yml:158~161`
  ```yaml
  rag:
    enabled: true
    top-k: 5
    similarity-threshold: 0.2        # 유사도 임계값 - 영어 문서 + 한국어 쿼리는 유사도가 낮음
  ```
- Spring AI `SearchRequest` 실제 기본값 (`spring-ai-vector-store-2.0.0-M1.jar` 디컴파일)
  ```
  public static final double SIMILARITY_THRESHOLD_ACCEPT_ALL = 0.0d;
  public static final int DEFAULT_TOP_K = 4;
  ```
- `SpringAiConfig.java:23` — `return new TokenTextSplitter();` (청크 크기·최소 길이 전부 라이브러리 기본값, 인자 0개)

**왜 틀렸나**
세 가지가 동시에 깨진다.
1. **"기본값 0.7"은 사실이 아니다.** 프레임워크 기본값은 0.0(전부 통과)이다. 0.7 은 이 프로젝트가 근거 없이 고른 값이다. 즉 서사가 "프레임워크가 준 값이 문제였다"가 아니라 "내가 근거 없이 고른 값이 문제였고, 그걸 다시 근거 없이 다른 값으로 바꿨다"가 된다.
2. **"Top-K 5로 제한"은 제한이 아니다.** 기본값 4보다 **1 크다**. 임계값을 0.2로 낮춰 무관 문서 유입이 늘어난 상태에서 topK 를 오히려 늘렸으므로, "정밀도 손실을 topK 로 상쇄했다"는 논리가 방향부터 반대다.
3. **청크 전략은 손대지 않았다.** `new TokenTextSplitter()` 는 기본 800토큰 청킹이다. 다국어 정렬 문제를 진단해 놓고 정작 검색 품질에 가장 크게 작용하는 청킹은 기본값 그대로다.

그리고 결정적으로, 0.7 → 0.2 사이의 **어떤 값도 비교하지 않았다.** 저장소에 임계값 스윕 결과가 없다. `RagServiceImpl.java:104~127` 의 `logDebugSearchInfo` 는 "임계값 없이 검색하면 몇 건 나오는지"를 로그로 찍는 디버그 코드일 뿐, 재현율 측정이 아니다.

**면접에서 어떻게 깨지나**
"0.2는 어떻게 나온 값인가요? 0.3이나 0.4는 왜 아니었나요?" → 실험이 없으므로 "검색이 0건이라 될 때까지 낮췄다"밖에 답할 게 없다. 그건 튜닝이 아니라 **증상 회피**다. 이어서 "그럼 0.2에서 무관 문서가 얼마나 섞이는지는 아시나요?"로 들어오면 정밀도 쪽 수치가 아예 없다는 게 드러나고, `:497` 의 "정밀도를 내주고 재현율을 산 교환"이라는 문장이 **양쪽 다 측정하지 않은 상태의 수사**로 판정된다.

**제안**
서술을 사실에 맞춘다. "튜닝" → "임계값을 실험 없이 낮춰 검색 0건 상태를 우선 해소했고, 정밀도 영향은 측정하지 못했다"로 낮추는 편이 오히려 강하다. 값의 근거를 만들고 싶다면 4-A1 제안(골든셋 + 스윕 테스트)이 이 코드베이스에서 반나절이면 가능하다. topK 는 "제한" 표현을 빼거나, 실제로 3으로 낮추고 근거를 붙인다.

### 논리 구멍

#### 4-L1. "조건부 빈 미결합"의 원인 진단은 정확하지만, 그것이 STAR 로 승격될 만한 문제였는지가 약하다

**주장** (`PORTFOLIO.html:480`)
> 조건부 빈은 "빈을 만들지 않는 것"만으로 안전해지지 않고 **그 타입을 주입받는 쪽까지 함께 봐야 방어가 성립**함

**코드 근거** — 이 주장은 **코드와 일치한다**.
- `RagServiceImpl.java:22~33` — 주석이 "빈을 안 만드는 것만으로는 방어가 안 된다"고 그 교훈을 정확히 기록
- `DisabledRagService.java:34~38` — `havingValue="false", matchIfMissing=true` 짝, `Flux.error(RAG_DISABLED)` 반환(빈 완료가 아님 — 상태머신 교착 회피 의도까지 일관)
- `QuestionNewServiceImpl.java:56~59, 200` — `ObjectProvider<VectorStore>` + `getIfAvailable()`
- `VectorStore` 주입 클래스 5개(`VectorStoreConfig`, `RagServiceImpl`, `DocumentServiceImpl`, `OpenAiLlmService`, `QuestionNewServiceImpl`) — `:481` 의 "다섯 개"는 정확

**왜 약한가**
사실관계는 다 맞다. 문제는 **이것이 사용자에게 무슨 일이 벌어진 사건이 아니라, 내가 플래그를 꺼봤을 때만 나는 기동 실패**라는 점이다. `git log` 상 `4636769 fix : app.rag.enabled=false 로 기동이 실패하던 문제 수정` 이 그 시점이다. 즉 "차단했다"의 대상은 운영 장애가 아니라 **자기 자신이 만든 설정 조합**이다. 제목(`:417`)이 "재현율 저하와 조건부 빈 미결합을 … 양쪽에서 차단"으로 두 사건을 병렬로 놓아, 뒤쪽을 앞쪽과 같은 급의 문제처럼 보이게 한다.

**면접에서 어떻게 깨지나**
"이 버그는 언제, 누가 발견했나요? 운영에서 터진 건가요?" → "제가 플래그를 꺼보다가"라고 답하면 규모가 즉시 축소된다. 다만 이건 **깨지는 게 아니라 정직하게 답하면 오히려 가산점**이 되는 항목이다 — "조건부 빈을 도입하면 그 타입의 모든 주입 지점을 추적해야 한다"는 일반화는 실제로 값어치가 있고, 그 일반화를 `ObjectProvider` 와 `havingValue=false` 짝이라는 **두 가지 다른 처방으로 구분해 적용**한 판단(`:481`)은 신입 수준을 넘는다.

**제안**
제목에서 두 사건을 병렬 나열하지 말고, "설정 플래그를 껐을 때만 드러나는 결합 문제"라고 범위를 명시한다. 축소가 아니라 **정확한 좌표 표시**다. 지금은 과장으로 읽힐 여지가 있어 손해다.

#### 4-L2. 재색인 경로가 없어서, 스스로 제시한 "근본 해결책"이 실행 불가능하다

**주장** (`PORTFOLIO.html:478, 497`)
> 근본 해결책 세 가지를 비교 — ① **다국어 임베딩 모델로 유사도 분포를 정상화** … 근본 원인인 다국어 임베딩 정렬은 **모델 교체 비용** 때문에 보류

**코드 근거**
- `DocumentServiceImpl.java:47~66` — 색인은 **문서가 1건이라도 있으면 통째로 건너뛴다**
  ```java
  List<Document> existingDocs = vectorStore.similaritySearch(checkRequest);
  if (!existingDocs.isEmpty()) {
      log.info("Vector store already contains {} document(s). Skipping re-indexing.", ...);
      initialized.set(true);
      return;
  }
  ```
- `PdfDocumentLoader.java:22~29` — 색인 진입점은 기동 시 `ApplicationRunner` 단 하나. 수동 재색인 API·배치·CLI 가 없다.
- `VectorStoreConfig.java:30` — `.dimensions(1536)` 하드코딩
- `VectorStoreConfig.java:36` — `.initializeSchema(false)`, 스키마는 Flyway V14 단일 관리(1536차원 컬럼)

**왜 틀렸나**
"비용 때문에 보류했다"는 문장은 **경로는 있는데 비용이 커서 안 했다**는 뜻으로 읽힌다. 실제로는 경로 자체가 없다. 다국어 모델로 바꾸려면 (1) `VectorStoreConfig.java:30` 의 차원, (2) Flyway 마이그레이션의 `vector(1536)` 컬럼, (3) `DocumentServiceImpl.java:62` 의 스킵 조건 — 세 곳을 동시에 고치고 기존 벡터를 전량 폐기·재적재해야 한다. 그 작업을 지원하는 코드가 하나도 없다. 즉 "비교했다"는 세 가지 대안 중 ①은 현재 구조에서 **평가 자체가 불가능**했다.

**면접에서 어떻게 깨지나**
"다국어 모델로 바꾸기로 결정했다면, 내일 아침 무엇부터 하시겠어요?" → 재색인 절차를 말해야 하는데 `DocumentServiceImpl` 은 스킵만 하고 삭제 API 가 없다. "DB 를 직접 truncate 하겠다"고 답하는 순간, 앞서 `VectorStoreConfig.java:35~36` 에 `removeExistingVectorStoreTable(false)` / Flyway 단일 관리라고 신중하게 설계해 둔 것과 **운영 절차가 어긋난다**는 게 드러난다.

**제안**

**제안**

**왜 틀렸나**
두 겹으로 틀렸다.
1. **기능 결함** — 카카오로 로그인한 사용자와 방금 가입한 사용자는 Redis 에 저장본이 없으므로 access token 이 만료된 뒤 `POST /auth/refresh` 가 **항상 401** 이다. 1시간마다 재로그인해야 한다.

#### 5-C2. "단일 통과점"이 단일이 아니다 — 그림이 그린 통과점을 재사용 분기는 지나지 않는다

**주장** (`PORTFOLIO.html:528` SVG 제목, `:557, 564, 574`)
> ② SSE 연결 생성 — **두 분기가 세션 초기화를 공통으로 지나며** 소유자 대조
> SSE 소유자 검증은 호출부가 아니라 세션 초기화 안쪽 **단일 통과점**에 뒀음 — 분기가 늘어나도 검증이 새지 않음
> SSE 소유자 검증을 **세션 초기화라는 단일 통과점**으로 모아, 연결 분기가 늘어나도 검증이 새지 않는 구조 확보

- 그리고 소유자 검증 호출은 **총 6곳에 흩어져 있다**

**왜 틀렸나**
"단일 통과점"에는 두 가지 뜻이 있고, 문서는 강한 쪽을 주장하면서 약한 쪽만 구현했다.
- (약) **판정 로직의 단일화** — `assertSessionOwner` 하나로 모음. **이건 사실이고 좋은 설계다.** 조건을 바꿀 때 한쪽만 고쳐 규칙이 갈라지는 문제를 실제로 막는다.

**면접에서 어떻게 깨지나**
"채팅 세션에 파일 첨부 API 를 새로 추가한다면, 소유자 검증은 자동으로 걸리나요?" → 안 걸린다. 개발자가 `validateSessionOwner` 를 직접 호출해야 한다. 그 순간 `:574` 의 "연결 분기가 늘어나도 검증이 새지 않는 구조 확보"가 **거짓 단정**으로 판정된다. 이어서 "그럼 무엇이 단일 통과점인가요?"에 "판정 로직입니다"라고 정정하면, 정정 자체는 맞지만 **문서가 과장돼 있었다**는 인상이 남는다.

**제안**
문장을 정확히 쓴다. "검증 **판정**을 단일 헬퍼로 모아 두 분기가 같은 규칙을 공유하게 했다. 다만 호출 자체는 각 진입점이 명시적으로 해야 하므로, 진입 통제까지 단일화하는 것(인터셉터/`@PreAuthorize`)은 후속 과제다" — 이렇게 쓰면 `:580` 의 기존 한계 서술과도 톤이 맞고, 5-A2 제안으로 자연스럽게 이어진다. SVG 는 재사용 분기 화살표를 `validateSessionOwner` 박스로 따로 빼서 실제 구조를 그린다.

#### 5-C3. `INVALID_SESSION` 이 400 / `C_001` 이라 방어 발동을 응답으로 구분할 수 없다

**주장** (`PORTFOLIO.html:574`)

**코드 근거**

**면접에서 어떻게 깨지나**
"남의 세션 접근 시도를 대시보드에서 알림 걸려면 어떤 조건을 쓰나요?" → `400 C_001` 로는 불가능하다. 요청 본문 오타와 세션 탈취 시도가 같은 버킷에 들어간다. `:562` 의 "방어 장치는 읽고 거부하는 코드가 있어야 검증된다"는 기준을 스스로 적용하면, **거부는 하지만 그 거부를 관측할 수 없는 상태**다.

**제안**
`INVALID_SESSION` 을 `403` + 고유 코드(예: `C_010`)로 분리한다. `report/2026-07-30-API-실측결과.md` 의 실측 표도 함께 갱신해야 하므로 재측정 부담이 있지만, 이 STAR 의 주제(관측 가능한 방어선)에 정확히 부합하는 수정이라 투자 대비 효과가 크다.

#### 5-L1. self-invocation 회피 설명이 자기모순 — 그 경로에는 애초에 `@CircuitBreaker` 가 없다

**주장** (`PORTFOLIO.html:564`)
> 헬퍼를 둔 두 번째 이유는 자기호출(self-invocation) — 같은 클래스 내 직접 호출은 **Spring AOP 프록시를 우회**해 `@CircuitBreaker` 를 건너뜀

**코드 근거**
- `ChatRedisServiceImpl.java:72~73` — `initializeSession` 에는 **`@CircuitBreaker` 애너테이션이 없다**
  ```java
  @Override
  public void initializeSession(Long sessionId, UUID userId) {
  ```
- `ChatRedisServiceImpl.java:227~229` — CB 는 `validateSessionOwner` 에만 있다
  ```java
  @Override
  @CircuitBreaker(name = "redis-chat", fallbackMethod = "validateSessionOwnerFallback")
  public void validateSessionOwner(Long sessionId, UUID userId) {
  ```
- `ChatRedisServiceImpl.java:84` — `initializeSession` 이 부르는 것은 private 헬퍼
- `ChatRedisServiceImpl.java:77` — 게다가 그 직전의 `redisTemplate.hasKey(sessionKey)` 도 CB 밖이다

**왜 틀렸나**
AOP 자기호출에 대한 **기술 설명 자체는 정확하다.** 문제는 그 설명이 여기서 아무것도 설명하지 못한다는 것이다. `initializeSession` 에 CB 가 없으므로, 헬퍼를 쓰든 `validateSessionOwner` 를 자기호출하든 **어느 쪽이든 CB 는 적용되지 않는다.** 헬퍼 추출의 진짜 효용은 판정 로직 단일화(5-C2 의 약한 의미)이고, CB 는 그 부산물이 아니다.

오히려 이 서술은 **현재 상태를 정당화하는 것처럼 읽힌다**. 실제 결과는 "신규 연결 경로의 Redis 접근은 CB 보호를 전혀 받지 못한다"이다. Redis 장애 시 `validateSessionOwner` 경로는 fast-fail 하지만 `initializeSession` 경로는 타임아웃까지 대기한다 — 같은 SSE 엔드포인트의 두 분기가 장애 시 **다르게 동작한다.**

**면접에서 어떻게 깨지나**
"`initializeSession` 은 CB 가 걸려 있나요?" → 없다. "그럼 자기호출 회피가 여기서 무엇을 지켰나요?" → 답이 없다. 이 질문은 AOP 를 아는 면접관이라면 애너테이션 위치를 눈으로 확인하는 순간 바로 던진다. **정확한 개념을 엉뚱한 곳에 붙인 사례**로 분류되면, 다른 기술 서술의 신뢰도까지 함께 떨어진다.

**제안**
`initializeSession` 에도 `@CircuitBreaker(name = "redis-chat", ...)` 를 붙이면 서술이 사실이 된다(한 줄 + fallback 오버로드 2개). 그 전까지는 `:564` 의 self-invocation 문장을 빼거나, "판정 단일화가 주 목적이고, CB 적용까지 맞추는 것은 후속"으로 정직하게 쓴다.

#### 5-L2. 로그아웃 멱등성 "5개 변형 전부 정상 종료"는 참이지만, 그중 하나는 refresh 를 무효화하지 못한다

**주장** (`PORTFOLIO.html:566`)
> 멱등성은 토큰 없음·변조·형식 불명·만료·이미 로그아웃 **5개 변형 전부 정상 종료** — "정상 입력에서만 동작"과 "어떤 입력에도 안전"은 다른 문제라 경계 입력도 따로 넣음

**코드 근거**
- `AuthServiceImpl.java:136~140` — `claim == null` 이면 **쿠키만 정리하고 `return`**
  ```java
  if (claim == null) {
      jwtUtil.clearAllTokenCookies(res);
      log.info("[Auth] 로그아웃 - 유효한 accessToken 없음, 쿠키만 정리");
      return;
  }
  ```
  → `:163` 의 `redisTemplate.delete("refreshToken:" + claim.getSubject())` 에 **도달하지 않는다**
- `AuthServiceImpl.java:181~184` — 만료 토큰만 예외적으로 `e.getClaims()` 로 살려 refresh 폐기까지 진행(이 판단은 정확하고 주석도 근거를 잘 남겼다)
- `report/2026-07-30-API-실측결과.md` 검증 4 — 4a(토큰 없음)·4b(변조)·4c(형식 불명) 모두 `200`. **HTTP 상태만 확인했고 Redis 키 잔존은 확인하지 않았다**

**왜 틀렸나**
"정상 종료"와 "무효화 완료"는 다른 명제인데, 검증은 앞의 것만 했고 결과 서술(`:573` "access·refresh 양쪽으로 정의")은 뒤의 것을 함의한다. 구체적 시나리오: accessToken 쿠키가 만료돼 브라우저가 이미 지운 상태에서 로그아웃을 누르면 → `claim == null` → 쿠키만 정리 → **서버의 `refreshToken:{userId}` 는 그대로 남는다.** refresh 쿠키의 `maxAge` 는 7일(`JwtUtil.java:175`)이고 브라우저에서는 지워지지만, 그 값을 탈취한 쪽은 최대 7일간 access token 을 계속 발급받는다. `:566` 이 강조한 "어떤 입력에도 안전"이 바로 이 지점에서 성립하지 않는다.

**면접에서 어떻게 깨지나**
"access 쿠키가 없는 상태에서 로그아웃하면 서버의 refresh 는 지워지나요?" → 안 지워진다. `:566` 의 5변형 검증이 **HTTP 200 만 본 검증**이었다는 게 드러난다. 이건 STAR 5 의 방법론 주장(`:554` "기능 테스트는 정상 흐름만 증명하지, 방어선이 실제로 거부하는지는 증명하지 못한다")과 같은 종류의 실수를 저자 자신이 반복한 사례라 특히 뼈아프다 — **상태 코드만 보는 것 역시 "정상 흐름만 증명"이다.**

**제안**
로그아웃 시 refresh 쿠키(`JwtUtil.extractRefreshTokenFromRequest`, 이미 존재)에서도 `subject` 를 복구해 Redis 키를 지우면 이 구멍이 닫힌다. 검증 절차에는 각 변형마다 `EXISTS refreshToken:{userId}` 확인을 추가한다.

#### 5-L3. refresh 토큰 회전이 없고 수명이 3중으로 어긋난다

**주장** (`PORTFOLIO.html:553`)
> 휠 파인더에서 Refresh Token 을 토큰 전문으로 키잡아 사용자 단위 폐기를 못 했고 … **같은 실수를 반복하지 않는 것이 이 절의 첫 요구사항**이었고, 그래서 **키 기준·장애 정책·검증 절차를 먼저 정하고** 구현에 들어갔음

**코드 근거**
- `AuthServiceImpl.java:193~218` `tokenRefresh` — **회전 없음.** 새 access 만 발급하고 refresh 는 그대로 둔다. `jwtUtil.setHttpOnlyAccessToken(response, newAccessToken)` 만 호출
- `JwtUtil.java:70~80` `generateRefreshToken` — **`jti` 없음.** subject/iat/exp 뿐이라 개별 폐기 불가
- 수명이 세 군데 다 다르다
  | 위치 | 값 |
  |---|---|
  | `application-dev.yml:145` | JWT `exp` = **14일** |
  | `FormAuthenticationSuccessHandler.java:91` | Redis TTL = **7일** |
  | `JwtUtil.java:175` | 쿠키 `maxAge` = **7일** |
- `FormAuthenticationSuccessHandler.java:89` 주석은 `TTL 7일 = RefreshToken 수명` 이라 적혀 있으나 **실제 수명은 14일**이다. `AuthServiceImpl.java:183` 주석도 "최대 7일간 살아남음"으로 같은 착오를 반복한다.
- access 블랙리스트는 `jti` 단위(`AuthServiceImpl.java:154`)라 **다른 기기의 access token 은 최대 1시간 생존**한다

**왜 틀렸나**
`:553` 은 "키 기준을 먼저 정했다"는 것을 이 STAR 의 출발점이자 성숙도의 증거로 내세운다. 그런데 refresh 키를 `userId` 로 잡은 것(개선 맞음) 외에, **수명 기준은 정해지지 않았다.** 세 값이 서로 다르고 주석은 틀린 값을 적고 있다. 실질적 귀결: 사용자는 7일이 지나면 JWT 는 아직 유효한데 Redis 저장본이 사라져 재발급이 실패한다 — **`exp` 14일은 죽은 설정이다.**

또한 "사용자 단위 폐기"는 refresh 에서만 달성됐다. access 는 여전히 토큰 단위라, 여러 기기에 로그인한 사용자의 다른 기기 세션은 로그아웃해도 최대 1시간 살아 있다. `:553` 의 "같은 실수를 반복하지 않았다"가 절반만 참이다.

**면접에서 어떻게 깨지나**
"토큰이 탈취됐다는 신고가 들어오면 그 사용자의 모든 세션을 어떻게 즉시 끊나요?" → refresh 는 키 하나 지우면 되지만 access 는 방법이 없다(각 토큰의 `jti` 를 모르므로). "그럼 refresh 회전은 하나요? 재사용 탐지는요?" → 없다. 탈취된 refresh 와 정상 사용자의 refresh 가 **구분 불가능**하다. `:553` 이 "이전 프로젝트의 실수를 반복하지 않기 위해 먼저 설계했다"고 선언한 만큼, 이 질문에 답이 없을 때의 낙차가 크다.

**제안**
- 최소: 세 수명을 하나로 맞추고(14일이면 Redis TTL 도 14일, 쿠키도 14일) 잘못된 주석 2곳을 고친다
- 권장: 5-A1 — `tokenRefresh` 에 회전 + 재사용 탐지 도입. 사용자 단위 무효화 키(`token-version:{userId}`)를 access 클레임에 실으면 access 쪽 사용자 단위 폐기도 함께 해결된다(휠-2 의 version 키 패턴을 이미 `:131` 에서 다루고 있으므로 서사 일관성도 좋다)

#### 5-L4. permitAll 우회 경로가 남아 있다 — `/test/**` 는 배포 환경에서 미인증 공개다

**주장** (`PORTFOLIO.html:500` 제목)
> 인증·세션 방어선을 **단일 통과점 구조로 설계**

**코드 근거**
- `SecurityConfig.java:65~73`
  ```java
  .requestMatchers(

          "/actuator", "/actuator/health", "/actuator/prometheus",
          "/test/**"  // dev-only: k6 스레드 풀 부하 테스트 엔드포인트

  ```
- `ThreadPoolTestController.java:15` — `@Profile("dev")`
- `backend/CLAUDE.md` — "**`dev` 는 실제로 뜨는 프로파일이다 — 배포 환경 포함**(`../docker-compose.dev.yml`)"
- `SecurityConfig.java:150~157` — CORS fallback 이 `allowedOriginPatterns(List.of("*"))`
- `SecurityConfig.java:64` — `dispatcherTypeMatchers(DispatcherType.ASYNC).permitAll()`

**왜 틀렸나**
주석은 "dev-only"라고 적혀 있지만, 이 프로젝트에서 dev 는 배포 프로파일이다. 따라서 **인증 없이 호출 가능한 스레드 점유 엔드포인트가 배포 환경에 열려 있다.** 부하 테스트용이므로 정의상 자원을 소모하는 코드다. `:500` 이 "방어선을 단일 통과점으로 설계"라고 선언하는 STAR 안에서, 그 통과점을 명시적으로 우회하는 경로가 남아 있는 셈이다.

CORS fallback 도 같은 성격이다. `app.cors.allowed-origins` 가 비면 모든 오리진을 패턴 허용한다. prod 프로파일의 origins 가 `example.com` 플레이스홀더인 것(`application-prod.yml:66~`)과 합치면, 설정 실수 하나로 조용히 전체 개방된다 — 이건 `:565` 에서 저자가 문제 삼은 "Spring Boot 는 모르는 프로퍼티를 조용히 무시한다"와 **정확히 같은 종류의 침묵**이다.

**면접에서 어떻게 깨지나**
"permitAll 목록에 `/test/**` 가 있는데 이건 배포에서도 열려 있나요?" → dev 가 배포 프로파일이므로 열려 있다. `:562` 의 "전수 검색해 대조했다"가 Redis 키에는 적용됐지만 **필터 체인에는 적용되지 않았다**는 게 드러난다. "단일 통과점"을 제목으로 내건 STAR 에서 통과점 우회 목록을 점검하지 않은 것은 범위 누락이다.

**제안**
`/test/**` permitAll 자체를 `@Profile` 로 분리하거나(SecurityConfig 를 dev/prod 로 나눔) 인증 뒤로 옮긴다. 문서에는 "permitAll 목록을 전수 점검해 남은 우회 경로를 정리했다"는 항목을 추가하면 `:562` 의 방법론이 Redis 를 넘어 필터 체인까지 확장됐다는 서사가 된다 — STAR 의 논지에 정확히 맞는 보강이다.

#### 5-D2. "런타임 검증 절차"에 actuator 노출 설정 변경 단계가 빠져 있다

**주장** (`PORTFOLIO.html:568, 575`)
> `/actuator/configprops` 로 계정 잠금 빈 바인딩, `/actuator/loggers` 로 로그 레벨 실효값 확인
> 설정은 "값을 적었다"와 "그 값이 실제로 바인딩됐다"를 **분리 검증하는 단계를 표준에 넣어**

**코드 근거**
- `application.yml:45` — `management.endpoints.web.exposure.include: health,info,metrics,prometheus,circuitbreakers,circuitbreakerevents` — **`configprops` 와 `env` 는 노출 대상이 아니다**
- `report/2026-07-30-API-실측결과.md` 4-0 절이 이를 스스로 기록
  ```
  actuator/env         -> 500   ← 노출 안 됨
  actuator/configprops -> 500   ← 노출 안 됨
  ```
- `SecurityConfig.java:69~71` — permitAll 은 `/actuator`, `/actuator/health`, `/actuator/prometheus` 뿐이라 `configprops` 는 인증 쿠키도 필요

**왜 문제인가**
"표준에 넣었다"(`:575`)는 **재현 가능한 절차**를 함의한다. 그런데 절차의 첫 단계(노출 설정을 임시로 바꾸고 인증 쿠키를 실어야 함)가 문서에 없어, 그대로 따라 하면 500 이 난다. 실측 리포트에는 이 함정이 정확히 기록돼 있는데 포트폴리오로 올라오면서 생략됐다.

**면접에서 어떻게 깨지나**
"configprops 는 기본 노출인가요?" → 아니다. "그럼 운영에서도 이 절차를 쓰나요?" → 운영에 configprops 를 열면 그 자체가 정보 노출이라, 답이 "운영에서는 못 쓴다"가 된다. `:575` 의 "표준" 이 **로컬 한정 절차**였다는 게 드러난다.

**제안**
`:568` 에 "확인용으로 `configprops` 를 임시 노출하고 인증 쿠키를 실어 조회했다(운영 기본 노출은 하지 않는다)"를 명시한다. 한 줄 추가로 재현성과 보안 감각을 동시에 보여줄 수 있다.

### 의도적 잔존 2건 — 논리 성립 여부만 판정

**① `:562` "읽고 거부하는 코드가 있다"로만 검증된다 — 기준 자체는 타당, 적용 범위가 미달**

기준은 옳다. `JwtAuthenticationFilter.java:99~121` 이 그 기준을 실제로 만족한다 — 쓰기(`AuthServiceImpl.java:152`), 읽기(`:111`), 거부(`:61~65`) 세 지점이 같은 키 접두사 상수(`:28`)로 묶여 있고, `jti` 없는 토큰을 폐기 취급하는 판단(`:105~108`)과 fail-close 선택(`:113~120`)까지 근거가 코드 주석에 남아 있다. **access 블랙리스트 하나에 관해서는 이 STAR 에서 가장 단단한 부분이다.**

문제는 같은 기준을 `refreshToken:{userId}` 에 적용하면 **쓰기가 4경로 중 1곳뿐**(5-C1)이라 기준을 통과하지 못한다는 것이다. 즉 기준은 유지하되, "모든 키에 대해 확인했다"는 범위 주장은 사실이 아니다. → **유지 권장. 단 `:562` 의 "키마다"를 "access 블랙리스트 키에 대해"로 좁힐 것.**

**② `:565` 미적용 설정 3건(SSE 30분 타임아웃 / dev 1분 계정 잠금 / prod 로그 레벨) — 사례 자체는 성립**

`report/2026-07-30-API-실측결과.md` 4-2·4-3 절이 `configprops` 로 `{"accountLock":{"lockDurationMinutes":1,"maxAttempts":5}}` 바인딩과 로거 실효 레벨을 확인한 기록을 남기고 있어 **근거가 있다.** `CLAUDE.md` 도 "`SecurityProperties` 는 최상위 `security.account-lock` 에 바인딩되며 `spring:` 하위로 넣으면 조용히 기본값으로 떨어진다"는 교훈을 기록했다. 논리적으로 성립한다. → **유지 권장.**

다만 이 사례의 설득력이 4-D2(`app.chat.history-window` 미선언)로 인해 자기모순을 안는다. **같은 문서 안에서 "설정을 yml 에 적고 바인딩까지 확인하는 것이 표준"이라 말하면서, 새로 도입한 튜닝 키는 yml 에 적지 않았다.** 그 키만 정리하면 이 사례는 흠 없이 강해진다.

## 추가하면 좋은 주제

이 코드베이스에서 **실제로 구현 가능한** 것만, 파일 근거와 함께 3개.

### A1. 토큰 발급 단일 진입점 + refresh 회전·재사용 탐지

**근거 파일**: `FormAuthenticationSuccessHandler.java:71~91`, `OAuth2AuthenticationSuccessHandler.java:85~93`, `AuthServiceImpl.java:78~84, 115~123, 193~218`, `JwtUtil.java:70~80`

지금 토큰 발급 코드가 4곳에 복제돼 있고, 그중 1곳만 Redis 에 쓴다(5-C1). `issueTokens(userId, role, name, response)` 하나로 모으면 **누락이 구조적으로 불가능**해진다. 여기에 `tokenRefresh` 회전(새 refresh 발급 + Redis 덮어쓰기)과, 저장본과 다른 refresh 가 들어오면 해당 사용자 refresh 를 전부 폐기하는 재사용 탐지를 얹는다.

이게 STAR 5 에 가장 잘 맞는 후속인 이유: `:562` 가 내세운 "쓰기·읽기·삭제 전수 대조"라는 **방법론이 실제로 결함을 잡아내 구조를 바꾼 사례**가 되기 때문이다. 지금은 방법론만 있고 산출물이 없다. 작업량은 헬퍼 1개 + 호출부 4곳 치환 + 회전 로직 정도다.

### A2. 세션 소유권 검증을 인터셉터/애너테이션으로 승격

**근거 파일**: `ChatServiceImpl.java:139, 214, 259, 358, 379`, `ChatMessageConsumer.java:58`, `ChatRedisServiceImpl.java:244~258`, `ChatController.java:47~141`

`sessionId` 를 받는 컨트롤러 메서드에 `@RequireSessionOwner` 를 붙이고 인터셉터가 `assertSessionOwner` 를 호출하게 하면, `:557` 이 문제로 제기한 "분기가 늘어날 때마다 검증이 샌다"가 **진짜로** 닫힌다. 판정 로직은 이미 헬퍼로 단일화돼 있어(`ChatRedisServiceImpl.java:244`) 재사용만 하면 된다.

부수 효과가 크다. 현재 `ChatServiceImpl.java:250~254, 353, 374` 는 소유자 검증보다 **먼저** `sinks.containsKey` 를 보고 `SESSION_EXPIRED(401)` 를 던지는데, `sinks` 는 인스턴스 로컬 맵(`ChatServiceImpl.java:82`)이라 소유권과 무관한 판정이 인가 판정보다 앞선다. 인터셉터로 올리면 순서가 자연히 교정된다. `:580` 이 남긴 "테스트 코드로 승격" 과제와도 이어진다 — 인터셉터는 `@WebMvcTest` 로 회귀 테스트를 붙이기 쉽다.

### A3. RAG 골든셋 + 임계값 스윕 테스트 하네스

**근거 파일**: `RagServiceImpl.java:42~47`(파라미터 외부화 완료), `DocumentServiceImpl.java:47~93`(색인 진입점), `src/test/java/spring/backend/domain/chat/service/impl/DisabledRagServiceTest.java`(테스트 뼈대 존재)

`src/test/resources/rag-golden.jsonl` 에 (질문, 정답 근거 문서 id) 20~30쌍을 만들고, 임계값을 0.1~0.7 로 스윕하며 recall@5 를 출력하는 테스트를 붙인다. 파라미터가 이미 `@Value` 로 외부화돼 있어(`RagServiceImpl.java:42~47`) 테스트에서 `@TestPropertySource` 로 주입만 하면 된다.

이게 4-C1·4-C3 을 **동시에** 해결한다. "32%→8%"는 사람 채점이라 재현이 어렵지만, recall@5 는 기계 채점이라 CI 에 넣을 수 있다. 그러면 `:476` 의 "0.7에서 0.2로 낮춰 재현율을 회복"이 인상이 아니라 **숫자와 재현 절차를 가진 주장**이 된다. 20문항이면 반나절이면 만들 수 있고, 포트폴리오에서 가장 약한 수치 하나를 가장 단단한 수치로 바꾸는 투자다.
