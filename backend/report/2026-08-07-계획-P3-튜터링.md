# P3 — AI 튜터링(ai-1~5) 전면 재구축 실행 계획

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development` (권장) 또는 `superpowers:executing-plans`.
> Task 단위로 구현한다. Step 은 체크박스(`- [ ]`)로 진행을 추적한다.

**Goal:** `PORTFOLIO.html` 139~583행이 이미 서술한 AI 튜터링 설계에 **코드를 맞추고**, 근거 없는 수치를 실측 산출물로 교체할 수 있는 상태를 만든다.

**Architecture:** 리액티브 경계(`Flux`)에서 무력화된 Resilience4j 서킷을 먼저 되살리고(3-1), 그 위에 타임아웃·실패 분류·fallback 정책을 쌓는다. 그 다음 데이터 정합(프롬프트에 질문 보장, read-after-write 선형화, 부분 응답 저장, 조용한 유실 제거)을 처리하고, 마지막으로 인가 통과점 단일화·토큰 발급 단일 진입점·계측/실험 하네스를 붙인다. 모든 단위 테스트는 Mockito 기반이며 Spring 컨텍스트를 띄우지 않는다.

**Tech Stack:** Java 21 · Spring Boot 4.0.0 · Spring AI 2.0.0-M1 · Project Reactor · Resilience4j 2.2.0 · Spring StateMachine 4.0.0 · Redis Cluster(Lettuce) · RabbitMQ · PostgreSQL + pgvector · Micrometer/Prometheus · JUnit 5 + Mockito + StepVerifier · Gradle

## 판단이 필요했던 항목 3건 — 결론과 근거

### (가) 3-7 — CB fallback 을 "실제 대체 응답"으로 바꿀 것인가

**결론: 지점별로 다르게 처리한다. LLM 은 fast-fail 을 유지하고 문서를 강등하며, Redis 저장 경로만 진짜 degradation 으로 승격한다.**

근거 셋.

1. **LLM 경로에서 그럴듯한 가짜 응답은 이 서비스에서 특히 해롭다.** 대상이 수능·모의고사 풀이를 배우는 학생이고, 같은 포트폴리오의 STAR 4 가 "검색 결과가 비면 컨텍스트를 억지로 채우지 않고 RAG 없는 프롬프트로 폴백한다 — 무관한 문서를 주입하는 쪽보다 안전한 방향"(`PORTFOLIO.html:477`)이라는 원칙을 이미 선언했다. 서킷이 열렸을 때 캐시된 과거 답변이나 정형 문구를 답변처럼 흘려보내면 그 원칙과 정면으로 충돌한다. 학습자는 fallback 응답과 진짜 응답을 구분할 수단이 없다.
2. **fast-fail 자체가 정당한 설계 선택이다.** 느린 실패보다 낫고, 이미 `LLM_CIRCUIT_OPEN(503, "C_010")` 이라는 전용 코드와 재시도 안내 메시지가 있다. 문서(`:407`, SVG `:363,:365`)의 "대체 응답 즉시 반환"을 "서킷 OPEN 시 503 으로 즉시 거부하고 재시도 안내를 SSE `error` 이벤트로 보낸다"로 강등하면 코드와 문서가 일치하면서 서술이 오히려 단단해진다.
3. **단, 지금은 fast-fail 조차 제대로 전달되지 않는다.** `ChatServiceImpl:337` 의 `emitError(sessionId, error.getMessage(), null)` 이 `errorCode` 를 `null` 로 버려서, 클라이언트는 "서킷 때문에 거부됐다"와 "LLM 이 실패했다"를 구분할 수 없다. `openerAnalysis`(`:485-495`)는 이미 `BusinessException` 을 인식해 코드를 실어 보내는데 `processMessage` 만 안 한다. **fast-fail 을 유지한다는 결정에는 "실패 이유를 정확히 전달한다"가 반드시 딸려야 한다.** Task 4 에서 고친다.

한편 **`saveMessage` fallback 은 승격한다.** 대화 버퍼 저장 실패가 진행 중인 스트리밍을 끊을 이유가 없다. 지금은 `MESSAGE_INPUT_FAIL(500)` 을 던져 사용자 요청 전체를 실패시킨다. Task 3 이 현재 질문을 프롬프트에 무조건 포함시키므로, 저장 1건이 빠져도 이번 턴의 LLM 입력은 온전하다 — 즉 Task 3 이 이 degradation 의 안전 조건이다. 그래서 Task 3 → Task 4 순서가 강제된다.

반대로 **`validateSessionOwner` fallback 은 fail-close 를 유지한다.** 소유자 검증은 인가 게이트이고, Redis 를 못 읽는 상태에서 통과시키면 그것이 곧 인가 우회다. 문서 `:407` 의 "캐시 저장소 일시 장애도 대체 응답으로 흡수돼 채팅 전체 중단 없이 동작"은 **삭제 대상**이다. 대신 "만료 세션 12건이면 서킷이 열려 전체 채팅이 막히는" 문제(3-13)는 실패 분류를 고쳐서 없앤다 — 그쪽이 진짜 원인이다.

### (나) 3-10 — 골든셋 규모와 만드는 방법, "32%→8%" 재현 여부

**결론: 32%→8% 는 재현하지 않는다. `recall@5` 기계 채점으로 기준을 새로 세우고, 골든셋은 24쌍으로 만든다.**

재현하지 않는 이유. 그 수치는 1인 비블라인드 사람 채점이고 원자료가 저장소에 없다(`TUTORING_MEASUREMENT_LOG.html:127` 이 스스로 "별도 / —"). 100문항을 다시 채점해도 여전히 채점자가 구현자이므로 같은 약점이 남고, 비용은 반나절 이상이다. **재현 가능성이 없는 지표에 비용을 쓰는 대신, 기계가 반복 채점할 수 있는 지표로 갈아탄다.** 포트폴리오의 `32% → 8%` 는 P4 에서 `실측` 배지를 떼고 정성 관찰로 강등하거나 삭제한다(P4 4-7 소관).

골든셋 설계.

- **규모 24쌍.** 임계값 스윕 지점이 0.10~0.70 을 0.05 간격으로 13개이고, 한 지점의 recall@5 는 `맞힌 수 / 24` 로 표현된다. 24쌍이면 1건 차이가 4.17%p 라 인접 임계값 간 차이를 읽을 수 있는 최소 해상도가 나온다. 20쌍 미만은 1건이 5%p 를 넘어 잡음과 구분이 안 되고, 30쌍 이상은 수작업 라벨링 비용만 늘고 해상도 이득은 작다.
- **구성.** `강의자료 본문 8` / `기출 문제 지문 8` / `개념 용어 8` 세 카테고리를 8문항씩. 카테고리를 나누는 이유는 "한국어 질문 ↔ 영어 임베딩 정렬"이라는 가설이 카테고리별로 다르게 나타나는지 보기 위함이다.
- **만드는 방법.** 이미 색인된 코퍼스에서 문단을 24개 고르고, 각 문단을 근거로 답해야만 하는 **한국어 질문 1개**를 작성한다. 정답 판정은 문서 id 가 아니라 **그 문단에만 등장하는 앵커 문자열**(고유 용어·수치·고유명사)로 한다. 문서 id 는 재색인 때마다 바뀌지만 앵커는 본문이 안 바뀌는 한 안정적이라, 색인을 다시 태워도 골든셋을 고치지 않아도 된다.
- **비용 통제.** 질문당 임베딩 API 를 13번 부르지 않는다. `similarityThreshold=0.0`, `topK=50` 으로 **질문당 1회만** 검색해 각 문서의 `distance` 를 받아오고, 임계값 스윕은 그 결과를 메모리에서 필터링해 계산한다. 임베딩 호출은 총 24회로 끝난다.
- **`@SpringBootTest` 금지 제약과의 양립.** `VectorStore` 가 필요한 실행부는 테스트가 아니라 `@Profile("ragsweep")` 러너(`RagSweepRunner`)로 둔다. 단위 테스트는 순수 판정 로직(`RecallScorer`)만 검증한다.

### (다) 3-4 — read-after-write 선형화의 범위

**결론: 읽기 전체를 master 로 돌리지 않는다. 창이 항상 열려 있는 읽기 1곳만 master 로 고정하고, 창이 조건부인 1곳은 "실패했을 때만 master 재확인"으로 처리한다.**

세 읽기 지점을 각각 판정한다.

| 읽기 지점 | read-after-write 창 | 결정 |
|---|---|---|
| `getRecentSessionMessages`(`ChatRedisServiceImpl:148`) — 프롬프트 조립 | **항상 열림.** `ChatServiceImpl:270` 이 쓰고 `:278 → OpenAiLlmService:83` 이 같은 요청 안에서 읽는다. 간격이 수 ms | **master 고정** |
| `assertSessionOwner`(`:244`) — 세션 해시 조회 | **조건부.** `initializeSession` 쓰기와 첫 메시지 사이라 보통 수 초. 다만 자동 클라이언트·즉시 재연결에서는 좁아질 수 있음 | **replica 우선, `storedUserId == null` 일 때만 master 로 1회 재확인** |
| `getSessionMessages`(`:142`) — 영속화 경로 | **넓음.** RabbitMQ 발행 → 소비까지 최소 수십 ms 이상. 게다가 Task 8 이 결손을 감지해 DLQ 로 보낸다 | **replica 유지** |

`assertSessionOwner` 를 통째로 master 로 돌리지 않는 이유가 핵심이다. 소유자 검증은 채팅 전 경로의 첫 관문이라 호출량이 가장 많다(`ChatServiceImpl:139, 214, 259, 358, 379` + `ChatMessageConsumer:58`). 이걸 master 로 보내면 읽기 트래픽 대부분이 master 로 몰려 `PORTFOLIO.html:319` 의 "읽기 트래픽을 Replica 로 분산시켜 Master 의 쓰기 부하를 경감"이 사실상 사라진다. 반면 **"세션을 못 찾았다"는 판정 직전에만 master 를 한 번 더 치면**, 정상 경로는 전부 replica 로 가고 복제 지연이 의심되는 순간에만 선형화가 걸린다. 이것이 "read-after-write 창에 한정"의 정확한 구현이다.

Lettuce 의 `ReadFrom` 은 커넥션 팩토리 단위 설정이라 요청 단위로 바꿀 수 없다. 그래서 `ReadFrom.MASTER` 전용 팩토리·템플릿을 하나 더 만들되, 호출량이 적으므로 풀을 작게(`maxTotal=5`) 잡아 커넥션 비용을 억제한다.

측정 가능성도 함께 붙인다. `chat.redis.read` Timer 에 `route=master|replica` 태그를 달아, 분산이 실제로 유지되는지를 비율로 보여줄 수 있게 한다. 문서에 "읽기 분산을 유지하면서 정합성이 필요한 지점만 선형화했다"고 쓰려면 그 비율이 근거로 필요하다.

```java
package spring.backend.shared.config;

import io.netty.channel.ChannelOption;
import java.time.Duration;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.client.reactive.ReactorClientHttpConnector;
import org.springframework.web.reactive.function.client.WebClient;
import reactor.netty.http.client.HttpClient;

// 완성품 대신 Builder 를 빈으로 노출 -> 호출처마다 baseUrl·헤더 등 다르게 커스터마이즈 가능
// 타임아웃 값을 생성자로 받는 이유 -> 설정이 실제로 동작하는지 단위 테스트로 확인 가능해짐
@Configuration
public class WebClientConfig {

  private final Duration connectTimeout;
  private final Duration responseTimeout;

  public WebClientConfig(
          @Value("${app.llm.connect-timeout:5s}") Duration connectTimeout,
          // responseTimeout 은 총 응답 시간이 아니라 read 사이의 최대 간격
          // 토큰이 계속 도착하는 정상 스트리밍은 끊기지 않고 상류가 멈춘 경우만 끊긴다
          @Value("${app.llm.response-timeout:20s}") Duration responseTimeout
  ) {
    this.connectTimeout = connectTimeout;
    this.responseTimeout = responseTimeout;
  }

  @Bean
  public WebClient.Builder webClientBuilder() {
    HttpClient httpClient = HttpClient.create()
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, (int) connectTimeout.toMillis())
            .responseTimeout(responseTimeout);

    return WebClient.builder()
            .clientConnector(new ReactorClientHttpConnector(httpClient));
  }
}
```

```java
import java.util.ArrayList;
import java.util.List;
import org.springframework.ai.chat.messages.Message;
import org.springframework.ai.chat.messages.UserMessage;

// 프롬프트 조립 규칙을 순수 함수로 분리 -> 복제 지연·저장 실패와 무관하게 질문 포함을 단위 테스트로 고정
public final class ChatPromptAssembler {

    private ChatPromptAssembler() {
    }

    // 히스토리는 replica 에서 읽어 stale 일 수 있다
    // 방금 쓴 질문이 빠지면 LLM 이 직전 턴에 다시 답하므로 호출자가 받은 원문을 명시적으로 보장한다
    public static List<Message> withCurrentQuestion(List<Message> history, String userMessage) {
        if (userMessage == null || userMessage.isBlank()) {
            return history;
        }

        String lastUserText = history.stream()
                .filter(m -> m instanceof UserMessage)
                .reduce((first, second) -> second)
                .map(Message::getText)
                .orElse(null);

        if (userMessage.equals(lastUserText)) {
            return history;
        }

        List<Message> merged = new ArrayList<>(history);
        merged.add(new UserMessage(userMessage));
        return merged;
    }
}
```

```java
package spring.backend.domain.chat.security;

import java.util.UUID;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;
import spring.backend.domain.chat.dto.request.SessionScoped;
import spring.backend.domain.chat.service.spec.ChatRedisService;
import spring.backend.shared.response.codes.ErrorCode;
import spring.backend.shared.response.exception.BusinessException;

// 판정 로직은 ChatRedisService 가, 진입 통제는 이 어드바이스가 맡는다
// 둘을 나눠야 새 엔드포인트가 생겨도 검증 호출을 잊는 경로가 생기지 않는다
@Slf4j
@Aspect
@Component
@RequiredArgsConstructor
public class SessionOwnerAspect {

    private final ChatRedisService chatRedisService;

    @Around("@annotation(spring.backend.domain.chat.security.RequireSessionOwner)")
    public Object enforce(ProceedingJoinPoint joinPoint) throws Throwable {
        Object[] args = joinPoint.getArgs();

        Long sessionId = extractSessionId(args);
        UUID userId = extractUserId(args);

        // 규약을 못 맞춘 메서드를 조용히 통과시키면 애너테이션이 방어가 아니라 장식이 된다
        if (sessionId == null || userId == null) {
            log.error("[SessionOwner] sessionId/userId 추출 실패 - method: {}",
                    joinPoint.getSignature().toShortString());
            throw new BusinessException(ErrorCode.INVALID_SESSION);
        }

        chatRedisService.validateSessionOwner(sessionId, userId);

        return joinPoint.proceed();
    }

    private Long extractSessionId(Object[] args) {
        for (Object arg : args) {
            if (arg instanceof Long id) {
                return id;
            }
            if (arg instanceof SessionScoped scoped) {
                return scoped.sessionId();
            }
        }
        return null;
    }

    private UUID extractUserId(Object[] args) {
        for (Object arg : args) {
            if (arg instanceof UUID id) {
                return id;
            }
        }
        return null;
    }
}
```

```java
package spring.backend.shared.infrastructure.security.service;

import jakarta.servlet.http.HttpServletResponse;
import java.time.Duration;
import java.util.UUID;
import java.util.concurrent.TimeUnit;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;
import spring.backend.domain.user.model.enums.Role;
import spring.backend.shared.infrastructure.security.util.JwtUtil;

// 토큰 발급의 유일한 진입점
// 발급 코드가 4곳에 복제돼 있으면 그중 한 곳만 Redis 저장을 빠뜨려도 컴파일도 테스트도 통과한다
@Slf4j
@Component
public class TokenIssuer {

    private static final String REFRESH_KEY_PREFIX = "refreshToken:";

    private final JwtUtil jwtUtil;
    private final StringRedisTemplate redisTemplate;
    // TTL 은 JWT exp 와 같은 설정에서 온다 -> 저장본이 먼저 사라져 재발급이 실패하는 창을 없앤다
    private final Duration refreshTtl;

    public TokenIssuer(
            JwtUtil jwtUtil,
            @Qualifier("authRedisTemplate") StringRedisTemplate redisTemplate,
            @Value("${jwt.refresh-token-expiration}") long refreshTokenExpirationMillis
    ) {
        this(jwtUtil, redisTemplate, Duration.ofMillis(refreshTokenExpirationMillis));
    }

    // 테스트에서 TTL 을 직접 넘기기 위한 생성자
    TokenIssuer(JwtUtil jwtUtil, StringRedisTemplate redisTemplate, Duration refreshTtl) {
        this.jwtUtil = jwtUtil;
        this.redisTemplate = redisTemplate;
        this.refreshTtl = refreshTtl;
    }

    public void issue(HttpServletResponse response, UUID userId, Role role, String name) {
        String accessToken = jwtUtil.generateAccessToken(userId, role, name);
        String refreshToken = jwtUtil.generateRefreshToken(userId);

        jwtUtil.setHttpOnlyAllToken(response, accessToken, refreshToken);

        // 발급과 저장이 한 메서드 안에 있어야 재발급 시 대조할 서버 보관본이 항상 존재한다
        redisTemplate.opsForValue().set(
                REFRESH_KEY_PREFIX + userId,
                refreshToken,
                refreshTtl.toSeconds(),
                TimeUnit.SECONDS);

        log.info("[Auth] 토큰 발급 완료 - userId: {}, refreshTtl: {}", userId, refreshTtl);
    }
}
```

```java
package spring.backend.domain.chat.rag;

import java.util.Comparator;
import java.util.List;
import java.util.Map;

// 사람 채점(32%→8%)은 재현이 불가능해 기계 채점 지표로 갈아탄다
// 판정 기준은 문서 id 가 아니라 본문 앵커 -> 재색인해도 골든셋을 고치지 않아도 된다
public final class RecallScorer {

    private RecallScorer() {
    }

    public static boolean isHit(List<ScoredDocument> docs, String anchor, double threshold, int topK) {
        return docs.stream()
                // similarity = 1 - distance -> OpenAiLlmService.logDebugSearchInfo 와 같은 환산식
                .filter(doc -> (1.0 - doc.distance()) >= threshold)
                .sorted(Comparator.comparingDouble(ScoredDocument::distance))
                .limit(topK)
                .anyMatch(doc -> doc.text().contains(anchor));
    }

    public static double recallAtK(
            Map<GoldenCase, List<ScoredDocument>> results, double threshold, int topK) {
        if (results.isEmpty()) {
            return 0.0;
        }

        long hits = results.entrySet().stream()
                .filter(entry -> isHit(entry.getValue(), entry.getKey().anchor(), threshold, topK))
                .count();

        return (double) hits / results.size();
    }
}
```

```java
package spring.backend.domain.chat.rag;

import com.fasterxml.jackson.databind.ObjectMapper;
import java.io.BufferedWriter;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.ai.document.Document;
import org.springframework.ai.vectorstore.SearchRequest;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Component;

// 테스트가 아니라 러너인 이유 -> VectorStore 가 필요해 단위 테스트로는 못 돌리고
// 이 저장소는 @SpringBootTest 를 쓰지 않는다
@Slf4j
@Component
@Profile("ragsweep")
@RequiredArgsConstructor
public class RagSweepRunner implements ApplicationRunner {

    private static final Path GOLDEN_SET = Path.of("src/test/resources/rag/golden-set.jsonl");
    private static final Path OUTPUT =
            Path.of("docs/measurements/2026-08-07-rag-threshold-sweep.csv");
    private static final int PROBE_TOP_K = 50;
    private static final int SCORE_TOP_K = 5;

    private final VectorStore vectorStore;
    private final ObjectMapper objectMapper;

    @Override
    public void run(ApplicationArguments args) throws Exception {
        List<GoldenCase> cases = loadGoldenSet();
        log.info("[RagSweep] 골든셋 로드 완료 - {}건", cases.size());

        // 질문당 검색 1회 -> 임계값 스윕은 메모리에서 필터링해 임베딩 호출을 24회로 묶는다
        Map<GoldenCase, List<ScoredDocument>> probed = new LinkedHashMap<>();
        for (GoldenCase c : cases) {
            SearchRequest request = SearchRequest.builder()
                    .query(c.question())
                    .topK(PROBE_TOP_K)
                    .similarityThreshold(0.0)
                    .build();

            List<Document> documents = vectorStore.similaritySearch(request);
            probed.put(c, toScored(documents));
        }

        try (BufferedWriter writer = Files.newBufferedWriter(OUTPUT, StandardCharsets.UTF_8)) {
            writer.write("threshold,recall_at_5,recall_강의자료,recall_기출,recall_개념\n");

            for (int step = 2; step <= 14; step++) {
                double threshold = step * 0.05;
                writer.write("%.2f,%.4f,%.4f,%.4f,%.4f%n".formatted(
                        threshold,
                        RecallScorer.recallAtK(probed, threshold, SCORE_TOP_K),
                        recallOf(probed, "강의자료", threshold),
                        recallOf(probed, "기출", threshold),
                        recallOf(probed, "개념", threshold)));
            }
        }

        log.info("[RagSweep] 결과 기록 완료 - {}", OUTPUT.toAbsolutePath());
    }

    private double recallOf(Map<GoldenCase, List<ScoredDocument>> probed,
                            String category, double threshold) {
        Map<GoldenCase, List<ScoredDocument>> subset = new LinkedHashMap<>();
        probed.forEach((c, docs) -> {
            if (category.equals(c.category())) {
                subset.put(c, docs);
            }
        });
        return RecallScorer.recallAtK(subset, threshold, SCORE_TOP_K);
    }

    private List<ScoredDocument> toScored(List<Document> documents) {
        List<ScoredDocument> scored = new ArrayList<>();
        for (Document doc : documents) {
            Object distanceObj = doc.getMetadata().get("distance");
            double distance = distanceObj != null ? ((Number) distanceObj).doubleValue() : 1.0;
            scored.add(new ScoredDocument(doc.getText(), distance));
        }
        return scored;
    }

    private List<GoldenCase> loadGoldenSet() throws Exception {
        List<GoldenCase> cases = new ArrayList<>();
        for (String line : Files.readAllLines(GOLDEN_SET, StandardCharsets.UTF_8)) {
            if (!line.isBlank()) {
                cases.add(objectMapper.readValue(line, GoldenCase.class));
            }
        }
        return cases;
    }
}
```

## 자체 검토 결과

**1. 항목 커버리지.** 3-1~3-17 전부 위 표에 매핑됐다. 마스터플랜 §6 P3 표의 17행과 1:1 대응한다.

**2. 플레이스홀더 스캔.** 초안에서 두 곳을 발견해 고쳤다.
- Task 5 Step 4 에 `getRecentSessionMessagesUnused` 라는 설명용 더미 메서드를 넣었다가 "쓰지 않는다"고 덧붙인 부분 — 실제 교체 코드만 남기고 삭제했다
- Task 6 Step 6 에서 `connectSession` 에 `@RequireSessionOwner` 를 붙이는 코드와 붙이지 말라는 설명이 충돌했다 — 붙이지 않는 쪽으로 통일했다. `connectSession` 은 세션이 아직 없을 수 있어 어드바이스의 "세션 존재" 전제를 만족하지 못한다

측정 산출물 문서(`2026-08-07-ttft.md` 등)의 `(기입)` 은 플레이스홀더가 아니라 **실행 결과를 적을 자리**다. 그 값을 지금 쓰면 그게 곧 이 정산이 없애려는 근거 없는 수치가 된다.

**3. 타입·메서드명 일관성.**
