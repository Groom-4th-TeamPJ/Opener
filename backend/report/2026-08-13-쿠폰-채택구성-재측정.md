# 선착순 쿠폰 채택 구성 재측정 — 폐기한 락 구성의 수치를 대체

- 일자 : 2026-08-13
- 대상 : groom-shopping · 선착순 쿠폰 발급 파이프라인 (포트폴리오 `eco-1`)
- 목적 : 결과 자리에 **채택 구성(Redis Lua 게이트 + Kafka 단일 판정)에서 잰 값이 하나도 부재**하던 문제 해소
- 산출물 : `backend/docs/measurements/coupon_adopted_2026-08-13.json`

## 1. 왜 이 측정이 필요했나

1·2차 교차 검토에서 **서로 다른 4개 에이전트가 독립적으로 같은 곳을 지목**.
결과 4항목 중 유일한 수치가 **폐기한 락 구성**에서 나온 값이었고,
같은 사례 앞부분은 그 락 구성을 두고 "중복 발급 1건을 실제로 관측"이라 적어
*"락은 상호배제가 깨졌다"* 와 *"락 구성에서 상한이 지켜졌다"* 가 나란히 놓임.

직전까지의 처방은 임시방편(수치를 결과 → 문제 원인으로 이동)이었고, 근본 해소는 채택 구성 실측.

## 2. 코드 확인 — 채택 구성이 실제로 그 상태인가

측정 전에 서술과 코드를 대조.

| 서술 | 코드 |
|---|---|
| 발급 경로에서 락 제거 | `CouponController:94` `// 발급 경로는 /issue-async 하나다` |
| 분산 락은 배치로 이관 | Redisson 은 `CouponStockReconciliationService` 에만 잔존 |
| Lua 가 중복을 재고보다 먼저 판정 | `SISMEMBER` → `GET` → `DECR` 순서 |
| 해시태그로 CROSSSLOT 대비 | 키가 `coupon:{1730}:stock` |

## 3. 조건

| 항목 | 값 |
|---|---|
| 쿠폰 수량 | 100 (신규 생성 id=1730) |
| 요청 | 5,000 (`ITERATIONS=5000`) |
| 동시성 | `VUS=200` · `USERS=200` |
| Hikari 풀 | 50 |
| 게이트 초기화 | `CouponStockWarmUpRunner` 가 SETNX 로 `coupon:{1730}:stock=100` |
| 프리플라이트 | DB 100 · Redis 100 · `issued_users` 0 · `coupon_issue` 0 |

## 4. 결과

```
iterations 5000   soldout 2559   dup 2341   pending 100
contention 0      mismatch 0     other 0
latency  avg 2.19s · med 1.13s · p95 6.69s · max 10.6s
```

`issue_success` 가 0 이고 `issue_pending` 이 100 인 것은 **실패가 아님** —
k6 가 접수 후 0.5초 한 번만 폴링하는데 컨슈머 확정이 그보다 늦게 끝난 것.
로그가 `[COUPON_ASYNC_SUCCESS] 100` 으로 전량 성공을 기록.

### 구간 분해

| 구간 | 건수 | 판정 주체 |
|---|---:|---|
| 게이트 차단 | **4,900** | Lua (품절 2,559 · 중복 2,341) |
| 브로커 도달 | **100** | 게이트 통과분 |

**필터율 98.0%.** 포트폴리오가 "100여 건"이라 적던 값이 **정확히 100건**으로 확정.

### 정합성 3중 대조

드레인 완료 후 세 값이 전부 일치.

| 축 | 값 |
|---|---|
| Redis `issued_users` | 100 |
| DB `coupon_issue` 행수 | 100 (사용자 중복 0) |
| DB `coupon.quantity` | 100 → 0 |

측정 직후 스냅샷은 60행 · quantity 31 로 어긋나 보였으나 **컨슈머 드레인 중이던 것** —
정합성 검증은 큐가 빈 뒤에 해야 성립.

## 5. 지연 수치는 사용 불가

`med 1.13s · p95 6.69s` 는 이전 런(`coupon.json`, med 341ms, 같은 VU 200 · 5,000)보다 3.3배 느림.
원인은 머신 부하 — **load average 12.47 / 10코어**로, 이 저장소가 세워 둔 전제(load < 10)를 초과.

건수는 결정적 결과라 부하와 무관하지만 지연은 종속되므로 **문서에 넣지 않음.**
포트폴리오의 어느 주장도 이 값을 필요로 하지 않음 — 핵심 주장인 "거짓 품절 소멸"은 카운터 0 으로 성립.

## 6. 문서 반영

`backend/docs/portfolio/PORTFOLIO.html` 4곳.

- **결과 신규 항목** — 채택 구성 실측(5,000 → 게이트 차단 4,900 → 브로커 100, 확정 100, 초과·중복 0,
  미초기화 폴백 0). 마지막 조건이 중요 — 폴백이 0 이어야 이 수치가 DB 폴백이 아닌 게이트를 잰 값
- **결과 "락과 DB를 동시에 제거"** — `거짓 품절이 원인 단계에서 소멸` 뒤에 `재측정에서 경합 실패 0건` 추가
- **해결 과정** — `5,000건 중 100여 건` → `5,000건 중 100건`
- **아키텍처 SVG 라벨** — `5,000건 → 통과 100여 건` → `통과 100건`
