# Redis 선점 게이트 재측정 — 정성 주장을 실측으로 교체

- 일자 : 2026-08-13
- 대상 : groom-shopping · 재고 차감 전략 설계 (포트폴리오 결과 [3])
- 목적 : `PG 호출 자체를 차단` 이 차단 건수 없이 정성 주장만이던 문제 해소

## 1. 측정 조건

기존 p2 런은 전부 초기 재고 10,000 · 시도 10,000 이라 **재고가 바닥나지 않아 게이트가 발동할 일이 없었음**
(`backend/docs/measurements/p2/README.md` 가 `confirm_blocked` 를 전 런 0건으로 기록한 이유).
게이트를 실제로 발동시키려고 재고만 3,000 으로 낮춤.

| 항목 | 값 |
|---|---|
| 초기 재고 | 3,000 (DB · Redis 동시 확인) |
| 시도 | 10,000 (`ITERATIONS=10000`) |
| 동시성 | `VUS=20` · `USERS=200` |
| 차감 전략 | 비관적 락 (`stock_optimistic_retries` 메트릭 부재로 확인) |
| Hikari 풀 | 50 |
| PG | WireMock healthy `:9300` |
| 산출물 | `backend/docs/measurements/p2/p2_gate_stock3000_vu20.json` |

## 3. 해석 — `other_fail` 6,989 는 실패가 아님

k6 스크립트는 **주문 생성(`POST /order`)이 201 이 아니면 곧바로 `confirm_other_fail` 로 계상하고 반환**함
(`k6/scripts/stock-concurrency-test.js`). 즉 이 6,989 건은 결제 확정에 도달조차 안 함.

`OrderApplicationService.java:98` 이 `product.getStock() < quantity` 일 때 `INSUFFICIENT_STOCK` 을 던지는 것이 반려 지점.

**세 근거가 상호 일치 :**

| 근거 | 값 | 대조 |
|---|---|---|
| 로그 `INSUFFICIENT_STOCK` | 34,956 건 | ÷ 주문 생성 재시도 5회 = **6,989** — `other_fail` 과 일치 |
| 로그 `[STOCK_RESERVE_OUT]` | 11 건 | `confirm_blocked` 와 일치 |
| DB 최종 재고 | 0 | 3,000 − 3,000(success) — 초과판매 0 |
| Redis 최종 | 0 | DB 와 일치 — 드리프트 0 |

폴백·충돌·보상 마커는 전량 0건 :
`[STOCK_RESERVE_FALLBACK]` 0 · `[STOCK_CONFLICT_GIVEUP]` 0 · `[PAYMENT_CONFIRM_DB_FAILED]` 0 ·
`[PAYMENT_COMPENSATION_SUCCESS]` 0 · `[PAYMENT_COMPENSATION_FAILED]` 0.

### 구간별 최종 분해

| 구간 | 건수 | 판정 주체 |
|---|---:|---|
| 결제 확정 성공 | 3,000 | 비관적 락 차감 |
| 주문 생성 반려 | 6,989 | `OrderApplicationService` 재고 검증 (결제 미도달) |
| Redis 게이트 차단 | 11 | `preReserve` DECR → `-1` (`PaymentApplicationService:181`) |

## 4. 결론 — 게이트의 값어치는 대량 차단이 아님

주문 생성의 재고 검증은 **읽고 나서 판단하는 비원자 검사**라, 통과한 뒤 결제 확정에 닿기까지의
틈에서 재고가 바닥나는 것을 막지 못함. Redis `DECR` 은 읽기와 차감이 한 연산이라 **그 틈만 전담**.

따라서 11 이라는 작은 수가 정상. 대량 트래픽은 앞단 검사가 이미 제거했고, 게이트에 도달하는 것은
경쟁 구간에 들어온 요청뿐이며 그 폭은 대략 동시성(VU 20) 규모.

**11 건은 상한이 아니라 하한** — k6 는 주문 생성 직후 곧바로 결제를 호출해 틈이 최소인 조건.
실사용자는 결제 수단 선택에 수십 초를 쓰므로 실제 창은 이보다 넓음.

## 5. 문서 반영

`backend/docs/portfolio/PORTFOLIO.html` 2건 수정.

- **결과 [3]** — 비용 절감(PG 왕복·환불) 앞세우기를 폐기하고 구간 분해 실측으로 교체.
  절감된 PG 호출이 11 건뿐이라, 비용을 근거로 삼으면 "그 정도면 게이트가 왜 필요한가" 에 답이 부재.
  대신 앞단 검사가 원리적으로 못 덮는 경쟁 구간 전담을 근거로 삼음
- **문제 원인 [3]** — `재고가 바닥난 상품인데도 결제 시도가 PG까지 도달` 은 실측과 충돌(대부분 주문 생성에서 반려).
  `비원자 검사의 판단·차감 사이 틈` 으로 좁힘. 좁히지 않으면 문제 원인이 결과보다 넓어 논리가 어긋남
