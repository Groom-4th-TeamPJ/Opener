기존 문단은 이렇게 쓰여 있었다:

같은 문제를 풀지만 회고가 아니라 설계가 된다.

## 축 1 — 재고 워밍업으로 폴백 진입 제거

### 현재 사실

| 항목 | 코드 근거 |
|---|---|
| `initStock` 프로덕션 호출자 | `CouponIssueService.java:219` **단 1곳** (DB 폴백 내부) |
| `CouponCommonService.createCoupon` | `initStock` 호출 **없음** (`:32-55`) |
| `StockWarmUpRunner` | 존재하나 **상품 전용**, 쿠폰 미취급 (`infrastructure/product/StockWarmUpRunner.java:46`) |

→ **모든 쿠폰의 첫 발급 요청은 반드시 `NOT_INITIALIZED` 로 DB 비관적 락 폴백을 탄다.**
이벤트 시작 순간이 곧 최대 트래픽 시점이므로, 하필 그때 다수 요청이 동시에 폴백으로 몰린다.

### 설계

1. 쿠폰 생성 시점(`createCoupon`)에 `initStock(couponId, quantity)` 호출
2. 이벤트 시작 전 배치 워밍업 러너 추가 (상품 쪽 `StockWarmUpRunner` 와 동일 패턴)
3. 폴백은 **삭제하지 않고 유지** — 워밍업 누락·Redis 재기동 시의 최후 방어선

### 효과

- 락 보유 시간에 DB I/O 가 포함되는 구간이 **정상 운영에서 발생하지 않음**
- 분산 락은 사용자 요청대로 **유지**되며, 역할이 "정상 경로 직렬화"가 아니라
  **"두 저장소에 걸친 예외 경로의 배타성 보장"** 으로 명확해진다

> 이것이 "락 범위를 좁히겠다"를 대체하는 서술이다. 락은 그대로 두고 **락이 비싼 일을 하는 상황을 없앤다.**

## 축 2 — 핫 쿠폰 재고 샤딩

### 현재 사실

- 재고 키: `coupon:stock:{couponId}` **단일 키** (`CouponStockRedisRepository.java:28`)
- 락 키: `coupon:lock:{couponId}` **단일 키** (`CouponIssueService.java:68`)
- `shard` 검색 결과 **0건**

→ 동일 쿠폰의 모든 요청이 **하나의 락 + 하나의 카운터**로 완전 직렬화된다.
이것이 현재 구조의 처리량 상한이다. 서버를 늘려도 이 벽은 그대로다.

### 설계

**재고 분할**: 수량 `Q` 를 `N` 개 샤드로 나눈다. 나머지는 앞 샤드부터 1씩 더한다.

```
Q = 1000, N = 8  →  shard0..shard7 = 125 each
Q = 1003, N = 8  →  shard0..2 = 126, shard3..7 = 125
```

**키 설계 — 해시 태그 필수**

```
coupon:{couponId}:stock:{shard}     ← 샤드별 재고
coupon:{couponId}:lock:{shard}      ← 샤드별 락
coupon:{couponId}:issued            ← 발급자 SET (샤딩하지 않음)
```

`{couponId}` 를 **해시 태그**로 감싸는 이유: Redis Cluster 에서 Lua 의 multi-key 연산은
모든 KEYS 가 **같은 슬롯**에 있어야 한다. 태그가 없으면 `stock:3` 과 `issued` 가 다른 노드로 흩어져
스크립트가 `CROSSSLOT` 으로 실패한다.
(같은 이유로 Opener 채팅 도메인도 `chat:{sessionId}:messages` 형태를 쓴다 — 프로젝트 간 일관된 판단)

**샤드 배정**: `shard = hash(userId) % N`

`userId` 기준이어야 하는 이유 — 같은 사용자의 재시도가 **항상 같은 샤드**로 가야
중복 판정이 흔들리지 않는다. 라운드로빈이나 랜덤이면 재시도마다 다른 샤드로 가서
샤드별 상태를 신뢰할 수 없게 된다.

**발급자 SET 은 샤딩하지 않는다**

1인 1매 판정은 **전역**이어야 한다. SET 을 샤드별로 쪼개면 한 사용자가
여러 샤드에서 각각 1매씩 받을 수 있다. `SISMEMBER`/`SADD` 는 O(1) 이고
Redis 는 어차피 단일 스레드라 이 키가 병목이 되지 않는다 —
**제거되는 병목은 Redis 명령이 아니라 분산 락 대기**다.

### 샤드 편차 문제와 대응

샤딩의 대가는 **"전체 재고는 남았는데 내 샤드만 비어 품절 응답"** 이다. 2단으로 막는다.

**(a) 샤드 스틸(steal)** — Lua 안에서 처리하므로 원자성 유지

자기 샤드가 0이면 `(shard+1) % N` 부터 순회한다. Lua 에 KEYS 배열로 전체 샤드 키를 넘기면
스크립트 한 번의 실행 안에서 탐색·차감이 끝나므로 check-then-act 경합이 생기지 않는다.

```lua
-- KEYS[1..N] = 샤드 재고 키(자기 샤드부터 회전 정렬), KEYS[N+1] = 발급자 SET
-- ARGV[1] = userId
if redis.call('SISMEMBER', KEYS[#KEYS], ARGV[1]) == 1 then
    return -1                      -- 중복 발급
end
for i = 1, #KEYS - 1 do
    local s = tonumber(redis.call('GET', KEYS[i]))
    if s == nil then
        return -2                  -- 미초기화 → 폴백
    end
    if s > 0 then
        redis.call('DECR', KEYS[i])
        redis.call('SADD', KEYS[#KEYS], ARGV[1])
        return i                   -- 차감에 성공한 샤드 번호
    end
end
return 0                           -- 전 샤드 소진 = 진짜 품절
```

**중복 검사를 루프 앞으로 뺀 것이 핵심**이다. 루프 안에 두면 샤드 수만큼 `SISMEMBER` 가 돌아
스크립트 실행 시간이 길어지고, Redis 단일 스레드를 그만큼 오래 점유한다.

**(b) 잔여 회수(rebalance)**

스틸은 탐색 비용이 최대 N회다. 소진 말기에는 대부분의 샤드가 0이라 매 요청이 N회를 다 돈다.
잔여 재고가 임계치 이하로 떨어지면 **남은 샤드를 하나로 합치는** 주기 작업을 둔다.
이 프로젝트에는 이미 Kafka Streams Punctuator 기반 지연 처리(eco-4)가 있으므로 **같은 메커니즘을 재사용**한다.

### 효과

- 락 경합이 이론상 `1/N`
- 정확성은 그대로: 초과발급 방어는 여전히 **Lua 원자성**이 담당하며, 샤딩은 **처리량 축**만 건드린다

## 축 3 — ZSet 대기 상태 (기존 자산의 확장)

### 현재 사실 — 이미 구현되어 있다

| 키 | 자료구조 | 용도 | 근거 |
|---|---|---|---|
| `coupon:seq:{couponId}` | String(INCR) | 접수 순번 발급기 (score 소스) | `CouponQueueRedisRepository.java:27` |
| `coupon:queue:{couponId}` | ZSet | `member=userId`, `score=seq` 대기열 | 같은 파일 `:28` |
| `coupon:issue:status:{requestId}` | String | `WAITING`/`SUCCESS`/`FAILED:{code}` | `CouponAsyncIssueService.java:31` |

- 조회 API: `GET /v1/coupon/issue-async/{coupon_id}/position` → `rank` + `size`
- `ZADD NX` 라 재요청해도 순번이 뒤로 밀리지 않는다
- 코드 주석(`:14`)이 **"보장 순번이 아니라 추정 순번"** 이라고 명시 — 실제 순서는 Kafka 파티션이 결정

> **포트폴리오 서술 주의**: "ZSet 을 도입하겠다"고 쓰면 **거짓**이다. 이미 있다.
> **"기존 ZSet 대기열을 샤딩과 결합한다"** 로 써야 사실이면서 설계 깊이가 드러난다.

### 샤딩과 결합할 때의 결정

1. **순번은 전역 유지** — 샤드별 순번은 사용자에게 의미가 없다("당신은 3번 샤드의 12등"은 정보가 아니다)
2. **샤드 정보는 응답에 노출하지 않는다** — 내부 분산 전략이 API 계약에 새면 나중에 N을 못 바꾼다
3. **현재 한계 보완** — 컨슈머가 예외를 로깅 후 삼켜(`CouponIssueRequestConsumer.java:30-33`)
   `requestId` 가 영원히 `WAITING` 에 남는다. DLQ 를 추가하고, 상태 TTL 만료를
   `UNKNOWN` 이 아니라 **타임아웃 확정 실패**로 전이시킨다

## 축 4 — 결제 시 쿠폰 재고 선점 (신규 · 실제 갭 해소)

### 현재 사실 — 방어가 없다

| 단계 | 방어 | 근거 |
|---|---|---|
| **발급** | 이중 방어 | Lua `SISMEMBER` (`CouponStockRedisRepository.java:43`) + DB `findByCouponIdAndUserId` (`CouponIssueService.java:204`) |
| **사용(소진)** | **없음** | `useCoupon`(`:393`) 프로덕션 호출자 **0건** — 테스트에서만 호출 |
| 결제 계층 | 쿠폰 참조 **0건** | `application/payment`·`domain/payment`·`interfaces/payment` 전체 검색 |

주문 생성 시 `calculateDiscount` 로 **할인액만 계산**하고(`OrderApplicationService.java:121-127`),
쿠폰을 소진 상태로 바꾸지 않는다.

→ **발급받은 쿠폰 1장으로 주문을 반복 생성하면 매번 할인이 적용된다.**
게다가 `useCoupon` 자체도 락 없는 read-modify-write(`:395-404`) 라 호출자가 생겨도 동시 요청에 취약하다.

### 설계 — 쿠폰 수명주기를 3상태로

```
ISSUED  ──(주문 생성)──▶  HELD  ──(결제 승인)──▶  USED
                          │
                          └──(결제 실패 / TTL 만료)──▶ ISSUED (복귀)
```

**1) 선점 (주문 생성 시)**

```
SET coupon:hold:{couponId}:{userId} {orderId} NX EX 600
```

- `NX` 가 **중복 선점을 원자적으로 차단**한다 — 이미 잡혀 있으면 실패
- `EX 600`(10분) — 결제가 중단돼도 선점분이 영구히 묶이지 않는다
- 값에 `orderId` 를 담아 **어느 주문이 잡았는지** 추적 가능

**2) 확정 (결제 승인 시)**

- `couponIssue.usedAt` 기록 + `isActive = false`
- **멱등키 = `orderId`** — PG 웹훅이 중복 도착해도 두 번 소진되지 않는다
- DB 유니크 제약 `(coupon_issue_id, order_id)` 로 최종 방어

**3) 해제 (결제 실패 / 타임아웃)**

- 명시적 `DEL` + TTL 자연 만료의 이중 회수
- eco-2 의 **Saga 보상 트랜잭션과 동일한 패턴** — 프로젝트 안에서 일관된 메커니즘

### 이 설계의 서술 가치

> 발급 단계는 이중 방어인데 소진 단계는 무방비였다.
> **동시성 방어는 자원의 수명주기 전체에 걸려야 완성된다** — 입구만 잠근 창고는 잠그지 않은 창고와 같다.

이 한 줄이 항목 4 재작성의 핵심 메시지다. 자백이 아니라 **원칙의 확장**으로 읽힌다.

## 축 5 — 락 수명 관리 (leaseTime · 워치독)

### 현재 사실

| 항목 | 값 | 코드 근거 |
|---|---|---|
| 락 종류 | **비공정 락** `getLock()` | `CouponIssueService.java:107` |
| 획득 방식 | `tryLock(waitTime=3s, leaseTime=5s)` | `:69-70`, `:111` |
| 임계 구역 범위 | `persistIssuedCoupon` 의 **DB 트랜잭션 전체 포함** | `:137` |
| Redis 연결 | `useSingleServer()`, 커넥션 풀 32 / minIdle 8 | `RedissonConfig.java:31-34` |
| `lockWatchdogTimeout` | **미지정 → Redisson 기본값 30,000ms** | 설정 자체가 없음 |
| Redisson 버전 | 3.27.2 | |

### 실측 — leaseTime 이 실제로 터졌다

k6 VU 200 · 5,000 요청 부하 (2026-07-30)

- 발급 요청 지연 **중앙값 10,650ms** ≫ leaseTime **5,000ms**

| 저장소 | 관측값 |
|---|---|
| DB `coupon.quantity` | 60 |
| DB `coupon_issue` 행 수 | 54 |
| DB distinct user | **53** (= 중복 발급 1건) |
| Redis 재고 | 49 |
| Redis 발급자 SET | 52 |

**네 숫자가 하나도 서로 맞지 않는다.** 초과발급 방어와 두 저장소 간 정합성이 **동시에** 붕괴했다.
원인은 단순하다 — 임계 구역이 끝나기 전에 leaseTime 이 만료돼 락이 자동 해제되고,
대기하던 스레드가 아직 작업 중인 구역으로 그대로 들어왔다.
**락을 걸었지만 락이 없는 것과 같은 상태**가 지연 10초 구간에서 만들어졌다.

### 워치독의 정확한 동작 — 이 절의 핵심은 오해 교정이다

Redisson 의 워치독은 흔히 "락을 무제한으로 잡아두는 위험한 옵션"으로 알려져 있는데, 사실이 아니다.

1. `tryLock(waitTime, unit)` 처럼 **leaseTime 을 생략**하면 워치독이 활성화된다
2. 락 TTL 을 `lockWatchdogTimeout`(기본 30초)으로 걸고, **`timeout/3` = 10초마다 갱신**한다
3. 프로세스가 죽으면 **갱신 스레드도 함께 죽는다** → 갱신이 멈추고 Redis 가 최대 30초 뒤 키를 만료시킨다

→ **인스턴스 크래시로 인한 영구 데드락은 발생하지 않는다.**
워치독은 "무제한 보유"가 아니라 **"유한 TTL 의 반복 갱신"** 이다.
지금 코드는 이 옵션을 쓰지 않으므로(고정 leaseTime 5초) 워치독의 기본값 30초는 **아직 아무 역할도 하고 있지 않다.**

### 워치독의 실제 위험 — 크래시가 아니라 다른 것

| 위험 | 내용 | 심각도 |
|---|---|---|
| **hang** | JVM 이 살아 있는 한 갱신이 계속된다 → 멈춘 스레드가 락을 무한 점유. **이것이 진짜 데드락** | 높음 |
| GC 정지 / 네트워크 단절 | 살아 있는데 갱신을 못 보낸다 → 락 만료 → 이중 진입. leaseTime 과 **같은 종류의 사고**이고 창이 5초에서 30초로 넓어질 뿐 | 중간 |
| 갱신 트래픽 | 락 하나당 10초에 1회 | 낮음 |

즉 워치독은 **"임계 구역이 예상보다 길어지는 경우"** 를 덮어주지만,
**"임계 구역이 끝나지 않는 경우"** 는 오히려 더 나쁘게 만든다.

### waitTime 과 leaseTime 은 다른 문제다 — 반드시 분리해서 읽어야 한다

| | 초과했을 때 벌어지는 일 | 잃는 것 | 워치독이 해결하나 |
|---|---|---|---|
| `leaseTime` (5초) | 작업 도중 락이 조기 해제 | **정합성** | ✅ 해결한다 |
| `waitTime` (3초) | 대기 중인 요청이 포기 | **가용성**(드랍) | ❌ 무관하다 |

두 값을 같이 묶어 "락 타임아웃"이라고 부르면 잘못된 처방이 나온다.
지금 코드에서 `waitTime` 초과 실패는 `COUPON_OUT_OF_STOCK` 으로 매핑되므로(`CouponIssueService.java:112-115`),
**재고가 남아 있는데도 사용자에게 품절로 응답한다.** 경합 실패와 품절이 같은 에러코드를 쓰고 있어
운영 중에 이 둘을 구분할 방법이 없다.

### 설계 — 권고 순서

**1) 임계 구역을 먼저 줄인다 (축 1과 동일한 처방)**

워치독은 긴 임계 구역을 **버티게** 할 뿐 **짧게** 만들지 못한다.
축 1(워밍업)으로 정상 경로에서 DB I/O 를 들어내면 leaseTime 압박 자체가 사라진다.
순서를 뒤집어 워치독부터 켜면 "10초짜리 임계 구역"이 정상 상태로 굳어진다.

**2) 워치독 전환과 상한을 함께 건다**

- `tryLock(waitTime, unit)` 형태로 전환해 leaseTime 만료로 인한 조기 해제를 없앤다
- `lockWatchdogTimeout` 을 기본 30초에서 **10~15초로 단축** — 크래시 후 회수 지연을 줄인다
- **DB 쿼리 타임아웃**과 임계 구역 애플리케이션 데드라인을 함께 건다

세 번째가 빠지면 안 된다. hang 대응이 없는 워치독은 무한 점유를 **허용하는** 설정이다.

**3) 드랍은 `waitTime` 을 늘려서 풀지 않는다**

`waitTime` 을 3초에서 10초로 늘리면 드랍은 줄지만 톰캣 스레드가 락 대기에 묶여 고갈된다.
쿠폰 발급이 서비스 전체를 끌어내리는 구조가 된다. 대신:

- **경합 전용 에러코드 분리** — 품절과 "지금 붐빔"을 구분해 클라이언트가 재시도 여부를 판단하게 한다
- **핫 쿠폰은 비동기 경로로 유도** — 축 3의 대기열이 이미 그 목적으로 존재한다
- **축 2(샤딩)로 대기열 자체를 짧게** 만든다

### 효과

- 정합성 붕괴의 직접 원인(조기 해제) 제거
- 락 실패를 **정합성 문제(leaseTime)** 와 **가용성 문제(waitTime)** 로 분리해 각각 다른 처방을 적용

> **서술 가치**: "타임아웃 값을 늘렸습니다"가 아니라
> **"타임아웃 하나가 두 가지 다른 실패를 감추고 있었다"** 가 이 절의 메시지다.
> 실측 수치 네 개가 전부 어긋난 표는, 락을 걸었다는 사실만으로는 아무것도 보장되지 않는다는 근거가 된다.

## 축 6 — 순번과 판정의 일원화 (선착순 공정성)

### 현재 사실 — 도착 순 발급은 보장되지 않는다

순서가 흐트러지는 지점이 **세 곳**이다.

**① 동기 경로 — 비공정 락**

`getLock()` 은 FIFO 를 보장하지 않는다. FIFO 를 원하면 `getFairLock()` 이어야 하는데
저장소 전체에서 **검색 0건**이다. 대기자 중 승자는 **락 해제 pub/sub 알림이 도착한 순서**로 정해지며,
요청이 서버에 도착한 순서와 아무 관계가 없다.

**② 비동기 경로 — 순번 발급과 큐 적재가 비원자적**

`CouponAsyncIssueService.enqueue`(`:52`)는

1. `couponQueueRedisRepository.enqueue`(`:58`) — INCR seq → ZADD NX
2. 그다음 **별도로** Kafka 발행 (`:62`)

두 단계 사이에 원자성이 없다. seq=1 을 받은 요청이 seq=2 를 받은 요청보다 **늦게 Kafka 에 도달**할 수 있다.
→ 화면에 "1번"으로 표시된 사용자가 "2번"보다 나중에 발급된다.
**표시 순번과 실제 결과 사이에 인과관계가 없다.**

**③ Kafka 프로듀서가 순서 역전을 허용한다**

`KafkaConfig` 의 프로듀서 설정(`:73-74`, `:129`, `:134`):

| 설정 | 값 | 함의 |
|---|---|---|
| `acks` | `1` | 명시했으므로 **멱등 프로듀서 비활성** |
| `retries` | `3` | 재시도 발생 |
| `max.in.flight.requests.per.connection` | **미설정 → 기본 5** | 동시 전송 배치 5개 |

`retries>0` + `max.in.flight>1` + 멱등성 off = **재시도 중 뒤 배치가 먼저 기록될 수 있다.**

`key=couponId` 로 같은 파티션에 보내도 이건 막지 못한다.
파티션이 보장하는 것은 **"기록된 순서대로 읽힌다"** 이지 **"보낸 순서대로 기록된다"** 가 아니다.

**코드가 이미 이 한계를 인정하고 있다** — `CouponQueueRedisRepository.java:14` 주석:

> 실제 처리 순서는 Kafka 파티션이 결정하므로, 이 순번은 "보장"이 아니라 "추정 대기 순번"이다.

### 정확성과 공정성은 다른 보장이다 — 이 절의 프레임

| | 보장 여부 | 근거 |
|---|---|---|
| **정확성** = 초과발급 0 | ✅ | Lua 원자 연산. 실측 `issue_success = 100` (수량 100) |
| **공정성** = 도착 순 발급 | ❌ | 위 ①②③ |

두 개를 뭉뚱그리면 "그래서 선착순이 맞나요"라는 질문에 답할 수 없다.
**정확성은 이미 지켜지고 있고, 공정성은 애초에 목표가 아니었다** — 이렇게 분리해야 논의가 성립한다.

그리고 분산 시스템에서 **"먼저 클릭한 순"은 서버가 알 수 없다.**
클라이언트 네트워크 편차, 로드밸런서 분배, 톰캣 스레드 스케줄링이 전부 서버 도달 전에 순서를 흐트러뜨린다.
현실의 선착순은 예외 없이 **"먼저 처리된 순"** 이다. 설계가 정할 수 있는 것은
"어디를 기준점으로 삼고, 그 기준점을 사용자에게 정직하게 보여줄 것인가"뿐이다.

### 대안 3가지

| 안 | 방법 | 대가 |
|---|---|---|
| ① 공정 락 | `getFairLock()` — Redisson 내부 List 로 FIFO 대기열 | Redis 왕복 급증 → 처리량 급락. 게다가 "Redis 도착 순"이라 근본 한계는 동일 |
| ② Kafka 순서 강화 | `enable.idempotence=true` + `acks=all` | 지연 증가. ①②의 역전은 **여전히 못 막는다** |
| ③ **순번을 판정의 근거로 승격** ← **권고** | Lua 한 번에 중복 검사 → `INCR seq` → `seq <= quantity` 판정 → 발급자 등록 → 순번 반환 | 재고 카운터(DECR)와 순번 카운터를 합치므로 **기존 Lua 재작성 필요** |

### ③안 설계

```lua
-- KEYS[1] = coupon:{couponId}:seq       순번 카운터
-- KEYS[2] = coupon:{couponId}:issued    발급자 SET
-- ARGV[1] = userId, ARGV[2] = quantity(정원)
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1                                  -- 중복 요청: 순번을 소비하지 않는다
end
local seq = redis.call('INCR', KEYS[1])
if seq > tonumber(ARGV[2]) then
    return 0                                   -- 정원 초과 = 확정 품절
end
redis.call('SADD', KEYS[2], ARGV[1])
return seq                                     -- 당첨 순번 = 사용자에게 보여줄 번호
```

**핵심 논지**: Redis 는 단일 스레드이므로 이 스크립트의 실행 순서가 곧 **도달 순서의 정의**다.
그 순서가 **당첨 여부이자 사용자에게 보여줄 번호**가 되므로
순번과 결과가 **정의상 일치**한다. 어긋날 여지가 구조적으로 없다.
그리고 판정이 Redis 한 번의 원자 실행 안에서 끝나므로 **정상 경로에 분산 락이 필요 없어진다.**

세부 결정 세 가지:

1. **중복 요청은 `INCR` 전에 걸러낸다** — 재시도가 순번을 소비하면 seq 와 실제 발급 수가 벌어져
   `seq <= quantity` 판정이 정원보다 적게 발급하는 쪽으로 틀어진다
2. **탈락자도 seq 를 소비한다** — `seq > quantity` 인 요청도 카운터는 올린다.
   그 값이 곧 "몇 번째로 늦었는가" 이므로 대기 인원 지표로 그대로 쓸 수 있다
3. **당첨 순번의 재조회** — SET 대신 HASH(`HSETNX coupon:{id}:issued userId seq`)를 쓰면
   중복 검사·등록·순번 보관이 한 연산으로 합쳐지고, 재접속한 사용자가 자기 번호를 다시 조회할 수 있다.
   SET 만 쓰면 응답을 놓친 사용자는 자기 순번을 잃는다

**`quantity` 는 ARGV 로 넘긴다** — Redis 에 재고 카운터를 따로 두지 않는다.
대신 애플리케이션이 쿠폰 정원을 알아야 하므로 **메타 캐시가 전제**가 된다(축 1과의 관계는 아래 충돌 검토 참조).

### 효과

- 표시 순번과 발급 결과가 **정의상 일치** — "1번인데 실패"가 원천적으로 불가능
- 정상 경로에서 분산 락 제거 → 축 5의 leaseTime 문제가 정상 경로에서 소멸
- `NOT_INITIALIZED` 폴백 진입 조건이 사라진다 (`INCR` 은 키가 없으면 0에서 시작하므로 초기화 개념이 없다)

> **서술 가치**: "공정하게 만들었습니다"가 아니라
> **"공정성은 락을 바꿔서 얻는 게 아니라, 순번을 판정의 근거로 만들어서 얻는다"** 가 이 절의 메시지다.
> ①②를 검토하고 기각한 과정 자체가 근거가 된다 — 공정 락은 처리량을 버리고도 근본 문제를 못 풀고,
> Kafka 순서 강화는 애초에 역전 지점이 Kafka 밖에 있어서 무효다.

## 6개 축의 상호 충돌 검토

| 조합 | 충돌 여부 | 근거 |
|---|---|---|
| 샤딩 × 분산 락 | 없음 | 락 키도 샤드 단위로 분리(`coupon:{id}:lock:{shard}`). 샤드 하나가 임계 구역 하나 |
| 샤딩 × 1인 1매 | **주의** | 발급자 SET 을 **샤딩하지 않아야** 성립. 샤딩하면 다중 발급 뚫림 |
| 샤딩 × Redis Cluster | **주의** | 해시 태그 `{couponId}` 없으면 Lua multi-key 가 `CROSSSLOT` 실패 |
| 샤딩 × ZSet 순번 | 없음 | 순번은 전역 `coupon:seq:{id}` 유지, 샤드와 독립 축 |
| 샤딩 × 워밍업 | 없음 | 워밍업이 `Q/N` 로 나눠 시딩. 오히려 워밍업이 **샤딩의 전제** |
| 재고 선점 × 발급 경로 | 없음 | 선점은 **주문/결제 단계**. 발급 파이프라인과 시간축이 분리 |
| 재고 선점 × Saga 보상 | 없음 | 동일 패턴 재사용 — 보상 대상에 쿠폰 HOLD 해제가 추가될 뿐 |
| 락 수명 × 워밍업 | 없음 (상호 보강) | 워밍업이 임계 구역에서 DB I/O 를 빼면 leaseTime 압박 자체가 사라진다. **축 1이 축 5의 전제** |
| 락 수명 × 샤딩 | 없음 | 샤드별 락이므로 락 하나의 보유 시간은 그대로지만 대기열이 `1/N` → `waitTime` 드랍이 줄어든다. 동시 보유 락이 N개가 되어 워치독 갱신 트래픽이 N배지만 10초에 N회 수준 |
| 락 수명 × ZSet 대기열 | 없음 | 축 5의 3번 권고(드랍을 비동기 경로로 유도)가 축 3의 대기열을 **사용처로 삼는다** |
| **순번 일원화 × 샤딩** | **충돌** | 아래 별도 항목 |
| **순번 일원화 × 락 수명** | **주의** | 축 6이 정상 경로의 락을 없애면 축 5는 **폴백 구간 전용**으로 범위가 좁아진다. 무의미해지지는 않는다 — 아래 별도 항목 |
| 순번 일원화 × 워밍업 | **주의** | 축 6은 재고 카운터를 없애므로 `NOT_INITIALIZED` 폴백이 사라진다 → 축 1의 "재고 시딩" 역할이 **"쿠폰 정원(`quantity`) 메타 캐시 워밍업"** 으로 바뀐다. 축 1이 불필요해지는 게 아니라 **대상이 바뀐다** |
| 순번 일원화 × ZSet 대기열 | 없음 (강한 시너지) | 축 3의 ZSet score 가 이미 `coupon:seq:{id}` 다. 축 6은 그 seq 를 판정 근거로 승격할 뿐이라 자료구조 변경이 없다. 오히려 `seq` 하나로 순위 계산이 되므로 `ZRANK` 조회 없이도 대기 순번 응답이 가능해진다 |
| 순번 일원화 × 재고 선점 | 없음 | 축 4는 **발급 이후**의 수명주기. 시간축이 분리 |
| 순번 일원화 × Kafka 순서 | 없음 (문제 해소) | 축 6은 판정을 Redis 도달 시점으로 확정하므로 Kafka 도착 순서가 **결과에 영향을 주지 않는다**. `enable.idempotence` 논의(②안)가 불필요해진다 |

### 충돌 1 — 축 6(순번 일원화) × 축 2(샤딩)

**정면 충돌이다.** 축 2는 카운터를 N개로 쪼개 직렬화를 푸는 설계이고,
축 6은 **전역 카운터 하나의 순서가 곧 판정**이라는 설계다. 샤딩하면 전역 순번이 성립하지 않는다.

세 가지 해소안을 검토한다.

| 해소안 | 방법 | 판정 |
|---|---|---|
| (a) 샤드별 seq + 샤드별 정원 | `shard = hash(userId) % N`, 각 샤드가 `Q/N` 을 배분받고 샤드 내 seq 로 판정 | ❌ 사용자에게 보여줄 번호가 다시 "3번 샤드의 12등"이 된다. 전역 번호를 따로 매기면 **표시 순번과 판정이 다시 어긋나** 축 6의 취지가 통째로 무너진다 |
| (b) 판정은 전역 seq, 재고만 샤딩 | 두 카운터를 병행 | ❌ 전역 `INCR` 이 여전히 모든 요청을 통과시키므로 **샤딩으로 얻는 게 없다** |
| (c) **축 6 채택 시 축 2를 보류** ← 권고 | 전역 `INCR` 단일 키를 유지하고, 샤딩은 그 키가 실제 병목으로 **측정된 다음** 꺼내는 카드로 미룬다 | ✅ |

(c)를 택하는 근거는 이 문서가 축 2에서 이미 쓴 문장 그대로다 —
**"제거되는 병목은 Redis 명령이 아니라 분산 락 대기다."**
축 6이 정상 경로의 분산 락을 제거하면 축 2가 겨냥하던 병목이 대부분 사라진다.
남는 것은 Redis 단일 키의 처리 한계인데, `INCR`+`SISMEMBER`+`SADD` 로 구성된 짧은 스크립트는
단일 노드에서 초당 수만~수십만 op 수준을 처리한다. **측정 없이 이걸 먼저 쪼개는 것은 근거 없는 최적화다.**

> 이 항목은 포트폴리오에서 오히려 유리하다. "두 설계를 모두 넣었습니다"보다
> **"두 설계가 충돌해서 한쪽을 측정 이후로 미뤘습니다"** 가 판단력의 증거로 읽힌다.

### 충돌 2 — 축 6(순번 일원화) × 축 5(락 수명)

축 6이 정상 경로의 락을 없애면 축 5가 무의미해지는지 — **아니다. 범위가 좁아질 뿐이다.**

| 경로 | 축 6 적용 후 락 필요 여부 |
|---|---|
| 정상 발급 | ❌ 불필요 — Lua 한 번의 원자 실행이 판정을 끝낸다 |
| Redis 장애 → DB 직접 발급 폴백 | ✅ **여전히 필요** — 다중 인스턴스가 DB 재고를 동시에 건드린다 |
| 재고 보정 / 관리자 수동 조정 | ✅ 필요 — Redis 와 DB 두 저장소에 걸친 쓰기 |

폴백 구간은 정의상 **DB I/O 를 임계 구역에 포함**하므로, 축 5가 지적한 leaseTime 문제가
**바로 그 구간에서 가장 심각하다.** 즉 축 6은 축 5를 대체하지 않고
**축 5가 진짜로 필요한 곳을 특정해 준다.**

그리고 이것이 이 문서 서두의 프레임 전환과 정확히 맞물린다 —
"락 범위를 폴백 경로로 좁히겠다"(회고)가 아니라
**"정상 경로가 락을 필요로 하지 않는 구조로 바꾸면, 락은 폴백에만 남는다"**(설계)가 된다.
결과는 같지만 전자는 자백이고 후자는 설계 결정이다.

## 포트폴리오 서술 시 지켜야 할 선

| 원칙 | 이유 |
|---|---|
| **"도입했습니다" 금지** | 미구현이다. 거짓 서술은 꼬리질문 한 번에 무너진다 |
| **"해야 합니다 / 필요합니다" 금지** | 감사 유형 A4 — 미완처럼 읽혀 감점 |
| **"확장 설계 / 이 규모에서는 이렇게 나눈다" 사용** | 로드맵은 자백이 아니라 **역량 과시**로 읽힌다 |
| ZSet 은 **"기존 자산의 결합"** 으로 서술 | 이미 구현돼 있으므로 신규 도입으로 쓰면 거짓 |
| 재고 선점은 **"원칙의 확장"** 으로 서술 | 갭 자체를 전면에 내세우면 A5(결함 자백)가 된다 |
| 축 5 실측은 **"한계를 측정했다"** 로 서술 | 정합성 붕괴 수치를 맥락 없이 실으면 결함 자백으로 읽힌다. 부하 실험의 결과라는 프레임이 필요 |
| 축 6은 **"공정성은 별도 보장"** 으로 서술 | "선착순이 안 지켜졌다"가 아니라 **"정확성은 지켰고 공정성은 목표가 아니었다"** 로 구분해야 방어된다 |
| 워치독을 **"위험한 옵션"** 으로 쓰지 않는다 | 흔한 오해다. 크래시 시 갱신 스레드도 죽어 TTL 이 만료된다는 사실을 정확히 쓰는 편이 더 강하다 |

## 미결 사항

1. **샤드 수 N** — 고정값(8)으로 쓸지, 수량 기반 동적(`min(수량/100, 16)`)으로 쓸지
   - 단, 축 6을 채택하면 축 2가 보류되므로 이 항목 자체가 유예된다 (충돌 1 참조)
2. **축 2 와 축 6 중 무엇을 전면에 둘지** — 둘은 동시에 쓸 수 없다 (충돌 1).
   축 6이 락 제거·공정성·폴백 소멸을 한 번에 설명하므로 서술 밀도는 축 6이 높다
3. 포트폴리오에 **6개 축 전부** 넣을지, 핵심만 추려 넣을지
   - 현재 eco-1 해결 과정은 이미 8개 항목이라 분량 부담이 있다
   - 축을 묶는 방법: 축 1+5(락이 비싼 일을 하지 않게 한다), 축 6(순번=판정), 축 4(수명주기 전체 방어) 3덩어리
4. **SVG 다이어그램 교체 여부** — 현재 `viz-frame` 은 단일 락 구조를 그리고 있어
   샤딩(축 2)과도, 락 없는 정상 경로(축 6)와도 어긋남
5. **축 5의 실측 표를 포트폴리오에 넣을지** — 네 저장소 수치가 전부 어긋난 표는 근거로서 강력하지만,
   그대로 실으면 "정합성이 깨진 시스템을 배포했다"로 읽힐 위험이 있다.
   **부하 실험 결과**(의도적으로 한계를 측정한 것)라는 맥락을 함께 써야 한다
