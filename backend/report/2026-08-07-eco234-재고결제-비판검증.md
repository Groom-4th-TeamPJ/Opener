### C2-1. `@Retryable(maxAttempts=30, 지터, maxDelay=1s)` 는 코드에 존재하지 않는다

**주장 인용** — `PORTFOLIO.html:858`
> 초기 설정은 `@Retryable(maxAttempts=3, backoff=100ms)`였고, 아래 계측을 근거로 최종

같은 주장이 SVG 다이어그램(`PORTFOLIO.html:834` — "@Retryable(30, 지터·상한 1s)"),
해결 8번(`:865` — "백오프 지터(`@Backoff(random = true)`)를 도입"),
결과 4번(`:876` — "`@Backoff(random = true)` 한 줄이 성공률과 지연을 동시에 개선") 총 4곳에 반복된다.

**코드 근거** — `backend/src/main/java/groom/backend/application/product/ProductStockService.java:40-45`
```java
@Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 100, multiplier = 2),
        listeners = "stockRetryListener"
)
```
증가 경로(`:80-85`)도 동일하게 `maxAttempts = 3`. 저장소 전체에서 `random`·`maxDelay`·`maxAttempts = 30` 이 나오는
Java 파일은 **0개**다(`grep -rn "maxAttempts\|random *= *true\|maxDelay" backend/src/main/java/` → 2건 모두 `maxAttempts = 3`).
git 이력·stash 에도 30회 버전은 없다.

**왜 틀렸나** — 문서는 "3회 → 30회 조정"을 이 STAR 의 **핵심 의사결정이자 계측의 결론**으로 제시한다.
계측 → 판단 → 조치의 사슬에서 마지막 고리인 "조치"가 통째로 비어 있다. 문서가 참이라면 지금 코드는 조정 이전 상태로 되돌아간 것이고,
그렇다면 "실측을 근거로 조정했다"는 서사 자체가 재현 불가능하다.

**면접에서 어떻게 깨지나** — "재시도 30회면 최악 지연이 얼마죠?" 로 시작해 파일을 열면 3회다.
지터가 없으므로 결과 4번의 A/B("`random = true` 한 줄이 +14.7%p")는 **비교 대상 코드가 존재한 적 없는 실험**이 된다.
포트폴리오에서 가장 나쁜 종류의 지적(수치 조작 의심)을 부른다.

**제안** — 둘 중 하나만 선택. ① 코드에 실제로 30회+지터를 적용하고 재측정한다. ② 문서를 `maxAttempts=3, 고정 백오프 100ms×2`
현실로 되돌리고, 30회·지터는 "검토했으나 미적용, 근거는 ○○" 로 강등한다. **현 상태(문서만 30회)는 유지 불가.**

### C2-3. Redis ↔ DB 이중 진실 원천 드리프트 — 실재하는 누수 경로

문서(`:873`)는 "드리프트 0, 초과판매 0" 을 결과로 내세우지만, 코드에는 **측정 조건에서 밟히지 않았을 뿐 실재하는 드리프트 경로**가 있다.

**경로 A — 재고 차감 성공 후, 같은 트랜잭션의 뒷단계 실패**

`applyApprovedPaymentInTx` (`PaymentApplicationService.java:190-246`) 내부 순서:
```
:232  reduceProductStock(order)      ← 내부 decreaseWithOptimisticLock 은 REQUIRES_NEW → 즉시 독립 커밋
:233  processTicketProducts(order)   ← IllegalStateException(:536) / IllegalArgumentException(:523) / raffle 검증 예외 가능
:240  appendPaymentCompletedOutbox() ← DB 저장 실패 시 전파(:260 주석에 명시)
```
`:233` 이나 `:240` 이 던지면 바깥 `REQUIRES_NEW` 트랜잭션은 롤백되어 Payment·Order 는 원복되지만,
`:232` 에서 **이미 독립 커밋된 DB 재고 차감은 남는다.** `reduceProductStock` 의 보상 catch(`:486-501`)는
루프 **내부** 실패만 덮으므로 이 경로에서는 실행되지 않는다.

그 직후 `confirmPayment` 의 catch(`:137`)가 `releaseStock(reservedItems)` 로 **Redis 재고만 원복**한다.
결과: **DB 재고 −N (영구), Redis 재고 ±0** → Redis 가 DB 보다 N 만큼 많다고 믿는 상태.
이후 그 N 만큼은 게이트를 통과하지만 DB 에는 없다 → 게이트가 걸러야 할 요청을 PG 까지 통과시킨다.

**경로 B — `StockWarmUpRunner` 의 무조건 SET 이 다중 인스턴스에서 선점분을 지운다**

`infrastructure/product/StockWarmUpRunner.java:46` → `ProductStockRedisRepository.java:46-48`
```java
public void initStock(UUID productId, int quantity) {
    redisTemplate.opsForValue().set(STOCK_KEY_PREFIX + productId, String.valueOf(quantity));
}
```
`ApplicationRunner` 이므로 **부팅할 때마다 DB 값으로 덮어쓴다.** 문서 개요(`:592`)는
"다중 인스턴스를 전제하면" 을 전 도메인 공통 전제로 선언하는데, 그 전제에서 2번 인스턴스가 롤링 배포로 뜨는 순간
1번 인스턴스가 진행 중이던 선점분이 전부 소멸하고 Redis 재고가 부풀어 오른다 → **초과판매 창**.
게다가 `release()`(`:64-66`)는 무조건 `increment` 라 상한 검사도 없다.

**왜 틀렸나** — 문서는 "Redis 는 부하 필터, 최종 정합은 DB `@Version`" 이라는 역할 분담으로 이중 진실 문제를 봉합한다.
그 논리는 **Redis 가 틀려도 안전한 방향(과소 계상)으로만 틀릴 때** 성립한다. 경로 A·B 는 둘 다
**Redis 가 실제보다 많다고 믿는 방향(과대 계상)** 이라 게이트가 무력해지는 쪽이다. 안전 방향 가정이 깨진다.

**면접에서 어떻게 깨지나** — "Redis 와 DB 가 어긋나면 어느 쪽으로 어긋나나요?" 한 문장.
"과소 계상이라 안전합니다"로 답하면 위 두 경로로 반박당한다.

**제안** — ① `initStock` 을 `SETNX` 또는 "부팅 시 1회 리더만" 으로 제한, ② 경로 A 를 문서의 「남은 한계」에 명시
(현재 한계 목록 `:881-882` 에 없음), ③ 어긋남을 **탐지**하는 대조 배치를 근거로 제시(§ 대안 5).

### L2-1. "실패의 100%가 낙관적 락 충돌" 은 **관측 불가능한 상태에서의 추론**이다

문서 `:874`
> 재현 측정에서도 실패의 에러 코드가 100% `PRODUCT_STOCK_CONFLICT` 단일이었음

C2-2 에서 확인했듯 **그 에러 코드는 응답 바디에 나올 수 없다.** 문서 자신이 바로 앞 단락(`:864`)에서
"그 카운터는 구조적으로 절대 증가할 수 없는 죽은 카운터였다" 고 인정해 놓고, 결과 절에서는
그 카운터로 측정한 듯한 "100%" 를 제시한다. **같은 STAR 안에서 자기모순이다.**

로그 마커 3종(`[STOCK_CONFLICT_GIVEUP]` / `[PAYMENT_CONFIRM_DB_FAILED]` / `[PAYMENT_COMPENSATION_SUCCESS]`)이
80/80/80, 98/98/98 로 짝지어졌다는 근거는 유효하다 — 이건 로그 기반 추론으로 정직하게 성립한다.
**그러나 "100% 단일" 이라는 배타성 주장까지는 못 간다.** 세 마커의 동수는 "충돌이 있었다"를 증명하지, "충돌 외에는 없었다"를 증명하지 않는다.
`confirm_other_fail` 1,019 건 안에 다른 원인이 섞여 있어도 이 로그로는 구별되지 않는다.

**제안** — "실패의 100%" → "확인된 실패 표본에서 락 충돌 마커가 지배적이었고, 나머지는 계측 불가였음" 으로 하향.

### L2-2. 라이브락·기아 한계를 문서가 인지하지 못한다

핫 상품 1행에 1만 요청이 몰리는 조건에서 `maxAttempts = 3` + 고정 백오프(100/200ms)는
사실상 "세 번 부딪히면 포기" 다. 여기에 `JpaProductRepository.save()`(`:35-38`)가 **매번 새 detached 엔티티를 만들어**
`springRepo.save()` 를 호출하므로 Hibernate 는 `merge` 경로를 탄다 → 시도 1회당 `findById` SELECT + merge 의 SELECT + UPDATE.
**충돌 창이 필요 이상으로 넓다.** 즉 충돌률이 높은 것은 경합 때문만이 아니라 구현 때문이기도 한데, 문서는 이 원인을 다루지 않는다.

문서 「남은 한계」(`:881-882`)에는 ① 게이트 효과 미측정 ② 크래시 시 보상 미실행 두 개뿐이고,
**고경합에서 낙관적 락이 기아 상태로 수렴한다**는 본질적 한계가 빠져 있다.

### L2-3. 재시도 소진 시 사용자 경험이 문서 어디에도 없다

`@Recover`(`ProductStockService.java:69`)는 예외를 던지지만, 이 시점은 **Toss 승인이 이미 끝난 뒤**다.
사용자에게는 500 이 가고 뒤에서 보상 취소가 돈다. 사용자 관점에서는 "결제 눌렀는데 서버 오류 났고 나중에 취소됨" 이다.
문서는 이 UX 를 한 줄도 다루지 않는다. 재고 차감 STAR 의 결론이 "정합성은 지켰다"에 머물고
"그래서 사용자는 무엇을 받았나"로 이어지지 않는 것이 면접 서사로서 가장 약한 지점이다.

**제안** — 동일 VU 로 지터 유무만 바꿔 다시 측정하거나, A/B 주장을 삭제하고 `stock.json` 단일 런의 정합성 결과(드리프트 0)만 남긴다.

# STAR 3 (885행) — PG 결제 부분 실패 Saga 보상

## 치명적 결함

### C3-1. "5개 상태 전이표" 는 존재하지 않는다 — 상태는 4개이고 전이 검증도 없다

**주장 인용** — `PORTFOLIO.html:936`
> 보상 레코드는 **5개 상태의 전이표**로 관리 — `PENDING → IN_PROGRESS → (SUCCEEDED | RETRY_SCHEDULED)`,
> `RETRY_SCHEDULED → IN_PROGRESS`(백오프 만료 시), `RETRY_SCHEDULED → GIVEN_UP`(5회 소진).
> **선언되지 않은 조합은 전이 자체가 거부되므로** "취소 성공 후 다시 재시도" 같은 비정상 경로가 코드 수준에서 차단됨

**코드 근거** — `domain/payment/model/enums/CompensationStatus.java` 전문:
```java
public enum CompensationStatus {
    PENDING("재시도 대기"),
    SUCCEEDED("보상 성공"),
    FAILED("보상 실패 (재시도 대상)"),
    GIVEN_UP("재시도 한도 초과 - 수동 처리 대상");
}
```
- 상태는 **4개**. `IN_PROGRESS`, `RETRY_SCHEDULED` 는 **둘 다 존재하지 않는다.** 문서가 든 전이 5개 중 4개가 존재하지 않는 상태를 참조한다.
- 전이 검증도 없다. `PaymentCompensation.java:82-104` 의 `markSucceeded()` / `markFailed()` 는 **현재 상태를 읽지 않고 필드를 무조건 대입**한다. `GIVEN_UP` 레코드에 `markSucceeded()` 를 호출해도 조용히 성공한다.
- 문서가 "코드 수준에서 차단됨" 이라 단정한 `SUCCEEDED → 재시도` 는, `PaymentCompensationRepository.findRetryable` 이 상태로 거르는 **쿼리 조건**에 의존할 뿐 상태 머신의 방어가 아니다.

**왜 틀렸나** — 상태 머신을 "구현했다" 와 "쿼리로 거른다" 는 견고성이 다르다.
전자는 코드 어디에서 호출하든 불법 전이가 막히고, 후자는 새 호출부가 하나 생기면 뚫린다.
문서는 없는 방어를 있다고 서술한다.

**면접에서 어떻게 깨지나** — "전이표 코드 어디 있나요?" → enum 4개 + setter 성격의 메서드 2개.
`PaymentStateTransition.java`(`domain/payment/model/`, 3.5K) 는 `Payment` 용이지 보상 레코드용이 아니다.
"5개" 라는 구체적 숫자를 틀리면 나머지 서술 전체의 신뢰가 함께 떨어진다.

**제안** — 실제 구조(`PENDING → SUCCEEDED | FAILED`, `FAILED → SUCCEEDED | FAILED | GIVEN_UP`, 4상태)로 정정하고,
"전이 검증은 미구현이고 조회 쿼리 조건에 의존한다" 를 「남은 한계」로 이동. 정직한 4상태가 허구의 5상태보다 강하다.

### C3-2. 보상 레코드가 **보상 시도와 같은 트랜잭션**에 있어, DB 장애 때 채무 기록 자체가 사라진다

**코드 근거** — `application/payment/PaymentCompensationService.java:46-60`
```java
@Transactional
public void compensate(UUID paymentId, String paymentKey, Integer amount, String failureReason) {
    ...
    compensation = compensationRepository.save(compensation);   // :55
    log.warn(...);
    executeCompensation(compensation);                          // :59  자기호출 → 같은 트랜잭션에 합류

```
`executeCompensation`(`:93-133`)은 같은 클래스 메서드 자기호출이라 프록시를 타지 않는다.
`compensate` 가 `@Transactional` 이므로 **보상 레코드 INSERT 와 Toss 취소 호출과 결과 기록이 전부 한 트랜잭션**이다.

문제는 이 경로에 **진입하는 조건**이다. `PaymentApplicationService.java:140` 은 "DB 후처리 실패" 직후 호출한다.
그 실패 원인이 DB 자체 장애(커넥션 고갈·타임아웃)라면:
- `:55` 의 INSERT 부터 실패 → 예외가 `compensate` 밖으로 전파
- `PaymentApplicationService.java:140` 은 try 로 감싸여 있지 않으므로 **`:146` `markPaymentFailed`, `:147` 재throw 가 모두 스킵**
- 결과: **Toss 승인은 완료 / 취소 안 됨 / 보상 레코드 없음 / Payment 는 FAILED 로도 기록되지 않음** → 배치가 주울 대상이 아무것도 없다

**왜 틀렸나** — 문서(`:934`)는 "그마저 실패하면 보상 테이블에 적재해 배치가 재시도" 라고 2단 방어를 주장하지만,
**적재와 시도가 원자적으로 묶여 있어 1단이 무너지면 2단도 같이 무너진다.** Saga 보상의 기본은
"의도 기록(레코드) 커밋 → 그 다음 실행" 인데 순서가 반대다.

**면접에서 어떻게 깨지나** — "보상의 보상은요?" → 문서 답변은 "배치 재시도 + GIVEN_UP".
"그 배치가 읽을 레코드는 언제 커밋되죠?" → 같은 트랜잭션임이 드러난다. 결제 도메인에서 가장 아픈 지적이다.

**제안** — `compensate` 를 "레코드 INSERT (`REQUIRES_NEW`, 즉시 커밋)" 와 "실행" 두 단계로 쪼갠다.
`PaymentApplicationService` 가 이미 `selfProvider` 로 프록시 우회 패턴을 쓰고 있으므로 동일 패턴 적용이 가능하다.
**이건 실제로 고칠 가치가 있고, 고친 뒤 문서에 쓰면 STAR 3 최고의 답변이 된다.**

### C3-3. "서킷과 보상이 서로를 고려해 설계됐다" — 취소 API 는 서킷 보호 대상이 아니다

**주장 인용** — `PORTFOLIO.html:947`
> 서킷브레이커와 보상 재시도의 **값이 서로를 고려해 정해졌음** — 서킷이 OPEN 인 구간에는 **취소 API 호출도 같은 인스턴스를 지나 fast-fail 되지만**,
> 첫 백오프 2분이 OPEN 30초를 충분히 넘기므로 2회차부터 정상 복구 경로에 진입함

**코드 근거** — `infrastructure/payment/TossPaymentClientImpl.java`
- 승인: `:42-45`
  ```java
  @CircuitBreaker(name = "toss", fallbackMethod = "confirmPaymentFallback")
  @Retry(name = "toss")
  @Override
  public TossPaymentResponse confirmPayment(...)
  ```
- 취소: `:88-89`
  ```java
  @Override
  public TossPaymentResponse cancelPayment(String paymentKey, String cancelReason, String idempotencyKey) {
  ```
  → **어노테이션 없음.** `@CircuitBreaker` 도 `@Retry` 도 붙어 있지 않다.

`application-dev.yml:142-154` 에도 `toss` 인스턴스 하나만 정의되어 있고, 이는 승인 경로에만 부착된다.

**왜 틀렸나** — 취소는 서킷을 지나지 않으므로 OPEN 이어도 fast-fail 되지 않고 **그냥 실제 호출을 시도한다**(그래서 타임아웃까지 대기).
문서가 설명한 상호작용("OPEN 30초 < 백오프 2분 이므로 2회차가 실질 첫 시도")은 **존재하지 않는 메커니즘에 대한 계산**이다.

서킷 보호 없이 매번 타임아웃까지 스레드를 붙잡고, 그것이 곧 `@Scheduled` 보상 배치(`:67-87`, 배치 크기 50)의 지연이 된다.
장애 시 최대 50건 × 타임아웃만큼 배치 스레드가 점유된다.

**면접에서 어떻게 깨지나** — "취소도 서킷 타나요?" → 파일 열면 3초 만에 판명.
그 다음 "그럼 PG 장애 때 보상 배치는 어떻게 되나요?" 로 이어져 위 점유 문제까지 드러난다.

**제안** — ① `cancelPayment` 에도 `@CircuitBreaker(name = "toss-cancel")` 를 붙이고(승인과 회로 분리 권장 — 취소를 승인 실패율에 물리면 안 됨) 문서 서술을 사실로 만들거나,
② 문서를 "취소는 서킷 미보호이며, 이는 알려진 한계" 로 정정. ①이 코드 3줄 + yml 8줄이므로 권장.

### L3-2. 멱등성 2단계 중 1단계는 경합에 열려 있다

문서 `:937`
> 승인 경로 멱등성은 내부 결제 키 선조회와 외부 PG `Idempotency-Key` 헤더의 2단계로 적용

`PaymentApplicationService.java:86-104` — 선조회는 `@Transactional(propagation = NOT_SUPPORTED)` 안의

실제로 이중 결제가 안 되는 이유는 **Toss 의 `Idempotency-Key`(2단계)와 `Payment` 상태 머신** 덕분이지

정확히 말하면 두 요청 모두 Toss 를 통과하고 `applyApprovedPaymentInTx` 에 진입하며,

다만 `:135` catch 가 잡지 못하는 예외(Error 등)면 남는다.

### L3-3. `retryPendingCompensations` 의 자기호출로 배치 경로는 트랜잭션 없이 돈다

`PaymentCompensationService.java:68` `retryPendingCompensations` 에는 `@Transactional` 이 없고,
`:80` 에서 `executeCompensation` 을 **자기호출**한다 → `@Transactional(:93)` 이 적용되지 않는다.
`findRetryable` 로 가져온 엔티티는 detached 상태이고, `markFailed` 후 `save()` 는 `merge` 로 처리된다.
동작은 하지만, `:106-107`(성공 기록)과 `:113-114`(실패 기록) 사이에 원자성이 없고,
`markFailed` 의 `retryCount` 증가가 **읽은 시점 값 기준**이라 배치가 두 인스턴스에서 동시에 돌면 카운트가 어긋난다.
문서는 배치의 다중 인스턴스 안전성을 언급하지 않는다(개요 `:592` 는 "분산 락은 배치의 배타 실행에만 남겼음" 이라 주장하는데,
`PaymentCompensationService` 에는 **락이 없다**).

**이건 개요와 코드의 드리프트이기도 하다.**

### L3-4. 백오프 값은 맞지만 Javadoc 은 틀렸다

`PaymentCompensation.java:91-104` 실제 동작: `retryCount` 를 먼저 증가시킨 뒤 `2^retryCount` 분 →
1차 실패 후 **2분**, 4분, 8분, 16분 = 총 30분. 5회째에 `retryCount >= maxRetryCount(5)` → `GIVEN_UP`.

다만 같은 파일 `:89` Javadoc 은 "1분, 2분, 4분, 8분, 16분" 이라 적어 코드와 다르다. 면접관이 주석을 읽으면 혼선이 생긴다.

### C4-1. 코드 카드가 실제 코드가 아니다

**주장 인용** — `PORTFOLIO.html:1004-1038` 코드 카드

- 클래스명: `CouponDeactivationProcessor` vs **`CouponDelayTransformer`**

실제로는 **DSL 의 `transform()` 연산자 + 구 `Transformer` 인터페이스**다.

**왜 틀렸나** — 포트폴리오의 코드 카드는 "내가 쓴 코드"로 읽힌다. 이건 실제 코드를 정리한 것이 아니라
**최신 API 로 다시 쓴 것**이고, 이름·API·스토어명 어느 것도 저장소와 대조되지 않는다.
"코드를 각색했다"는 인상은 수치 조작 다음으로 치명적이다.

**면접에서 어떻게 깨지나** — "이 클래스 어느 파일인가요?" → 없다.
"Processor 랑 Transformer 차이 아세요?" → 문서가 Processor 라 썼는데 코드는 Transformer 라 오히려 준비가 덜 된 것으로 보인다.

**제안** — 코드 카드를 `CouponDelayTransformer.java` 실제 코드로 교체하고(주석만 축약),
본문 `:995` 를 "구 Transformer API 로 구현했고, 신 Processor API(`process()`) 로의 이관이 남아 있음" 으로 바꾼다.
**deprecated API 를 쓰고 있다는 사실을 아는 것 자체가 좋은 답변 소재다.** 숨기면 손해다.

### C4-2. "이미 비활성이면 no-op 인 조건부 UPDATE" 는 코드에 없다

**주장 인용** — `PORTFOLIO.html:998`
> **비활성화 자체를 멱등**(`WHERE is_active = true` 조건부 UPDATE 로 이미 비활성이면 no-op)으로 설계해 재처리를 흡수하도록 했음

**코드 근거** — `domain/coupon/repository/CouponRepository.java:29-31`
```java

@Query("UPDATE Coupon c SET c.isActive = false where c.id = :couponId")
Integer updateIsActiveFalse(@Param("couponId") Long couponId);
```
`WHERE` 절에 **`is_active = true` 조건이 없다.** 호출부 `CouponService.java:23` 은 `> 0` 으로 성공을 판정하는데,
조건이 없으니 **몇 번을 재실행해도 항상 1** 을 반환한다 — 즉 "이미 비활성이었다" 를 감지할 수단이 없다.

**왜 틀렸나** — 결과적으로 `false` 를 두 번 쓰는 것이 값으로는 같으므로 **실효 멱등성은 있다.**
그러나 문서는 **"그렇게 설계했다"는 구체적 메커니즘**을 주장했고 그 메커니즘이 없다.
그리고 no-op 감지가 불가능하므로 "재처리가 몇 번 일어났는지" 를 관측할 수도 없다.

**제안** — 쿼리에 `AND c.isActive = true` 를 추가하면 문서가 참이 되고 재처리 관측까지 가능해진다. **코드 1줄.**

### L4-3. WALL_CLOCK vs STREAM_TIME 선택 근거가 코드 주석에만 있고 문서에는 결론만 있다

### L4-4. 리밸런싱 중 중복 실행 가능성 — 문서가 "구조적으로 막는다"고 과장

문서 `:994`

게다가 C4-2 로 확인했듯 no-op 조건이 없어 중복 실행을 흡수는 하되 **감지하지 못한다.**

3. **"punctuate 안에서 range iterator 를 열어 둔 채 `store.delete()` 를 하는데 안전한가요?"** (`:160-183`) → RocksDB 이터레이터는 스냅샷 기반이라 실무상 동작하지만, **문서에도 주석에도 근거가 없다.** 준비 필요.
4. **"`delayMillis` 가 이미 지난 이벤트면요?"** → L4-1. 조용히 사라진다.
5. **"1.1s 는 어떻게 쟀나요?"** → 문서 `:1044` 는 "이벤트 발행~비활성 전환 시각 차 직접 측정" 이라 서술하나, `measurements/` 에 해당 산출물이 없다(`coupon.json` 은 발급 부하 5,000 iter 로 별건).
6. **"EOS 를 켰는데 `commit.interval.ms=1000` 이면 지연에 어떤 영향이 있나요?"** → punctuate 1s 주기와 커밋 1s 가 겹쳐 실측 최악 1.1s 를 설명하는 좋은 소재인데 문서에 없다. **넣으면 강점이 된다.**

# 세 STAR 공통 — 면접 논리 흐름 평가

| 항목 | eco-2 | eco-3 | eco-4 |
|---|---|---|---|
| 원인이 진짜 원인인가 | △ Lost Update 는 맞으나 "충돌이 잦은 이유" 에 merge 왕복(L2-2)이 빠짐 | ○ 비가역/가역 혼재는 정확한 진단 | ✕ "기존 폴링" 자체가 미검증(C4-3) |
| 해결이 코드에 있는가 | ✕ 핵심 3개 중 0개 | △ 설계는 있음, 서킷 연계는 없음 | ○ 있음 (단 코드 카드는 각색) |
| 결과가 근거를 갖는가 | ✕ A/B 수치 불일치·VU 미통제 | △ 0.6s 는 방어, 9배·98.7% 는 산출물 없음 | △ 1.1s 실측 근거 파일 없음 |
| 트레이드오프를 숨겼는가 | ✕ 라이브락·UX·드리프트 미언급 | △ PG 윈도우는 정직, 크래시 창은 누락 | ○ standby·EOS 범위는 정직 |

**"제거했다/방지했다" 단정 검토.**
- `:814` "Lost Update 를 **방지**" → DB `@Version` 한정으로는 참. 그러나 **Redis 게이트를 포함한 전체 경로**로는 C2-3 경로 A·B 에서 초과판매 창이 남으므로 무조건 단정은 위험.
- `:957` "폴링 지연을 **제거**" → 폴링을 1s punctuate 로 바꾼 것이지 지연을 제거한 것이 아니다. 문서 `:1043` 이 이미 "직접 원인은 주기 단축" 이라 정직하게 밝히고 있으므로, **제목만 과장이다.** 제목을 "1초 이내로 단축" 으로 바꾸면 본문과 일관된다.

# 재고 차감 주제를 차별화할 대안 (근거 포함)

전제: "낙관적 락 + 재시도" 는 신입 포트폴리오의 최빈 주제다. 차별화는 **락 종류를 바꾸는 것이 아니라
"왜 충돌이 그렇게 잦았는가" 와 "두 저장소가 어긋난 걸 어떻게 알았는가" 로 축을 옮기는 데서** 나온다.
아래 5개는 모두 이 저장소의 기존 파일만으로 실현 가능하다.

## 대안 1 — 죽은 카운터를 **실제로** 복구하고, 재시도 한도를 데이터로 결정한다 (최우선)

- **무엇을 바꾸나**: `PaymentApplicationService.java:147`(및 `:128`)의 무조건 재포장을
  `if (dbError instanceof BusinessException be) throw be;` 선행 분기로 바꾼다.
  `GlobalExceptionHandler` 는 이미 `BusinessException → errorCode.getStatus()` 매핑(`:26-31`)이 있으므로 **409 가 그대로 나간다.**
  그 뒤 `k6/scripts/stock-concurrency-test.js` 를 재실행해 `confirm_conflict` 가 실제로 증가하는 런을 `measurements/` 에 남긴다.
- **왜 이 코드베이스에 맞나**: k6 의 분류 로직(`:132-138`)과 `ErrorCode.PRODUCT_STOCK_CONFLICT(HttpStatus.CONFLICT)`(`ErrorCode.java:142`)가
  **이미 그 응답을 기다리도록 만들어져 있다.** 빠진 건 중간 4줄뿐이다. `stock.json`·`stock_fixed.json` 둘 다 conflict 0 이라
  "고치기 전/후" 대비가 산출물로 선명하게 남는다.
- **난이도**: 하 (코드 4줄 + 부하 재측정 1회)
- **부르는 질문**: "관측 가능성이 없다는 걸 어떻게 알았나요?" / "왜 500 이 아니라 409 인가요?" /
  "재시도 소진을 클라이언트가 어떻게 다뤄야 하나요?" → **재시도 한도를 몇 회로 잡을지의 근거를 데이터로 말할 수 있게 된다.**
- **리스크**: 낮음. 다만 409 노출 후 k6 의 `check`(200/4xx)가 통과로 바뀌어 성공률 지표 해석이 달라진다 — 문서에 명시 필요.
- **가장 큰 이득**: 문서 `:864`·`:868` 의 최고 서사(예외 재포장이 관측성을 지운다)가 **허구에서 사실로 바뀐다.**

## 대안 2 — 재고를 `product_stock` 테이블로 분리하고 조건부 UPDATE 로 전환한다

- **무엇을 바꾸나**: `ProductJpaEntity.java:33` 의 `stock` 컬럼을 별도 엔티티/테이블로 떼고,
  차감을 `UPDATE product_stock SET stock = stock - :qty WHERE product_id = :id AND stock >= :qty` 단일 쿼리로 바꾼다.
  `ProductStockService` 의 `@Retryable`·`REQUIRES_NEW`·`@Recover` 구조는 그대로 두되 **충돌 자체가 거의 사라진다.**
- **왜 이 코드베이스에 맞나**: 같은 저장소가 쿠폰에서 **정확히 이 패턴**을 이미 쓴다 —
  `CouponRepository.java:37-39` `decreaseQuantityAtomically` + `AND c.quantity > 0`, 그리고 `:33-36` 주석이
  "락도 재시도도 필요하지 않다" 는 이유까지 적어 두었다. 문서 `:866` 이 기각 사유로 든 "`@Version` 공유" 는
  분리하면 그대로 해소된다. Flyway 마이그레이션 디렉터리(`backend/src/main/resources/db/`)도 이미 있다.
- **난이도**: 중 (마이그레이션 1개 + 리포지토리 1개 + `ProductStockService` 차감 경로 교체. 조회 경로는 join 또는 별도 쿼리)
- **부르는 질문**: **"같은 서비스 안에서 쿠폰은 조건부 UPDATE, 상품은 낙관적 락이었습니다. 왜 달랐고 왜 통일했나요?"**
  → 두 도메인을 잇는 답변이 되어 STAR 1 과 STAR 2 가 하나의 서사로 묶인다. 이게 이 저장소 고유의 차별점이다.
  이어서 "조건부 UPDATE 면 재고 부족을 어떻게 아나요?"(영향 행 수 0) / "행 락 경합은 여전하지 않나요?" 로 심화된다.
- **리스크**: 조회 경로(`JpaProductQueryRepository`, `ProductApplicationService`)와 `StockWarmUpRunner:43` 의
  `findByIdGreaterThanOrderByIdAsc` 가 모두 `ProductJpaEntity.stock` 에 의존한다 — 파급이 넓다. 마이그레이션 실수 시 데이터 손실.

## 대안 3 — `merge` 왕복을 제거해 "충돌이 잦았던 진짜 원인"을 규명한다

- **무엇을 바꾸나**: `JpaProductRepository.java:35-38` 의 `save()` 는 **매 호출 새 detached `ProductJpaEntity` 를 빌드**해
  `springRepo.save()` 에 넘긴다 → Hibernate 는 `merge` 경로 → **UPDATE 전에 SELECT 가 한 번 더** 나간다.
  `ProductStockService.decreaseOnce:56-60` 의 `findById` 까지 합치면 **시도 1회당 SELECT 2 + UPDATE 1** 이다.
  이를 ① 영속 엔티티 dirty checking 으로 바꾸거나 ② 재고 전용 `@Modifying @Query` 로 바꾼다.
- **왜 이 코드베이스에 맞나**: `StockRetryMetricsListener`(`infrastructure/product/StockRetryMetricsListener.java:34-39`)가
  **이미 호출당 재시도 횟수를 Micrometer summary 로 노출한다.** 즉 변경 전후의 평균 재시도 변화를 **바로 측정할 수 있다.**
  문서 `:862` 가 자랑하는 "0.35회/건" 계측 인프라를 원인 규명에 재사용하는 것이라 추가 도구가 필요 없다.
- **난이도**: 하~중 (리포지토리 1개. 다만 도메인/엔티티 분리 구조를 유지하려면 설계 판단 필요)
- **부르는 질문**: **"충돌률을 낮추려고 락을 바꾸기 전에 뭘 먼저 확인하셨나요?"**
  → "충돌 창의 길이" 라는 답이 나온다. "`save()` 가 왜 SELECT 를 부르나요?"(detached + merge),
  "`@Version` 이 null 이면?"(INSERT 로 처리 — `Product.java:28-30` 주석) 등 JPA 깊이를 보여줄 수 있다.
- **리스크**: 낮음. 다만 **효과가 없을 수도 있다** — 그 경우에도 "측정해서 아니었음" 이 유효한 결과다.

## 대안 4 — Redis 게이트를 **홀드 원장**으로 승격하고 워밍업을 조건부로 바꾼다

- **무엇을 바꾸나**: ① `StockWarmUpRunner.java:46` → `ProductStockRedisRepository.initStock`(`:46-48`)의 무조건 `SET` 을
  `SETNX`(또는 부팅 리더 1대만 수행)로 바꿔 다중 인스턴스에서 진행 중 선점을 덮어쓰지 않게 한다.
  ② `release()`(`:64-66`)의 무제한 `increment` 에 상한(`DB stock` 초과 방지)을 Lua 로 건다.
- **왜 이 코드베이스에 맞나**: `RESERVE_SCRIPT`(`ProductStockRedisRepository.java:29-41`)가 이미
  `-2 미초기화 / -1 부족 / 0+ 성공` 3분기 Lua 다 — **복원 스크립트도 같은 스타일로 붙이면 대칭이 맞는다.**
  문서 `:861` 이 강조한 "임계 구역이 Redis 안에서 완결되므로 분산 락이 불필요" 라는 논리는
  복원까지 Lua 로 원자화해야 완결되는데 현재는 복원만 비원자적이다.
- **난이도**: 중 (Lua 1개 추가 + 부팅 리더 선출. 리더 선출은 `RedissonConfig` 가 이미 있으므로 재활용 가능)
- **부르는 질문**: "롤링 배포 중에 재고가 어떻게 되나요?" / "Redis 가 DB 보다 많아지는 경우가 있나요?" /
  "TTL 을 안 쓴다면 크래시한 선점은 누가 회수하나요?" → **문서 `:863` 의 TTL 미사용 결정이 훨씬 단단해진다.**
- **리스크**: `SETNX` 로 바꾸면 DB 가 원천인데 Redis 가 과거 값을 유지하는 반대 위험이 생긴다 —
  대안 5 의 대조 배치와 **반드시 짝으로** 가야 한다.

## 대안 5 — Redis↔DB 대조·보정 배치로 "드리프트를 탐지했다" 를 주제로 삼는다

- **무엇을 바꾸나**: `product:stock:{id}`(Redis)와 `product.stock`(DB)를 주기적으로 대조해
  차이·방향·건수를 Micrometer 게이지로 노출하고, 임계 초과 시 경보한다. 보정은 우선 **보고만** 하고 자동 보정은 옵션.
- **왜 이 코드베이스에 맞나**: `StockWarmUpRunner.java:37-53` 이 **이미 전 상품을 키셋 페이지네이션으로 순회하는 코드**다.
  같은 순회를 `@Scheduled` 로 돌리고 `initStock` 대신 비교로 바꾸면 골격이 그대로 재사용된다.
  또 `StockRetryMetricsListener` 가 이미 `MeterRegistry` 를 쓰고 `application-dev.yml:173-187` 이 Prometheus 를 노출하므로
  대시보드까지 즉시 붙는다. 문서 `:882`·개요 `:592` 가 예고한 "대조·보정 배치" 를 **말이 아니라 코드로** 만드는 셈이다.
- **난이도**: 중 (배치 1개 + 게이지 2개. 실행 중 선점분 때문에 순간 오차가 정상이라 **판정 기준 설계가 실제 어려움**)
- **부르는 질문**: **"실행 중에는 선점 때문에 Redis 가 항상 DB 보다 작을 텐데, 진짜 드리프트와 어떻게 구분하나요?"**
  → 최고의 꼬리질문이다. 답: 정상 방향(Redis ≤ DB)과 이상 방향(Redis > DB)을 나눠 후자만 경보 /
  또는 유휴 구간 샘플링. 이어서 "얼마나 자주 도나요?" / "보정을 자동화하지 않은 이유는?" 으로 확장된다.
- **리스크**: 낮음(읽기 전용으로 시작 가능). 자동 보정까지 가면 보정이 새로운 드리프트 원인이 될 수 있다.
