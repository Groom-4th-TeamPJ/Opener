## 실패 원인 — 추정에서 확정으로

**1차 측정에서 실패 4,272건이 100% `PRODUCT_STOCK_CONFLICT` 였다.**

이 에러코드는 `ProductStockService.recover()` (`:69-72`) 에서만 던져지고,
`@Recover` 는 **재시도 한도를 전부 소진한 뒤에만** 호출된다.

→ 실패 경로는 **재시도 소진 단 하나**로 확정. 다른 원인(선점 미회수·커넥션 고갈 등)은 관측되지 않았다.

포트폴리오의 기존 서술 *"재시도 소진으로 추정되며 … 실패 사유를 분리 계측하지 않았으므로 원인은 추정입니다"* 를
이제 **단정형으로 교체할 수 있다.**

|---|---|---|---|---|---|---|---|---|---|

**모든 조건에서 드리프트 0** — 낙관적 락(`@Version`)의 정합성 보장은 재시도 정책과 무관하게 성립했다.
바뀐 것은 **완주율**뿐이다. 즉 정합성과 가용성은 이 구조에서 분리된 축이다.

### 관측 1 — 지터 (#1 → #2)

`@Backoff(random = true)` 한 줄로 **성공률 +14.73%p, 평균 지연 -20.7%**.

고정 백오프(100/200/400ms)는 충돌한 스레드가 **모두 같은 시점에** 재시도해 재충돌한다(thundering herd).
난수를 섞으면 재시도 시점이 흩어져 충돌 확률이 떨어진다.
지연까지 함께 줄어든 것은 재충돌로 낭비되던 시도가 줄었기 때문이다.

### 관측 2 — 백오프 상한의 역할 (#3 vs #4)

`delay=100, multiplier=2` 는 **상한이 없으면** 10번째 재시도에서 `100 × 2⁸ = 25.6초`를 기다린다.
`#3`(상한 없음)이 100%를 달성하고도 46초가 걸린 이유다 —
대부분은 3~4회에 끝나는데 **소수의 불운한 요청이 수십 초를 잡아먹어** 전체를 끌었다.

`maxDelay = 1000` 을 씌우자 전체 소요가 **46.4s → 15.3s (1/3)**, 평균 지연이 **300ms → 152ms (절반)** 로 떨어졌다.
대신 대기가 짧아진 만큼 같은 시도 횟수로는 덜 흩어져 성공률이 99.00%로 내려갔다.

→ **상한은 "재시도 횟수를 늘려서" 보상해야 한다.** 이것이 #4~#7 의 곡선이다.

### 관측 3 — 수익 체감 (#4 → #7)

| 재시도 | 성공률 |
|---|---|
| 10회 | 99.00% |
| 15회 | 99.90% |
| 20회 | 99.99% |
| 30회 | 100.00% |

**5회를 더 줄 때마다 9가 하나씩 붙는다.** 로그 스케일로 수렴하는 전형적인 형태다.
꼬리로 갈수록 비용이 급격히 비싸지므로, 목표를 100%로 두느냐 99.9%로 두느냐가 곧 설계 결정이 된다.

## 채택 정책

```java
@Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 30,
        backoff = @Backoff(delay = 100, multiplier = 2, random = true, maxDelay = 1000),
        listeners = "stockRetryListener"
)
```

**채택 근거**: 100% 완주가 가능한 두 조건(#3, #7) 중 #7이 전체 소요 **46.4s → 24.4s (약 47% 단축)**.
상한 없는 #3은 최악 대기가 25초를 넘어 실사용 타임아웃에 걸릴 위험이 있다.

**함께 변경한 것**: 보상 경로 `increaseWithOptimisticLock` 도 동일 정책으로 정렬.
코드 주석(`:77-78`)이 "차감과 동일하게 '재시도 바깥 / REQUIRES_NEW 안쪽' 구조로 통일" 이라고 선언하고 있어,
한쪽만 바꾸면 그 서술이 거짓이 된다.

### 이 정책의 대가 (포트폴리오에 함께 써야 정직함)

- 평균 지연 47ms → 366ms (경합 최대 조건 기준)
- 최악의 요청은 최대 30회 × 최대 1초 = 이론상 30초 대기
- 이 수치는 **10,000 요청이 단일 상품 행에 몰리는 극단 조건**이며, 실제 트래픽 분포에서는 훨씬 낮다
  (기존 Micrometer 실측 평균 재시도 **0.35회/건** 이 이를 뒷받침)

## ⚠️ 재현성 경고 — 절대 수치를 그대로 쓰면 안 된다

채택 정책(#7, 30회 + 상한 1s)으로 **동일 코드를 재실행한 결과가 크게 달랐다.**

| 실행 | 조건 | 성공률 | 전체 소요 | 드리프트 |
|---|---|---|---|---|
| #7 최초 | 격리 실행 | 100.00% | 24,369 ms | 0 |
| 검증 A | `product.*` 전체와 동반 실행 | 99.98% | 78,766 ms | 0 |
| 검증 B | 격리 재실행 (`--rerun-tasks`) | **88.80%** | **280,304 ms** | 0 |

### 원인 — 머신 부하

측정 시점 `uptime` 기준 **load average 44.19 / 39.71 / 29.05**, 코어 수 **10개**.
약 4.4배 과부하 상태였다. 단일 폭주 프로세스가 아니라 데스크톱 누적 부하였다.

| 프로세스 | %CPU |
|---|---|
| Arc 브라우저 | 22.8 |
| Docker VM | 20.4 |
| claude (측정 수행 세션) | 18.2 |
| Riot Client | 13.5 |
| IntelliJ IDEA | 9.2 |

전체 소요가 24s → 280s (약 11배) 로 늘어난 것은 코드 변경이 아니라 **CPU 경쟁** 때문이다.
낙관적 락 재시도는 대기·재시도 타이밍에 의존하므로 CPU 스케줄링 지연에 직접 영향을 받는다.

### 그래도 흔들리지 않은 것

**9회 측정 전부에서 드리프트 = 0.**

성공률이 57%든 88%든 100%든, DB 최종 재고는 항상 정확히 `초기재고 − 성공건수` 였다.
→ **정합성은 부하와 무관하게 성립하고, 부하에 좌우된 것은 완주율뿐이다.**
   이 둘이 분리된 축이라는 사실 자체가 이번 측정의 가장 견고한 결과다.

### 결론 — 포트폴리오 서술 기준

| 쓸 수 있는 것 | 쓸 수 없는 것 |
|---|---|
| "모든 조건에서 드리프트 0 · 초과판매 0" (9회 재현) | "1만 건 100% 완주" (재현 실패) |
| 지터 도입 효과 (백투백 A/B라 상대 비교 유효) | 특정 성공률 절대값 |
| 실패 원인 = 재시도 소진 **확정** (에러코드 100% 단일) | 특정 지연·소요 시간 절대값 |

**절대 수치를 쓰려면 유휴 상태(load average < 코어 수)에서 3회 이상 재측정해 중앙값을 써야 한다.**

## 남은 한계 (정직하게 기록)

1. **낙관적 락은 단일 핫 행에 구조적으로 불리하다.** 한 라운드에 커밋 성공은 1건뿐이고
   나머지는 전부 충돌하므로, 경합이 셀수록 재시도 횟수로 메꿔야 한다.
   근본 대안은 비관적 락 또는 Redis 원자 카운터를 정합성의 근거로 승격하는 것이다.
2. **Redis 선점 게이트는 이번 측정 경로에 없다.** `decreaseWithOptimisticLock` 는 DB 전용이며,
   게이트는 재고가 요청보다 적을 때만 조기 차단 효과가 있다.
   재고 10,000 / 요청 10,000 조건에서는 전량 통과하므로 DB 경합을 줄이지 못한다.
3. **HikariCP 풀이 기본값 10** 이다. 200 스레드가 커넥션 10개를 두고 경쟁하는 조건이므로,
   풀 크기를 올리면 곡선이 달라질 수 있다. 이번 측정에서는 변수를 고정하기 위해 손대지 않았다.
