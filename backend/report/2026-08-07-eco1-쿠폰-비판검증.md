## 치명적 결함

### C-1. 데이터 흐름이 문서와 코드가 정반대다 — Lua 게이트는 Kafka **뒤**에 있다

**주장** (`PORTFOLIO.html:772`)
> "Lua 스크립트는 '이미 마감됐는가 · 이 사용자가 이미 신청했는가'를 왕복 한 번에 판정해 **브로커 앞에서 물량을 자름** — 5,000건 중 실제로 Kafka에 실리는 것은 100여 건이라, 어차피 버려질 메시지가 브로커와 컨슈머 자원을 쓰지 않음"

아키텍처 SVG도 같은 순서로 그린다 — `API 서버 → Lua 게이트(205,70) → Kafka(450,70) → 컨슈머(700,70)` (`PORTFOLIO.html:739~743`), 그리고 `PORTFOLIO.html:749` 의 "5,000건 → 통과 100여 건" 라벨이 게이트와 브로커 **사이**에 붙어 있다.

**코드 근거**

`CouponAsyncIssueService.java:48-58` — 접수(enqueue) 경로 전부:
```java
public String enqueue(Long couponId, Long userId) {
    String requestId = UUID.randomUUID().toString();
    redisTemplate.opsForValue().set(STATUS_KEY_PREFIX + requestId, STATUS_WAITING, STATUS_TTL);
    CouponIssueRequestEvent event = new CouponIssueRequestEvent(requestId, couponId, userId);
    send(REQUEST_TOPIC, couponId.toString(), event);   // ← 검증 없이 바로 발행
    return requestId;
}
```
Lua 호출(`tryIssue`)이 **없다**. 게이트는 컨슈머 안에서 처음 실행된다 — `CouponAsyncIssueService.java:70` → `CouponIssueService.issueCouponWithoutLock` → `CouponIssueService.java:160-161` → `CouponStockRedisRepository.tryIssue`.

**왜 틀렸나**
1. 5,000건이 **전부** 브로커에 실린다. 문서가 주장하는 "브로커 보호" 효과는 0이다. 오히려 요청 1건당 Redis 왕복(WAITING 상태 기록) + Kafka 발행이 붙어 접수 비용이 늘었다.
2. 컨슈머는 파티션당 1개로 직렬 소비하므로, **컨슈머 안에서 실행되는 Lua의 원자성은 아무것도 지키지 않는다.** 이미 직렬화된 구간 안에서 `DECR` 을 원자적으로 하는 것은 의미가 없다. 문서 773행의 "Lua를 쓴 이유는 서버 대수와 무관하게 원자성이 유지되기 때문"은 이 배치에서는 성립하지 않는 논거다.
3. 따라서 Lua의 실제 역할은 "부하 필터"가 아니라 **재고 카운터의 단일 진실 저장소**다. 코드 주석이 이걸 명시적으로 말한다 — `CouponIssueService.java:148`: *"정확성의 책임이 Redis 한 곳에 모여 있고, **재고의 단일 진실도 Redis 다**"*. 문서 772행의 "Redis를 **정확성의 근거에서 내리고** 부하 필터로 재배치했음"과 **코드 주석이 정면으로 충돌한다.**

**면접에서 어떻게 깨지나**
> "5,000건 중 100건만 Kafka에 실린다고 하셨는데, `enqueue()` 어디에서 거르나요?"

한 줄 열면 끝난다. 그리고 이어서 *"그럼 Redis가 부하 필터라는 서술과, 코드 주석의 '재고의 단일 진실은 Redis' 중 어느 쪽이 사실인가요?"* 로 들어오면 이 절의 중심 논지(자원마다 정합성 근거가 다르다 — `PORTFOLIO.html:592`)까지 함께 무너진다.

**제안**
둘 중 하나를 골라야 한다. (A) 코드를 문서에 맞춘다 — `enqueue()` 안에서 `tryIssue` 를 먼저 호출하고 SUCCESS 일 때만 발행. 단 이 경우 게이트 통과 순서와 Kafka 발행 순서가 어긋나는 새 문제가 생긴다(L-2 참조). (B) 문서를 코드에 맞춘다 — "Redis는 재고의 단일 진실이고, Kafka는 그 카운터에 접근하는 순서를 직렬화한다"로 재서술. **B가 정직하고 방어 가능하다.** 지금 구조에서 Redis는 실제로 정확성의 근거이며, 그걸 인정하면 "Redis 되감기 시 초과발급"(문서 765행)이 남은 한계로 올라온다.

### C-2. 분산 락이 "발급 경로에서 걷어내고 배치로 옮겨졌다"는 서술은 **정확히 반대**다

**주장** (`PORTFOLIO.html:777`, `592`, `802`)
> "분산 락은 발급 경로에서 걷어내고 배치·관리 경로로 옮겼음. (…) 재고 대조·보정 배치와 조기 마감 처리에는 인스턴스 중 하나만 실행하도록 락을 걸었음"
> "분산 락은 두 발급·차감 경로 어디에도 두지 않고 **배치의 배타 실행에만** 남겼음" (592행)

**코드 근거**

Redisson 락을 쓰는 파일은 전 저장소에서 **딱 하나**이고, 그것이 발급 경로다:
```
$ grep -rl "redissonClient\|RLock" backend/src/main/java
backend/src/main/java/groom/backend/application/coupon/CouponIssueService.java
backend/src/main/java/groom/backend/infrastructure/config/RedissonConfig.java
```
- `CouponIssueService.java:118-141` — `redissonClient.getLock("coupon:lock:" + couponId)`, `tryLock(3s)`, 발급 경로 한복판.
- 기본 발급 엔드포인트 `POST /v1/coupon/issue/{coupon_id}` 가 이걸 호출한다 — `CouponController.java:147`.
- **재고 대조·보정 배치는 존재하지 않는다.** `@Scheduled` 는 `PaymentCompensationService`, `RaffleScheduler`, `SseService`, `PaymentEventPublisher` 넷뿐이고 쿠폰 재고를 다루는 것은 없다. 조기 마감은 Kafka Streams(`CouponDelayConsumer`) 소관이라 락과 무관하다.
- 코드 자신이 이 상태를 명시한다 — `CouponAsyncIssueService.java:21-22`: *"**기존 동기 발급(Redisson 락)을 유지한 채** 추가되는 비동기 경로다"* (Strangler 미완).

**왜 틀렸나**
문서는 락의 위치를 "발급 → 배치"로 이동했다고 하는데, 실제로는 **발급에만 있고 배치에는 없다.** 방향이 뒤집힌 정도가 아니라, 이동의 목적지 자체가 코드에 없다. 그리고 락이 붙은 동기 경로가 **여전히 기본 엔드포인트**이며, k6 측정도 그 경로를 때린다(`k6/scripts/coupon-issue-test.js:85` → `/coupon/issue/${couponId}`). 비동기 경로 `/issue-async/`는 병렬로 추가된 실험적 경로다.

**면접에서 어떻게 깨지나**
> "발급 경로에서 락을 걷어냈다고 하셨는데, `CouponController` 의 `POST /issue/{id}` 는 어느 서비스를 부르나요?"

`issueCoupon()` → `tryLock`. 여기서 *"그럼 걷어낸 게 아니라 옆에 하나 더 만든 거네요"* 가 나오고, 이어 **"보정 배치는 어디 있죠?"** 에서 두 번째로 무너진다. 문서 811행이 보정 배치를 "이 구조의 **필수 구성요소**"라고 못 박아 뒀기 때문에, 없다는 사실이 곧 "필수 구성요소가 빠진 채로 완료라고 썼다"가 된다.

**제안**
`해결 과정` 8번(777행)과 `남은 한계` 811행을 "미구현"으로 명시하거나, 절 전체를 **AS-IS(락 기반, 측정 있음) / TO-BE(Kafka 단일 판정, 설계·부분 구현)** 2단 구성으로 재편할 것. 지금은 두 구조가 한 시제로 뒤섞여 있어 어느 쪽을 말하는지 독자가 구분할 수 없다.

### C-3. "최후 방어선"인 DB 유니크 제약이 **존재하지 않는다**

**주장** (`PORTFOLIO.html:776`, SVG `730`)
> "최후 방어선은 DB 유니크 제약(`couponId, userId`)에 두었음. (…) **중복 발급이 물리적으로 불가능한 지점**을 저장소 제약으로 한 번 더 잡은 것임 — 애플리케이션 로직이 틀려도 여기서 막힘"

**코드 근거**
- `V1__Initial_schema.sql:172-177` — `coupon_issue` 에 걸린 것은 FK 2개(`fk_coupon_issue_user`, `fk_coupon_issue_coupon`)와 **일반 인덱스 2개**(`idx_coupon_issue_user_id`, `idx_coupon_issue_coupon_id`)뿐. UNIQUE 없음.
- 전 마이그레이션에서 `coupon_issue` 대상 UNIQUE 제약 0건. 엔티티 `CouponIssue.java` 에도 `@Table(uniqueConstraints=...)` 없음(저장소 내 `@UniqueConstraint` 는 `CartItemJpaEntity`, `RaffleTicketJpaEntity` 둘뿐).
- 리팩토링 계획 문서가 이 항목을 **P1 "가장 먼저"** 로 지정해 뒀다(`REFACTORING_PLAN_COUPON.html`: `ALTER TABLE coupon_issue ADD CONSTRAINT uk_coupon_issue_user UNIQUE (coupon_id, user_id);`). 즉 **가장 먼저 하기로 한 일이 안 돼 있다.**

**왜 틀렸나 — 그리고 이건 이론이 아니라 재현 가능한 결함이다**

중복 발급을 막는 유일한 장치는 Redis SET `coupon:issued_users:{id}` 의 `SISMEMBER`/`SADD`다(`CouponStockRedisRepository.java:43,47`). 그런데:

1. 이 SET에는 **TTL이 없고, 재시작 시 복원되지 않는다.** 워밍업 러너는 재고 카운터만 심는다 — `CouponStockWarmUpRunner.java:50` 은 `initStockIfAbsent`(SETNX, stock 키만) 호출이고 발급자 SET을 재구축하는 코드는 저장소 어디에도 없다.
2. 따라서 **이벤트 진행 중 Redis가 재시작/플러시되면**: stock 키가 사라짐 → 러너가 DB `quantity` 로 SETNX 재시드 → `issued_users` 는 빈 SET → 이미 받은 사용자가 다시 요청하면 `SISMEMBER=0` → SUCCESS → `persistIssuedCoupon` 이 **두 번째 `CouponIssue` 행을 INSERT** 한다. 막을 제약이 없다.
3. `decreaseQuantityAtomically`(`CouponRepository.java:37-39`)가 총량은 지키지만 **1인 다수 발급은 못 막는다.** quantity 조건은 `> 0` 뿐이다.

문서가 "애플리케이션 로직이 틀려도 여기서 막힌다"고 자랑한 바로 그 시나리오에서, 아무것도 막지 않는다.

**면접에서 어떻게 깨지나**
> "Redis가 이벤트 도중 재시작하면 어떻게 되나요?"

문서 765행이 이미 "Redis는 되감길 수 있다"고 스스로 말해 뒀으므로, 면접관은 **문서의 논리를 그대로 이어서** 이 질문을 한다. 답이 "유니크 제약이 막습니다"인데 제약이 없으면, 방어선이 아니라 **없는 것을 있다고 말한 것**이 된다. 신입 지원자에게 가장 치명적인 유형의 감점이다.

**제안**
마이그레이션 1줄이면 끝나는 일이므로 **문서를 고치기 전에 코드를 고쳐라.** (기존 데이터 중복 확인 후 `ALTER TABLE`.) 추가로 발급자 SET 재구축(부팅 시 `SELECT user_id FROM coupon_issue WHERE coupon_id=? AND is_active` → SADD) 또는 SET을 신뢰하지 않고 DB 제약 위반을 정상 경로로 처리하는 설계 중 하나를 선택해야 한다.

### C-4. `Redis Cluster` · `해시태그 슬롯 고정` · `CROSSSLOT` — **클러스터가 없고, 해시태그도 없다**

**주장** (`PORTFOLIO.html:588`, `711`, `715`, `773`, `810`)
> 태그: `Redis Cluster` (588행)
> "Cluster에서는 스크립트가 다루는 키가 모두 같은 슬롯에 있어야 하므로(아니면 `CROSSSLOT` 오류) 키를 `coupon:{couponId}:stock` 형태로 잡아 **해시태그로 슬롯을 고정**했음" (773행)
> "해시태그로 한 쿠폰의 키를 한 슬롯에 몰았으므로 Redis는 그 노드가 상한임" (810행)

**코드 근거**
- 실제 키 (`CouponStockRedisRepository.java:28-29`):
  ```java
  public static final String STOCK_KEY_PREFIX = "coupon:stock:";
  public static final String ISSUED_USERS_KEY_PREFIX = "coupon:issued_users:";
  ```
  → `coupon:stock:1`, `coupon:issued_users:1`. **중괄호 해시태그가 없다.** 문서가 적은 `coupon:{couponId}:stock` 형태가 아니다. 실제 클러스터에 올리면 두 키가 서로 다른 슬롯으로 가서 이 Lua는 **CROSSSLOT 에러로 항상 실패**한다.
- 클러스터 자체가 없다: `RedissonConfig.java:39` `config.useSingleServer()`, `docker-compose.dev.yml:17-19` 단일 `redis:latest` 컨테이너, `application-dev.yml:18-29` `host: localhost / port: 6379` 이고 cluster 블록은 **주석 처리**돼 있다.

**왜 틀렸나**
이 항목은 "구현했는데 미측정"이 아니라 **문서에만 존재하는 사실**이다. 더 나쁜 것은, 문서가 이 가짜 사실 위에 두 개의 논증을 더 쌓았다는 점이다 — (a) 문제 원인 765행의 "Cluster 비동기 복제라 되감김" 논거, (b) 남은 한계 810행의 "핫 단일 쿠폰이 한 슬롯에 몰려 확장 안 됨" 논거. 인프라가 standalone이면 (a)는 이 프로젝트의 문제가 아니고, (b)의 원인 진단도 틀린다(단일 노드라 슬롯 얘기 자체가 성립 안 함).

**면접에서 어떻게 깨지나**
> "해시태그로 슬롯 고정했다고 하셨는데, 실제 키 문자열 보여주실 수 있나요?"

`coupon:stock:1`. 그리고 *"그럼 이 Lua는 클러스터에서 돌아본 적이 없겠네요"* → *"클러스터 태그는 왜 붙이셨죠?"* 순으로 이어진다. **이력서 기술 태그의 신뢰도 전체**가 이 한 지점에서 흔들린다.

**제안**
셋 중 하나. (a) 실제로 해시태그를 넣고 클러스터로 띄워 검증, (b) 태그와 서술에서 Cluster/CROSSSLOT/해시태그를 전부 제거하고 "standalone Redis"로 정정, (c) "클러스터 전환 시 필요한 조치"로 **미래 시제로** 재서술. 최소 비용은 (b)+(c) 조합이다.

### C-5. `acks=all + min.insync.replicas=2` — 한쪽은 설정돼 있고, **핵심인 min.insync.replicas는 없으며 물리적으로 만족 불가**

**주장** (`PORTFOLIO.html:770`, SVG `719`)
> "고른 이유는 유일해서가 아니라 `acks=all` + `min.insync.replicas=2` 로 **동기 복제를 강제할 수 있는 유일한 계층**이기 때문임 — 리더가 죽어도 커밋된 순서는 보존됨"
> SVG 라벨: "acks=all · ISR 2" (719행)

**코드 근거**
- `acks=all` 은 맞다 — `KafkaConfig.java:248` (`paymentEventProducerFactory`, 쿠폰 비동기 경로가 이 템플릿을 재사용한다: `CouponAsyncIssueService.java:42,110`).
- `min.insync.replicas` 는 **저장소 어디에도 없다.** 프로듀서 설정도, 토픽 생성 코드(`NewTopic` 빈 0개)도, 브로커 환경변수도 없다.
- **브로커가 1대다** — `docker-compose.dev.yml:41-58`, `KAFKA_BROKER_ID: 1` 단일, `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1`, `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1`. 토픽은 `KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"` 로 자동 생성되므로 **replication factor 1**.

**왜 틀렸나**
RF=1에서 `acks=all` 은 `acks=1` 과 **완전히 동일**하다(ISR이 리더 혼자). 그리고 `min.insync.replicas=2` 를 실제로 걸면 모든 produce가 `NOT_ENOUGH_REPLICAS` 로 **전부 실패**한다. 즉 문서가 Kafka를 선택한 **유일한 근거로 제시한 성질이, 이 프로젝트 환경에서 검증된 적이 없고 현재 구성으로는 켤 수도 없다.**

여기서 논증 사슬 전체가 끊긴다. 문서 770행의 논리는 "클라이언트 시각 ✗ / 서버 시각 ✗ / Redis ✗ / **Kafka만 동기 복제 가능 ✓**" 인데, 마지막 항이 성립하지 않으면 "왜 Kafka인가"에 대한 답이 사라진다. Kafka 오프셋이 **결정적이고 조작 불가능한 전순서**라는 것은 여전히 맞고 그것만으로도 충분히 좋은 근거인데, 문서는 굳이 검증 안 된 쪽을 근거로 내세웠다.

**면접에서 어떻게 깨지나**
> "브로커 몇 대로 띄우셨어요?" → "1대" → "그럼 acks=all이 acks=1과 뭐가 다르죠? min.insync.replicas=2는 그 구성에서 켜지나요?"

이건 Kafka를 아는 면접관이면 **반드시** 묻는다. 그리고 답이 없다.

**제안**
- SVG 719행 "acks=all · ISR 2" → "acks=all (단일 브로커 · RF=1, ISR 2는 미적용)" 로 정정하거나, 브로커 3대 구성으로 실제 검증.
- 770행의 선택 근거를 **"결정적 전순서 + 재생 가능성(오프셋)"** 으로 바꿔라. 이쪽은 단일 브로커에서도 참이고, 방어가 쉽다.
- 덧붙여 `enable.idempotence` 를 명시하지 않았다(`KafkaConfig.java:242-251`). Kafka 3.x 기본값이 true라 `acks=all`+`retries=3` 조합에서는 파티션 내 순서가 유지되지만, **누군가 acks를 "1"로 되돌리는 순간 재시도가 순서를 조용히 깬다.** 순서가 이 절의 핵심 주장이므로 `enable.idempotence=true` 와 `max.in.flight.requests.per.connection` 을 **명시적으로** 박아야 한다.

## 논리 구멍

### L-1. "선착순"은 코드가 보장하는 것이 아니다 — 보장되는 것은 **총량 상한 + (조건부) 1인 1매**

문서는 `선착순` 을 7군데(685, 689, 720, 761, 770, 800, 810)에서 쓰고, `한정 수량` 은 이 절에 **0회**다(591행 프로젝트 개요에만 1회). 그런데 코드가 실제로 지키는 것을 하나씩 보면:

| 보장 | 지키는 주체 | 코드 근거 | 상태 |
|---|---|---|---|
| 총 발급량 ≤ quantity | **DB 조건부 UPDATE** | `CouponRepository.java:37-39` (`SET quantity = quantity-1 WHERE quantity > 0`) | ✅ 실제로 지켜짐 |
| 1인 1매 | Redis SET (`SISMEMBER`/`SADD`) | `CouponStockRedisRepository.java:43,47` | ⚠️ Redis 재시작 시 깨짐 (C-3) |
| 발급 **순서** | — | 없음 | ❌ |

핵심: **이 시스템에서 가장 강한 보장을 제공하는 장치는 `decreaseQuantityAtomically` 조건부 UPDATE인데, 이 절 129행 어디에도 언급이 없다**(`조건부`/`UPDATE` grep 결과 762행 `SELECT ... FOR UPDATE` 한 건뿐, 그것도 "문제 원인"에서 비판 대상으로). 반대로 실제로 없는 유니크 제약은 "최후 방어선"으로 강조돼 있다. **있는 강점은 안 쓰고, 없는 것을 자랑하는** 구성이다.

순서 쪽은 이렇다:
- **동기 경로(기본 엔드포인트, 측정된 경로)**: Redisson `getLock()` 은 비공정 락이다. 대기 스레드 중 누가 먼저 깨어날지는 정의되지 않는다. 순서 보장 **전무**.
- **비동기 경로**: Kafka 오프셋 순서는 결정적이지만 **"요청 도착 순서"가 아니다.** (a) N대 API 인스턴스가 각자 프로듀서를 갖고, 배치·linger·네트워크 지연에 따라 리더 도달 순서가 정해진다. (b) 한 인스턴스 안에서도 N개 요청 스레드가 동시에 `KafkaTemplate.send` 를 호출하므로 accumulator 적재 순서는 스레드 스케줄링에 좌우된다.

문서 800행("선착순의 기준이 '무엇의 순서인가'로 답할 수 있게 됐음 — Kafka 브로커 도달 순서")은 **정직한 프레이밍이고 방어 가능하다.** 문제는 제목(685)과 761행이 그냥 "선착순"이라고 써서 독자에게 **도착 순서**를 약속한다는 것이다. 두 서술이 같은 절 안에서 다른 것을 말한다.

**제안**: 제목과 본문의 `선착순` 을 **"한정 수량 · 브로커 도달 순서 기준 발급"** 으로 통일하고, 도착 순서와 브로커 도달 순서가 다르다는 점을 `남은 한계` 에 한 줄로 명시. 이건 감점이 아니라 **가점 요인**이다 — "선착순을 정의할 수 없다는 것을 알고 정의 가능한 대체 기준을 골랐다"는 서술이 훨씬 성숙해 보인다.

### L-2. 게이트 통과 순서와 Kafka 발행 순서는 **원리적으로 일치할 수 없다** (C-1을 고칠 때 생기는 함정)

C-1의 제안 (A)(게이트를 접수 앞으로 옮김)를 택하면 새 결함이 생긴다. 스레드 T1이 `DECR` 을 먼저 성공시켜도, T1이 `send()` 를 호출하기 전에 컨텍스트 스위칭이 나면 T2의 레코드가 먼저 브로커에 실린다. 즉 **"게이트를 통과한 순서"와 "오프셋 순서"가 다르다.** 그러면 게이트 통과분과 확정분의 순서가 어긋나고, 게이트가 이미 재고를 깎았는데 컨슈머 판정에서는 다른 순서로 확정되는 상태가 된다.

지금 코드(게이트가 컨슈머 안)는 **이 문제를 우연히 회피**하고 있다 — 판정이 오프셋 순서 한 곳에서만 일어나기 때문이다. 즉 **현재 코드가 문서보다 구조적으로 옳다.** 문서를 코드에 맞추는 방향(C-1 제안 B)이 맞는 두 번째 이유다.

### L-3. "거짓 품절이 원인 단계에서 소멸함"은 **정상 경로에 해당하지 않는다**

**주장** (`PORTFOLIO.html:801`)

게다가 비동기 경로에도 거짓 품절 유사물이 남아 있다:
- `persistIssuedCoupon` 의 `@Transactional(timeout=3)` (`CouponIssueService.java:194`) 초과 → `TransactionTimedOutException` → `CouponAsyncIssueService.java:81-88` 이 잡아 `FAILED:SERVER_ERROR` 기록. 재고는 `rollbackIssue` 로 복구되지만 **사용자 요청은 그냥 실패**한다. 재시도 없음.

**면접에서**: *"소멸했다는 게 두 경로 다인가요, 새 경로만인가요?"* → 새 경로만. → *"기본 엔드포인트는 아직 락 경로죠?"* → C-2로 합류. 단정형 서술 하나가 두 결함을 동시에 노출시키는 구조다.

- Redis 게이트 품절 (`CouponIssueService.java:164`) — **진짜 품절**
- DB 수량 소진 (`CouponIssueService.java:221`) — 저장소 불일치
- DB 폴백 경로 품절 (`CouponIssueService.java:251`) — 진짜 품절

### L-5. "중복 시도 28건 전량 거부" — 분모가 틀렸다

**주장** (`PORTFOLIO.html:803`)
> "수량 100개 쿠폰에 VU 200 · 5,000 요청을 걸어 100건 발급 · **중복 시도 28건 전량 거부**"

**코드로 계산**: `coupon-issue-test.js:71` `userNum = ((__VU-1) % USERS) + 1`, USERS=200, VUS=200 → VU마다 고유 사용자. `shared-iterations` 5,000 / 200 VU = **VU당 약 25회 요청**. 100명이 발급 성공했으므로 그들의 나머지 요청 **약 2,400건이 전부 중복 시도**다. 28건이 아니다.

왜 28건만 잡혔나 — Lua 스크립트의 **검사 순서** 때문이다(`CouponStockRedisRepository.java:36-48`):
```lua
if stock <= 0 then return 0 end          -- 품절 검사가 먼저
if SISMEMBER(KEYS[2], userId) == 1 then return -1 end  -- 중복 검사는 그 다음
```
재고가 0이 된 뒤에는 **이미 발급받은 사용자의 재요청도 `ALREADY_ISSUED` 가 아니라 `OUT_OF_STOCK` 으로 응답**된다. 28건은 "재고가 남아 있던 짧은 구간에 발생한 중복 시도"일 뿐이고, 나머지 ~2,372건은 품절로 집계됐다.

**두 가지가 동시에 문제다**
1. **문서**: "중복 시도 28건 전량 거부"는 중복 시도의 총량이 28건이었다는 인상을 준다. 실제 중복 시도는 그 100배 가까이 되고, 그중 대부분은 **잘못된 사유로** 거부됐다.
2. **코드(UX 결함)**: 이미 쿠폰을 받은 사용자가 새로고침하면 "이미 발급받으셨습니다"가 아니라 "품절입니다"를 본다. 중복 검사를 재고 검사보다 앞에 두면 해결된다.

**면접에서**: *"200 VU가 5,000번 쐈고 100명이 성공했는데 중복 시도가 28건이면, 나머지 성공자들은 재요청을 안 했다는 건가요?"* — 산수가 맞지 않는다는 것은 계산기 없이도 보인다.

### L-6. 도구 3종의 역할이 겹친다 — "겹치지 않음"이라는 주장이 성립하지 않는다

**주장** (`PORTFOLIO.html:802`)
> "네 도구가 각각 다른 보호 범위를 맡아 **겹치지 않음** — Lua는 접수의 원자성(부하 필터), Kafka 오프셋은 순서의 진실, 컨슈머는 정합성의 근거, 분산 락은 배치의 배타 실행. 이전 구조에서 락과 Lua가 같은 임계 구역을 이중으로 지키던 것이 정리됐음"

**실제 코드에서 셋을 하나씩 빼 보면:**

| 뺐을 때 | 실제로 깨지는 것 | 판정 |
|---|---|---|
| **Redisson 락 제거** (동기 경로) | 아무것도 안 깨진다. Lua가 원자적이고 `decreaseQuantityAtomically` 가 lost update를 막는다. `CouponIssueService.java:148` 주석이 스스로 인정한다 — *"이 메서드 자체는 락을 잡지 않는다"* | **순수 잉여** |
| **Lua 제거** (컨슈머 안) | 파티션 직렬 소비라 원자성은 필요 없다. 단 재고 카운터가 사라지므로 **모든 요청이 DB를 친다** → 성능만 깨지고 정확성은 유지 | **역할이 문서 서술과 다름**(원자성 아님, 캐시임) |
| **Kafka 제거** | 순서 기준이 사라지고, 응답 경로에서 DB가 다시 들어온다 | **유일하게 대체 불가** |
| **DB 조건부 UPDATE 제거** | 총량 상한이 Redis 단독 근거가 된다 → Redis 재시작 = 초과발급 | **문서에 언급조차 없는데 가장 중요** |

즉 "겹치지 않음"이 아니라, **동기 경로에서는 락과 Lua가 여전히 이중으로 같은 임계 구역을 지키고 있고(문서가 "정리됐다"고 한 바로 그 상태가 그대로 남아 있고), 비동기 경로에서는 Lua가 파티션 직렬성과 겹친다.** 정리된 것은 문서 안에서지 코드 안에서가 아니다.

**면접에서**: *"이 셋 중에 하나만 남긴다면 뭘 남기시겠어요?"* 는 이 구조를 본 면접관이 던질 가장 자연스러운 질문이고, 답을 준비 못 하면 "도구를 이해하고 조합한 게 아니라 배운 걸 다 넣었다"로 읽힌다.

## 꼬리질문 취약점

무너지는 순서대로. 각 항목은 "면접관 질문 → 지금 답할 수 있는 것 → 무너지는 지점".

### Q1. "`enqueue()` 코드 좀 보여주세요. 5,000건을 어디서 100건으로 거르나요?"
→ 못 보여준다. **C-1.** 이 질문 하나로 아키텍처 다이어그램 전체가 무효가 된다. 다이어그램이 틀렸다는 것은 "구조를 이해하고 그린 게 아니라 그리고 싶은 걸 그렸다"로 읽힌다.

### Q2. "Redis가 이벤트 도중 재시작되면 이미 받은 사람이 또 받을 수 있나요?"
→ **받을 수 있다.** 유니크 제약 없음(C-3), 발급자 SET 재구축 없음(`CouponStockWarmUpRunner.java:50`). 문서 765행에서 저자가 **스스로 이 위험을 제기해 놨기 때문에** 면접관은 자연스럽게 이 질문에 도달한다. 자기 문서가 유도하는 질문에 방어가 없는 상태.

### Q3. "Redisson `getLock()` 은 공정 락인가요?"
→ 비공정이다. 그러면 *"그럼 락 기반 구조에서는 선착순이 아니었네요?"* → 인정할 수밖에 없음 → *"그럼 문서의 '기존 구조에서 총량 상한은 지켜졌다' 외에 선착순 관련 실측은 없는 거죠?"* → 803행이 정확히 그렇게 쓰여 있어 여기까지는 방어 가능. **하지만 제목(685행)이 "선착순 순서"를 문제로 정의했기 때문에**, 해결 전에도 후에도 순서를 측정한 적이 없다는 결론이 남는다. **L-1.**

### Q4. "브로커 몇 대죠? `min.insync.replicas=2` 는 어떻게 거셨어요?"
→ 1대, 안 걸었다. **C-5.** Kafka 선택의 유일한 근거가 사라진다.

### Q5. "VU 200 × 5,000 요청인데 중복 시도가 28건이면 계산이 안 맞는데요?"
→ **L-5.** 수치의 신뢰성 자체가 의심된다. 하나가 안 맞으면 803행의 "100건 발급"도, 764행의 "341ms → 10,650ms"도 같이 의심받는다.

### Q6. "락 · Lua · Kafka 중 하나만 남긴다면?"
→ **L-6.** 준비 안 돼 있으면 도구 나열형 이력서로 보인다. 반대로 위 표를 그대로 답하면 **가장 좋은 인상을 줄 수 있는 질문**이기도 하다. 반드시 준비할 것.

### Q7. "ZRANK로 순번 조회한다고 하셨는데 API 좀…"
→ **D-7.** ZSet 코드가 통째로 없다. `CouponController.java:176-177` 주석이 "대기 순번은 응답하지 않는다"고 명시적으로 반대 결정을 적어 뒀는데 문서는 여전히 ZSet 절(774행) 전체와 SVG 원장 박스(727-728)를 유지하고 있다. 이건 **의도적 설계 판단을 문서가 따라잡지 못한 것**이라 정정이 쉽고(삭제하면 됨) 방치할 이유가 없다.

### Q8. "컨슈머에서 예외 나면 그 요청은 어떻게 되나요?"
→ 로그만 남고 오프셋 커밋, **영구 소실**. `CouponIssueRequestConsumer.java:30-33`. 그런데 Lua는 이미 `DECR` 했으므로 **재고 1이 증발**한다. 문서 811행이 이 누수를 인정하면서 해결책으로 제시한 보정 배치가 없으므로(D-14), 누수가 영구화된다. **"Kafka 도입했는데 DLQ가 없다"는 신입에게 흔한 지적**이고, 여기서는 재고 누수라는 실질 피해까지 붙는다.

### Q9. "쿠폰 수량을 관리자가 수정하면 Redis 재고는요?"
→ 동기화 코드가 없다. `CouponCommonService.updateCoupon` (`:106-122`) 은 DB만 바꾸고 `couponStockRedisRepository` 를 호출하지 않는다(생성 경로 `:42`, `:59` 에만 워밍업이 붙어 있다). `deleteCoupon` (`:124-133`) 도 Redis 키를 지우지 않아 **삭제된 쿠폰의 재고 키가 남는다.** 문서 범위 밖이지만 "Redis가 재고의 단일 진실"이라는 코드 주석과 정면 충돌하는 운영 결함.

### Q10. "두 발급 경로가 동시에 열려 있는데 서로 배제되나요?"
→ 동기 경로는 Redisson 락, 비동기 경로는 파티션 직렬성. **둘은 서로를 배제하지 않는다.** 코드가 이걸 인지하고 있고(`CouponIssueService.java:215-216` 주석), 그래서 `decreaseQuantityAtomically` 로 방어한다. **이건 잘한 판단이고 문서에 없다.** 답변 소재로 반드시 넣어라.

## 설계 대안 제안

### 우선순위 1 — 코드 (총 3개, 각 1시간 이내)

1. **유니크 제약 추가** (`ALTER TABLE coupon_issue ADD CONSTRAINT uk_coupon_issue_user UNIQUE (coupon_id, user_id)`). 계획 문서가 P1으로 지정했고 문서가 이미 있다고 주장하는 것. 기존 중복 데이터 확인 후 Flyway 마이그레이션 1개. **C-3 해소.**
2. **Lua 검사 순서 교체** — `SISMEMBER` 를 `stock <= 0` 검사보다 **앞으로**. 이미 받은 사용자가 "품절" 대신 "이미 발급"을 받게 되고, 측정 카운터의 오분류(L-5)도 사라진다. 3줄 이동.
3. **에러 코드 분리** — `COUPON_OUT_OF_STOCK` 를 최소 3개로: `COUPON_OUT_OF_STOCK`(진짜 품절) / `COUPON_ISSUE_CONTENTION`(락 대기 초과·인터럽트) / `COUPON_STORE_MISMATCH`(DB 수량 소진). k6 스크립트도 코드 기준 분류로 바꾸면 **"거짓 품절 0건"을 실제로 측정해 주장할 수 있게 된다** — 지금 문서가 근거 없이 단정하는 바로 그 지점(801행)에 근거가 생긴다.

### 우선순위 2 — 문서 (코드를 못 고치면 최소한 이것만은)

4. **절 구조를 AS-IS / TO-BE 2단으로 분리.** 지금은 두 구조가 한 시제로 섞여 있는 것이 모든 드리프트의 근원이다. `해결 과정` 1~8번 중 **실제 구현된 것은 1(부분)·2·6(비동기 경로만)** 이고, **3·4·5·7·8은 미구현 또는 사실과 다름**이다. 시제를 나눠라 — 구현분은 "~했음", 설계분은 "~하도록 설계했음(미구현)".
5. **없는 것 삭제**: ZSet 절(774행 전체)·SVG 원장 박스(727-728)·태그 `ZSet`(588), `Redis Cluster` 태그와 CROSSSLOT/해시태그 서술(715·773·810), `ISR 2`(719)·`min.insync.replicas=2`(770), 유니크 제약(730·776 — 코드 수정 시 유지), 보정 배치(735·737·750·777·811).
6. **코드카드를 실제 코드로 교체**(782-795 ↔ `CouponStockRedisRepository.java:36-48`). 문서 카드가 실제와 반환값·검사 순서·롤백 유무 모두 다르다.
7. **없는 강점 추가**: `decreaseQuantityAtomically` 조건부 UPDATE(총량 상한의 실제 근거)와 **두 발급 경로가 서로를 배제하지 않으므로 감산 자체를 원자적으로 만들었다**는 판단(`CouponIssueService.java:214-216`). 이건 신입 수준에서 드물게 좋은 판단인데 문서에 없다.

### 우선순위 3 — 구조에 대한 제안

8. **`min.insync.replicas` 대신 다른 근거로 Kafka를 정당화하라.** 단일 브로커에서도 참인 근거: (a) 오프셋이 결정적·조작 불가능한 전순서를 제공, (b) 로그가 보존돼 재판정·감사가 가능, (c) 컨슈머 그룹의 파티션 소유권이 **락 없이** 상호배제를 준다. (c)가 이 절의 핵심이고 771행에 이미 잘 쓰여 있다 — 770행의 복제 논거는 빼는 게 낫다.
9. **동기 경로의 Redisson 락을 실제로 제거하고 측정하라.** L-6 표대로 락은 잉여다. 제거 후 동일 k6 스크립트로 재측정하면 **"락을 뺐더니 지연이 얼마 줄었다"는 실측이 생긴다.** 지금 이 절에는 재설계를 지지하는 실측이 하나도 없고(808행이 인정), 이건 반나절 작업으로 만들 수 있는 유일한 실측이다.
10. **컨슈머에 DLQ + 재시도를 붙이고, 실패 시 `rollbackIssue` 를 보장하라.** 현재는 예외 삼킴 → 재고 영구 증발(Q8). `paymentEventKafkaListenerContainerFactory` 에 `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` 를 붙이면 되고, 같은 저장소의 `couponDelayEventConcurrentKafkaListenerContainerFactory`(`KafkaConfig.java:215-223`)에 **이미 그 패턴이 구현돼 있다.** 복사해 오면 된다 — 왜 한쪽에만 있는지 물으면 답이 없다.
11. **토픽 파티션 수를 명시하라.** `NewTopic` 빈으로 `coupon-issue-requests` 를 파티션 N개로 생성. 지금은 자동 생성 1파티션이라 D-11/D-12대로 "쿠폰 단위 확장"조차 안 된다. 이건 코드 5줄이고, **문서의 확장성 서술이 참이 되게 만드는 최소 조치**다.

## 부록: 이 절에서 **잘한 것** (방어 소재로 쓸 것)

비판만 남기면 무엇을 지켜야 할지 알 수 없으므로 명시한다. 아래는 코드로 확인된, 문서보다 오히려 나은 판단들이다.

- **`decreaseQuantityAtomically` 조건부 UPDATE** (`CouponRepository.java:37-39`) — 총량 상한의 실질적 유일 보증. 읽고-빼기의 lost update 창을 제거한 것이 맞고, 두 발급 경로가 서로를 배제하지 않는다는 인식(`CouponIssueService.java:215-216`) 위에서 내린 판단이라 논리도 온전하다.
- **워밍업의 SETNX 선택** (`CouponStockWarmUpRunner.java:21-25`, `CouponStockRedisRepository.java:64-74`) — "이벤트 중 Redis가 살아 있는 카운터이므로 SET으로 덮으면 커밋 전 요청 수만큼 재고가 되살아난다"는 이유가 정확하다. 상품 도메인과 의도적으로 다르게 간 것도 근거가 있다.
- **고정 `leaseTime` 폐기 + 워치독 + `@Transactional(timeout=3)` 조합** (`CouponIssueService.java:69-81`, `RedissonConfig.java:27-32`) — "워치독은 긴 임계 구역을 버티게 할 뿐 짧게 만들지 못한다"는 인식과, Hikari `connection-timeout` 이 그 상한 밖에 있다는 한계까지 주석에 적어 뒀다. **이 절에서 가장 성숙한 부분인데 포트폴리오에는 문제 원인(764행)의 소재로만 쓰이고 해결로는 안 나온다.**
- **커밋 이후 Redis 반영** (`runAfterCommit`, `CouponIssueService.java:498-511`; `CouponCommonService.warmUpStockAfterCommit:70-87`) — 롤백된 트랜잭션의 결과가 Redis에만 남는 사고를 막는다. 이유까지 주석에 있다.
- **대기 순번을 응답하지 않기로 한 결정** (`CouponController.java:176-177`) — "판정은 컨슈머 도달 순서로 정해지므로 큐 적재 순번을 돌려주면 지킬 수 없는 순서를 약속하게 된다". **이 절 전체에서 가장 좋은 판단**이고, 문서는 이걸 반영하기는커녕(774행) ZSet 순번 조회를 여전히 자랑한다. 문서에서 ZSet을 빼고 이 결정을 넣으면 절의 설득력이 올라간다.
