## 1. ZSet — 무엇이 정확하고 무엇이 부정확한가

### 자료구조는 정확하다

`CouponQueueRedisRepository.enqueue`(`:35-43`)는 `INCR seq` 로 원자적 순번을 받아 `ZADD NX` 로 등록한다.
score 가 단조 증가하는 Redis 카운터이므로 **ZSet 안에서 `rank()` 는 결정적이고 정확**하다.
"ZSet 이 정확한 순서를 제공하지 않는다"고 서술하면 **기술적으로 틀린 말이 되어 꼬리질문에서 뒤집힌다.**

### 부정확해지는 지점은 세 곳이다

| # | 지점 | 근거 |
|---|---|---|
| 1 | **동기 발급 경로는 ZSet 을 전혀 건드리지 않는다** | `CouponIssueService.java` 전체에 `enqueue`/`Queue` 참조 0건 |
| 2 | ZSet 등록과 Kafka 발행이 **비원자적** | `CouponAsyncIssueService.java:58`(ZADD) → `:62`(send) 두 단계 |
| 3 | 실제 발급 판정은 **Lua `tryIssue` 의 `DECR`** 이 한다 | `CouponStockRedisRepository.java:34-51` |

→ 즉 **사용자에게 보여주는 숫자와 결과를 결정하는 숫자가 서로 다른 계통**이다.
`rank` 는 "대기열에 등록된 순서"이고, 발급은 "Lua 에 도달한 순서"로 정해진다. 둘이 같다는 보장이 없다.

코드는 이를 정직하게 반영한다 — 주석은 `추정 대기 순번`, 응답 필드는 `position`/`waiting`,
포트폴리오는 `ZSet은 조회 전용 지표`라고 못박았다. **거짓은 없다.**
다만 이 hedge 가 하는 일이 크다. 뒤집어 말하면 **ZSet 은 아무것도 보장하지 않는 표시등**이다.

### 더 근본적인 지점 — 선착순은 애초에 보장되지 않는다

`redissonClient.getLock()`(`CouponIssueService.java:107`)은 **비공정 락**이다(`getFairLock` 검색 0건).
락 획득 순서는 도착 순서와 무관하다. 따라서 현재 구현이 보장하는 것은:

- ✅ **정확성** — 초과발급 없음 (Lua 원자 연산)
- ❌ **공정성** — 먼저 온 사람이 먼저 받는다는 보장 없음

재설계안 축 6 이 "정확성과 공정성은 다른 보장이다"라고 프레임을 세운 것은 **정확한 진단**이다.
제기한 위화감의 정체가 이것이다 — 기능 이름은 선착순인데 시스템은 선착을 보장하지 않는다.

## 2. leaseTime — 성능이 아니라 정합성 문제다

### 임계 구역에 DB I/O 가 들어 있다

```
lock.tryLock(3s, 5s)          CouponIssueService.java:111
  ├─ Lua tryIssue              :119   (수 ms)
  ├─ persistIssuedCoupon       :137   REQUIRES_NEW — DB INSERT + UPDATE
  └─ (NOT_INITIALIZED 이면)
       issueCouponInDbOnly     :130 → :194 SELECT FOR UPDATE + INSERT + UPDATE + initStock
finally unlock                 :148-150
```

`@Transactional(NOT_SUPPORTED)`(`:104`)가 막는 것은 **DB 커넥션 점유**이지 **락 보유**가 아니다.
락은 DB 쓰기가 끝날 때까지 잡혀 있다. 폴백 경로는 여기에 **비관적 락까지** 겹친다.

### leaseTime 초과가 뜻하는 것

- 명시적 leaseTime 은 **Redisson 워치독을 비활성화**한다 → 갱신 없는 하드 캡 5초
- 5초를 넘기면 **작업 중에 락이 조용히 풀린다** → 다른 요청이 진입 → 상호배제가 성립하지 않음
- 이 상태는 예외도 로그도 남기지 않는다. `isHeldByCurrentThread()`(`:149`)가 false 라 `unlock` 만 건너뛴다

**따라서 제기한 대로다 — 직렬화가 심해질수록 leaseTime 을 넘고, 넘는 순간 락이 하던 일이 사라진다.**
재설계안 축 5 는 이를 실측으로 재현했고(4개 수치 전부 어긋남), waitTime(가용성)과 leaseTime(정합성)을
분리해야 한다는 지적도 옳다.

### 다만 초과발급으로 직결되지는 않는다

정상 경로의 초과발급은 Lua 가 막는다. 락이 풀려도 `DECR` 은 여전히 원자적이다.
락 소실이 실제로 깨는 것은 **보상 구간의 배타성**이다 — Lua 성공 후 DB 실패 → `rollbackIssue`(`:139-141`)
사이에 다른 요청이 끼어들어 **재고가 곧 복구될 것을 모른 채 품절 응답**을 받는다.

> 즉 leaseTime 붕괴의 결과는 "초과발급"이 아니라 **"거짓 품절"** 이다.
> 이 구분을 못 하면 면접에서 위험을 과장하게 되고, 그것도 감점이다.

## 3. "억지로 맞춘 것 같다"는 위화감의 정체

도구 선택 자체는 방어 가능하다. 어긋난 것은 **진단과 처방이 같은 층위에 있지 않다**는 점이다.

| 포트폴리오의 진단 (문제 원인) | 실제 처방 |
|---|---|
| "임계 구역 안에 DB I/O 가 들어가 있는 한 서버를 늘려도 이 벽을 넘지 못함" | 분산 락 임계 구역 **안에 여전히 DB I/O 가 있다** (`:137`) |
| "커넥션 풀 크기가 곧 동시 처리 상한" | 커넥션 상한은 풀었다(`NOT_SUPPORTED`). **직렬화 상한은 그대로** |

DB 행 잠금이 Redis 키 잠금으로 바뀌어 **커넥션 고갈은 해소**됐지만,
"임계 구역에 DB I/O 가 있다"는 원래 진단은 **해소되지 않았다.** 위화감은 여기서 온다.

### 락이 정상 경로에서 하는 일은 하나뿐이다

포트폴리오는 이미 `정상 경로의 초과발급은 Lua만으로 차단되며, 여기서 락은 정확성에 기여하지 않음`이라
스스로 밝혔다. 그렇다면 정상 경로에서 락이 사는 이유는 **보상 창(Lua 성공 → DB 실패 → 롤백)을
다른 요청에게 감추는 것** 하나다(포트폴리오도 이 근거를 명시한다).

**비용 대비가 성립하지 않는다** — 드물게 일어나는 DB 실패의 관측 창을 가리려고
**모든 요청을 직렬화**하고, 그 대가로 leaseTime 상한과 waitTime 드랍(거짓 품절)을 떠안는다.

## 5. 권고 — 재설계 기반 서술 대신 "축 1 하나만 구현"

재설계안 전체를 포트폴리오의 기반으로 삼는 것에는 **반대**한다. 이유는 이미 스스로 세운 원칙 그대로다 —
*"이건 보고서가 아닌 포트폴리오다. 확장설계는 현재 되어있는 내용이 아니니 넣을 필요가 없다."*
미구현 6축을 기반으로 쓰면 "안 만든 걸 왜 썼나"가 되고, 지금 서술의 강점(실측·자기검증)까지 같이 죽는다.

### 대신 축 1 을 구현하면 연쇄로 해결된다

`createCoupon`(`domain/coupon/service/CouponCommonService.java:31-55`)에 `initStock` 한 줄 +
상품 쪽 `StockWarmUpRunner` 패턴을 복제한 쿠폰 러너. **작업량이 작다.** 효과는 연쇄적이다:

1. 정상 경로에서 `NOT_INITIALIZED` 폴백이 사라진다 → **락 임계 구역에서 DB I/O 가 빠진다**
2. → leaseTime 압박 소멸 (§2 의 정합성 문제가 원인 단계에서 사라짐)
3. → §3 의 "진단과 처방 불일치"가 해소된다. "임계 구역에 DB I/O 가 있으면 안 된다"는 진단이
   **새 구조에서 실제로 지켜진다**
4. → 포트폴리오의 단일 기준 `"임계 구역이 Redis 밖으로 나가는가"` 가 **비유가 아니라 사실**이 된다.
   락은 그대로 두되 역할이 "정상 경로 직렬화"가 아니라 "예외 경로 배타성"으로 좁혀진다

> 재설계안 축 1 의 문장이 이미 이 결론을 담고 있다 — **"락은 그대로 두고 락이 비싼 일을 하는 상황을 없앤다."**

### 포트폴리오 서술 조정 (구현 없이 지금 할 수 있는 것)

1. **정확성과 공정성을 분리해 명시한다.** 현재 제목·본문은 초과발급 차단(정확성)만 주장하므로 거짓은 없으나,
   "선착순인데 순서를 보장하나요"에 답이 준비돼 있어야 한다.
   답: *비공정 락이라 도착 순서는 보장하지 않는다. 보장하는 것은 수량 정확성이고,
   순서 보장이 요구사항이면 순번을 판정 근거로 올려야 한다(축 6).*
2. **leaseTime 붕괴의 결과를 "거짓 품절"로 정확히 서술한다.** "초과발급 위험"으로 쓰면 과장이고,
   Lua 가 막는다는 자기 서술과 충돌한다.
3. **락의 정상 경로 역할을 한 줄로 좁힌다.** "보상 구간을 다른 요청에 감춘다"까지가 사실이다.
4. `경합 전용 에러코드 분리`는 지금대로 **후속 과제**로 둔다 — 코드와 일치한다
   (`CouponIssueService.java:115·123·146·202` 네 경우가 모두 `COUPON_OUT_OF_STOCK`).

## 6. 종합

제기한 위화감은 **근거가 있다.** 다만 결함의 위치가 생각과 조금 다르다.

- 도구 선택(Lua·분산락·ZSet)은 방어 가능하고, 포트폴리오는 이미 각 도구의 보호 범위를 정확히 나눠 서술한다
- 실제 결함은 **락의 임계 구역이 진단과 어긋나는 것** 하나이고, leaseTime 문제와 거짓 품절이 전부 여기서 파생된다
- ZSet 은 부정확한 게 아니라 **판정과 연결되지 않은 것**이다. 표현을 이렇게 바꿔야 반박당하지 않는다
- 재설계안은 진단이 강하다. 특히 축 5 의 워치독 오해 교정과 waitTime/leaseTime 분리는 그대로 쓸 값어치가 있다.
  다만 축 6 ③ 의 Kafka 근거는 틀렸다

**한 문장으로**: 재설계안 6축을 서술 기반으로 올리지 말고, **축 1 하나를 실제로 구현해
지금 쓴 문장이 사실이 되게 만드는 것**이 가장 적은 비용으로 논리를 맞추는 길이다.
