## 1. 한 줄 결론

포트폴리오의 논리 구조와 설계 판단은 대체로 옳다. 문제는 **문서가 코드보다 3~4걸음 앞서 있고, 그 격차가 측정 수치 주장에까지 번진 것**이다. 따라서 이 작업은 "문장 다듬기"가 아니라 **드리프트 정산** — 각 주장을 ①코드를 고쳐 참으로 만든다 ②정직하게 강등한다 ③삭제한다 중 하나로 판정하는 일이다.

## 2. 근본 원인

`project_portfolio_code_coevolution` 에 기록된 결정 — **"포트폴리오를 명세로 두고 코드를 거기에 맞춰 간다"** — 자체는 합리적이었다. 실제로 그 방식이 코드 결함을 찾아낸 사례도 있다(eco-1 의 "임계 구역이 Redis 밖으로 나가는가" 기준이 비동기 경로의 락 부재를 지목).

문제는 **따라잡기가 완료되지 않은 채 문서가 계속 앞서 나갔다는 것**이다. `docs/plans/REFACTORING_PLAN_COUPON.html` 이 스스로 *"포트폴리오는 이미 TO-BE 구조로 서술돼 있으므로, 계획은 서술을 구현으로 따라잡는 작업 목록"* 이라고 적어 두었다. 즉 **드리프트는 사고가 아니라 알려진 상태**다. 그런데 포트폴리오의 `남은 한계` 절이 인정하는 것은 "미측정" 뿐이라, **미구현 범위가 은폐된 형태**로 남았다.

## 6. 방어 가능한 부분 (지켜야 할 것)

감사가 코드와 일치함을 확인한 항목들이다. 정산 과정에서 **같이 깎이지 않게 주의**한다.

- **eco-1**: SETNX 워밍업(SET 이면 재기동 시 재고 부활) / 워치독+`@Transactional(timeout)` 조합(둘 중 하나만이면 이전보다 나쁨) / `runAfterCommit` / `decreaseQuantityAtomically` 조건부 UPDATE / 대기 순번 미응답 결정 — **다만 마지막 것은 문서가 정반대로 서술 중**
- **eco-3/4**: 백오프 2·4·8·16분/총 30분 / `fastfail_latency.avg`=632.9ms≈0.6s / EOS 경계 한정 서술 / changelog 복구·standby 미설정 한계 명시 / 멱등키에서 retryCount 배제 근거
- **ai-3**: CB 임계값 3종 수치 전부(`application.yml:88-126` 과 일치) / 빈 응답 고착 발견·전이 2개 보강 / 30초 heartbeat / failover 7.18s 실측(`cluster-node-timeout 5000` 과 정합) / Auth Standalone 유지 근거
- **eco-2**: `@Retryable` 자기호출 함정을 `selfProvider.getObject()` 로 회피한 것은 **정확함**
- **eco-1 비동기 경로 설계 논리**: "파티션 단위 직렬 소비라 배타 제어가 이미 성립하므로 락 없이 같은 발급 코어를 재사용한다" — 이 판단이 eco-1 서사의 진짜 자산이다

## 7. 사용자 질문에 대한 답

### Q3. 쿠폰 선착순(분산락·Lua·Kafka)의 논리 허점

**논리 자체는 틀리지 않았다.** "선착순의 기준점을 Kafka 오프셋으로 정의하고, 파티션 소유권으로 락 없이 직렬성을 얻는다"는 논지는 정확하다. 허점은 논리가 아니라 **그 논리가 코드에 내려오지 않은 것**이다 — Tier 1 #4(게이트 위치)·#5(UNIQUE)·Tier 3(ZSet·ISR·Cluster·배치).

**선착순 발급 + 결제라는 목표는 유지 가능하다.** 버릴 이유가 없다.

다만 정직하게 강등해야 할 것이 하나 있다 — **Kafka 오프셋은 "브로커 도달 순서"이지 "사용자 클릭 순서"가 아니다.** 여러 API 인스턴스가 각자 프로듀서를 갖고 있어 `linger.ms` 배치·재시도에 따라 뒤집힐 수 있다. 문서가 이미 "기준점을 정의했다"로 방어하고 있으므로, **"시스템이 관측 가능한, 위조 불가능한 유일한 순서"** 라는 한정을 한 줄 더 붙이면 성립한다.

### Q5. 각 프로젝트에 추가하면 좋은 주제

**튜터링**
1. **`resilience4j-reactor` 1줄 추가 후 "안전장치는 실패 주입으로 검증해야 한다" STAR** — 가장 강하다. *"서킷을 붙였는데 리액티브 경로에서 안 걸리고 있었다. 실패를 주입해 보고 알았다"* 는 서사는 신입 포트폴리오에서 드물고, 원인(AOP는 반환까지만 감쌈)이 기술적으로 정확하다
2. **`chat.sse.ttft` Timer 로 TTFT 진짜 실측** — Timer 가 이미 있다. Tier 1 #8 의 근거 없는 300ms 를 실측으로 대체
3. **read-after-write 경로만 선형화** — Tier 2 A 를 고치면서 *"읽기 분산은 성능 최적화가 아니라 일관성 모델 변경"* 이라는 논지로 STAR 화

**커머스**
4. **Redis↔DB 대조 배치**(위 재고 4안) — eco-1 이 "필수 구성요소"라 못 박았으나 존재하지 않는 보정 배치와 같은 주제라 **두 STAR 를 동시에 참으로 만든다**
5. **경합 실패 / 진짜 품절 에러코드 분리** — 현재 락 타임아웃·인터럽트·진짜 품절·DB 소진이 전부 `COUPON_OUT_OF_STOCK` 하나(`ErrorCode.java:132`). 분리해야 "거짓 품절이 소멸했다"가 **측정 가능한 주장**이 된다
