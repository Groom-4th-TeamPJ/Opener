## 3. 완성된 HTML 블록

### 3-1. 교체 — `해결 과정` `<p>` 부터 `</ol>` 까지 (원본 638~652행 전체를 아래로 대체)

```html
<p class="sec-label solve">해결 과정</p>
<ol class="bul-num">
  <li>JPA 비관적 락을 Redisson 분산 락으로 전환하고 쿠폰별 락 키(<span class="mono">coupon:lock:{couponId}</span>)로 격리해 서로 다른 쿠폰끼리는 대기하지 않게 했습니다. <span class="mono">tryLock(waitTime=3s, leaseTime=5s)</span>로 무한 대기를 막고, 락을 잡은 인스턴스가 죽어도 5초 뒤 자동 해제되도록 해 데드락을 차단했습니다</li>
  <li>Redis Lua 스크립트로 "수량 확인 → 중복 체크 → 차감 → 발급자 기록"을 단일 원자 연산으로 묶었습니다 — Redis가 명령을 단일 스레드로 처리해 Lua가 하나의 명령처럼 실행되므로, 확인과 차감 사이에 다른 요청이 끼어드는 check-then-act 경합이 성립하지 않습니다. <b>정상 경로의 초과발급은 Lua만으로 차단되며, 여기서 락은 정확성에 기여하지 않습니다</b></li>
  <li>두 도구를 함께 쓴 이유는 <b>보호 범위가 다르기</b> 때문입니다 — Lua는 Redis 안에서 끝나는 연산의 원자성을, 분산 락은 Redis 밖까지 걸친 구간의 배타성을 담당합니다. 락이 반드시 필요한 지점은 DB에서 수량을 줄인 뒤 그 값을 Redis에 되쓰는 <b>미초기화 폴백 경로</b> 하나입니다. DB 비관적 락은 Redis를 보호하지 못하므로, <b>두 저장소에 걸친 이 구간을 배타 실행할 수 있는 수단은 분산 락뿐</b>입니다</li>
  <li>같은 원칙을 다른 도메인에도 일관되게 적용했는지 스스로 검증했습니다 — 재고 선점은 <b>락 없이 Lua만으로</b> 같은 성격의 문제를 풉니다. 재고는 미초기화 시 게이트를 건너뛰고 Redis에 쓰지 않아 임계 구역이 Redis 안에서 완결되기 때문입니다. 즉 <b>"임계 구역이 Redis 밖으로 나가는가"라는 단일 기준</b>이 두 도메인의 선택을 모두 설명합니다</li>
  <li>발급 진입 메서드를 <span class="mono">@Transactional(NOT_SUPPORTED)</span>로 선언해 락 대기·Lua 구간에는 DB 커넥션을 점유하지 않고, DB 쓰기만 <span class="mono">REQUIRES_NEW</span> 독립 트랜잭션으로 짧게 열도록 경계를 분리했습니다</li>
  <li>Lua 성공 직후 DB 저장이 실패하는 부분 실패는 <b>락이 아니라 보상이 담당</b>합니다 — 락은 동시 진입을 막을 뿐 이미 일어난 차감을 되돌리지 못하므로, DB 저장이 예외를 던지면 Redis 재고를 <span class="mono">INCR</span>하고 발급자 집합에서 제거하는 보상을 같은 흐름 안에서 실행합니다</li>
  <li>확인한 한계와 후속 조치는 두 가지입니다 — ① 락 획득 실패(대기 3초 초과)가 품절과 같은 응답으로 나가 재고가 남았는데도 사실과 다른 안내가 되므로, <b>경합을 품절과 다른 에러코드로 분리</b>하는 것을 후속 과제로 두었습니다 ② 단일 핫 쿠폰에 요청이 몰리면 락이 직렬화하는 만큼 대기가 누적되므로, 접수 즉시 응답하는 <b>비동기 발급 경로</b>(쿠폰 단위 큐를 직렬 소비해 락 경합이 없음)와 Redis ZSet 기반 <b>대기 순번 표시</b>를 후속 도입했습니다 — ZSet은 <b>조회 전용 지표</b>이고, 재고·중복 판정은 Lua가 담당합니다</li>
</ol>
```

### 4-2. 금지 표현 · 사실성

- "해야 합니다" 0회, "필요합니다" 0회, "확장 설계" 0회, "축으로" 0회 (grep 확인)
