# AI 튜터링 (ai-1~5) 평가

## 총평 (5줄 이내)
프로즈(해결 과정·결과) 서술은 코드와의 대조 정확도가 매우 높다. CB 정책 3지점 수치, State Machine 8상태·전이 2건 추가, RAG 임계값 0.7→0.2·Top-K 5, `app.chat.history-window` 기본 20, JWT 블랙리스트·`refreshToken:{userId}` 삭제·fail-close, Redis Cluster `testOnBorrow`·`REPLICA_PREFERRED`, RabbitMQ `max-attempts: 3` — 전부 소스와 정확히 일치했고 어긋난 곳을 찾지 못했다. 유일한 실질적 결함은 **ai-1의 코드 카드 하나**로, 실제 컨트롤러와 SSE 아키텍처가 다르게 그려져 있다(아래 참조). 나머지는 신규 지적 없음(선행 보고서의 §4 ai-4 제목 지적은 유효하며 "기존 지적"으로만 표기).

## 섹션별

### ai-1 SSE 연결의 스레드 고정 점유 문제
- 논리: 문제(platform 스레드 점유) → 원인(blockLast 동기 대기) → 조치(Flux 전환 + boundedElastic 오프로딩) → 검증(스레드 20개 고정 통제 실험) → 한계(대리 부하, 스레드 종속성 해소까지로 범위 한정) 사슬이 끊김 없이 이어진다. `streamStarted.compareAndSet` 로 첫 청크에서만 스레드명을 남기는 계측(`ChatServiceImpl.java:284-298`)은 "주장을 코드가 아니라 런타임으로 확인" 서술과 정확히 일치한다.
- 아키텍처: `publishOn(Schedulers.boundedElastic())` 이후 Redis 저장 + 상태 전이(`ChatServiceImpl.java:306-333`), 오프너 분석 경로는 같은 위치에 JDBC 트랜잭션까지(`ChatServiceImpl.java:420,464-476`) — "후자가 이벤트 루프를 잡으면 영향이 가장 크다"는 판단과 실제 구현이 일치한다.
- 설득력: 🔴 코드 카드가 실제 구조와 다르다(근거 아래). 프로즈는 강하나, 유일하게 제시된 코드 증거가 이를 훼손한다.
- 🔴 [높음] **코드 카드가 실제 아키텍처와 다른 흐름을 보여준다** — 문서(`docs/PORTFOLIO.html:175-180`)의 카드는 `@GetMapping("/chat/stream")` 하나가 `llmClient.streamTokens(sessionId)` 를 바로 구독해 SSE 로 흘려보내는 단일 엔드포인트 그림이다. 실제로는 `ChatController.java:47-57`(`GET /chat/connect`)이 세션 연결만 담당하고, LLM 스트리밍은 별도 `POST /chat/message` → `ChatServiceImpl.processMessage`(`ChatServiceImpl.java:240-344`)가 기존 Sink 에 push 하는 두 엔드포인트 구조다. 카드에는 `chatRedisService.validateSessionOwner`·`initializeSession`·State Machine 전이 등 실제 `connectSession`(`ChatServiceImpl.java:129-202`)의 핵심 로직이 전혀 없다. 필드명(`sinks`)만 실제 코드와 같아 "단순화한 예시"인지 "실제 코드 발췌"인지 구분이 안 되고, 뒤의 ai-5 가 같은 연결 경로를 "신규·재사용 두 분기 + 단일 통과점 소유자 검증"으로 정교하게 설명하는 것과 정면으로 배치된다.
  - 제안: 카드 상단에 "개념을 보여주기 위한 단순화 예시"라고 명시하거나, 실제 시그니처(`GET /chat/connect`, `Flux<ServerSentEvent<String>> connectSession(Long sessionId, UUID userId)`, `existingSink.asFlux()` 재사용 분기)를 반영해 교체.
  - 꼬리질문: "이 컨트롤러가 실제 코드인가요? SSE 연결과 메시지 전송이 왜 분리돼 있죠?" — 현재 카드로는 막힌다. `ChatController.java:47-57`, `66-70`(`POST /message`)을 보여줘야 방어된다.

### ai-2 채팅 Redis SPOF 제거
- 논리: SPOF → 도메인 공유 위험 → 수동 복구 지연 → (분리 + Cluster + 읽기분산 + 풀 검증) → 가용성≠내구성 한계 선언까지 결함 없음.
- 아키텍처: `ChatRedisConfig.java:92`(`testOnBorrow(true)`), `:97`(`ReadFrom.REPLICA_PREFERRED`), `docker-compose.local.yml:48-151`(redis-chat-1~6, 6노드) 모두 서술과 일치. "Redis는 버퍼로만" 주장도 `ChatMessageConsumer.java:89-90`(DB 저장 성공 후에만 `deleteMessage`)와 부합한다.
- 설득력: 🟢 문제없음. "약 7초 자동 복구"·"5~10분 수동 복구"는 실측/과거 경험치라 코드 대조 범위 밖 — **미확인**(장애 주입 재현이 필요, 소스에서 확인 불가).
- 🟢 지적 없음(선행 보고서 §6-1의 "연결 제한 없이" 문구 지적은 기존 지적, 유효함).

### ai-3 Circuit Breaker · State Machine
- 논리: 장애 전파 위험 → CB 3지점 차등 정책 → 최소 호출 수의 근거(표본 오판 방지) → State Machine 8상태 → "차단≠회수" 재발견 → 보완. 근거→조치 비약 없음.
- 아키텍처: `application.yml:91-125` — llm-chat/llm-rag(window10·min5·50%·OPEN30s·half-open3), redis-chat(window20·min10·60%·OPEN10s·half-open5) 수치가 본문과 **완전히 일치**(단, half-open 허용 건수는 redis-chat 이 5건인데 본문엔 별도 언급 없음 — 누락이 아니라 본문이 다루지 않은 세부일 뿐이라 결함 아님). State Machine: `ChatSessionState`(IDLE·CONNECTED·PROCESSING·STREAMING·COMPLETED + CONNECTION_ERROR·PROCESSING_ERROR·STREAM_ERROR = 8개, `ChatStateMachineConfig.java`), STREAM_ERROR→PROCESSING(`:119-123`)·PROCESSING_ERROR→PROCESSING(`:125-131`) 전이 2건 추가가 본문 서술과 정확히 일치. 빈 응답 시 STREAM_ERROR 회수 로직(`ChatServiceImpl.java:306-319`, `440-454`)도 일치.
- 설득력: 🟢 이 섹션이 5개 중 코드-문서 정합도가 가장 높다. "가상 장애 주입 → 약 1ms fast-fail"은 `test-circuit` CB 인스턴스(`application.yml:118-125`)가 실제로 존재해 방법론 자체는 뒷받침되나, 1ms 수치 자체는 런타임 측정값이라 **미확인**.
- 🟢 지적 없음.

### ai-4 RAG 검색 재현율 저하
- 논리: 임계값 0.7 기본값 → 재현율 저하 → 원인(언어 정렬) → 조치(0.2 하향 + Top-K5 + 폴백) → 근본원인 3안 비교 → 비용 근거로 보류, 흐름 견고. 다만 후반 3항목(조건부 빈 짝, VectorStore 5개소, 히스토리 윈도우)은 재현율과 무관한 주제 — **기존 지적**(선행 보고서 §4, 제목 확장 권고 유효).
- 아키텍처: `RagServiceImpl.java:42-58` — `topK`(기본 5)·`similarityThreshold`(기본 0.7, `@Value` 디폴트), `application-dev.yml:159-161`에서 `top-k: 5`, `similarity-threshold: 0.2` 로 오버라이드 — 본문의 "0.7에서 0.2로 낮췄다"·"Top-K 5" 서술과 정확히 일치. `LlmService`/`RagService` 조건부 빈 짝, `QuestionNewServiceImpl` 의 `ObjectProvider<VectorStore>`(`searchSimilarDocuments`, `QuestionNewServiceImpl.java:199`), `ChatHistoryProvider.getRecentHistory`/`getFullHistory` 두 계약 분리(`ChatHistoryProvider.java:18,22`) 전부 코드와 일치 — `backend/CLAUDE.md` 의 "Feature flags" 절 서술과도 정합.
- 설득력: 🟡 내용은 정확하지만 제목("RAG 검색 재현율 저하 해결")이 후반부 내용을 못 담는다 — 기존 지적 유지.
- 꼬리질문: "재현율 32%→8% 측정에서 사람이 채점했다는데, 채점자 간 일치도(inter-rater agreement)는 어떻게 관리했나요?" — 본문에 채점자 수·기준이 없어 현재 문서로는 답변 불가. 보강하려면 "1인 채점/2인 교차검증" 여부를 한 줄 추가.

### ai-5 인증·세션 방어선
- 논리: "방어가 동작한다를 무엇으로 증명하나" 질문 제기 → 3지점 계약 정의 → 검증 계층 선택(단일 통과점) → 재현 실험 → 설정 실효값 분리 검증. STAR 흐름이 가장 성숙하다.
- 아키텍처: `assertSessionOwner`(`ChatRedisServiceImpl.java:244-258`) 가 `initializeSession`(`:72-107` 내부에서 호출, 84행)과 `validateSessionOwner`(`:227-241`)의 공통 판정을 맡는 **단일 private 헬퍼** — 본문의 "단일 private 헬퍼로 모아 신규 연결·재사용이 같은 판정을 공유" 서술과 정확히 일치, 자기호출로 인한 `@CircuitBreaker` 프록시 우회 근거(`ChatRedisServiceImpl.java:82-83` 주석)도 코드에 그대로 있다. `JwtAuthenticationFilter.java:99-121` 의 fail-close(jti 없음도 폐기 취급, Redis 예외 시 인증 거부)와 `AuthServiceImpl.java:127-165`(로그아웃 시 `blacklist:access:{jti}` 등록 + `refreshToken:{userId}` 삭제 + 쿠키 정리, 손상 토큰도 정상 반환하는 멱등 처리) 모두 서술과 일치.
- 설득력: 🟢 방어 도구가 "쓰기만 구현됐다"는 이전 세션의 함정(PROJECT_NOTES "보안 기능이 쓰기만 구현된 경우")이 이번엔 재발하지 않았음을 코드로 확인했다 — 읽기(`isBlacklisted`)·거부(SecurityContext 미주입) 지점이 실재한다.
- 🟢 지적 없음. "TTL 3579초", "401/400/423" 등 수치는 런타임 재현값이라 **미확인**(코드상 로직은 정합적이나 정확한 초 단위는 기동 필요).

## 프로젝트 공통 패턴 (강점 / 약점)
- 강점: 수치·기술 용어 단위(CB 정책 4쌍, State 8개, RAG 임계값·Top-K, 블랙리스트 키 이름 등)가 **본문·코드·설정 파일 세 지점에서 한 글자도 안 틀리고 일치**한다. 이 정도 정합도는 흔치 않다 — 실제 구현자가 아니면 이렇게 세부값을 맞추기 어렵다는 점에서 설득력의 근거가 된다.
- 약점: 5섹션 중 코드 증거(code-card)가 있는 곳은 ai-1 하나뿐인데, 하필 그 하나가 실제 구조를 단순화하다 못해 다른 섹션(ai-5)의 서술과 충돌하는 그림을 준다. "증거를 하나만 보여줄 거라면 정확해야 한다"는 원칙이 깨진 지점.

## 예상 꼬리질문 Top 5
1. **"ai-1 코드 카드가 실제 컨트롤러인가요?"** — 현재 문서로 답변 불가. `ChatController.java:47-57`(`connect`)과 `66-70`(`message`)을 별도로 보여줘야 함.
2. **"State Machine 을 굳이 쓴 이유는? boolean 플래그 몇 개로도 충분하지 않나요?"** — 답변 가능. "비정상 전이를 코드 수준에서 차단"(전이 테이블 미선언 조합은 자동 거부)이 핵심 논거이고 `ChatStateMachineConfig.java` 전이표가 그대로 근거.
3. **"CB 최소 호출 수(5건/10건)는 어떻게 정했나요? 근거가 있나요?"** — 부분 답변 가능. 본문은 "표본이 적을 때 오판 방지"라는 정성적 근거만 제시, 통계적 도출 과정(신뢰구간 등)은 없음 — "실험적으로 정한 값"이라고 솔직히 답하는 편이 나음.
4. **"RAG 재현율 32%→8% 채점을 1인이 했나요, 여러 명이 했나요?"** — 현재 문서로 답변 불가(위 ai-4 참조).
5. **"Redis Cluster 장애 자동 복구 7초는 재현 가능한가요? Split-brain 은 어떻게 막나요?"** — 부분 답변 가능. "복제본 자동 승격" 메커니즘은 Redis Cluster 표준 동작이라 설명 가능하나, split-brain·quorum 관련 서술은 문서에 없어 별도 질문이 이어지면 막힘.
