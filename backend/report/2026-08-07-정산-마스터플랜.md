### 0.0.1 Lua 원자성 모순 해소 (2026-08-09) — §1-2 의 서술을 정정한다

`critic-tech` 미반영 지적 4건 중 **eco-1 Lua 원자성 모순**을 닫았다.
포트폴리오가 *"Lua는 끼어들 수 없음"* 과 *"동시 요청 둘이 Redis 중복 검사를 함께 뚫었다"* 를
같은 섹션에 함께 적어 자기붕괴하고 있었다.

**그 주장은 물리적으로 불가능하다.** Redis 는 스크립트를 끝까지 실행하고 다음 명령을 받으므로
**56ms 떨어진 두 호출은 완전히 직렬**이고, 뒤엣것의 `SISMEMBER` 는 반드시 1 을 돌려준다.
56ms 는 Lua 왕복(수십 µs)보다 세 자릿수 크다 — 애초에 동시성 창이 아니다.
따라서 **최소 한 건은 게이트를 거치지 않았다.**

**가설 검증 — "게이트 이전의 유물"은 틀렸다.** 임시 컨테이너로 groom 볼륨(`groom-shopping_db_data`)만
5433 에 붙여 조회했다(Opener 인프라 무중단).

| 사실 | 값 | 출처 |
|---|---|---|
| 스키마 최초 생성 (V1) | 2026-08-07 10:44 | `flyway_schema_history` |
| 중복 2건 생성 | 2026-08-07 11:40:14 (56ms 간격) | §1-2 기록 |
| V13 유니크 제약 + `DELETE` | 2026-08-07 13:49 | `flyway_schema_history` |
| Lua 게이트 최초 도입 | **2026-04-18** (`f472bba4`) | git |

**게이트가 4개월 전부터 있던 상태에서 난 중복이다.** DB 가 10:44 에 새로 만들어져
재고 키가 비어 있던 창이므로, `NOT_INITIALIZED`(-2) → `issueCouponInDbOnly` DB 폴백 경로가
유력하다 — 그 시점 DB 에는 아직 제약이 없었다(13:49). **다만 로그가 없어 단정하지 않는다.**

**서술 방침 (사용자 결정 2026-08-09)** — 확정 서술이 아니라 **추론 명시**로 쓴다.

### 0.0.2 `critic-tech` 미반영 3건 해소 (2026-08-09) — 이로써 4건 전부 닫힘

**ai-2 배포 토폴로지 미기재** — `docker-compose.dev.yml` 에 배치 제약이 없어
**마스터 3 + 복제본 3 이 전부 같은 호스트의 컨테이너**다. 견디는 것은 노드(프로세스·컨테이너)
장애뿐이고 **호스트 장애면 마스터와 복제본이 함께 죽는다.** 7초 회복도 그 전제 위의 값이다.
→ `남은 한계` **첫 항목**으로 신설. 가장 큰 미공개 한계라 맨 앞에 뒀다.

**eco-1 Kafka RF=1 논리 자기붕괴** — Redis 탈락 사유가 *"failover 에서 되감김"* 인데
RF=1 Kafka 는 복제가 아예 없어 **같은 잣대로는 Kafka 도 탈락**한다. 기존 서술은
RF=1 을 두 번 공개하고도 **이 비대칭을 설명하지 않아** 선택 근거가 사후 정당화로 읽혔다.
→ **축을 갈랐다.** 정상 운영의 순서 결정성·재생 가능성(확보) vs 장애 시 순서 보존(미획득).
가른 기준은 현재 상태가 아니라 **도달 가능한 상한** — Kafka 는 `RF≥3 · acks=all ·
min.insync.replicas=2` 로 얻지만 Redis 는 비동기 복제 + 재생 로그 부재로 **어떤 설정으로도 못 얻는다.**

**eco-3 결제 보상 배치 분산 락 없음** — 확인해 보니 `남은 한계`에 **이미 정확히 공개돼 있었다.**
진짜 빈 곳은 *"쿠폰 배치엔 락이 있는데 여긴 왜 없나"* 라는 **비대칭의 근거**였다.
→ **기준은 연산이 멱등인가.**

| 배치 | 연산 | 중복 실행 결과 | 배타 장치 |
|---|---|---|---|
| `CouponStockReconciliationService` | `initStock(id, expected)` = 읽고 계산해 **SET** (read-modify-write) | 보정이 서로를 덮음 (클래스 주석 `:30` 이 명시) | **RLock 필요** |
| `PaymentCompensationService` | Toss 취소 + **보상 레코드 ID 기반 불변 멱등키** | PG 가 흡수, 이중 환불 없음 | 락 불필요 |

**락은 멱등성을 살 수 없을 때 쓰는 수단**이다. 남는 `retryCount` 이중 증가는
`PaymentCompensation` 에 `@Version` 이 없어 실재하지만, **락이 아니라 조건부 UPDATE 로 풀 문제**다.

**적용 범위** — `PORTFOLIO_v2.html` · `PORTFOLIO.html` **각 3곳(총 6곳)**.
분량 변화: `ai-2` 7,843 → **8,178** · `eco-1` 13,829 → **14,153** · `eco-3` 8,675 → **8,987**.
**eco-1 이 기준(8,000)의 1.77배로 가장 크다** — 축소 단계의 1순위다.

### P3 주요 판단 (계획서에 근거 수록)

- **CB fallback 은 지점별로 다르게 처리한다.** LLM 경로는 **fast-fail 유지 + 문서 강등**,
  Redis 저장 경로만 진짜 degradation 으로 승격.
  근거 — 수능·모의고사를 배우는 학생이 대상이라 **그럴듯한 가짜 응답이 특히 해롭고**,
  같은 포트폴리오 STAR 4 가 이미 *"검색 결과가 비면 컨텍스트를 억지로 채우지 않는다"*(`PORTFOLIO.html:477`)를
  세워 뒀으므로 fast-fail 이 그 원칙과 일관된다
- **RAG 는 "32%→8%" 를 재현하지 않고 새 기준으로 다시 잰다.** `recall@5` 골든셋 24쌍
  (강의자료 8 / 기출 8 / 개념 8), 앵커 문자열 기반 기계 채점.
  **한계까지 문서화한다** — 24쌍이라 1건이 4.17%p라 그보다 작은 차이는 구분 못 함,
  정밀도 미측정, 질문 작성자가 구현자와 같아 코퍼스 어휘에 치우칠 수 있음
- **선형화는 "실패했을 때만 master 재확인"으로 한정한다.** 읽기 지점 3곳을 각각 판정하고,
  `chat.redis.read` Timer 에 `route=master|replica` 태그를 달아
  **읽기 분산이 실제로 유지되는지를 비율로 근거화**한다 (문서에 "분산을 유지하면서 필요한 곳만 선형화"라 쓰려면 그 비율이 필요)
- **`connectSession` 은 소유자 검증 어드바이스에서 제외한다** — 어드바이스는 진입 시점에 세션이
  이미 있다고 전제하는데 신규 연결은 그 세션을 지금 만드는 요청이라 전제가 성립하지 않는다
- **`ChatMessageConsumer` 도 어드바이스 대상이 아니다** — RabbitMQ 리스너는 HTTP 진입점이 아니고
  검증 실패 시 처리(ACK/DLQ)가 달라 명시 호출을 유지한다

### 정정: 포트폴리오의 RAG 임계값 서술

Spring AI 프레임워크 기본값은 `topK=4` · `threshold=0.0` 이다.
- "기본값 0.7" → **프레임워크 기본값이 아니라 프로젝트가 고른 값**이라는 뜻으로 정정
- "Top-K 5로 제한" → **5는 기본값 4보다 크므로 제한이 아니다.** 표현을 고치거나 실제로 낮춘 뒤 표로 근거를 댄다
