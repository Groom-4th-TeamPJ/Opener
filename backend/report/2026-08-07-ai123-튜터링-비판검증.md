# STAR 1 — SSE / Virtual Thread / Flux (153~262행)

## 치명적 결함

### 1-A. 9.5 → 55 req/s 는 Flux 리팩토링이 아니라 `spring.threads.virtual.enabled` 토글의 효과다

**주장**
> 220행: "개선을 측정할 때 **스레드 수를 20개로 고정**하는 통제를 뒀음 — 스레드를 자유롭게 늘리면 '스레드를 더 줬으니 빨라진 것'이라는 반박을 배제할 수 없어, 같은 스레드 수에서 처리량 차이가 나야 원인이 구조에 있다고 확정됨"
> 254행: "스레드 20개 고정 통제 실험에서 처리량 9.5 → 55 req/s(약 5.8배), p95 20s → 2s ... **같은 스레드 수에서 벌어진 차이**이므로"

**코드 근거**
- `backend/docs/measurements/TUTORING_MEASUREMENT_LOG.html` M1-b 표:
  - before = **"VT off + Tomcat threads 20"** → p95 20.08s / 9.47 req/s
  - after = **"VT on"** → p95 2.01s / 55.3 req/s
- 부하 대상: `k6/10_load_sync.js:46` → `POST /test/load-sync?seconds=2`
- 그 엔드포인트의 실체: `src/main/java/spring/backend/shared/test/ThreadPoolTestService.java:53` `holdThreadSync()` = `Thread.sleep(durationSeconds * 1000L)`

**왜 틀렸나**
1. **"같은 스레드 수" 통제는 존재하지 않았다.** before 만 20으로 묶었고 after 는 VT on, 즉 스레드 수 무제한이다. 문서가 방법론적 강점으로 내세운 바로 그 통제가 실험 설계와 정반대다. 측정 로그 자체도 "before(blocking) 는 VT off + 고정 스레드 풀 상태로 별도 측정해야 하며, 현재 실행은 after(reactive+VT) 기준"이라고 적어 두었다.
2. **측정 경로에 이 STAR 의 해결책이 하나도 없다.** `holdThreadSync` 는 `Flux` 도 `Sinks` 도 SSE 도 LLM 도 거치지 않는 단순 sleep 이다. 즉 이 숫자는 "Virtual Thread 가 블로킹 대기를 흡수한다"는 명제의 근거이지, "Flux 스트리밍으로 바꿔서 빨라졌다"의 근거가 아니다.
3. 심지어 before 의 20개는 **Tomcat 요청 스레드**이고, 옛 구현이 실제로 쓰던 것은 `@Async` 전용 풀(core 10 / max 50 / queue 100, `4e7d91fd^` 의 `AsyncConfig`)이다. 재현 대상 자체가 어긋난다.

**면접에서 어떻게 깨지나**
- "before 와 after 사이에 바꾼 변수가 정확히 무엇입니까?" → yml 한 줄(`spring.threads.virtual.enabled`).
- "그럼 Flux 로 바꾼 것의 효과는 따로 재셨습니까?" → 재지 않았다.
- "20개 고정이 통제였다면 after 도 20개여야 하지 않나요?" → 여기서 끝난다.

**제안**
254행의 수치를 STAR 1 의 결과에서 떼어내고, "Virtual Thread 도입으로 처리량의 스레드 풀 종속성 해소"라는 별도 문장으로 재라벨한다. 220행의 "인과 확정" 서술은 실험이 그렇게 설계되지 않았으므로 삭제하거나, after 도 `server.tomcat.threads.max=20` 으로 묶어 재측정한 뒤에만 유지한다. (참고: `server.tomcat.threads.max` 는 저장소 어떤 yml 에도 없다 — before 런은 외부 주입으로만 재현 가능하다.)

### 1-B. 문제 원인으로 지목한 "platform 스레드 고갈"은 리팩토링 시점에 이미 해소돼 있었다

**주장**
> 207행: "초기 구현은 `@Async` + `SseEmitter` + `blockLast()` 동기 대기 조합으로, 연결 1개가 **platform 스레드 1개**를 스트림 종료까지 그대로 점유"
> 208행: "platform 스레드는 ... 무한정 늘릴 수 없어, 동시 접속자가 늘수록 '스레드 풀 고갈 → 신규 연결 거부'로 이어지는 구조적 한계"

**코드 근거 (git)**
- `4e7d91fd` "feat : virtual thread 도입에 필요한 설정 변경" (2026-04-18) — `AsyncConfig` 에서 `ThreadPoolTaskExecutor(core 10 / max 50 / queue 100)` 제거, `application.yml` 에 `spring.threads.virtual.enabled` 추가
- `03bca96e` "refactor : 기본 채팅 서비스 webflux로 리펙토링" (2026-04-18)
- `git merge-base --is-ancestor 4e7d91fd 03bca96e` → **참**. VT 가 먼저다.
- `4e7d91fd` 이후 `03bca96e` 직전의 `AsyncConfig` 주석: "Virtual Thread가 활성화되면 Spring Boot가 자동으로 VT 기반 SimpleAsyncTaskExecutor를 제공하므로 수동 Executor 불필요"

**왜 틀렸나**
`@Async` + `SseEmitter` + `blockLast()` 조합 자체는 실재했다(`03bca96e^` 의 `ChatServiceImpl:241` `@Async processMessageAsync`, `OpenAiLlmService:186` `.blockLast()`). 그러나 **Flux 로 바꾸기 직전 상태에서는 그 `@Async` 가 이미 virtual thread 위에서 돌고 있었다.** 그 시점의 `blockLast()` 는 platform 스레드가 아니라 virtual thread 를 park 시켰고, VT 는 한 요청당 하나씩 무제한으로 찍히므로 "풀 고갈 → 신규 연결 거부"는 일어나지 않는다. 207~208행이 서술하는 실패 모드는 `4e7d91fd` **이전** 상태이지, 이 STAR 가 서술하는 리팩토링의 직전 상태가 아니다.

**면접에서 어떻게 깨지나**
- "Virtual Thread 는 언제 켜셨습니까?" → 커밋 로그로 즉시 드러난다. 두 변경을 하나의 STAR 로 합친 것이 보인다.
- "VT 가 켜진 상태에서 `blockLast()` 는 무엇을 점유합니까?" → carrier 가 아니라 virtual thread. 208행의 전제가 무너진다.

**제안**
STAR 를 둘로 쪼갠다. (1) 바운디드 풀 → VT 로 스레드 종속성 해소(측정 있음), (2) `blockLast()` 제거 → 토큰 도착 즉시 전달(구조 개선, TTFT 지표로 별도 측정). 지금은 (2)의 서사에 (1)의 숫자를 붙여 놓은 상태다.

### 1-C. "버퍼가 넘치면 유실이 아니라 연결을 끊는다"가 코드와 정반대다

**주장**
> 218행: "버퍼로 흡수해 **유실 없이** 순서대로 전달 ... 버퍼가 넘치면 **유실이 아니라 연결을 끊는 쪽으로** 두었음"

**코드 근거**
- `ChatServiceImpl.java:166` — `Sinks.many().multicast().onBackpressureBuffer()` (인자 없는 형태 = 버퍼 `Queues.SMALL_BUFFER_SIZE`, 기본 256)
- `ChatServiceImpl.java:558-562`
  ```java
  Sinks.EmitResult result = sink.tryEmitNext(sse);
  if (result.isFailure()) {
      log.warn("[SSE] emit 실패 - sessionId: {}, event: {}, result: {}", sessionId, eventName, result);
  }
  ```

**왜 틀렸나**
버퍼가 넘치면 `tryEmitNext` 가 `FAIL_OVERFLOW` 를 반환한다. 코드는 **경고 로그만 찍고 그 청크를 버린다.** 연결을 끊는 코드는 없다. 즉 실제 동작은 "연결 유지 + 조용한 유실"로, 218행이 말한 것의 정확히 반대다. 게다가 그 청크는 `llmResponseBuilder` 에는 이미 append 되므로(`:304`) Redis 에 저장되는 전문과 사용자가 본 화면이 어긋난다.

**면접에서 어떻게 깨지나**
- "`FAIL_OVERFLOW` 는 어디서 처리하십니까?" → `log.warn`.
- "유실 없이 전달한다고 하셨는데, 버퍼 크기는 얼마입니까?" → 명시한 적 없음(기본 256).

**제안**
문서를 코드에 맞춰 "오버플로 시 청크를 드롭하고 경고를 남긴다(개선 대상)"로 낮추거나, `onBackpressureBuffer(N)` 로 크기를 명시하고 `FAIL_OVERFLOW` 에서 `sink.tryEmitError` → 연결 종료를 실제로 구현한 뒤 현재 문장을 유지한다.

### 1-D. 클라이언트가 끊어도 LLM 스트림은 끝까지 돈다 — 서버측 취소 경로 부재

- `ChatServiceImpl.java:343`, `:503` — `.subscribe()` 의 반환 `Disposable` 을 어디에도 보관하지 않는다.
- `ChatServiceImpl.java:181-186` `doOnCancel` 은 `sinks`/StateMachine 만 정리한다.
- 이후 `emitEvent`(`:544-549`)는 매 청크마다 "Sink 없음" 경고만 찍고, OpenAI 토큰은 응답이 끝날 때까지 계속 소비·과금된다.

문서는 "연결 끊김"을 브라우저 자동 재연결(213행)과 heartbeat 정리(402행)로만 다루고, **서버가 상류 스트림을 취소하는 이야기가 없다.** "SSE 연결의 스레드 고정 점유 문제를 해결"이라는 제목이 다루는 자원은 스레드인데, 실제로 남는 자원 누수는 상류 구독과 LLM 비용이다.

꼬리질문: "사용자가 답변 도중 탭을 닫으면 OpenAI 호출은 어떻게 됩니까?" → 끝까지 돈다.
제안: `Disposable` 을 `sessionId` 별로 보관하고 `doOnCancel`/`disconnectSession` 에서 `dispose()`.

### 1-E. `sinks.remove(sessionId)` 가 값 비교 없는 무조건 제거 — 빠른 재연결에서 새 Sink 를 지운다

`ChatServiceImpl.java:182`, `:657` 모두 `sinks.remove(sessionId)` 다. 클라이언트가 끊고 즉시 재연결하면 (1) 새 연결이 `:169` 에서 새 Sink 를 `put`, (2) 이어서 옛 구독의 `doOnCancel` 이 실행되어 **방금 넣은 새 Sink 를 제거**한다. 그 뒤 `POST /chat/message` 는 `:250` 에서 `SESSION_EXPIRED`(401)로 거부된다. `sinks.remove(sessionId, sink)` 여야 한다.

추가로 `:140` 의 기존 Sink 재사용 경로는 `existingSink.asFlux()` 를 **`doOnCancel` 없이** 그대로 반환한다. 133행 주석이 말하는 "재연결 시 스트림을 잃지 않게"라는 의도와 달리, 이 경로로 붙은 구독은 정리 훅이 없다.

### 1-F. `publishOn(boundedElastic)` 뒤로 옮긴 것은 콜백뿐 — 조립 구간의 블로킹은 요청 스레드에 그대로 남아 있다

- `ChatServiceImpl.java:277` 주석: "non-blocking subscribe -> 요청 스레드를 붙잡지 않고"
- 그러나 `.subscribe()` 에 도달하기 전, 요청 스레드에서 동기로 실행되는 것:
  - `:259` `validateSessionOwner` (Redis)
  - `:270` `saveMessage` (Redis)
  - `:278` `llmService.chatStream(...)` **호출 자체** → `OpenAiLlmService.java:83` `getRecentHistory`(Redis) + `:105` `vectorStore.similaritySearch`(pgvector JDBC + **OpenAI 임베딩 HTTP 왕복**)
- 즉 `POST /chat/message` 는 "본문 없이 200 만 반환"(239행)이지만, 200 을 주기 전에 임베딩 API 왕복과 벡터 검색을 기다린다. `RagServiceImpl.java:62-63` 도 동일 구조다.

문서 215행 "요청 스레드 경로에 남아있던 동기 Redis 조회만 Virtual Thread로 흡수해 **요청 스레드를 즉시 반납**"은 두 겹으로 틀렸다. (a) 요청 스레드가 곧 virtual thread이므로 "VT 로 흡수"라는 별도 조치가 존재하지 않는다. (b) VT 는 스레드를 반납시키지 않는다 — 블로킹 동안 carrier 에서 unmount 될 뿐, 요청은 계속 같은 VT 위에 있다. 그리고 남은 동기 작업은 Redis 조회만이 아니라 pgvector 검색과 임베딩 호출이다.

### 1-G. Virtual Thread 와 Reactor 를 동시에 쓴 이유가 문서에 없고, pinning 검토 흔적도 없다

214행은 "WebFlux(Netty) 전환 대신 Reactor 타입만 도입"이라는 트레이드오프를 잘 설명한다. 그러나 **VT 가 이미 있는데 왜 Reactor 가 추가로 필요했는지**는 어디에도 없다. 실제 답은 코드에 있다 — `OpenAiLlmService.java:142-147` 의 Spring AI `ChatClient.stream().content()` 가 `Flux<String>` 만 반환한다. 선택이 아니라 API 제약이었다는 사실이 빠져 있어, "유행어 두 개를 같이 썼다"로 읽힐 여지가 크다.

pinning: `ChatSessionStateMachineService.java:35` `.block()`, `:59` `.blockLast()` 가 virtual thread(요청 스레드)에서 호출된다. Reactor 의 `block()` 자체는 `LockSupport.park` 라 VT 친화적이지만, Spring StateMachine 내부의 `synchronized` 구간은 carrier 를 pin 할 수 있다. 이 검토 흔적이 코드 주석에도 문서에도 없다. 스택 구성상 실제 문제 여부는 미확인이나, "Virtual Thread 를 도입했다"고 말하는 이상 답을 준비해야 하는 질문이다.

### 3-A. `resilience4j-reactor` 가 클래스패스에 없어 `Flux` 반환 메서드의 서킷브레이커가 LLM 스트리밍 실패를 전혀 기록하지 못한다

**코드 근거**
- `./gradlew dependencies --configuration runtimeClasspath` 의 resilience4j 모듈 전체:
  `annotations, bulkhead, circuitbreaker, circularbuffer, consumer, core, framework-common, micrometer, ratelimiter, retry, spring-boot3, spring6, timelimiter`

  - `reactor.core.publisher.Flux` (있음)
  - `io.github.resilience4j.reactor.AbstractSubscriber` (**없음** — `resilience4j-reactor` 모듈 소속)
  - 불충족 시 로그: `"Reactor related Aspect extensions are not activated because Resilience4j Reactor module is not on the classpath."`
- 따라서 `ReactorCircuitBreakerAspectExt` 빈이 등록되지 않고, `CircuitBreakerAspect` 는 기본 동기 처리로 폴백한다.

**왜 틀렸나**
`OpenAiLlmService.java:80-81`
```java
@CircuitBreaker(name = "llm-chat", fallbackMethod = "chatStreamFallback")
public Flux<String> chatStream(String sessionId, String userMessage) { ... }
```
Reactor 확장이 없으므로 서킷은 **`Flux` 객체를 조립해 반환하는 순간까지만** 감싼다. `Flux` 반환은 즉시 성공하고, OpenAI 의 5xx·타임아웃·연결 끊김은 **반환 이후 구독 중**에 발생하므로 서킷이 실패로 세지 않는다. `RagServiceImpl.java:51` 도 동일하다.

**결과적으로**
1. `llm-chat`/`llm-rag` 서킷은 **LLM 장애로 열리지 않는다.** STAR 3 의 제목이 성립하지 않는다.
2. 역설적으로, 그 서킷이 실제로 세고 있는 것은 반환 전 동기 구간의 실패 — 즉 `getRecentHistory`(Redis)와 `vectorStore.similaritySearch`(pgvector + 임베딩 API)다. **"LLM 서킷"이 사실상 Redis/pgvector 서킷이다.**
3. `fallbackMethod` 도 스트리밍 중 오류에는 호출되지 않는다. (서킷이 이미 OPEN 인 상태에서 `CallNotPermittedException` 은 동기로 던져지므로 그 경로의 fallback 은 정상 동작한다 — 즉 "열린 뒤"는 동작하고 "열리게 만드는" 부분이 죽어 있다.)

**면접에서 어떻게 깨지나**
- "OpenAI 가 스트리밍 도중 502 를 반환하면 서킷 실패 카운트가 오릅니까?" → 오르지 않는다.
- "`Flux` 반환 메서드에 `@CircuitBreaker` 를 붙이면 무엇이 측정됩니까?" → 조립 시간. 이 질문 하나로 STAR 3 전체가 무너진다.

**제안**
`build.gradle` 에 `implementation 'io.github.resilience4j:resilience4j-reactor:2.2.0'` 한 줄을 추가하면 `ReactorCircuitBreakerAspectExt` 가 활성화된다. 추가 후 **반드시 재검증**한다(기동 로그의 위 경고 사라짐 + 실제 실패 주입 시 `resilience4j_circuitbreaker_calls{kind="failed"}` 증가). 이 발견 자체를 STAR 로 승격하는 것이 지금 문서를 방어하는 것보다 훨씬 강하다 — 아래 "추가하면 좋은 주제" 1번.

### 3-B. 결과(407행)의 근거 실험이 프로덕션 경로를 검증하지 않았고, "타임아웃 3s 설정"은 존재하지 않는 설정이다

**주장**
> 407행: "가상 장애 주입 통제 실험에서 느린 실패(CB OPEN 전, 외부 호출 타임아웃 `3s` `설정` 까지 대기) → 서킷 OPEN 후 즉시 거부 `약 1ms` 로 fast-fail 전환 검증"

**코드 근거**
- 측정 로그 M3: "외부 호출 없이 `/test/circuit`(가상 장애: delayMs 3s + 예외)로 서킷 동작 재현"
- `ThreadPoolTestService.java:66-77`
  ```java
  @CircuitBreaker(name = "test-circuit", fallbackMethod = "unstableFallback")
  public String unstableCall(boolean fail, long delayMs) {
      Thread.sleep(delayMs);
      if (fail) throw new RuntimeException("simulated external failure");
      return "ok";
  }
  ```
  → 반환 타입이 `String`, 즉 **동기 메서드**. 3-A 의 결함이 없는 유일한 케이스다.
- `application.yml:118-126` `test-circuit` 인스턴스는 `llm-chat` 과 같은 값이지만 **별개의 서킷**이다.

**왜 틀렸나**
1. 검증된 것은 `test-circuit` 하나뿐이다. 이것을 STAR 3 전체(LLM 2지점 + 캐시 1지점)의 근거로 제시하면, 하필 **구조적으로 동작하지 않는 두 지점**을 동작하는 지점의 결과로 대변하는 셈이 된다.
2. **3s 는 "설정"이 아니라 k6 가 넘긴 `delayMs` 파라미터다.** OpenAI 호출에는 타임아웃 설정이 어디에도 없다:
   - `application.yml` / `application-dev.yml` 에 `spring.ai.openai` 관련 read/connect timeout 없음 (grep 결과 타임아웃은 Hikari 30000, Redis 3000, Redis chat 3000, mvc async 1800000 뿐)
   - `WebClientConfig.java:13-14` 는 `return WebClient.builder();` — `responseTimeout` 없음
   - `@TimeLimiter` 사용처 없음
3. 따라서 389행이 문제로 지목한 "요청이 **타임아웃까지** 매달려 느린 실패가 누적됨"의 그 타임아웃이 **존재하지 않는다.** OpenAI 가 응답을 멈추면 스트림은 MVC async 타임아웃 30분까지 살아 있을 수 있다. 문제 서술과 해결책이 서로 다른 세계를 가리킨다.

**제안**
407행의 `설정` 배지를 `가정` 으로 바꾸고, 측정이 `test-circuit` 에 한정됨을 명시한다. 그리고 실제 타임아웃을 하나 넣는 것(`WebClient responseTimeout` 또는 `@TimeLimiter`)이 389행을 참으로 만드는 최소 작업이다.

### 3-C. "OPEN → fallback → 대체 응답 즉시 반환"이 코드와 정반대다

**주장**
> SVG `:363`, `:365`: "OPEN → fallback / **대체 응답 즉시 반환**"
> 407행: "**캐시 저장소 일시 장애도 대체 응답으로 흡수돼 채팅 전체 중단 없이 동작**"

**코드 근거 — 세 fallback 전부 에러다**
- `OpenAiLlmService.java:184` — `return Flux.error(new BusinessException(ErrorCode.LLM_CIRCUIT_OPEN));`
- `RagServiceImpl.java:131-136` — 동일
- `ChatRedisServiceImpl.java:263-266` — `saveMessageFallback` → `throw new BusinessException(ErrorCode.REDIS_CIRCUIT_OPEN)`
- `ChatRedisServiceImpl.java:280-283` — `validateSessionOwnerFallback` → `throw new BusinessException(ErrorCode.REDIS_CIRCUIT_OPEN)`
- `ErrorCode.java:53-54` — `LLM_CIRCUIT_OPEN(503, "C_010", ...)`, `REDIS_CIRCUIT_OPEN(503, "C_011", "채팅 저장소가 일시적으로 이용 불가능합니다.")`

**왜 틀렸나**
"대체 응답(fallback response)"은 하나도 없다. 전부 fast-fail 이다. 특히 407행의 캐시 관련 문장은 정확히 반대다 — `validateSessionOwner` 는 채팅 전 경로의 첫 관문이므로(`ChatServiceImpl.java:139` connect 재사용, `:259` message, `:358` save, `:379` analysis), `redis-chat` 서킷이 열리면 **모든 사용자의 채팅이 10초 동안 503 으로 전면 중단**된다. graceful degradation 이 아니라 전면 차단이다.

**면접에서 어떻게 깨지나**
- "서킷이 열렸을 때 사용자는 무엇을 봅니까?" → 503 에러 메시지. 문서는 "대체 응답"이라고 썼다.
- "캐시가 죽어도 채팅이 돈다고 하셨는데, 소유자 검증은 어디서 합니까?" → 그 캐시에서. 한 문장에서 끝난다.

**제안**
SVG 와 407행을 "OPEN → 503 fast-fail (대체 콘텐츠 없음)"로 정정한다. fast-fail 자체는 정당한 설계 선택이므로(느린 실패보다 낫다) 정직하게 쓰면 오히려 강해진다. 진짜 degradation 을 원한다면 `validateSessionOwner` 만 별도 서킷/짧은 캐시로 분리하는 설계를 제시할 수 있다.

## 논리 구멍

### 3-D. 비즈니스 예외가 서킷을 오염시킨다 — 사용자 오류로 서킷이 열린다

- `application.yml:88-126` 의 세 인스턴스 모두 `recordExceptions`/`ignoreExceptions`/`recordFailurePredicate` 미설정 → Resilience4j 기본값은 **모든 `Throwable` 을 실패로 기록**한다.
- `ChatRedisServiceImpl.java:229 validateSessionOwner` 는 인프라 장애가 아닌 상황에도 예외를 던진다:
  - `:247-251` 세션 없음(TTL 만료·LRU 축출) → `INVALID_SESSION`
  - `:253-256` 소유자 불일치 → 권한 예외
- `redis-chat` 정책은 window 20 · min 10 · 실패율 60%(`:112-114`). **만료된 세션에 대한 요청 12건이면 서킷이 열리고, 그 순간 모든 사용자의 채팅이 `REDIS_CIRCUIT_OPEN`(503)으로 막힌다.**

397~398행은 임계값의 근거를 세 문단에 걸쳐 설명하지만, **"무엇을 실패로 셀 것인가"는 정하지 않았다.** 서킷 설계에서 임계값보다 먼저 오는 결정이다. 414행의 "남은 한계"도 임계값 이야기만 하고 이 문제는 인식하지 못한 상태다.

꼬리질문: "4xx 성격의 예외도 서킷 실패로 셉니까?" → 셉니다. "그럼 사용자가 남의 sessionId 를 반복 요청하면 어떻게 됩니까?" → 서킷이 열린다.
제안: `ignoreExceptions: [spring.backend.shared.response.exception.BusinessException]` 또는 인프라 예외만 `recordExceptions` 로 화이트리스트. 이건 yml 2줄이고, 발견 → 수정 → 근거 서술이 깔끔해서 그 자체로 좋은 STAR 소재다.

### 3-E. State Machine 이 막은 것을 401 로 알린다 — 프론트가 로그아웃한다

- `ChatServiceImpl.java:262-266` — `sendEvent(SEND_MESSAGE)` 거부 시 `throw new BusinessException(ErrorCode.SESSION_EXPIRED)`
- `ChatServiceImpl.java:382-386` — `openerAnalysis` 도 동일
- `ErrorCode.java:46` — `SESSION_EXPIRED(401, "C_003", "만료된 세션입니다.")`

408행이 자랑하는 "스트리밍 중 재전송을 구조적으로 차단"의 실제 사용자 경험은 **401 Unauthorized** 다. 표준적인 프론트엔드는 401 에 토큰 갱신 또는 로그아웃으로 반응한다. 의미상 409 Conflict(상태 충돌) 또는 429 성격인데 인증 실패로 나가고 있다. "코드 수준에서 차단했다"는 성취가 클라이언트 계약에서는 회귀로 나타난다.

### 3-F. 서킷으로 안 덮인 LLM 호출이 트랜잭션 안에서 돈다

- `ChatMessageConsumer.java:37-39` — `@RabbitListener` + `@Transactional`
- `ChatMessageConsumer.java:80` — `String summary = llmService.summaryChat(sessionId.toString());`
- `OpenAiLlmService` / `OpenAiLlmServiceWithoutRag` 의 `summaryChat` 에는 **`@CircuitBreaker` 가 없다.** 그리고 `.call().content()` 는 완전 동기 블로킹 호출이다.

즉 **DB 트랜잭션이 열린 채 OpenAI 응답을 통째로 기다린다** → HikariCP 커넥션(max 20, `application-dev.yml:10`)을 LLM 응답 시간(십수 초) 동안 점유한다. LLM 이 느려지면 커넥션 풀이 고갈되고, 이것이 정확히 390행이 말한 "연쇄 지연(Cascading Failure)"이다. 게다가 실패 시 `max-attempts: 3` 로 같은 LLM 호출을 3번 반복한 뒤 DLQ 로 간다.

"LLM 장애 전파를 차단했다"는 제목과 정면으로 충돌하는, **문서가 인지하지 못한 남은 전파 경로**다.

### 3-G. 스트리밍 중간에 끊기면 이미 보낸 토큰이 히스토리에서 사라진다 (부분 응답 미처리)

- `ChatServiceImpl.java:322-324` — Redis 저장은 **`doOnComplete` 안에서만** 일어난다.
- `ChatServiceImpl.java:335-342` `doOnError` 는 error 이벤트 발행과 `STREAM_ERROR` 전이만 한다. `llmResponseBuilder` 에 쌓인 부분 응답은 **버려진다.**

결과: 사용자 화면에는 절반쯤 쓰인 답변이 남아 있는데, 다음 턴의 LLM 히스토리에는 그 답변이 없다. **모델과 사용자가 서로 다른 대화를 보게 된다.** 400행은 "상태 회수"(PROCESSING 고착)를 잘 다뤘지만 "데이터 회수"는 다루지 않았다. 1-C 의 버퍼 오버플로 드롭과 합쳐지면 같은 종류의 불일치가 두 경로에서 발생한다.

꼬리질문: "스트리밍 도중 LLM 이 끊기면 이미 보낸 토큰은 어떻게 됩니까?" → 화면에는 남고 저장은 안 된다. 문서에 답이 없다.

### 3-H. `CONNECTION_ERROR` 상태는 도달 불가능한 죽은 코드다

- `ChatStateMachineConfig.java:65-71` — `IDLE → CONNECTION_ERROR (CONNECT_FAIL)` 전이 선언
- `ChatSessionEvent.CONNECT_FAIL` 을 `sendEvent` 로 발화하는 코드가 **저장소에 없다.** `connectSession` 의 catch 블록(`ChatServiceImpl.java:191-201`)은 예외만 던지고 상태 전이를 하지 않는다.

399행의 "에러 3상태(총 8개)" 중 하나가 장식이다. 전이 테이블 설계를 자랑하는 STAR 에서 도달 불가 상태가 있는 것은 "선언은 했지만 검증은 안 했다"의 증거로 쓰인다.

### 3-I. 전이 테이블에 대한 테스트가 0건이다

- `src/test/java/spring/backend/domain/chat/service/impl/ChatServiceImplTest.java:63` — `@Mock private ChatSessionStateMachineService stateMachineService;`
- `:97` — `when(stateMachineService.sendEvent(SESSION_ID, ChatSessionEvent.SEND_MESSAGE)).thenReturn(true);`

`ChatStateMachineConfig` 의 전이 테이블은 **단 한 번도 실행되지 않는다.** 저장소 전체 테스트에서 `CircuitBreaker`/`StateMachine` 을 참조하는 파일은 이 하나뿐이고, 그마저 둘 다 목이다. 399·408행의 "코드 수준에서 차단"에 회귀 안전망이 없다.

### 3-J. Spring StateMachine 을 고른 이유가 문서에 없다

상태 8개 · 전이 15개에 대해 라이브러리가 제공한 것은 실질적으로 리스너 로깅(`ChatStateMachineConfig.java:30-38`) 정도다. 대신 치른 비용은 명확하다 — 세션당 머신 인스턴스(`ChatSessionStateMachineService.java:32-38`), `.block()`/`.blockLast()` 두 곳(`:35`, `:59`), 그리고 인메모리 레지스트리(`:27`)로 인한 단일 인스턴스 제약.

`EnumMap<ChatSessionState, EnumSet<ChatSessionEvent>>` 자체 구현 대비 무엇을 얻었는지 답할 수 있어야 한다. 참고로 **STAR 1 의 "남은 한계"(261행)는 `sinks` 맵만 인스턴스 로컬이라고 적었는데, 상태 머신 레지스트리도 똑같이 인스턴스 로컬이다.** 스케일아웃 제약이 두 곳인데 한 곳만 고백했다.

# 추가하면 좋은 주제

이 코드베이스에서 **실제로 구현·측정 가능한** 것만 3개.

## 1. "서킷이 있는데 열리지 않았다" — 리액티브 경계에서 안전장치가 무력화된 사례

- **근거 파일**: `build.gradle:83-84`(의존성 누락), `resilience4j-spring6-2.2.0.jar` 의 `ReactorOnClasspathCondition`(두 클래스 동시 요구), `OpenAiLlmService.java:80`·`RagServiceImpl.java:51`(대상 지점), `ThreadPoolTestService.java:66`(왜 측정이 이 결함을 못 잡았는지)
- **할 일**: `resilience4j-reactor:2.2.0` 추가 → 기동 로그에서 "Reactor related Aspect extensions are not activated..." 경고 소멸 확인 → `ResilienceMetricsConfig.java` 로 이미 노출 중인 `resilience4j_circuitbreaker_calls{kind="failed"}` 로 before/after 대조. 실패 주입은 `spring.ai.openai.base-url` 을 죽은 포트로 돌리면 외부 비용 없이 가능하다.
- **왜 좋은가**: 지금 STAR 3 을 방어하려 애쓰는 것보다 훨씬 강하다. "어노테이션을 붙였다"가 아니라 **"안전장치는 붙였다고 동작하는 것이 아니라 실패를 주입해 확인해야 동작한다"**는 이야기가 되고, `test-circuit` 으로만 검증했던 것이 왜 이 결함을 놓쳤는지까지 설명할 수 있다. 조건부 빈이 조용히 비활성화되는 Spring 의 패턴(이 저장소의 `app.rag.enabled` 사례와 같은 계열)과도 자연스럽게 연결된다.

## 2. `chat.sse.ttft` 타이머로 첫 토큰 지연을 진짜로 재기

- **근거 파일**: `ChatServiceImpl.java:275`(`ttftStartNanos`), `:296-297`(`meterRegistry.timer("chat.sse.ttft").record(...)`), `application.yml:31`(`percentiles-histogram: chat.sse.ttft: true`), `k6/09_sse_ttft.js`(현재 TTFB 근사 + 로그인 경로 오류로 미실행)
- **할 일**: 계측과 히스토그램이 이미 다 있으므로, 세션 하나에 실제 채팅 몇 턴을 돌리고 Grafana 에서 p50/p95 를 읽는 것으로 끝난다. 동시에 `09_sse_ttft.js` 가 재는 것이 `connected` 합성 이벤트의 TTFB 라는 사실을 문서에 남긴다.
- **왜 좋은가**: 253행의 유일한 `실측` 배지를 근거 있는 것으로 바꾼다. 더 중요하게는 **"응답 완료 시간과 첫 토큰 시간은 다른 지표"라는 253행의 좋은 통찰에 실제 숫자를 붙일 수 있다.** 지금은 통찰만 있고 숫자는 비어 있다.

## 3. 읽기 분산과 프롬프트 정합성의 충돌 — read-after-write 경로만 선형화

- **근거 파일**: `ChatRedisConfig.java:97`(`ReadFrom.REPLICA_PREFERRED`), `ChatServiceImpl.java:270`(쓰기), `ChatRedisServiceImpl.java:148,163`(읽기), `OpenAiLlmService.java:83,136`(프롬프트 조립), `OpenAiLlmServiceWithoutRag.java:78`(`userMessage` 미사용)
- **할 일**: 두 단계로 나눌 수 있다. (a) 즉시 — `chatStream` 이 받은 `userMessage` 를 히스토리 뒤에 명시적으로 append 해서 복제 지연과 무관하게 질문을 보장. (b) 구조 — 프롬프트 조립 읽기만 master 로 고정하고 나머지(히스토리 조회, 요약)는 replica 유지.
- **왜 좋은가**: STAR 2 의 319행이 "stale read 를 인지하고 범위를 한정했다"고 주장하는데, **한정한 범위가 실제 위험 지점을 비껴갔다**는 것을 스스로 발견하고 고친 이야기가 된다. "읽기 분산은 성능 최적화가 아니라 일관성 모델 변경"이라는 결론으로 이어지고, 이건 STAR 2 를 지금보다 훨씬 단단하게 만든다.
