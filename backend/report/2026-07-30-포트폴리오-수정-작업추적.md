### 4. eco-1 선착순 쿠폰 발급 파이프라인 재설계 (에이전트 팀)

**문제**: 현재 구조가 과도한 락을 쓰고 있다고 스스로 인정하는 문단이다.

**대체 방향** — 사용자 지정 재설계 스코프
1. 분산 락은 **유지** (두 저장소에 걸친 구간 배타성이라는 역할을 근거로 정당화)
2. Redis ZSet 으로 **본인의 현재 처리 상태/대기 순번** 제공
3. 결제 시 쿠폰 **오버셀링 방지를 위한 재고 선점**
4. **핫 쿠폰 샤딩**으로 병렬 발급 처리

→ 회고가 아니라 **파이프라인 재설계 제안**으로 서술한다.

**에이전트 팀 산출물 요구**
- groom-shopping 실제 코드 기준의 현재 파이프라인 구조 (락 범위, Lua 스크립트, ZSet 사용처, 큐 경로)
- 샤딩 키 설계와 샤드 간 잔여 재고 회수 방식
- 재고 선점 TTL/회수 절차
- 위 4가지가 서로 충돌하지 않는지 (샤딩 + 단일 락 키의 양립성)

#### 코드 분석 결과 (완료) — 상세는 `agent-out-쿠폰-파이프라인-현황.md`

| 요청 항목 | 코드 실태 | 재설계 서술 방향 |
|---|---|---|
| 분산 락 유지 | ✅ 있음. 단 **락 구간 안에 DB 트랜잭션 전체 포함** (`CouponIssueService.java:137`) | 유지하되 **역할을 폴백 구간 배타성으로 명확히 한정** |
| ZSet 처리 상태 | ✅ **이미 구현됨** (`coupon:queue:{id}` ZSet + `coupon:seq:{id}` INCR, `GET .../position`) | "도입하겠다"는 **거짓**. **"기존 ZSet 을 샤딩과 결합"** 으로 서술 |
| 결제 시 재고선점 | ❌ **실제 갭** — `useCoupon` 프로덕션 호출자 0건 (테스트만) | **가장 강한 재료.** 발급은 이중 방어인데 소진은 무방비 |
| 핫 쿠폰 샤딩 | ❌ 없음 (`shard` 검색 0건) | 신규 설계. 단일 락 = 처리량 상한을 N배로 |

**추가로 확인된 구조 사실**
- 비동기 경로는 **Kafka** (RabbitMQ 아님). 토픽 `coupon-issue-requests`, **key = couponId → 동일 파티션 직렬** → 락 없이 동시성 해소
- 컨슈머 concurrency 미설정 = 기본 1 (`KafkaConfig.java:270-276`) → 직렬 전제 성립
- **쿠폰 재고 워밍업 없음** — `initStock` 호출자는 DB 폴백 1곳뿐 → **모든 쿠폰의 첫 발급은 반드시 DB 비관적 락 경로**
- `leaseTime=5s` 안에서 DB 트랜잭션이 돎 → DB 지연 시 **락 자동 해제된 채 임계 구역 계속 실행** 가능 (Lua 원자성이 초과발급은 막음)

- `rollbackIssue` 의 INCR·SREM 이 **Lua 로 안 묶여 비원자적**

## 2차 라운드 — 재설계안 축 5·6 추가 (2026-07-30)

사용자 질문에서 출발해 **코드 검증으로 확정한 사실 2건**을 축으로 추가한다.

### 축 5 — 락 수명 관리

**사용자 가설**: `waitTime`·`leaseTime` 초과로 대기자가 드랍되니, 설정값을 빼고 워치독으로 무한 연장하자.
다만 멀티 인스턴스에서 락 보유 중 서버가 죽으면 반환이 안 돼 영구 데드락이 되지 않겠나.

**검토 결과 — 직관은 옳고, 전제 2개가 틀렸다.**

| 판정 | 내용 |
|---|---|
| ✅ 맞음 | `leaseTime` 초과가 실제로 시스템을 깨뜨린다. **오늘 p99 재측정에서 재현됨** — 지연 중앙값 10,650ms ≫ leaseTime 5,000ms → DB 수량 60 / `coupon_issue` 54행 / distinct user 53(**중복 1건**) / Redis 재고 49 / SET 52. 네 숫자 전부 불일치 |
| ❌ 틀림 | **워치독은 무한 연장이 아니다.** TTL `lockWatchdogTimeout`(기본 30,000ms)을 `timeout/3`=10초마다 갱신한다. 프로세스가 죽으면 갱신 스레드도 죽어 최대 30초 후 Redis 가 만료 → **크래시로 인한 영구 데드락 없음**. 오히려 현재 `leaseTime=5s` 보다 안전하다 |
| ❌ 틀림 | **`waitTime` 과 `leaseTime` 은 다른 문제다.** `leaseTime` 초과 = 정합성 붕괴(워치독이 해결) / `waitTime` 초과 = 드랍(워치독과 **무관**). 워치독은 획득 후 TTL 연장이지 대기자에게는 영향이 없다 |

**워치독의 진짜 위험**: 크래시가 아니라 **hang**. JVM 이 살아있으면 계속 갱신되어 무한 점유.
그다음이 GC 정지·네트워크 단절(창이 5s→30s 로 넓어질 뿐 이중 진입은 여전).

**설정 현황**: `RedissonConfig` 는 `useSingleServer()` + pool 32 / minIdle 8, **`lockWatchdogTimeout` 미지정 → 기본 30초**. Redisson 3.27.2.

### 축 6 — 순번과 판정의 일원화 (선착순 공정성)

**사용자 질문**: ZSet 을 쓰는데 이게 진짜 선착순인가?

**검토 결과 — 진짜 선착순이 아니다. 순서가 흐트러지는 지점이 3곳.**

| # | 지점 | 근거 |
|---|---|---|
| ① | **동기 경로 비공정 락** | `redissonClient.getLock()` (`CouponIssueService.java:107`). `getFairLock` 저장소 전체 **검색 0건**. 승자는 락 해제 pub/sub 알림 도착 순 |
| ② | **비동기 경로 비원자성** | `enqueue()` 가 `INCR seq → ZADD` 후 **별도로** Kafka 발행. seq=1 이 seq=2 보다 늦게 도달 가능 → **표시 순번과 결과에 인과관계 없음** |
| ③ | **Kafka 순서 역전** | `acks=1`, `retries=3`, `max.in.flight` 미설정(기본 5), 멱등성 off → 재시도 중 뒤 배치가 먼저 기록 가능. `key=couponId` 로도 못 막음 (파티션은 "기록된 순서대로 읽힘"만 보장) |

코드 주석이 이미 인정: `CouponQueueRedisRepository.java:14` — "보장 순번이 아니라 추정 순번".

**정확성 ≠ 공정성**

| | 보장 | 근거 |
|---|---|---|
| 정확성 (초과발급 0) | ✅ | Lua 원자성. 실측 `issue_success = 100` |
| 공정성 (도착 순 발급) | ❌ | 위 ①②③ |

→ **포트폴리오 서술은 문제없다.** eco-1 제목은 "초과발급 위험 차단"이라 정확성만 주장하고,
ZSet 도 본문에서 "발급 정합성에 관여하지 않는 조회 전용 지표"로 이미 한정돼 있다.

**권고안**: Lua 하나로 `중복 검사 → INCR seq → seq <= quantity 판정 → 발급자 등록 → 순번 반환`.
Redis 단일 스레드가 정한 도달 순서가 **곧 당첨 여부이자 표시 번호**라 둘이 정의상 일치하고, 분산 락이 불필요해진다.

**추가 인식**: 분산 시스템에서 "먼저 클릭한 순"은 서버가 알 수 없다 —
클라이언트 네트워크 편차·로드밸런서 분배·톰캣 스레드 스케줄링이 서버 도달 전에 순서를 흐트러뜨린다.
현실의 선착순은 전부 "먼저 처리된 순"이다.

### 축 간 충돌 — 예상 못 한 결론

**축 6 × 축 2(샤딩) = 정면 충돌.** 축 2는 카운터를 N개로 쪼개고, 축 6은 전역 카운터 하나의 순서를 판정 근거로 삼는다.

| 해소안 | 판정 |
|---|---|
| (a) 샤드별 seq + 샤드별 정원 | ❌ 표시 번호가 다시 "3번 샤드의 12등". 전역 번호를 따로 매기면 순번과 판정이 또 어긋나 축 6 취지가 무너짐 |
| (b) 판정은 전역 seq, 재고만 샤딩 | ❌ 전역 `INCR` 이 모든 요청을 통과시켜 샤딩 이득 없음 |
| (c) **축 6 채택 시 축 2를 보류** | ✅ 채택 |

(c)의 근거는 축 2가 스스로 쓴 문장 — **"제거되는 병목은 Redis 명령이 아니라 분산 락 대기다."**
축 6이 정상 경로의 락을 없애면 축 2가 겨냥하던 병목이 대부분 사라진다.
`INCR`+`SISMEMBER`+`SADD` 짧은 스크립트는 단일 노드에서 초당 수만~수십만 op 수준이므로,
**측정 없이 먼저 쪼개는 것은 근거 없는 최적화**다.

**축 6 × 축 5 = 대체 아님, 범위 축소.** 정상 발급에는 락이 불필요해지지만
Redis 장애 폴백·재고 보정에는 여전히 필요하다. 그리고 폴백 구간은 정의상 DB I/O 를 임계 구역에 포함하므로
**축 5가 지적한 leaseTime 문제가 바로 거기서 가장 심각하다.**
→ 축 6은 축 5를 대체하지 않고 **축 5가 진짜 필요한 곳을 특정해 준다.**

## 4차 라운드 — 어투 전환(경어체 → 개조식) + 멱등키 코드 수정 (2026-07-30)

### 어투 전환

사용자 지시: **"~했음, ~구현, ~설계 처럼 바꿔줘"**

**변환 규칙** (에이전트 3개에 동일 규칙표 주입)

| 규칙 | 대상 | 변환 |
|---|---|---|
| 1 | 동작명사 + 하다 | `설계했습니다` → **`설계`** (명사 종결) |
| 2 | 존재·상태·지정 | `있었습니다` → `있었음` / `구조입니다` → `구조임` |
| 3 | 일반 동사 | `잡았습니다` → `잡았음` / `됐습니다` → `됨` |

명사 어간이 없는 동사(`택하다`·`달하다`)는 규칙 1이 아니라 `~했음`으로 처리했다.

**진행 경과**
- `tone-wf` 에이전트 31건 완료 → 유일성 31/31 검증 후 적용
- `tone-ai`·`tone-eco` 는 **세션 한도로 실패** → 직접 처리로 전환

**⚠️ 함정 1 — 치환 순서**: `확인했습니다` 안에 `했습니다` 가 포함된다.
짧은 어형부터 치환하면 `확인했음` 이 되어 명사 종결이 깨진다. **긴 어형부터** 적용해야 한다.

**⚠️ 함정 2 — `합니다` 에는 `습니다` 가 없다**: `합`(ㅎㅏㅂ) ≠ `습`(ㅅㅡㅂ).
1차 정규식이 `(?:습니다|입니다)` 만 잡아 **`~ㅂ니다` 계열 29개를 통째로 놓쳤다**
(`담당합니다`·`설명합니다`·`풉니다`·`씁니다`·`됩니다` 등). 2차 패스로 수습.

**⚠️ 함정 3 — 태그가 어미를 자른다**: `<b>구조</b>입니다` 는 `[가-힣]+입니다` 로 안 잡힌다.
3차로 어미 문자열만 직접 치환해 마무리.

**결과**: 경어체 종결 **178 → 0개**. 문서 91,683 → **91,041자**.
태그 균형 ALL MATCHED / viz-frame 13 / code-card 3 / 핵심 수치 13종 전수 보존 확인
(`9.5 → 55 req/s`, `341ms`, `1,258ms`, `0.35회/건`, `98.7%`, `3579` 등).

### 멱등키 코드 수정 (사용자 지시로 코드 변경)

**문제**: 포트폴리오가 "하면 안 된다"고 명시한 것을 코드가 그대로 하고 있었다.

- 문서: *"재시도 횟수처럼 시도마다 변하는 값이 키에 섞이면 첫 번째 성질이 깨져 … 멱등키가 목적을 잃는다"*
- 코드 (`PaymentCompensationService.java:96`): `paymentKey + ":compensate:" + getRetryCount()`

**왜 결함인가**: 멱등키는 재시도가 **같은 키로 도착해야** 상대(Toss)가 중복을 거른다.
`retryCount` 를 섞으면 재시도마다 키가 달라져 —
`1차 취소 → Toss 처리 완료 → 응답 타임아웃 유실 → 2차 재시도(다른 키) → Toss 가 새 요청으로 인식 → 이중 환불`.
주석이 "이중 환불을 방지"라고 적어둔 코드가 **이중 환불을 가능하게** 하고 있었다
(ai-4의 "주석은 '부팅 실패 방지'인데 부팅 실패를 유발" 과 같은 유형).

**조치**: `getRetryCount()` → `getId()` (보상 레코드 식별자).
문서가 든 세 성질을 모두 만족한다 — ① 같은 보상 = 같은 ID = 같은 키 ② 다른 보상 = 다른 ID ③ DB 영속이라 재시작에도 생존.
`compileJava` 통과 확인(exit 0).
