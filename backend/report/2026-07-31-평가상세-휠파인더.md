## 총평 (5줄 이내)

짧은 게 문제가 아니라 **짧아지면서 사슬의 뒤쪽 두 칸(`검증`·`한계`)이 통째로 잘려나간 것**이 문제다.
4개 섹션 `결과` 12개 항목 전부에 **측정값이 0개**다 — 문서에 나오는 숫자(TTL 7일·15분·10분, 포트 8080·3000)는 전부 설정값이지 관측값이 아니다.
wf-1 은 문제원인이 선언한 두 요구(전체 로그아웃 / Refresh Token 추적) 중 하나를 조치가 해결하지 못하는데 결과는 해결했다고 적었다 — 이 프로젝트에서 가장 무거운 결함이다.
wf-3 은 서사 자체는 성립하나 **"왜 위치는 그대로 두고 경로만 바꿨는가"** 한 문장이 없어서, 있으면 성장으로 없으면 실수로 갈리는 자리에 정확히 비어 있다.
차별화 가치는 wf-2 하나에 몰려 있고(인스턴스 경계를 넘는 SSE — ai 프로젝트가 못 가진 것), wf-1·wf-4 는 각각 중복과 나열이다.

## 섹션별

### wf-1 JWT 무효화 한계를 Redis 이중 블랙리스트로 해결

- **논리**: `문제 → 조치` 는 촘촘하나 `검증` 칸이 통째로 없고, `한계` 칸도 없다. 특히 문제원인 2("사용자가 가진 **모든 Refresh Token** 을 일일이 추적하기 어려웠음")를 세워놓고 해결과정 1은 `refresh_token:{token}` — **토큰을 키로 잡았으므로 사용자 단위 열거가 여전히 불가능**하다. 세운 문제와 놓은 조치가 어긋난다.
- **아키텍처**: "이중"이 이중화(redundancy)가 아니라 **무효화 단위의 이원화**다. SVG2 라벨이 `둘 중 하나라도 일치 → 401 거부`, 즉 OR 결합이므로 두 키는 같은 것을 두 번 막는 게 아니라 **서로 다른 범위(토큰 단위 / 사용자 단위)를 나눠 맡는다**. 구조 자체는 타당하고 version 키 TTL 15분을 Access Token 수명과 맞춰 "키 선만료 창"을 막은 대목은 이 섹션에서 가장 좋은 판단이다.
- **설득력**: 수치 0. code-card 0. 검증 서술 0. 같은 주제를 다룬 ai-5 는 `실측 3579초`·`401 거부 재현`·`fail-close 근거`까지 붙어 있어, **한 문서 안에서 나란히 놓이면 wf-1 이 "검증하지 않은 버전"으로 읽힌다**.

| | 지적 |
|---|---|
| 🔴 [치명] | **전체 로그아웃이 실제로는 전체가 아니다.** 문제원인 2 *"비밀번호 변경이나 보안 사고 시 '모든 기기에서 로그아웃'이 필요"* → 조치는 `blacklist:user:{userId}:version` 카운터 증가로 *"그 시점 이전에 발급된 **모든 Access Token**"* 만 무효화. 그런데 `refresh_token:{token}`(TTL 7일)은 사용자 단위로 지울 수단이 없다. 탈취자가 살아있는 Refresh Token 으로 재발급하면 **증가된 version 이 찍힌 새 Access Token** 이 나와 그대로 통과한다. 결과 2 *"카운터 증가만으로 즉시 전체 무효화"* 와 결과 3 *"탈취 의심 시 즉시 삭제로 재발급 경로 차단"* 은 **개별 토큰을 알고 있을 때만** 참이다 — 제안: 키를 `refresh_token:{userId}` 로 잡았다고 정정하거나(ai-5 는 `refreshToken:{userId}` 다), 사실이 아니면 *"Access Token 전체 무효화까지 다뤘고 Refresh Token 은 개별 삭제만 가능해 사용자 단위 폐기는 후속 과제로 남았음"* 으로 범위를 한정 |
| 🔴 [높음] | **무상태를 상태로 되돌린 대가가 어디에도 없다.** 문제원인 1 이 *"JWT는 자체 서명으로 검증하는 무상태(stateless) 토큰"* 이라는 성질을 문제로 삼았으므로, 그 성질을 포기한 비용이 결과에 와야 사슬이 닫힌다. 실제로는 (a) 매 요청 Redis 조회 2회, (b) 인증 경로가 Redis 가용성에 완전 종속, (c) Redis 장애 시 통과냐 차단이냐 — 셋 다 없다. 같은 저자가 ai-5 에서는 *"fail-open은 장애 지속 시간만큼 폐기 토큰을 되살리므로 fail-close, 근거는 코드에 남김"* 이라고 명시했다 — 제안: 해결과정 끝에 fail-close/fail-open 결정 한 줄 + 결과에 *"무상태의 이점을 내주고 즉시 무효화를 산 교환"* 한 줄 |
| 🟡 [중간] | **version 키가 어떻게 판정에 쓰이는지가 없다.** 카운터를 올리는 것만으로는 특정 토큰이 그 이전 발급인지 알 수 없다 — 토큰 claim 에 version 을 심어 비교한다는 서술이 있어야 성립하는데 문서에 없다. SVG2 도 `둘 중 하나라도 **일치**` 라고만 적어, 멤버십 조회처럼 읽힌다 — 제안: *"발급 시 토큰 claim 에 현재 version 을 실어, 필터가 저장된 version 과 비교해 낮으면 거부"* 한 줄 |
| 🟡 [중간] | **키에 토큰 전문(全文)을 쓴다.** `blacklist:access:{token}`·`refresh_token:{token}` 인데 ai-5 는 `blacklist:access:{jti}` 다. 같은 저자·같은 문제에서 뒤 프로젝트가 jti 로 옮겨간 것이므로 사실은 **성장의 증거**인데, 두 섹션이 서로를 참조하지 않아 그냥 "한쪽이 조잡한" 상태로 방치돼 있다 (선행 진단 §6-4 가 지적한 "역행으로 읽힐 여지"의 반대 방향 사례) — 제안: ai-5 에 *"이전 프로젝트에서 토큰 전문을 키로 쓰던 것을 jti 기준으로 정리"* 한 줄 |
| 🟡 [낮음] | **명명 충돌.** 같은 문서 ai-2 가 *"Redis 단일 장애점(SPOF)을 Cluster 이중화로 제거"* 로 이중화=redundancy 로 쓴다. wf-1 의 "이중 블랙리스트"는 redundancy 가 아니라 2단(개별·전체)이므로 첫 3초에 오독을 부른다 — 제안: 제목을 *"개별·전체 2단 블랙리스트"* 로 |

### wf-2 보호자 실시간 위치 공유를 SSE + Redis Pub/Sub으로 구현

- **논리**: wf 4개 중 사슬이 가장 온전하다. 문제원인 3(인스턴스 경계) → 조치(Pub/Sub) → 결과 1 이 정확히 대응한다. 다만 `검증`이 없다 — *"인스턴스를 늘려도 동작하는 구조 확보"* 는 **2인스턴스로 실제 띄워 확인했는지**가 안 적혀 있어 설계 주장에 머문다.
- **아키텍처**: 확장 한계 3가지가 전부 미언급이다. ① **백프레셔** — `SseEmitter.send()` 는 블로킹이라 느린 보호자 클라이언트 하나가 Redis 메시지 리스너 스레드를 잡으면 **같은 인스턴스의 다른 관계 전달까지 밀린다**. ai-1 에는 *"Backpressure Buffer로 흡수해 유실 없이 순서대로 전달"* 이 있으므로 개념을 모르는 게 아니라 이 섹션에만 없다. ② **재연결 갭** — 10분 타임아웃 → EventSource 자동 재연결 사이에 발행된 위치는 Pub/Sub 특성상 유실되는데, wf-3 이 같은 성질을 *경로*에 대해서만 문제 삼는다. ③ **구독 수명주기** — 채널이 `location:{relationId}` 로 관계마다 쪼개져 있는데 각 인스턴스가 언제 subscribe/unsubscribe 하는지가 없다(SVG3 은 두 인스턴스가 모두 받아 `isConnect 확인` 으로 거르는 그림이다).
- **설득력**: 수치 0. 동시 연결 수·전달 지연·인스턴스 수 중 **하나도** 없어서, 규모 감각을 줄 근거가 전무하다.

| | 지적 |
|---|---|
| 🟡 [중간] | **다중 기기 보호자가 구조적으로 불가능한데 이걸 장점으로 적었다.** *"보호자-사용자 관계(relationId)마다 SseEmitter를 발급하고 ConcurrentHashMap<relationId, SseEmitter>"* + *"재연결 시 기존 연결을 새 연결로 교체"* → 관계당 커넥션 1개이므로 보호자가 폰·PC 두 곳에서 열면 **먼저 연 쪽이 끊긴다**. 결과 2 는 이를 *"메모리 누수 가능성 최소화"* 로만 적어 트레이드오프가 감춰졌다 — 제안: *"관계당 1커넥션으로 제한한 결과 보호자 다중 기기는 지원하지 않음. 관계·기기 복합키로 확장 가능하나 요구사항 밖이라 두지 않았음"* |
| 🟡 [중간] | **느린 소비자 대비가 없다.** 위 ① — 제안: 한 줄이라도 *"전달은 리스너 스레드에서 직접 send 하므로 느린 클라이언트가 같은 인스턴스 전달을 지연시킬 수 있음. 별도 디스패치 스레드/버퍼는 넣지 않았음"* 으로 한계 선언 |
| 🟡 [중간] | **확장 주장이 검증되지 않았다.** 결과 1 *"인스턴스를 늘려도 동작하는 구조 확보"* — 실제 2인스턴스 기동 확인 여부가 없다. 문서 다른 곳(ai-4)은 *"플래그를 양방향으로 실제 기동해 확인했음"* 처럼 확인 행위를 적는다 — 제안: 확인했으면 그렇게, 아니면 *"설계상 성립하며 다중 인스턴스 실기동 검증은 하지 못했음"* |
| 🟢 [정보] | **이 섹션이 wf 의 유일한 차별 자산인데 그렇게 배치돼 있지 않다.** ai-1 의 SSE 관리는 `ConcurrentHashMap<sessionId, Sink>` 인메모리로, **인스턴스 경계를 넘는 장치가 없다**. wf-2 는 그 빈칸을 정확히 메우는 사례인데 두 섹션이 서로를 참조하지 않아 독자가 대비를 만들어내야 한다 — 제안: wf-2 첫 줄에 *"프로세스 로컬 맵만으로는 인스턴스 경계를 못 넘는다는 것을 이 프로젝트에서 먼저 다뤘음"* |

### wf-3 Pub/Sub 발행 시점 유실 한계를 Redis Stream으로 보완

- **논리**: `문제 → 조치` 는 명료하나 `검증` 0, `한계` 0. 그리고 **판단 근거 한 칸이 비었다** — 아래 첫 지적.
- **아키텍처**: 자기 부정 서사에 대한 판정 — **지금 문서로는 "설계를 발전시켰다"로 읽히지 않는다. "처음에 잘못 골랐다"에 가깝게 읽힌다.** 근거는 문서가 대는 이유가 *성질의 차이*가 아니라 *요구의 추가*이기 때문이다: 문제원인 3 이 *"보호자가 뒤늦게 접속했을 때도 '현재 안내 중인 경로'를 조회할 수 있어야 한다는 **요구가 있었다**"* — 즉 "요구가 나중에 생겨서 바꿨다"는 서술이라 설계 판단이 개입한 흔적이 없다. 실제로는 **위치는 초 단위로 갱신되는 연속 스트림이라 재생 가치가 없고, 경로는 안내 시작 시점에 한 번 발생하는 이산 이벤트라 놓치면 복구 불가**라는 성질 차이가 있고, 이게 "같은 Pub/Sub 인데 하나만 바꾼" 유일한 정당화다. 이 문장이 들어가면 즉시 성장 서사가 되고, 없으면 *"왜 위치는 안 바꿨나 / 그럼 처음부터 Stream 이 맞았던 것 아닌가"* 로 무너진다.
- **설득력**: 수치 0. 게다가 해결과정 4가 **자기 근거를 깎는다** — *"Consumer Group 없이 단일 최신값 조회로 요구사항을 충분히 만족"* 이라고 적는 순간, Stream 을 고를 이유(소비자 오프셋·재처리·팬아웃)가 남지 않는다.

| | 지적 |
|---|---|
| 🔴 [높음] | **위치/경로를 가른 기준이 없다.** 위 본문 — 제안: 문제원인에 한 줄 *"위치는 초 단위로 새 값이 오는 연속 스트림이라 놓친 값의 재생 가치가 없지만, 경로는 안내 시작 시 한 번 발생하는 이산 이벤트라 그 시점에 미접속이면 복구 경로가 없음 — 이 성질 차이를 근거로 두 데이터에 다른 전달 방식을 적용"* |
| 🔴 [높음] | **Stream 을 고른 근거가 문서 안에서 스스로 소거된다.** *"XADD 로 적재 … XREVRANGE ... COUNT 1 로 가장 최근 항목 조회 … 도착 시 DEL"* = SET/GET/DEL 과 관측 가능한 차이가 없고, 해결과정 4가 Consumer Group 을 명시적으로 배제한다. 즉 List/String 대신 Stream 을 쓸 이유가 본문에 남아 있지 않다 — 제안: 실제 이유(경로 변경 이력이 append-only 로 쌓여 필요 시 추적 가능 / 단일 키에 시계열 누적)를 적거나, 그런 이유가 없었다면 *"요구만 보면 String 으로도 충분했고, 이후 경로 이력 조회 확장을 염두에 두고 Stream 을 택했음"* 으로 정직하게 |
| 🟡 [중간] | **키 수명이 도착 이벤트에만 걸려 있다.** *"목적지 도착 시 해당 Stream 키를 DEL로 정리"* — 도착하지 않고 앱을 종료·이탈하면 지울 트리거가 없고 TTL 서술도 없어 키가 영구히 남는다. wf-1 이 *"TTL을 토큰의 남은 유효시간만큼만 계산해 … 불필요한 메모리 누적을 방지"* 로 TTL 을 정교하게 다룬 것과 **같은 문서 안에서 기준이 어긋난다** — 제안: TTL 을 함께 걸었으면 그렇게, 아니면 한계로 명시 |
| 🟡 [낮음] | **MAXLEN 언급이 없다.** 도착 전 안내를 여러 번 재시작하면 항목이 누적되는데 XADD 에 상한이 없다. 읽기가 COUNT 1 이라 기능은 멀쩡하고 메모리만 는다 — 위 TTL 지적과 묶어 한 줄이면 충분 |

### wf-4 Nginx 라우팅 분리 + Docker Compose 인프라 설계와 CI/CD 자동화

- **논리**: **`문제 정의`부터 성립하지 않는다.** 세 항목이 전부 *"~구성이 필요"*, *"~수동 작업이 필요"*, *"~재현하기 어려웠음"* 으로 **요구사항 서술이지 진단이 아니다.** 원인 판단 근거 0, 검증 0, 한계 0, 결과 항목 2개(다른 섹션은 3개). 사슬 5칸 중 2칸만 있다.
- **아키텍처**: 판정 — **지금 형태로는 백엔드 역량 서사가 아니라 설정 나열이다.** 판정 근거는 "무엇을 썼는가"만 있고 **"왜 그것이었는가"가 한 건도 없다**는 점이다: `/api/v1/` 라우팅은 선택지가 없는 규칙이고, Compose 로 5개를 묶은 것도 대안 비교가 없으며, GitHub Actions → SSH → 재기동은 파이프라인 중 가장 단순한 형태다. 유일하게 판단이 담긴 문장은 TLS 종료 항목 *"각 애플리케이션 서버가 인증서를 직접 다루지 않도록 **책임을 분리**"* 하나뿐이다 — 이 섹션 전체에서 설계 사고가 드러나는 곳은 여기가 전부다.
- **설득력**: 이 배포 방식의 알려진 대가(재기동 구간 다운타임, 롤백 절차 부재, EC2 위 빌드로 인한 배포 시간·자원 점유, 이미지 태깅 없음)가 **하나도 인정되지 않았다.** 선행 진단 §0 이 이 문서의 최대 자산으로 꼽은 것이 *"수치마다 출처를 구분해 표기"* 와 한계 선언인데, wf-4 는 그 표준을 지키지 않는 유일한 종류의 섹션이다.

| | 지적 |
|---|---|
| 🟡 [중간] | **문제원인이 진단이 아니다.** *"프론트엔드(Next.js)와 백엔드(Spring Boot)를 하나의 도메인에서 서비스해야 했는데 … 구성이 **필요**"* — 이건 문제가 아니라 과제다. 다른 11개 섹션은 전부 "무엇이 깨졌는가"로 시작한다 — 제안: 실제 겪은 증상으로 바꾼다(예: CORS·쿠키 도메인 불일치, 팀원 로컬에서 재현 안 되던 구체 사례) |
| 🟡 [중간] | **한계 선언 0.** 위 본문 — 제안: 결과에 한 줄 *"재기동 방식이라 배포 구간에 짧은 중단이 있고 롤백은 수동 재배포에 의존함. 무중단 배포와 이미지 레지스트리 도입은 후속 과제"* — 이 한 줄이 들어가면 섹션 성격이 나열에서 판단으로 바뀐다 |
| 🟡 [낮음] | **결과가 조치의 되풀이다.** 결과 1 *"각 서버의 역할이 Nginx 설정으로 명확히 분리되는 구조 확보"* 는 해결과정 1의 재진술이고, 결과 2 는 해결과정 2+4의 재진술이다. 새로 확인된 사실이 없다 — 제안: 배포 소요 시간이나 팀원 온보딩 시간처럼 **한 개라도 관측값**을 넣는다 |
| 🟡 [낮음] | **본문과 다이어그램 불일치.** SVG1 라벨은 `OAuth │ Kakao·Naver·Google` 로 3개 제공자인데 본문·기술 스택·인트로는 카카오만 언급한다. 본인이 "인증 담당"이라고 적은 프로젝트라 이 불일치는 바로 질문거리다 — 제안: 셋 다 붙였으면 인트로에 적고, 아니면 SVG 라벨을 정정 |

## 다른 두 프로젝트와의 주제 중복 판정

| wf 섹션 | 겹치는 상대 | 중복도 | 근거 (원문) | 어느 쪽이 강한가 |
|---|---|---|---|---|
| wf-1 JWT 블랙리스트 | **ai-5** 인증·세션 방어선 | **높음 (정면)** | wf-1 *"로그아웃 시 `blacklist:access:{token}` … TTL을 토큰의 남은 유효시간만큼"* ↔ ai-5 *"블랙리스트 TTL은 고정값이 아니라 토큰 잔여 수명 연동(실측 3579초)"* — 같은 키·같은 TTL 전략 | **ai-5.** 실측·E2E·fail-close 결정을 갖췄다. wf-1 의 우위는 사용자 단위 version 카운터 하나뿐인데 그 자리가 곧 🔴 두 건의 발생 지점 |
| wf-2 SSE + Pub/Sub | ai-1 SSE 스트리밍 / ai-3 연결 정리 | **중간 (부분)** | wf-2 *"ConcurrentHashMap<relationId, SseEmitter>로 연결을 관리"* ↔ ai-1 *"각 SSE 연결을 ConcurrentHashMap<sessionId, Sink>로 관리"* / wf-2 *"onCompletion/onTimeout/onError 콜백에서 맵의 연결을 제거"* ↔ ai-3 *"SSE Heartbeat를 30초 주기로 … 죽은 연결을 조기 감지·정리"* | **연결 관리는 ai 가, 인스턴스 경계 돌파는 wf 가 강하다.** ai 쪽에 Pub/Sub 팬아웃이 없어 **wf-2 만이 가진 주제**가 실재한다 |
| wf-3 Redis Stream | eco-4 Kafka Streams StateStore | **중간 (개념)** | 둘 다 "발행 시점에 못 받으면 유실"을 영속 저장으로 푸는 이야기. eco-4 *"이벤트 상태 영속 저장으로 서버 재시작 후 대기 작업 유실 가능성 최소화"* | **eco-4.** code-card·실측(12s→1.1s)·exactly_once·DLQ·관측까지 있다. wf-3 은 XADD/XREVRANGE 3줄 |
| wf-4 Nginx·Compose·CI/CD | **없음** | **중복 없음** | ai·eco 어디에도 인프라·배포 섹션이 없다 | — (유일하게 안 겹치지만 4개 중 가장 얇다) |

**요약**: 4섹션 중 주제가 온전히 서는 것은 **wf-2 하나**다. wf-1 은 더 잘 쓰인 ai-5 와 정면 충돌하고, wf-3 은 eco-4 의 축소판이며, wf-4 는 겹치지 않는 대신 내용이 얇다.

## 존치 권고: **(c) 축소·통합**

**4섹션 → 2섹션으로 재편한다.** 총 분량은 현재와 비슷하거나 소폭 줄지만 섹션당 밀도가 두 배가 된다.

| 새 구성 | 내용 | 근거 |
|---|---|---|
| **새 wf-1** = 현 wf-2 + wf-3 통합<br>*"보호자 실시간 위치·경로 공유 — 인스턴스 경계와 발행 시점 의존성"* | Pub/Sub 팬아웃(공간 축) + Stream 보완(시간 축)을 **하나의 문제의 두 축**으로 묶는다 | 두 섹션은 이미 같은 기능의 앞뒤다(wf-3 문제원인 1이 *"초기에는 … 위치와 동일하게 Redis Pub/Sub으로만"*). 통합하면 wf-3 의 🔴 "위치/경로를 가른 기준" 이 서술의 **중심축**이 되어 자동으로 메워지고, 자기 부정 서사가 "한 문제를 두 축으로 나눠 푼 것"으로 재프레이밍된다 |
| **새 wf-2** = 현 wf-4 + 현 wf-1 압축 흡수<br>*"인증·배포 인프라 설계"* | 인증은 *"토큰 단위·사용자 단위 2단 무효화와 TTL 설계"* 2~3줄로 축약, Nginx/Compose/CI 는 유지하되 TLS 책임 분리 문장을 중심으로 재구성 + 한계 한 줄 | wf-1 을 통째로 남기면 ai-5 옆에서 "검증 안 한 버전"으로 읽히고 🔴 두 건이 노출된다. 압축하면 **중복은 사라지고 팀장으로서 인증 설계를 맡았다는 사실은 남는다** |

**왜 (b) 보강이 아닌가.** 보강으로 메울 수 있는 건 *근거*뿐이고 *증거*는 아니다 — 2025-10 종료 프로젝트라 수치를 새로 뽑을 수 없다. 수치 0 인 상태로 분량만 늘리면 ai·eco 의 실측 밀도와 격차가 오히려 커진다. 반대로 압축하면 "짧은 건 이 프로젝트가 팀 프로젝트라서"라는 자연스러운 해석이 서고, 남은 wf-2 통합 섹션은 **ai 프로젝트가 가지지 못한 다중 인스턴스 실시간 전달**이라는 고유 자산 하나에 집중된다.

**왜 (d) 삭제가 아닌가.** wf-2 의 인스턴스 경계 돌파는 ai·eco 어디에도 없고, 4인 팀 팀장·기획안/ERD/API 명세 작성이라는 협업 축도 다른 두 프로젝트에 없다. 프로젝트 자체는 값을 한다 — 값을 못 하는 건 wf-1 과 wf-4 의 현재 서술이다.

> **공통 보강 1건 (Top 5 밖이지만 우선순위 최상)**: 4개 섹션 `결과` 12항목에 관측값이 하나도 없다. 지금 회고로 확보 가능한 것 — 동시 SSE 연결 수, 관계 수, Compose 서비스 기동 시간, 배포 1회 소요 시간 — 중 **하나라도** 넣고, 나머지는 *"팀 프로젝트 기간 내 부하 측정은 하지 못했고 이 섹션의 근거는 구조 설계에 한정됨"* 으로 범위를 선언한다. 문서 전체가 "수치의 출처를 구분해 적는다"를 지키고 있으므로, **측정하지 않았다고 적는 것 자체가 그 표준을 지키는 행위**가 된다.
