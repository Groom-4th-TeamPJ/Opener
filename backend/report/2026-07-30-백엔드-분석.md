## 2. P0 — prod 프로필로는 기동되지 않는다

세 건 모두 **dev 프로필에만 존재하는 설정을 prod 가 상속하지 못해** 발생한다.

### P0-1. `RagService` 빈 부재 → `ChatServiceImpl` 주입 실패

- `RagServiceImpl.java:26-31` — `@ConditionalOnProperty(prefix="app.rag", name="enabled", havingValue="true", matchIfMissing=false)`
- `app.rag.enabled` 는 `application-dev.yml:157-158` 에만 존재. `application-prod.yml` 에 없음
- `ChatServiceImpl.java:64,90` — 생성자가 `RagService` 를 **필수**로 요구
- `implements RagService` 전수 검색 결과 구현체는 `RagServiceImpl` **1개뿐** → 대체 빈 없음
- 결과: prod 기동 시 `NoSuchBeanDefinitionException`

> 대조: `LlmService` 는 `OpenAiLlmServiceWithoutRag.java:25-30` 이 `matchIfMissing=true` 로 받아주도록
> 설계돼 있다. 즉 **RAG 토글의 폴백 설계가 `LlmService` 에만 적용되고 `RagService` 에는 누락**됐다

### P0-2. Chat Redis 클러스터 노드 미정의 → NPE

- `ChatRedisConfig.java:34` — `@ConfigurationProperties(prefix="spring.data.redis.chat")`
- `ChatRedisConfig.java:52` — `new RedisClusterConfiguration(cluster.getNodes())`, `nodes` 는 초기값 없는 `List<String>`
- 노드 목록은 `application-dev.yml:44-53` 에만 존재
- `docker-compose.prod.yml:24-40` 은 **standalone Redis 1대**뿐이라 클러스터 자체가 없음

### P0-3. `jwt.*` 미정의

- `JwtUtil.java:35-37` — `@Value("${jwt.secret}")`, `${jwt.access-token-expiration}`, `${jwt.refresh-token-expiration}` 모두 **기본값 없음**
- `jwt:` 블록은 `application-dev.yml:140-144` 에만 존재
- `docker-compose.prod.yml:46-51` 에 `JWT_SECRET` 없고 `env_file` 지시자도 없음
- 완화 여지: 릴랙스드 바인딩상 `JWT_SECRET`·`JWT_ACCESS_TOKEN_EXPIRATION` 환경변수를 주면 해결된다.
  다만 prod compose 에 그 주입 경로가 정의돼 있지 않다

### 종합 판단

실제 배포는 **dev 프로필**이다 — `docker-compose.dev.yml:215-250` 이 `env_file: .env`,
Pinpoint 에이전트, redis-chat 3노드 헬스체크를 갖춘 반면
`docker-compose.prod.yml` 은 모니터링·클러스터·시크릿 주입이 전부 빠져 있다.
따라서 **P0 3건은 "지금 장애"가 아니라 "prod 경로가 검증된 적 없다"는 신호**로 읽어야 한다.
선택지는 둘 중 하나다 — prod 프로필을 dev 수준으로 정합화하거나, 명시적으로 폐기 선언하는 것.

## 4. P1 — 리액티브 콜백 안에서 블로킹 I/O

`ChatServiceImpl.java:264-297`(일반 채팅), `:371-426`(오프너 분석)의
`doOnNext`/`doOnComplete`/`doOnError` 는 **OpenAI 응답이 도착하는 스레드**에서 실행된다.
Spring AI 의 스트리밍이 WebClient 기반이므로 이는 Reactor Netty 이벤트 루프다.
그 안에서 다음 블로킹 호출이 일어난다:

| 위치 | 블로킹 대상 |
|---|---|
| `ChatServiceImpl.java:284,388` | `chatRedisService.saveMessage` — Lettuce 동기 API |
| `ChatSessionStateMachineService.java:59` | `machine.sendEvent(...).blockLast()` |
| `ChatServiceImpl.java:394-405` | `transactionTemplate.executeWithoutResult` — **JDBC** |
| `ChatServiceImpl.java:424` | `canService.recoverUserCan` — JPA |

Netty 이벤트 루프는 기본 `2 × 코어 수` 로 매우 적다.
여기서 JDBC 트랜잭션이 돌면 **진행 중인 모든 LLM 스트림이 함께 지연**된다.
Virtual Thread 가 켜져 있어도 이 스레드들은 VT 가 아니므로 보호받지 못한다.

권장: 부수효과 직전에 `.publishOn(Schedulers.boundedElastic())` 을 넣거나,
DB/Redis 작업을 VT 실행기로 오프로딩한다.

> ⚠️ **가정**: 스레드 소속은 코드에서 직접 확인할 수 없다.
> `build.gradle:34` 주석("Required for Spring AI streaming")과 `WebClientConfig.java` 의 존재로 추정했다.
> 콜백 안에서 `Thread.currentThread().getName()` 을 한 번 찍어보면 확정된다

## 6-bis. P0 — 인증/인가 (security-reviewer 병렬 감사 + 교차검증)

아래 3건은 모두 **부모가 직접 grep 으로 교차검증**했다. 나머지 P1~P3 은 §6-ter 참조.

### P0-4. SSE Sink 하이재킹 — 남의 대화가 공격자에게 스트리밍된다

**부모가 직접 발견한 건이다.** `ChatServiceImpl.connectSession` 의 두 경로가 비대칭이다.

| 경로 | 소유자 검증 |
|---|---|
| 기존 Sink 재사용 (`:133-140`) | `validateSessionOwner` **호출함** ✅ |
| 신규 Sink 생성 (`:143-182`) | **호출 안 함** ❌ — `initializeSession` 만 부름 |

그런데 `ChatRedisServiceImpl.initializeSession:71-76` 은 **키가 이미 있으면 소유자 확인 없이 조기 return** 한다.

공격 시나리오:
1. 피해자 A 가 `sessionId=123` 으로 연결 → Redis 에 `chat:{123}:session` 의 `userId=A` 기록, TTL 1시간
2. A 의 SSE 가 끊김 → `doOnCancel`(`:177-182`)이 `sinks` 에서 제거. **Redis 키는 살아있음**
3. 공격자 B 가 `GET /chat/connect?sessionId=123` → `existingSink == null` → 소유자 검증 건너뜀
   → `initializeSession` 은 키가 있으니 조기 return → **B 의 Sink 가 `sinks[123]` 에 등록됨**
4. A 가 재연결 → 이번엔 `existingSink != null` → `validateSessionOwner(A)` **통과**(A 가 진짜 소유자)
   → A 는 **B 가 만든 Sink** 를 받는다. `multicast` 이므로 둘 다 구독 중
5. A 가 `POST /chat/message` → `validateSessionOwner(A)` 통과 → 청크가 공유 Sink 로 emit
   → **A 의 학습 대화·오프너 분석 내용이 B 에게 실시간 전달**

조치: 신규 Sink 생성 경로에서도 `initializeSession` **이전에** `validateSessionOwner` 를 호출하거나,
`initializeSession` 이 기존 키 발견 시 소유자를 대조하고 불일치면 예외를 던지도록 바꾼다.

> 선행 보고서(2026-07-28)의 IDOR 은 `questionResultId` 대상이고, 이 건은 `sessionId`/Sink 대상이라 별개다

- `AuthServiceImpl.logout()`(`:125-151`)이 `refreshToken:{userId}` 키를 **삭제하지 않는다**
- `refreshToken:` 키 전수 검색 결과 — 쓰기 1곳(`FormAuthenticationSuccessHandler.java:90`), 읽기 1곳(`AuthServiceImpl.java:163`). **삭제 0곳**
- 결과: 로그아웃 후에도 남은/탈취된 refreshToken 쿠키로 `POST /auth/refresh` 하면 새 access token 재발급
- 조치: `logout()` 에 `redisTemplate.delete("refreshToken:" + userId)` 추가

## 8. 권장 조치 순서

1. **인증 P0 3건 (§6-bis)** — 지금 운영 중인 결함이라 최우선.
   Sink 소유자 검증, 블랙리스트 조회, logout 시 refreshToken 삭제. 셋 다 수정 범위가 작다
2. **YAML 들여쓰기 6곳 교정 (§3)** — 비용이 가장 낮고 파급이 크다. 교정 후 `/actuator/env` 로 실제 바인딩 확인
3. **토큰 타입 클레임 + logout 500 (§6-ter P1/P2)** — `typ` 클레임 도입은 필터·리프레시 양쪽을 함께 고쳐야 한다
4. **prod 프로필 결정 (§2)** — 정합화(RAG 폴백·Redis·JWT·CORS) 또는 명시적 폐기 선언. 어느 쪽이든 CLAUDE.md 에 기록
5. **리액티브 콜백 블로킹 오프로딩 (§4)** — 먼저 스레드명 실측 → 확인되면 `boundedElastic` 분리
6. **chat/auth 도메인 테스트 도입 (§6-5)** — `reactor-test` 를 이미 추가했으므로 `StepVerifier` 로 스트림 계약부터
7. **`.env` ↔ yml 키 정합화 + `.env.example` 생성 (§6-6)** — 死 키 15개 제거 또는 yml 에서 참조

### 검증 방법

| 대상 | 방법 |
|---|---|
| 설정 바인딩 | 기동 후 `GET /api/actuator/env` 에서 `spring.mvc.async.request-timeout`, `security.account-lock.*` 확인 |
| SSE 타임아웃 | `curl -N /api/chat/connect?sessionId=...` 로 유휴 연결 유지 후 heartbeat 없이 30초 경과 관찰 |
| 콜백 스레드 | `doOnNext` 에 `Thread.currentThread().getName()` 1회 로깅 |
| prod 기동 | `SPRING_PROFILES_ACTIVE=prod ./gradlew bootRun` — P0 3건이 순서대로 재현되는지 |
| **Sink 하이재킹 (P0-4)** | 계정 A 로 `/chat/connect?sessionId=N` 연결 → 끊기 → 계정 B 토큰으로 같은 `sessionId=N` 연결(성공하면 결함 확정) → A 재연결 후 A 가 메시지 전송 → **B 의 스트림에 A 의 응답이 뜨는지** |
| **블랙리스트 (P0-5)** | 로그인 → access token 확보 → `/auth/logout` → 같은 토큰으로 보호 API 호출. **200 이 나오면 결함 확정** |
| **refresh 무력화 (P0-6)** | 로그인 → `/auth/logout` → 로그아웃 전에 확보한 refreshToken 쿠키로 `/auth/refresh`. **새 access 가 발급되면 결함 확정** |

> Docker 인프라(PostgreSQL·Redis Cluster·RabbitMQ)가 필요한 항목은 사용자에게 기동을 요청한 뒤 진행한다

## 부록: 분석 방법 메모

- tokensave 인덱스가 `stage` 만 추적하고 있어 먼저 `tokensave branch add be/setting/branch-update` 로 현재 브랜치를 등록했다.
  다만 MCP 서버가 기동 시점의 branch-meta 를 캐시해 여전히 fallback 경고를 반환한다 — **MCP 재연결 필요**
- `./gradlew compileJava --offline` 은 **성공**(exit 0). 컴파일 수준 결함은 없다
- 런타임·테스트·Docker 는 사용하지 않았다. "가정"으로 표시한 2건(§3-a, §4)은 실측 전까지 확정이 아니다
