# 이력서·포트폴리오 서술 vs 코드 실제 — 차이 기록

- **작성일**: 2026-07-30
- **대상 문서**: `backend/docs/RESUME_SIMPLE.html`, `backend/docs/PORTFOLIO.html`
- **작성 배경**: 사용자 결정에 따라 이 두 문서는 **"코드의 현재 구현"이 아니라 "설계 의도와 논리"** 기준으로 서술한다.
  코드라는 닻이 없어지므로, 의도로 쓴 항목을 전부 이 표에 올려 면접에서 방어 가능한 상태로 유지한다
- **불변 원칙** (완화되지 않은 것): 측정 수치 위조 금지 / 기존 실측치 유지 / 새 수치 생성 금지
- **근거**: `docs/INTERVIEW_LOGIC_AUDIT.html`(논리 감사), `2026-07-30-리팩토링-계획.md` §7, 코드 직접 확인

## 0. 이 표를 쓰는 방법

면접에서 해당 주장을 물으면 **"설계는 이렇고, 현재 코드는 여기까지 와 있으며, 남은 것은 이것입니다"** 순서로 답한다.
가장 위험한 것은 **면접관이 먼저 발견하는 것**이다. 지원자가 먼저 말하면 같은 사실이 강점이 된다.

**차이 성격 분류**

| 분류 | 뜻 |
|---|---|
| **코드 결함** | 설계 의도·문서 서술과 코드가 어긋나 있고, 그 어긋남이 실제 위험을 만든다. 수정이 필요하다 |
| **미구현** | 문서가 개선 항목·후속 과제로 명시했고 코드에는 없다 |
| **부분 구현** | 코드는 들어갔으나 검증(실측·실행)이 남았다 |
| **설계만 존재** | 판단·원칙으로만 존재하고 코드 산출물이 없다 |

## 1. 코드 결함 — 4건 중 **3건 해소 · 1건 미해소**

> **1-1 이 유일한 필독 항목이다.** 나머지 3건은 코드를 고쳐 해소했으므로 이제 면접에서 강점이 된다(발견 → 수정 → 실행 검증 완결).
> 1-2·1-3 은 **API 실측 중 새로 발견된 것**으로 이력서에 쓰지 않았으나, 사용자가 알고 있어야 하므로 등재한다.

> | 항목 | 상태 | 위치 |
> |---|---|---|

### 1-1. 보상(환불) 경로 멱등키가 재시도마다 바뀐다

> # ⚠️ 필독 1순위 — 이 항목은 포트폴리오만 읽고 면접에 가면 뚫린다
>
> 포트폴리오 `eco-2` 는 **설계 의도**("재시도 간 불변 키")로 서술돼 있고 **코드는 그 의도를 위반**한다.
> 면접관이 "멱등키를 어떻게 만드셨죠?" 라고 물으면 문서의 문장이 아니라 **아래 방어 문장**을 말해야 한다.
> 이 하나만 준비 안 되면 결제 STAR 전체의 신뢰가 흔들린다.


| 항목 | 내용 |
|---|---|
| **이력서 서술** | PORTFOLIO `eco-2` 해결 과정 — "보상(취소) 경로에도 같은 원칙을 적용하도록 설계했습니다 … 보상 레코드의 식별자처럼 **재시도 간 불변인 값**을 키로 삼는 것을 기준으로 잡았습니다" |
| **코드 실제** | 보상 호출 멱등키가 `paymentKey + ":compensate:" + retryCount` 로 조립된다. `PaymentCompensation.markFailed()`(`PaymentCompensation.java:91`)가 재시도마다 `retryCount` 를 먼저 1 증가시키므로, **시도마다 키가 달라진다**. 감사 문서 기준 — `INTERVIEW_LOGIC_AUDIT.html` 판정표 #3 ⚠️ 조건부 |
| **차이 성격** | **코드 결함** |
| **왜 위험한가** | 멱등키의 첫 번째 성질("동일 의도 = 동일 키")을 위반한다. 정확히 멱등키가 필요한 상황 — **PG는 취소를 처리했는데 응답만 타임아웃된 경우** — 에서 재시도가 새 요청으로 인식되어 키가 목적을 잃는다 |
| **실제로 이중 환불이 안 나는 이유** | 우리 키 설계가 막는 것이 아니라 **Toss가 이미 취소된 결제의 재취소를 거부**하기 때문이다. 즉 안전성이 외부 PG의 동작에 의존하고 있다 |
| **면접 방어 문장** | "설계 원칙은 '재시도 간 불변 키'인데 현재 구현은 `retryCount` 가 섞여 그 원칙을 위반합니다. 실제로 이중 환불이 나지 않는 건 Toss가 이미 취소된 결제의 재취소를 거부해서이고 저희 키가 막은 게 아닙니다 — 보상 레코드의 id 처럼 재시도 간 불변인 값으로 바꾸는 것이 수정 방향입니다" |
| **수정 방향** | 멱등키를 `compensation.getId()` 기반으로 교체. 이 저장소가 아니라 이커머스 프로젝트(`groom-shopping`) 코드다 |

### 1-2. 존재하지 않는 경로가 404 대신 500으로 나간다 — ✅ **수정 완료 (차이 해소)**

> **수정 (2026-07-30)**: `GlobalExceptionHandler` 에 `NoResourceFoundException` → **404 / `B_001`**,
> `HttpRequestMethodNotSupportedException` → **405 / `V_003`**(신규 `ErrorCode`) 핸들러를 추가하고
> 응답 조립을 `toErrorResponse(ErrorCode, detail)` 로 공통화했다. 로그도 `error` → `warn` 으로 낮췄다 —
> 오탈자 URL 은 장애가 아니므로 에러 로그를 오염시켜선 안 된다.
>
> **실기동 검증** (인증 쿠키 보유 상태):
>
> | 요청 | 결과 |
> |---|---|
> | `GET /api/no-such-path` | **404** + `B_001` (수정 전 500 + `S_001`) |
> | `DELETE /api/users/me/cans/count` | **405** + `V_003` |
> | `GET /api/users/me/cans/count` (대조군) | **200** |
>
> ⚠️ **단위 테스트만으로는 검증이 안 됐다.** 인증 없이 `GET /api/no-such-path` 를 치면 **401** 이다 —
> Security 필터 체인이 `DispatcherServlet` 앞에 있어 `@RestControllerAdvice` 까지 요청이 도달하지 않는다.
> 핸들러 메서드를 직접 호출하는 단위 테스트(`GlobalExceptionHandlerTest`)로는 이 사실을 알 수 없다.
> 회귀 테스트 4건 추가(404·`B_001`·405·포괄 500 유지).

**아래는 발견 당시 기록이다 (수정 전 상태).**


| 항목 | 내용 |
|---|---|
| **이력서 서술** | 없음 (이력서에 쓰지 않았다) |
| **코드 실제** | `GlobalExceptionHandler` 에 핸들러가 **3개뿐**이다 — `BusinessException`(`:20`), `MethodArgumentNotValidException`(`:48`), 포괄 `Exception`(`:85`). 스프링이 던지는 `NoResourceFoundException`(미매핑 경로)이 앞의 둘에 걸리지 않아 포괄 핸들러로 떨어진다. 실측 결과 없는 경로 요청이 `S_001` 코드와 함께 **500**으로 응답된다 |
| **차이 성격** | **코드 결함** |
| **왜 위험한가** | 클라이언트 오류(4xx)가 서버 오류(5xx)로 집계된다. 모니터링·알림이 5xx 비율을 기준으로 동작하므로 **오탈자 URL 같은 무해한 요청이 장애 신호를 오염**시킨다. 서킷브레이커·에러율 대시보드를 5xx로 판단하는 구조에서는 실제 장애가 노이즈에 묻힌다 |
| **면접 방어 문장** | "예외 핸들러가 포괄 `Exception` 하나로 수렴해서, 미매핑 경로가 404가 아니라 500으로 나갑니다. 클라이언트 오류를 서버 오류로 집계하면 5xx 기반 모니터링이 무의미해지므로 `NoResourceFoundException`·`HttpRequestMethodNotSupportedException` 같은 스프링 표준 예외를 명시적으로 매핑하는 게 먼저입니다" |
| **수정 방향** | `GlobalExceptionHandler` 에 `NoResourceFoundException` → 404 매핑 추가. 이 저장소(`backend`) 코드다 |

### 1-3. 계정 잠금이 슬라이딩 방식이라 영구히 풀리지 않을 수 있다 — ✅ **수정 완료 (차이 해소)**

> **채택 정책 = 고정 창(fixed window)**. 본 항목의 "수정 방향"대로 **잠금 중 시도는 카운터 증가와
> `lockedUntil` 갱신에서 제외**한다. 이제 문서·이력서가 서술한 "5회 실패 → dev 1분 잠금"과 동작이 일치한다.
>
> **수정 위치는 호출부가 아니라 엔티티다.** `Credentials.recordLoginFailure` 진입부에 `isAccountLocked()`
> 가드를 넣어 잠금 중이면 즉시 반환한다. `isAccountLocked()` 는 만료된 잠금을 스스로 해제하고 카운터를
> 초기화하므로, 만료 후 첫 실패가 자동으로 **새 창의 1회**가 된다.
> `FormAuthenticationFailureHandler` 는 한 줄도 고치지 않았다 — 도메인 불변식을 엔티티가 지키면
> 미래의 호출부까지 함께 보호된다.
>
> **실기동 검증** (신규 계정, dev `maxAttempts=5` / `lockDurationMinutes=1`):
>
> | 단계 | 결과 |
> |---|---|
> | 오답 1~4회 | 401 |
> | 오답 5회 | **423** — `failed_login_attempts=5`, `locked_until=17:09:14` |
> | 잠금 중 오답 4회 + **정답 2회** | 전부 423, DB 값 **완전 불변** (`5 / 17:09:14`) |
> | 만료 후 정답 로그인 | **200** — `failed_login_attempts=0`, `locked_until=NULL` |
>
> **정답 비밀번호도 423 인 것은 의도된 동작이다.** `CustomUserDetailService:33` 이 비밀번호 검증 **전에**
> 잠금을 차단하므로 잠금 창 안에서는 정답도 거부된다. 달라진 건 **그 시도가 더는 잠금을 연장하지 않는다**는 점이다.
>
> **왜 슬라이딩이 됐는지 (근본 원인)**: `CustomUserDetailService` 가 던진 `BusinessException` 을
> Spring 의 `DaoAuthenticationProvider.retrieveUser` 가 `InternalAuthenticationServiceException`
> (= `AuthenticationException`)으로 **감싼다**. 그래서 `FormAuthenticationFailureHandler:42` 의
> `exception instanceof LockedException` 분기를 비껴가 else 로 떨어지고, 거기서 다시
> `recordLoginFailure` 가 호출돼 카운터가 올라갔다. 회귀 테스트 6건 추가(`CredentialsTest`).

|---|---|
| **이력서 서술** | PORTFOLIO `ai-5` — 설정 6곳 항목에서 "**dev 1분 계정 잠금**"이 미적용이었다고 서술, 결과에서 "dev 계정 잠금은 423 응답과 함께 잠금 해제 시각이 마지막 실패 시각 + 1분으로 계산되는 것까지 확인" |

| **면접 방어 문장** | "설정은 '5회 실패 시 5분(dev 1분) 잠금'이지만 실제 동작은 슬라이딩입니다. 잠금 중 시도도 카운터를 올리고 해제 시각을 뒤로 밀기 때문에, 계속 시도하면 영구히 안 풀립니다. 무차별 대입 억제로는 오히려 유리하지만 문서가 서술한 고정 창(fixed window)과는 다른 동작이라 — 정상 사용자가 스스로 잠금을 연장하는 문제가 있으므로 잠금 중 시도는 카운터에서 제외하는 게 맞다고 봅니다" |
| **수정 방향** | 잠금 상태에서의 시도는 `failed_login_attempts` 증가와 `lockedUntil` 갱신에서 제외. 이 저장소(`backend`) 코드다 |

### 1-4. `app.rag.enabled=false` 로 끄면 서버가 기동 실패했다 — ✅ **수정 완료 (차이 해소)**

> **이번 독립 감사의 최대 소득이었고, 코드를 고쳐 해소했다.** 문서가 "RAG를 꺼도 서버가 뜬다"고 주장하고 있었고
> 그 주장은 **플래그 하나만 뒤집으면 반증되는** 종류였다. 문서를 사실로 좁히는 데 그치지 않고 코드를 고쳐
> 원래 주장이 참이 되게 만들었다 — **양방향 실제 기동으로 검증**했다.
>
> **면접에서 쓸 수 있는 형태로 바뀌었다.** 이제 "발견 → 수정 → 실행 검증"이 완결된 이야기이고,
> 아래 "추가 발견" 행이 이 항목의 가치를 만든다 — **첫 수정만으로는 안 고쳐졌다.**

| 항목 | 내용 |
|---|---|
| **이력서 서술 (정정 후)** | PORTFOLIO `ai-4` — "**일반 채팅 경로**는 … 짝으로 두고 플래그로 갈아끼우게 해서 … 빈이 하나는 생기고" / "다만 **오프너 분석 경로는 이 짝을 갖추지 못했습니다** … 컨텍스트 기동 자체가 실패합니다" |

| **휠 파인더 코드 접근** | `wf-1`~`wf-4`(`PORTFOLIO.html:982~1136`)도 같은 상황이다 — 이 저장소에 휠 파인더 코드가 없어 **어떤 주장도 코드로 재확인하지 않았다.** JWT 이중 블랙리스트·SSE + Redis Pub/Sub·Redis Stream·Nginx 라우팅 서술은 전부 미검증 상태다. 세 프로젝트 중 이 항목만 추적 기록이 빠져 있어 이번에 추가했다. 감사 문서(`INTERVIEW_LOGIC_AUDIT.html`)도 휠 파인더는 다루지 않으므로 **인용 근거조차 없다** — `eco-*` 보다 검증 수준이 한 단계 더 낮다 |
| SSE 소유자 검증 E2E | Chat Redis 클러스터 광고 주소(`--cluster-announce-hostname`)를 로컬 환경에 맞추면 검증 가능하다. 환경 문제이며 코드 수정 대상이 아니다 |
