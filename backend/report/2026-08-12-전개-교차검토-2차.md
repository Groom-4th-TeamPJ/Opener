# 논리·설득 전개 2차 교차 검토

- 대상: `PORTFOLIO_v2_short.html` (제목 개편 + `기능`/`개선` 요약 블록 신설 이후)
- 방법: 에이전트 2개를 **읽는 방식 자체를 반대로** 제약해 병렬 실행
- 결과: **22건 지적. 겹침은 2건뿐** — 제약 분리가 의도대로 작동
- 결론: **상단 요약 블록(오늘 신설)에 결함이 집중**됐고, 그와 별개로 **사례 배치·프로젝트 순서라는 구조 문제**가 처음 드러남

---

## 1. 교차 설계

| 에이전트 | 읽는 방식 | 못 보게 막은 것 | 렌즈 |
|---|---|---|---|
| **R1 · 정합** | 사례마다 `제목+기능+개선` 3줄을 먼저 읽고 약속을 적은 뒤 본문과 대조 | 다른 버전, 이전 리포트 | 상단이 본문과 어긋나는가 |
| **R2 · 전개** | 처음부터 끝까지 순서대로 통독 | **`case-brief` 블록 전체**, 문장 단위 근거 | 흐름이 끊기거나 신뢰가 흔들리는가 |

R2에게 요약 블록을 가린 것이 핵심이다. 가리지 않으면 R2도 요약을 읽고 판단해, 요약에 기대어 **본문 자체의 전개 결함이 가려진다.**

**결과**: R1 12건 / R2 10건 중 겹친 것은 **2건**. 나머지 20건은 서로의 시야 밖이었다.

---

## 2. 두 팀이 함께 지목 (최우선)

### 2-1. 선착순 쿠폰의 유일한 실측이 폐기한 구성에서 나옴 — **세 번째 독립 확인**

- R1 #6 (상단↔본문): 상단은 `Redis 게이트 + Kafka 단일 판정`을 약속하는데 결과의 총량 상한 수치는 **락 구성**에서 잰 값
- R2 #3 (통독): 같은 사례 70행 앞에서 그 락 구성을 두고 `중복 발급 1건을 실제로 관측`했다고 적음 → **"락은 상호배제가 깨졌다"와 "락 구성에서 총량 상한이 지켜졌다"가 나란히 놓임**

이 지적은 **1차 교차 검토에서도 A1 #3 · A2 #1로 나왔다.** 서로 다른 4개 에이전트가 독립적으로 같은 곳을 짚었다.

> R2 표현: *"문서 전체에서 가장 야심찬 설계 전환인데, 전환 후를 재지 않았다는 사실이 결과 자리에서 드러남."*

**처방**: 이 수치를 `결과`에서 내려 `문제 원인`(락 구성 평가)으로 옮기고, 결과에는 채택 구성의 근거(5,000건 → 통과 100여 건 필터율)를 둔다. 재측정 전까지는 이게 최선.

### 2-2. 쿠폰 자동 비활성화 — 실재한 적 없는 폴링을 "제거"

- R1 #1: 상단 `폴링 지연을 …로 제거` → 기존 폴링 구현이 있었던 것으로 읽힘. 본문은 `커밋된 구현이 아니라 설계 단계 대안`이라고 **명시적으로 부정**
- R2 #9: 그 미구현 대안과의 비교에 지면·코드가 과다

**처방**: 상단을 `폴링 대안(도출 12s) 대신 StateStore + Punctuator로 최악 지연 1.1s 확보`로. 결과 본문도 스스로 `지연 단축의 직접 원인은 주기 단축(10s → 1s)`이라 하므로 **"제거"가 아니라 "단축"** 이 맞다.

## 3. R1 단독 — 상단 요약 블록 결함 10건

오늘 신설한 `기능`/`개선` 2행에 결함이 몰렸다. **새로 만든 블록의 결함 밀도가 가장 높다.**

| # | 사례 | 어긋남 | 고칠 곳 |
|---|---|---|---|
| 2 | RAG | **원인 지점과 처방을 뒤바꿈** — 기동 실패는 `RagService`인데 처방으로 적은 `짝 구성`은 실패가 안 난 `LlmService` 쪽. 실제 처방은 `ObjectProvider` | 상단 |
| 3 | 채팅 세션 저장소 | `샤드 분할`을 SPOF 제거 근거로 승격 — 본문은 해시 태그를 **"겪은 장애를 고친 게 아니라 선제 조치"**로 스스로 한정. 게다가 이 사례 최대 축인 **읽기 라우팅이 상단에 없음** | 상단 |
| 7 | 채팅 영속화 | 상단은 **두 갈래**(만료·유실), 결과는 **세 사유**(expired·lost·unauthorized). 트랜잭션 경계 축소 축도 누락 | 상단 |
| 9 | RAG | `기능` 행이 코퍼스를 **`수능·모의고사 자료`**라 했으나 실측은 `5,799청크 전부 한국어 수학 모의고사 문제·풀이` | 상단 |
| 8 | 채팅 영속화 | `기능` 행이 트리거를 안 밝혀 **자동 영속화로 읽힘**. 실제로는 `POST /chat/save-message` 요청이 트리거(단서는 사례 1에만 있음) | 상단 |
| 4 | 안정화 계층 | 상단은 `차단`만 약속. 본문 핵심은 **"차단으로 부족 → 고착 상태 회수"** | 상단 |
| 5 | PG 결제 | 결과 4줄 중 3줄이 **서킷브레이커 성과**인데 상단에 서킷이 없음 | 상단 |
| 10 | 실시간 채팅 | 본문이 `고쳐야 할 것이 둘`이라 선언하는데 상단은 **Virtual Thread 축을 통째로 누락** | 상단 |
| 11 | 인증 | `기능` 행은 발급 경로 **2개**, 본문 최대 결함은 **`4경로 중 3경로`** 누락 | 상단 |
| 12 | 재고 차감 | 본문 최장(산문 3,786자) · 축 4개인데 상단은 앞의 둘만 약속 | 상단 또는 사례 분할 |

**정합한 사례**: 조회 경로 · 추첨 예약 · 휠 파인더 3건.

> 10건 중 9건이 **"상단을 고쳐라"** 다. 본문은 대체로 맞고 **요약이 본문을 잘못 대표**하고 있다.

## 4. R2 단독 — 배치·전개 결함 8건

사례 내부가 아니라 **사례 사이·프로젝트 사이**의 문제. 통독하지 않으면 안 보인다.

### [높음] 휠 파인더 1이 오프너 1을 역행시킴

휠 파인더 1: *"프로세스 로컬 맵만으로는 인스턴스 경계를 넘지 못한다는 것을 **이 프로젝트에서 먼저 취급**"*

오프너 1은 `ConcurrentHashMap<sessionId, Sink>` 하나로 SSE를 관리하고 인스턴스 경계 언급이 **한 줄도 없다**(문서 전체 `인스턴스 경계` 3회는 전부 휠 파인더·이커머스).

> R2: *"2025-09 프로젝트에서 이미 푼 문제를 2025-12 대표 프로젝트에서 다시 프로세스 로컬 맵으로 되돌린 것으로 읽힘. '먼저 취급'이라는 표현이 그 비교를 문서가 직접 유도함."*

**문서가 자기 발등을 찍는 유일한 문장.**

### [높음] 추첨 예약이 앞 사례가 세운 원칙 셋을 동시에 어김

1. **Redis 내구성** — 오프너 4와 이커머스 1에서 두 번 부정한 성질(`복제 비동기, 승격 시 되감김`)을 이커머스 4는 `프로세스 밖에 있어 재기동에도 잔존`으로 근거 삼음
2. **N대 중복 실행** — 이 사례가 **문제 원인에 직접 적어 둔 항목**인데 해결 과정에 처방이 없음. 이커머스 1은 같은 문제에 분산 락으로 답했음
3. **폴링 비판** — 문제 원인에서 DB 폴링을 깠는데 채택안도 60초 폴링. 비용이 DB → Redis로 옮겨간 것

### [높음] 성장 서사가 문서 양 끝으로 찢어짐

오프너 6은 `출발점은 이전 프로젝트의 제약 — 휠 파인더에서…`로 시작하는데 그 휠 파인더는 **700행 뒤 마지막 사례**. 프로젝트는 최신순인데 서사는 시간순이라 **앞에서는 안 읽은 것을 참조하고 뒤에서는 700행 전 것을 회수**한다.

게다가 도착했을 때 휠 파인더 3이 **중복으로 읽힌다** — 블랙리스트·잔여 수명 TTL·fail-close는 오프너 6에서 더 정교하게 이미 읽었고, 새로운 건 version 카운터 하나뿐.

### [높음] 문서가 가장 약한 재료로 끝남

마지막 두 사례가 `Nginx 경로 분기 · docker-compose · GitHub Actions SSH 배포`와 `JWT 블랙리스트`. 앞 13개가 실패 주입·서킷 계측·3종 실측 수준인데 **마무리가 부트캠프 표준 구성으로 내려앉는다.** 잔상은 마지막 3,000자가 만든다.

### [중간] 그 밖

- **RAG가 2번 자리에서 전면 철회** — 대표 프로젝트 두 번째 사례가 통째로 자기 철회 구조(임계값 무근거 → 진단 오류 → 스윕 반증). 정직함은 강점이나 **배치가 문제**. 이후 사례를 읽는 기본 자세가 여기서 정해짐
- **이커머스 2 ↔ 5가 한 트랜잭션 경계를 양쪽에서 서술**하는데 3·4가 사이를 가름 → `1 → 2 → 5 → 3 → 4` 순서 제안
- **오프너 1·3·4·5가 같은 요청 경로의 네 층** — 순서대로 읽으면 같은 코드 경로를 네 번 재방문. 섹션 도입부에 층 구조 한 줄이면 중복이 깊이로 바뀜
- **오프너 4가 오프너 3의 성과를 사후에 되물림** — 3에서 완결감을 받은 영속화 파이프라인이, 4에서 `영속 경로는 Redis의 하류`로 밝혀짐

## 6. 권고 — 층위를 갈라서

세 층위가 섞여 있어 한꺼번에 처리하면 안 된다.

### 층 1 · 지금 고칠 것 (문구, 저위험)

R1 지적 10건 — **전부 상단 `기능`/`개선` 행 수정**이고 본문은 손대지 않는다. 오늘 만든 블록의 자기 교정이라 위험이 없다. 여기에 2-1(락 구성 수치 이동)과 2-2(제거 → 단축)를 더한다. **총 12건.**

### 층 2 · 결정이 필요한 것 (배치)

- 오프너 안에서 RAG를 뒤로 옮길지
- 이커머스를 `1 → 2 → 5 → 3 → 4`로 바꿀지
- 휠 파인더 3을 version 카운터 중심으로 축약할지
- 휠 파인더 섹션을 3개 → 1~2개로 줄일지

**전부 되돌리기 쉬우나 서사가 바뀐다.** 사용자 판단 사항.

### 층 3 · 서술로는 못 푸는 것

- 오프너 1의 단일 인스턴스 전제 — 문구로 덮을지, 실제로 Pub/Sub 팬아웃을 넣을지
- 추첨 예약의 N대 중복 실행 — 락을 적용할지, 한계로 내릴지
- 선착순 쿠폰 채택 구성 재측정

## 부록 — R2의 한 문장 총평

> *"자기가 만든 것의 결함을 남보다 먼저 찾아내 수치로 못 박는 사람인데, 그 능력을 사례마다 각개로 쓰느라 프로젝트 사이에서는 같은 실수를 다시 하고 있다."*

앞 절은 문서가 의도한 인상과 일치한다. **뒤 절이 이번 검토의 수확** — 사례 안은 촘촘한데 사례 사이가 비어 있다는 지적이고, 층 2·3이 정확히 그 지점이다.
