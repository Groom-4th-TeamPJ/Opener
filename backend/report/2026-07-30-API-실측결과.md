#### 5-3. 핵심 — 유저 B 가 유저 A 의 sessionId 로 접속

소유자 검증은 코드상 **두 경로**에 있어서 둘 다 실측했다.

**경로 1 — sink 가 살아있는 상태** (`ChatServiceImpl.connectSession` → `validateSessionOwner`)

유저 A 가 `sessionId=555002` 로 연결을 유지한 상태에서, 유저 B 의 토큰으로 같은 sessionId 접속:

```bash
$ docker exec redis-chat-1 redis-cli -c -p 6380 HGET "chat:{555002}:session" userId
2ded8225-7f10-4da8-965a-85d0037fcaa2      ← 소유자는 userA

$ curl -m 15 -D - -b "accessToken=$TB" "http://localhost:8080/api/chat/connect?sessionId=555002"
HTTP/1.1 400
Content-Type: application/json

{"code":400,"data":null,"error":{"field":null,"rejectedValue":null,
 "reason":"사용자의 세션 접근권한이 없습니다.","code":"C_001"},
 "message":"사용자의 세션 접근권한이 없습니다.","status":"error"}
<<status=400>>
```

**경로 2 — sink 가 사라지고 Redis 세션만 남은 상태** (`initializeSession` 의 재사용 방어선)

유저 A 의 SSE 연결이 끊긴 뒤(sink 제거) Redis 세션은 TTL 이 남아 있다. 코드 주석이 지적한 "TTL 이 남은 남의 세션에 그대로 올라타는" 시나리오다:

```bash
$ docker exec redis-chat-1 redis-cli -c -p 6380 TTL "chat:{555002}:session"
3537                                       ← 세션은 아직 살아있음
$ docker exec redis-chat-1 redis-cli -c -p 6380 HGET "chat:{555002}:session" userId
```

## 발견된 문제

### 코드 결함

#### D-1. 존재하지 않는 경로가 404 대신 500 을 반환한다

`GlobalExceptionHandler` 에는 핸들러가 3개뿐이다 — `BusinessException`(:20), `MethodArgumentNotValidException`(:48), 그리고 포괄 `Exception`(:85). Spring 이 던지는 `NoResourceFoundException`(본래 404)이 포괄 핸들러에 걸려 500 으로 변환된다.

```bash
$ curl -b "accessToken=$T" http://localhost:8080/api/nosuchpath
{"code":500,"data":null,"error":{"reason":"No static resource nosuchpath for request '/api/nosuchpath'.",
 "code":"S_001"},"message":"서버 내부 오류가 발생했습니다","status":"error"}
<<status=500>>

$ curl -b "accessToken=$T" http://localhost:8080/api/actuator/nosuchthing
{"code":500,...,"reason":"No static resource actuator/nosuchthing for request '/api/actuator/nosuchthing'.",
 "code":"S_001"},...}
<<status=500>>
```

영향: 클라이언트가 오타·잘못된 경로를 서버 장애로 오인한다. 모니터링에서도 5xx 로 집계되어 실제 장애 신호를 오염시킨다. 4단계에서 미노출 actuator 엔드포인트가 404 대신 500 으로 보였던 것도 같은 원인이다.

> 참고: 이 결함은 이번 리팩토링 범위 밖의 기존 동작으로 보인다. P0 3건과는 무관하다.

#### D-2. 계정 잠금이 슬라이딩 윈도로 동작한다 (설계 의도 확인 필요)

잠금 중의 로그인 시도가 실패 카운터를 올리고 `locked_until` 을 다시 1분 뒤로 미룬다. 결과적으로 사용자가 계속 시도하면 잠금이 영구히 풀리지 않는다.

실측: 10초 간격으로 **올바른** 비밀번호를 12회 시도했더니 121초가 지나도 계속 423 이었고, `failed_login_attempts` 가 19(최초 오답 6회 + 재시도 12회 + 1)까지 올라갔다. 시도를 멈추고 75초 대기하니 1회 시도에 바로 200 이었다.

메커니즘:
1. `CustomUserDetailService.java:36` — 잠금 확인이 **비밀번호 검증보다 먼저** `ACCOUNT_LOCKED` 를 던진다. 그래서 올바른 비밀번호도 "실패"로 처리된다
2. `Credentials.recordLoginFailure:96-104` — `failedLoginAttempts++` 후 `failedLoginAttempts >= maxAttempts` 면 `lockedUntil = now + lockDurationMinutes` 를 **다시** 설정한다. 이미 잠긴 상태에서도 조건이 항상 참이므로 매번 갱신된다

```java
public void recordLoginFailure(int maxAttempts, int lockDurationMinutes) {
    this.failedLoginAttempts++;
    this.lastFailedLoginAt = LocalDateTime.now();
    if (this.failedLoginAttempts >= maxAttempts) {
        this.lockedUntil = LocalDateTime.now().plusMinutes(lockDurationMinutes);
    }
}
```

무차별 대입 억제 관점에서는 유리한 성질이지만, **"5회 실패 → 5분 잠금"이라는 문서상 계약과 실제 동작이 다르다.** 정상 사용자가 잠금 후 조급하게 재시도하면 잠금이 계속 연장되어 체감 잠금 시간이 무한정 늘어난다. 의도된 정책이면 문서를 고치고, 아니면 잠금 상태에서는 카운터를 올리지 않도록 해야 한다.

**어느 쪽이든 코드는 수정하지 않았다 — 정책 판단이 필요한 사안이라 보고만 한다.**

### 환경 문제 (코드 결함 아님)

#### E-1. `test` 태스크가 `.env` 를 로드하지 않는다

`build.gradle:119` 의 `.env` 주입이 `bootRun` 에만 걸려 있어서, `./gradlew test` 는 `OPENAI_API_KEY`·`REST_API_KEY`·`CLIENT_SECRET_KEY` 를 해결하지 못하고 `BackendApplicationTests.contextLoads` 가 실패한다. `src/test/resources/` 디렉터리도 없어서 테스트 전용 프로퍼티 오버라이드 지점이 아예 없다.

- 근거: 세 값을 더미로 주입하니 `BUILD SUCCESSFUL` (1-3절)
- 영향: CI 에서 `.env` 없이 돌리면 항상 이 1건이 깨진다
- 참고 해결 방향(미적용): `tasks.named('test')` 에도 동일한 `.env` 로딩을 걸거나, `src/test/resources/application.yml` 에 테스트용 더미 값을 두는 방법

#### E-2. Chat Redis Cluster 를 호스트에서 접근할 수 없다 — **✅ 해소됨**

**이 항목은 다음에 같은 함정을 만날 사람에게 가장 값진 기록이므로 원인·해법·검증을 모두 남긴다.**

##### 증상

클러스터 자체는 정상(`cluster_state:ok`, 6노드 healthy)인데 애플리케이션에서 chat Redis 를 전혀 쓸 수 없다. `/actuator/health` 의 `chatRedisConnectionFactory` 만 DOWN, `Unable to connect to Redis`.

##### 원인 — seed 주소가 아니라 "광고 주소"가 문제다

Redis Cluster 클라이언트는 2단계로 붙는다.

1. **seed 접속** — 설정에 적힌 주소로 아무 노드에나 붙어서 `CLUSTER NODES` / `CLUSTER SHARDS` 를 조회한다
2. **토폴로지 갱신** — 그 응답에 적힌 **각 노드가 스스로 광고한 주소**로 전체 노드에 개별 연결을 만든다. 키마다 슬롯 소유 노드로 직접 보내야 하므로 클라이언트는 모든 노드에 붙어야 한다

여기서 1번은 성공하고 **2번이 실패**했다. `docker-compose.local.yml:51` 이 각 노드에 광고 주소를 컨테이너 이름으로 못박아 놨기 때문이다:

```yaml
command: redis-server /etc/redis/redis.conf --port 6380
         --cluster-announce-hostname redis-chat-1
         --cluster-announce-port 6380 --cluster-announce-bus-port 16380
```

그래서 클러스터는 자신을 컨테이너 내부 주소로 광고한다:

```bash
$ docker exec redis-chat-1 redis-cli -p 6380 CLUSTER NODES | awk '{print $2, $3}'
172.19.0.6:6380@16380,redis-chat-1 myself,master
172.19.0.7:6381@16381,redis-chat-2 master   ...
```

호스트에서는 seed 는 열려 있는데 광고된 이름은 해석되지 않는다 — **이 두 줄이 증상의 핵심**이다:

```bash
$ nc -z localhost 6380   → succeeded         # 1단계 seed 접속: OK
$ ping -c1 redis-chat-1  → cannot resolve    # 2단계 토폴로지: 실패
```

로그가 정확히 그 단계를 가리킨다:

```
WARN i.l.c.c.t.DefaultClusterTopologyRefresh
  - Unable to connect to [redis-chat-1/<unresolved>:6380]: Failed to resolve 'redis-chat-1' [A(1)] 2 queries
```

**코드 결함이 아니다.** compose 구성이 "백엔드도 도커 네트워크 안에서 실행"을 전제하는데(그 안에서는 `redis-chat-N` 이 DNS 로 해석된다) 이번 검증은 호스트에서 `bootRun` 으로 띄웠기 때문에 생긴 전제 불일치다.

##### 해법 — `/etc/hosts` 6줄

```
127.0.0.1 redis-chat-1
127.0.0.1 redis-chat-2
127.0.0.1 redis-chat-3
127.0.0.1 redis-chat-4
127.0.0.1 redis-chat-5
127.0.0.1 redis-chat-6
```

**왜 이것으로 충분한가** — 두 조건이 맞아떨어지기 때문이다.

1. **광고 주소가 IP 가 아니라 호스트명이다.** `--cluster-announce-hostname` 을 썼으므로 클라이언트는 `redis-chat-N` 이라는 **이름**으로 접속을 시도한다. 이름은 `/etc/hosts` 로 가로챌 수 있다. (만약 `--cluster-announce-ip 172.19.0.6` 처럼 IP 를 광고했다면 hosts 로는 손댈 수 없고 compose 를 고쳐야 한다)
2. **포트가 1:1 매핑이다.** `6380:6380` … `6385:6385` 로 컨테이너 포트와 호스트 포트가 같다. 그래서 `redis-chat-3:6382` 를 `127.0.0.1:6382` 로 돌려도 정확히 그 노드에 도달한다. 포트를 바꿔 매핑했다면(예: `16380:6380`) 이름만 돌려도 포트가 어긋나 실패한다.

즉 **"이름으로 광고 + 포트 1:1"** 조합일 때만 통하는 해법이다. 클러스터 버스 포트(`16380-16385`)도 동일하게 1:1 매핑돼 있어 문제없다.

##### 해소 확인 (실측)

```bash
$ grep -n redis-chat /etc/hosts
10:127.0.0.1 redis-chat-1   …   15:127.0.0.1 redis-chat-6
$ ping -c1 redis-chat-1
PING redis-chat-1 (127.0.0.1): 56 data bytes      ← 해석됨
```

재기동 후:

```bash
$ curl http://localhost:8080/api/actuator/health
{"groups":["liveness","readiness"],"status":"UP"}        ← DOWN → UP

# 컴포넌트 상세
redis.chatRedisConnectionFactory: UP {'cluster_size': 3, 'slots_up': 16384, 'slots_fail': 0}
```

이후 A-1 SSE E2E 와 Hash Tag 슬롯 검증을 정상 수행했다(검증 5, 5-A).

##### 참고 — 통하지 않는 우회

`application-dev.yml:42-43` 주석은 `/etc/hosts` 에 `host.docker.internal` 을 추가하라고 안내하지만 이 문제에는 듣지 않는다. (a) `.env` 가 `REDIS_CLUSTER_NODE_*=localhost:638X` 로 덮어쓰고 있고, (b) 무엇보다 `host.docker.internal` 은 **seed 주소**를 바꾸는 것이고 실패 지점은 2단계 광고 주소이므로 seed 를 무엇으로 바꿔도 해결되지 않는다. 문서를 고칠 때 이 구분을 명시하는 게 좋다.
