## 1. 🔴 자기모순 — "임계 구역에서 DB I/O를 들어냈다"는 사실이 아니다

### 어긋난 지점

| 위치 | 서술 |
|---|---|
| eco-1 해결과정 3 | "락을 걷어내는 대신 **락이 DB I/O를 감싸는 상황을 없앤 것**임" |
| eco-1 결과 2 | "워밍업으로 **임계 구역에서 DB I/O 자체를 들어냈음**" |
| eco-1 **코드 카드** | `return self.persistIssuedCoupon(...)` 가 `tryLock` ~ `finally unlock` **안에 있음** |

### 사실

워밍업이 없앤 것은 **폴백 경로의 DB I/O**(`SELECT FOR UPDATE` + INSERT + UPDATE + `initStock`)뿐이다.
정상 경로의 `persistIssuedCoupon`(INSERT + UPDATE)은 **여전히 락 안에서 실행된다**
(`CouponIssueService.java` 의 `tryLock` 블록 내부, 포트폴리오 코드 카드에도 그대로 노출).

따라서 임계 구역은 `Lua만`이 된 것이 아니라 **`Lua + DB 쓰기 1건`으로 줄어든 것**이다.
문제원인이 "임계 구역 안에 DB I/O가 들어가 있는 한 서버를 늘려도 이 벽을 넘지 못함"이라고 선언했으므로,
이 과장은 **진단과 처방의 불일치를 해소한 척**하는 문장이 된다.

### 왜 위험한가

면접관이 코드 카드를 읽는 데 3초 걸린다. 본문과 코드가 **같은 화면 안에서** 반대를 말하고 있어
"직접 쓴 코드인가"라는 의심으로 직행한다. 다른 모든 섹션의 신뢰도까지 함께 깎인다.

### 정정안

- 해결과정 3 → "락을 걷어내는 대신 **락이 비관적 락·DB 폴백을 감싸는 상황을 없앤 것**임"
- 결과 2 → "워밍업으로 **임계 구역에서 폴백 경로의 DB I/O를 들어냈음**"

정직하게 줄여도 논지는 그대로 산다. 임계 구역이 `비관적 락 + 다중 쿼리` 에서 `INSERT 1건` 으로 줄었다는
것만으로 충분히 큰 개선이고, 오히려 **남은 것이 무엇인지 아는 사람**으로 읽힌다.

## 2. 🟠 논리 구멍 — 폴백에 진입하지 않는다면 락은 왜 남아 있나

### 전제들이 만드는 귀결

1. 해결과정 2: "정상 경로의 초과발급은 **Lua만으로** 차단되며, **여기서 락은 정확성에 기여하지 않음**"
2. 해결과정 3: "락이 **반드시 필요한 지점은** DB 수량을 줄인 뒤 Redis에 되쓰는 **미초기화 폴백 하나**임"
3. 해결과정 3 (2026-07-31 추가): "그 폴백에는 **정상 운영에서 진입하지 않도록** 재고를 심었음"

1 + 2 + 3 → **정상 운영에서 락이 필요한 지점은 존재하지 않는다.** 그런데 락은 남아 있다.
본문 어디에도 "그래도 왜 남기는가"의 답이 없다.

역설적으로 **워밍업을 넣은 것이 이 구멍을 만들었다.** 넣기 전에는 "폴백이 실제로 발생하니 락이 필요하다"가
성립했는데, 폴백 진입을 없애면서 근거가 함께 사라졌다.

### 실제 답은 있다 — 다만 본문이 아니라 코드 주석에 있다

코드 카드 주석: *"락 안에서 Redis 롤백까지 끝내야 두 저장소 정합이 깨진 틈에 다른 요청이 못 끼어듦"*

즉 정상 경로에서 락이 하는 일은 **보상 창(Lua 성공 → DB 실패 → `rollbackIssue`)을 다른 요청에게 감추는 것**
하나다. 이게 없으면 곧 복구될 재고를 두고 다른 요청이 **거짓 품절**을 받는다.

### 권고

해결과정 6(보상 항목)에 한 마디를 붙여 구멍을 메운다.
예: "**락이 정상 경로에 남는 이유가 이것임** — 차감과 보상 사이의 창을 다른 요청에게 감추는 역할이고,
폴백은 워밍업 누락·Redis 재기동을 대비한 최후 방어선으로 유지".

이 한 문장이 들어가면 §1 의 정정과 맞물려 **"락은 정확성이 아니라 관측 일관성을 위해 남았다"** 는
정확하고 방어 가능한 서술이 된다.

## 3. 🟡 기준의 비일관 적용 — eco-3 의 "다음 단계 네 갈래"

eco-1 에서는 미구현 확장 설계(축 1~6)를 **의도적으로 들어냈다.** 근거는 사용자가 세운 원칙이었다 —
*"이건 보고서가 아닌 포트폴리오다. 확장설계는 현재 되어있는 내용이 아니니 넣을 필요가 없다."*

그런데 eco-3 해결과정 마지막 항목은 **네 갈래 후속 설계**를 그대로 담고 있다.

| 갈래 | 상태 |
|---|---|
| ① 원자적 조건부 UPDATE | 미구현 (설계) |
| ② 차감 시점을 PG 승인 이전으로 이동 | 미구현 (설계) |
| ③ 백오프 지터 | **구현됨** — 결과 섹션에 A/B 실측(57.28% → 72.01%) |
| ④ 예외 재포장 중단 | 미구현 (설계) |

같은 문서 안에서 같은 성격의 내용이 한쪽에서는 제거되고 다른 쪽에서는 유지된다.
③은 실측 근거가 있으니 남기고, ①②④는 `report/` 로 옮기거나 **"검토한 대안"으로 한 줄 압축**하는 것이 일관된다.

> 참고: 이건 "지워라"가 아니라 "기준을 하나로 하라"는 지적이다. ①②④를 남기기로 한다면
> eco-1 에서 축 1~6 을 뺀 결정도 재검토 대상이 된다.

## 4. 🟡 제목이 내용을 담지 못하는 섹션 — ai-4

제목: **"RAG 검색 재현율 저하를 임계값 재조정으로 해결"**

해결과정 9항목 중 뒤쪽 3항목은 재현율과 무관한 주제다.
- 조건부 빈 짝 맞추기(`LlmService` / `RagService` 페어, `ObjectProvider`)
- 벡터 저장소 주입 5개 클래스 점검
- 대화 히스토리 윈도우와 영속화 계약 분리

내용 자체는 좋다. 특히 "조건부 빈은 빈을 만들지 않는 것만으로 안전해지지 않고 **주입받는 쪽까지 함께 봐야
방어가 성립**한다"는 대목과 "최적화가 저장 데이터를 훼손하지 않도록 경로를 갈라놓았다"는 대목은
이 문서에서 손에 꼽히는 통찰이다. **문제는 배치다.**

ai-4 는 해결과정 **9항목 1,820자**로 문서 최다이기도 하다(기준 6~7항목 · 1,100~1,400자).

**두 선택지**
- (a) 제목을 넓힌다 — 예: "RAG 재현율 저하 해결과 플래그·컨텍스트 운영 경로 정비"
- (b) 뒤 3항목을 덜어낸다 — 분량 기준에도 맞고 제목도 살아난다

(a)를 권한다. 덜어내기엔 내용의 질이 아깝고, 세 항목 모두 "**하나를 고치면 그 하나만 보면 되는가**"라는
동일한 물음을 다루고 있어 묶을 명분이 있다.

## 5. 🟢 흐름 — 방법론이 실행되고 있으나 선언되지 않는다

이 문서의 진짜 강점은 개별 기술이 아니라 **반복되는 작업 방식**이다. 13섹션에 일관되게 나타난다.

| 축 | 등장 |
|---|---|
| 측정의 목적을 숫자가 아니라 **인과 확정**으로 잡음 | ai-1(스레드 20개 고정 통제), eco-3(9회 반복·A/B) |
| **차단과 회수는 다른 문제** | ai-3(전이 차단 vs 상태 회수) |
| **역할을 갈라 책임을 분리** | ai-2(가용성=Cluster / 내구성=영속 경로), eco-3(부하 필터=Redis / 최종 정합=`@Version`) |
| **적었다 ≠ 걸렸다** | ai-5(런타임 바인딩 검증) |
| **보호 범위로 도구를 나눔** | eco-1 ↔ eco-3(임계 구역이 Redis 밖으로 나가는가) |
| 한계를 **범위로 한정해 선언** | ai-1(대리 부하), ai-2(7초는 인프라 회복 시간), eco-1(전후 비교 불가) |

그런데 문서 어디에도 이 방식이 **한 줄로 선언되지 않는다.** 프로젝트 인트로는
"아래 5개 기능은 제가 직접 설계·구현한 핵심 문제 해결 사례임" 수준의 열거다.
결과적으로 독자가 **13개 사례에서 패턴을 스스로 귀납**해야 한다 — 면접관이 그 수고를 해줄 이유가 없다.

**권고**: 문서 최상단(부제 자리)에 한 줄. 예 —
*"측정으로 원인을 확정하고, 파라미터가 아니라 구조로 처리하며, 남은 한계는 범위로 한정해 적었음"*

이 한 줄이 있으면 이후 모든 섹션이 **그 주장에 대한 증거**로 읽힌다. 지금은 독립 사례 13개다.
