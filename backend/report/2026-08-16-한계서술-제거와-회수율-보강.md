## 1. 적용 기준

제거와 유지를 가른 선은 **그 문장이 없으면 앞뒤가 무너지는가**.

| 성격 | 처리 | 예 |
|---|---|---|
| 측정 공백 고백 | **제거** | "스윕 실측도 부재해 원인 규명이 아니라 증상 대응" |
| 미구현 고백 | **리드 교체** | "다만 장애 내성까지 확보하지는 못한 상태" |
| 자기 반증 | **프레임 전환** | "그 진단은 반증됨" → "자료 전수 확인으로 원인 후보를 배제" |
| 선택의 대가 | **유지** | "무상태의 이점을 내주고 즉시 무효화를 산 교환" |
| 구조의 성질 | **리드만 교체** | "남는 것은 설계 한계" → "값이 아니라 구조의 성질" |

**제거가 아니라 프레임 교체를 택한 이유** — 실측 수치(5,799청크 · 중앙값 0.40 · RF≥3 설정)는 면접에서 파고들 근거이므로 남기고, 그 수치를 감싸는 리드만 자책에서 판단으로 전환. 같은 사실이 변명 대신 설계 근거로 읽힘.

## 3. (A) 회수율 보강 — 문제 항목 추가

해결·결과는 미변경. **문제 섹션에만 항목을 추가**해 결과가 소급될 자리를 만듦.

### RAG 검색 (문제 2 → 5)

- **RAG를 끄면 애플리케이션이 기동 실패** — 조건부 빈이 켜짐 쪽에만 존재해 `VectorStore` 를 요구하는 주입 지점이 그대로 남는 구조라, 플래그를 내리는 것이 곧 장애
  → 해결의 짝 구현체 · `ObjectProvider` · 양방향 기동 검증을 회수
- **플래그가 켜지면 일반 채팅도 같은 벡터 검색 경로를 경유** — 분기 기준이 질문의 용도가 아니라 플래그 하나
  → 결과의 `path=chat|opener` 태그 비용 비교를 회수
- 대화 히스토리를 **전량 프롬프트에 주입**하는 구조라 턴이 쌓일수록 토큰 비용과 첫 토큰 지연이 함께 증가
  → 해결의 `app.chat.history-window` 와 조회 계약 분리를 회수

### 조회 경로 데이터 모델 (결과 2 → 3)

- **스크랩북 필터 조회가 화면에 필요한 컬럼만 가져오는 경로로 성립** — 엔티티 로딩이 없어 쓰지 않는 연관이 미동반, 컬렉션 `fetch join` 이 만드는 메모리 페이징도 회피
  → 문제 3번(화면에 쓰는 컬럼이 엔티티의 일부)을 회수

### 인증·세션 방어선 (문제 3 → 4)

- 보안 설정은 **yml 에 값을 적는 것과 실제 빈에 바인딩되는 것이 별개** — 키 위치가 한 단계만 어긋나도 기동 오류 없이 기본값으로 조용히 대체되는 구조
  → 결과의 "값을 적었다 vs 실제로 바인딩됐다 분리 검증"을 회수

### PG 결제 보상 (3 · 11 · 4 → **7 · 11 · 5**)

추가한 문제 4건

  → 해결 3(의도 기록을 `REQUIRES_NEW` 로 먼저 커밋) · 해결 4(배치 자기호출로 트랜잭션 미적용) 회수
- **보상 레코드에 상태 개념이 없으면 재시도가 성공 건을 덮어씀** — 조회 조건에만 의존하면 새 호출부에서 뚫림
  → 해결 6(4개 상태 전이표) 회수
- **멱등키는 PG 멱등성 윈도우 안에서만 유효** — 한도·백오프를 윈도우와 무관하게 정하면 키가 목적을 상실
  → 해결 9 회수
- **Cascading Failure 위험 + 승인·취소는 실패의 의미가 상이** — 한 회로로 묶으면 한쪽 장애가 반대쪽을 함께 차단

추가한 문제 4건

- **토큰마다 붙는 콜백이 응답을 읽는 스레드 위에서 실행** — 같은 루프가 담당하는 다른 사용자의 스트림까지 정지 → 해결 4 회수
- **생산 속도를 늦출 수 없는 스트림** — 넘치면 화면에 없는 내용이 저장본에, 끊기면 반대로 화면에만 잔존 → 해결 5 · 6 회수

추가한 결과 2건

- **한 사용자의 콜백이 다른 사용자의 스트림을 멈추지 않는 구조**
- **클라이언트가 떠나면 상류 LLM 구독까지 함께 정리** — 취소 지점 세 곳

**섹션 분할은 미실시.** 목차·앵커·자매 문서 참조까지 건드리는 구조 변경이라 되돌리기 어렵고, 문제 보강만으로 회수 구조가 성립. 분할이 필요하면 별도 판단 사항.

### (E) 개선 요약 층위 통일 — 8건 교체

수단·도구 나열을 결과 서술로 교체. 목차에서 먼저 읽히는 문장이므로 "무엇을 썼는가"가 아니라 "무엇이 달라졌는가"로 통일.

| 섹션 | 이전 | 이후 |
|---|---|---|
| 실시간 채팅 | 스레드 고갈과 일괄 전달을 두 단계로 나눠 해소하고, 상류 구독 누수까지 차단 | 연결 상한과 첫 글자 대기를 함께 걷어내고, 화면·저장본·상류 구독이 어긋나던 경로까지 차단 |
| RAG | …기동 실패를 **짝 구현체와 선택적 주입으로** 해소 | …플래그를 내리면 기동이 깨지던 경로를 **양방향으로 성립** |
| 세션 저장소 | …책임을 갈라**(CQRS) 지점별로 라우팅** | …무거운 조회가 쓰기를 막던 구조를 갈라 **포화 지점을 뒤로 이동** |
| 선착순 쿠폰 | 순서와 병목을 **Redis 게이트 + Kafka 단일 판정으로** 해결 | **"선착순"이 무엇의 순서인지를** 단일 판정으로 확정하고, 발급 경로에서 락과 DB를 제거 |
| PG 결제 | 부분 실패를 **Saga 보상으로** 복구하고, 승인·취소를 **별도 서킷으로** 분리 | 부분 실패에도 **장부가 남게** 만들고, 한쪽 장애가 반대쪽 보상을 막지 않도록 회로를 분리 |
| 추첨 예약 | **Redis 지연 큐 + Kafka 수동 ACK로** 분리해 at-least-once 보장 | 예약을 프로세스 밖에 두어 **재기동에 견디게** 하고, 발행·처리 실패가 모두 재시도로 수렴 |
| 위치 공유 | 인스턴스 경계는 **Pub/Sub**, 발행 시점 의존성은 **Stream**으로 해소 | **어느 인스턴스에 연결돼도 위치가 닿게** 하고, **늦게 접속해도 최신 경로를 받게** 전환 |
| 배포·라우팅 | **Nginx 경로 라우팅 + Compose·CI/CD로** 해결 | 도메인 하나로 두 서버를 공존시키고, **로컬·운영의 실행 방식 차이와** 수동 배포 절차를 제거 |

### (H) 파트 간 연결

기존에는 **세 번째 파트(휠 파인더) 소개에만** 연결 문장이 존재("세 프로젝트 중 가장 이른 것으로, 여기서 부딪힌 키 설계·인스턴스 확장 제약이 뒤의 두 프로젝트에서 설계 기준이 됨"). 문서 최말단이라 독자가 순서를 뒤늦게 인지.

앞의 두 파트 소개에 대응 문장을 추가해 세 파트가 나열이 아니라 순서로 읽히게 함.

- **Opener** — "세 프로젝트 중 가장 나중으로, 앞의 두 곳에서 부딪힌 키 설계·인스턴스 확장 제약을 출발 조건으로 삼아 키 기준·장애 정책·검증 절차를 먼저 정하고 착수"
- **groom-shopping** — "휠 파인더 다음 프로젝트로, 동시성과 외부 연동을 정면으로 다루며 선택을 실측으로 확정하는 방식이 자리 잡은 지점"
