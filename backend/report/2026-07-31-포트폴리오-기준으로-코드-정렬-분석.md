# 포트폴리오의 논리를 기준으로 코드를 정렬하기 — 개선 분석

**작성** 2026-07-31 · **전제** 포트폴리오를 명세로 삼고 코드를 거기에 맞춰 간다
**선행 문서** `2026-07-31-포트폴리오-논리흐름-재검토.md` (결함 진단) · `2026-07-31-쿠폰-설계-논리-평가.md`

각 개선안은 세 층으로 적는다 — **(A) 포트폴리오가 주장할 문장 / (B) 그 주장이 성립하려면 코드가 어때야 하는가 / (C) 현재 코드와의 격차**.
포트폴리오가 스스로 "후속 과제"로 적어둔 항목(경합 전용 에러코드 등)은 **의도적으로 제외**했다.
여기 담은 것은 *포트폴리오의 기준이 스스로 지목한 격차*다.

---

## 🔴 개선 1 — 비동기 경로가 포트폴리오의 단일 기준을 위반한다

### (A) 포트폴리오가 이미 주장하고 있는 문장

> **"임계 구역이 Redis 밖으로 나가는가"라는 단일 기준**이 두 도메인의 선택을 설명 (eco-1 해결과정 4)
> 정상 경로의 초과발급은 **Lua만으로** 차단 (eco-1 해결과정 2)

### (B) 그 주장이 성립하려면

임계 구역이 **DB와 Redis 두 저장소에 걸치는 경로**는 예외 없이 둘 중 하나여야 한다.
- 분산 락으로 배타 실행하거나
- Redis에 되쓰지 않아 임계 구역이 한 저장소 안에서 완결되거나

### (C) 현재 코드 — 세 번째 경로가 존재한다

`POST /issue-async/{coupon_id}` → Kafka → `CouponAsyncIssueService.process:69` → **`issueCouponInDbOnly`**

| 단계 | 코드 |
|---|---|
| DB 비관적 락으로 수량 차감 | `CouponIssueService.java:225` `coupon.decreaseQuantity()` |
| 커밋 후 **Redis 재고를 SET** | `:239` `runAfterCommit(() -> initStock(couponId, remainingQuantity))` |
| 분산 락 | **없음** (`CouponAsyncIssueService`·`CouponIssueRequestConsumer` 에 `RLock`/`tryLock` 검색 0건) |

→ **DB와 Redis 두 저장소에 걸친 쓰기인데 분산 락이 없다.** 기준을 정면으로 위반한다.

### 축 1(워밍업)이 이 문제를 활성화시켰다

| | 워밍업 전 | 워밍업 후 |
|---|---|---|
| `issueCouponInDbOnly` 진입 조건 | Redis 재고가 **없을 때만**(첫 요청) | 비동기 경로는 **항상** 이 메서드를 탐 |
| 그때 `initStock` 의 의미 | 빈 키에 **심기**(seed) | 살아 있는 카운터를 **덮어쓰기**(SET) |

**사고 시나리오**
1. 동기 요청 A: 분산 락 획득 → Lua `DECR` (Redis = N−1) → DB INSERT 진행 중(아직 커밋 전)
2. 비동기 요청 B: 락 없이 `issueCouponInDbOnly` 커밋 → 자기 DB 뷰(A의 차감 미반영, 수량 = N−1) 로 **Redis SET**
3. → A의 Redis 차감이 지워지고 재고가 되살아난다 → **초과발급 가능**

이것은 eco-1 **문제 원인 4번째 문단이 서술한 바로 그 사고**다 —
*"두 요청이 동시에 폴백에 진입하면 … Redis 되쓰기의 도착 순서가 뒤바뀌어 … 재고가 되살아나 초과 발급"*.
동기 경로에서 막아낸 사고가 **비동기라는 다른 문으로 되돌아왔다.**

### 권고 — 비동기 경로도 Lua를 쓰게 한다

`CouponAsyncIssueService.process` 가 `issueCouponInDbOnly`(DB 비관적 락 + Redis SET) 대신
**`tryIssue` Lua → DB 영속화 → 실패 시 `rollbackIssue`** 순서를 타게 한다.

효과가 연쇄적이다.
1. Redis가 재고의 **단일 진실**이 되고 `initStock`(SET)이 정상 경로에서 사라진다
2. 임계 구역이 **Redis 안에서 완결** → 포트폴리오 기준상 락이 필요 없고, 큐 직렬 소비로 충분하다
3. 동기·비동기가 **같은 원자 연산을 공유**한다 → 두 경로의 차이가 하나로 정리된다

> **서술 이득이 크다.** 지금은 비동기 경로가 "락 경합을 피하는 우회로"로만 설명된다.
> 정렬 후에는 이렇게 쓸 수 있다 —
> *"두 경로 모두 Lua가 정확성을 책임지고, 차이는 **차감과 보상 사이의 창을 락으로 감추는가(동기)**,
> **큐 직렬화로 창 자체를 만들지 않는가(비동기)** 하나뿐임."*
> 같은 문제를 두 가지 비용으로 푼 대비가 되고, eco-1의 단일 기준이 **세 경로 전부**를 설명하게 된다.

**과도기 안전장치**: 정렬 전까지는 `issueCouponInDbOnly` 의 `initStock`(SET)을
`initStockIfAbsent`(SETNX)로 바꾸는 것만으로도 덮어쓰기 사고는 막힌다(재고 동기화는 포기).

## 🟢 개선 2 — 방법론을 선언한다 (코드 변경 없음)

13섹션에 같은 작업 방식이 일관되게 나타나는데 **문서 어디에도 선언되지 않는다.**

| 축 | 등장 |
|---|---|
| 측정의 목적을 숫자가 아니라 **인과 확정**으로 | ai-1(스레드 20개 고정), eco-3(9회 반복·A/B) |
| 발견을 파라미터가 아니라 **구조로 처리** | eco-1(leaseTime → 워치독 + 워밍업), ai-3(전이 추가) |
| **역할을 갈라 책임 분리** | ai-2(가용성/내구성), eco-3(부하 필터/최종 정합) |
| 한계를 **범위로 한정해 선언** | ai-1(대리 부하), ai-2(7초는 인프라 회복 시간) |

**권고**: 최상단 부제에 한 줄.
> *"측정으로 원인을 확정하고, 파라미터가 아니라 구조로 처리하며, 남은 한계는 범위로 한정해 적었음"*

이 한 줄이 있으면 이후 13섹션이 **그 주장의 증거**로 읽힌다. 지금은 독립 사례 13개다.
**편집 비용 대비 효과가 이 문서에서 가장 크다.**

## 🟡 개선 3 — 기준의 비일관 적용을 없앤다 (eco-3)

eco-1 에서는 미구현 확장 설계를 원칙에 따라 들어냈는데, eco-3 해결과정 마지막 항목은
**네 갈래 후속 설계**(① 원자적 조건부 UPDATE ② 차감 시점 이동 ③ 백오프 지터 ④ 예외 재포장 중단)를 담고 있다.
이 중 **③만 구현**됐고 결과 섹션에 A/B 실측이 있다.

**권고**: ③은 남기고 ①②④는 "검토한 대안" 한 줄로 압축하거나 `report/` 로 옮긴다.
*구현하라는 뜻이 아니다* — 같은 문서 안에서 기준이 둘인 상태를 없애자는 것이다.

## 🟡 개선 4 — 제목이 내용을 담게 한다 (ai-4)

제목 "RAG 검색 재현율 저하를 임계값 재조정으로 해결" 인데 해결과정 9항목 중 뒤 3항목은
조건부 빈 짝 맞추기 · `ObjectProvider` · 히스토리 윈도우로 **재현율과 무관**하다.
(9항목 1,820자로 문서 최다이기도 하다)

세 항목 모두 실은 **"하나를 고치면 그 하나만 보면 되는가"** 라는 동일한 물음을 다룬다.
제목을 넓히면 흩어져 보이던 항목들이 한 주제로 묶인다.

**권고**: "RAG 재현율 저하 해결과 **플래그·컨텍스트 운영 경로 정비**" 류로 확장.

## 🟡 개선 5 — 짝인 섹션을 인접 배치 (eco 순서)

eco-1(쿠폰 동시성)과 eco-3(재고 동시성)은 **"임계 구역이 Redis 밖으로 나가는가"라는 한 기준으로 묶인 짝**인데
사이에 eco-2(결제 보상)가 끼어 있다. eco-1 에서 재고 도메인을 근거로 들고 2섹션 뒤에 그 근거가 나온다.

**권고**: `eco-1 → eco-3 → eco-2 → eco-4` 로 재배치하면 기준의 대비가 연속으로 읽힌다.
번호 재부여 비용이 있으니 우선순위는 낮다.

## 우선순위

| | 항목 | 코드 변경 | 효과 |
|---|---|---|---|
| 1 | **비동기 경로를 Lua로 정렬** (개선 1) | **있음** | 정합성 결함 제거 + 단일 기준이 전 경로를 설명 |
| 2 | 부제 한 줄 (개선 2) | 없음 | 흐름 개선폭 최대, 비용 최소 |
| 3 | eco-3 기준 통일 (개선 3) | 없음 | 문서 내 기준 일원화 |
| 4 | ai-4 제목 확장 (개선 4) | 없음 | 제목·내용 정합 |
| 5 | eco 순서 재배치 (개선 5) | 없음 | 논증 인접성 |

**1번만 코드 작업이고, 나머지는 서술 정리다.**
그리고 1번은 포트폴리오를 고치려고 코드를 바꾸는 것이 아니라,
**포트폴리오가 이미 선언한 기준이 코드의 실제 결함을 찾아낸 경우**다 — 순서가 거꾸로가 아니다.

> 이 보고서는 분석만 담았고 코드는 수정하지 않았다.
